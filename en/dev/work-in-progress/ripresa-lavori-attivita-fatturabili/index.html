    Ripresa lavori - attivita_fatturabili (22-02-2026)¶

    1) Obiettivo¶

    Riprendere il dominio attivita_fatturabili allineandolo al livello raggiunto dalla pipeline lotto, partendo prima dai refactor trasversali dei punti 20 e 21 del documento WIP.

    Riferimento base: - docs/it/dev/work-in-progress/fatturazione-attivita-progetto.md

    2) Stato reale sintetico (oggi)¶

    2.1 Gia` presente¶

    • Pipeline lotto Django matura (runner, step executor, task policy, task runs).
    • Registry task DB multi-dominio (dbops.domini_task, dbops.pipeline_task_registry, dbops.pipeline_task_registry_impl).
    • Struttura DB pipeline attivita presente:
    • vendite.attivita_fatturabili_pipeline
    • funzioni vendite.fn_resolve_attivita_pipeline_step e vendite.fn_list_attivita_pipeline_steps.
    • Refactor lotto/fatture lato DB avanzato:
    • fatturazione_lotti.emittente_soggetto_ruolo_id
    • fatturazione_lotti_fatture.stato_esecuzione
    • sync automatica fatture_log -> fatture.critical -> stato_esecuzione con trigger.

    2.2 Gap ancora aperti (bloccanti per ripartenza attivita)¶

    • Nessun runner Django dedicato per dominio ATTIVITA_FATTURABILI.
    • Nessuna API dedicata run/status/task-runs per pipeline attivita.
    • Mancano task-runs e policy runtime dedicati al dominio attivita (equivalenti al dominio lotto).
    • Routing errori perimetro ATTIVITA_FATTURABILI non ancora consolidato come standard unico end-to-end.

    5) Ripartenza pipeline attivita_fatturabili (modello non lineare)¶

    Premessa funzionale confermata: - la pipeline attivita deve essere piu` libera della pipeline lotto; - rami indipendenti per sorgente (es. PREVENTIVI, ORDINI) non devono bloccarsi automaticamente tra loro.

    5.1 Modello proposto¶

    1. Esecuzione per branch indipendente (branch_code).
    2. Dipendenze esplicite opzionali (depends_on in meta).
    3. Politica blocco configurabile:
    4. block_scope = BRANCH (default)
    5. block_scope = GLOBAL.
    6. Resume/rerun per branch, non per intera pipeline.

    5.2 Estensioni schema (bozza)¶

    Su vendite.attivita_fatturabili_pipeline: - branch_code text (default DEFAULT) - block_scope text (BRANCH|GLOBAL) - depends_on jsonb (opzionale)

    Nuove tabelle speculari a lotto: - vendite.attivita_fatturabili_pipeline_task_policy - vendite.attivita_fatturabili_task_runs

    5.3 Runtime Django (bozza)¶

    Nuovi componenti: - AttivitaPipelineRunner - AttivitaPipelineStepExecutor - repository dedicato AttivitaPipelineRepository

    Regole minime: - dispatch via registry DB dominio ATTIVITA_FATTURABILI - tracing task run per branch - blocco solo nel branch salvo policy GLOBAL.

    5.4 Allineamento strutturale con fatturazione_lotti (nuovo delta richiesto)¶

    Obiettivo: ridurre divergenze semantiche tra pipeline fatturazione_lotti e attivita_fatturabili_lotti, cosi` da riusare pattern runtime, test e API.

    Delta schema proposto¶

    1. vendite.attivita_fatturabili_lotti
    2. aggiungere stato_operativo text not null default 'APERTO'
    3. aggiungere emittente_soggetto_ruolo_id bigint null references anagrafica.soggetti_ruoli(id)
    4. mantenere stato_lotto come stato tecnico pipeline; usare stato_operativo come stato business.
    5. vendite.attivita_fatturabili
    6. aggiungere stato_esecuzione text not null default 'PENDING'
    7. vincolo check su set coerente con fatturazione (PENDING|RUNNING|COMPLETED|ERRORE).

    Nota progettuale: - stato_lotto eil runtime della pipeline. -stato_operativoe la visione funzionale del lotto (aperto/chiuso/annullato). - stato_esecuzione su riga attivita elo stato tecnico puntuale, analogo afatturazione_lotti_fatture.stato_esecuzione. - Allineamento trasversale confermato: anchefatturazione_lotti_fatture.stato_esecuzioneconverge suPENDING|RUNNING|COMPLETED|ERRORE(superato legacyOK|ERRORE`).

    Impatti funzione/facade da introdurre o adeguare¶

    1. fn_get_or_create_lotto_attivita(...)
    2. valorizzare anche emittente_soggetto_ruolo_id (fallback coerente al dominio vendite).
    3. impostare default stato_operativo='APERTO'.
    4. fn_set_attivita_lotto_stato(...) (nuova o estensione della funzione stato esistente)
    5. separare aggiornamento stato_lotto (tecnico) da stato_operativo (business).
    6. fn_sync_attivita_stato_esecuzione(...) (nuova)
    7. sincronizzazione batch per lotto_attivita_id.
    8. mapping esito task/pipeline -> stato_esecuzione righe attivita.
    9. Funzioni di summary/segnalazioni lotto attivita
    10. includere conteggi per stato_esecuzione e condizioni bloccanti.

    Policy runtime da rendere esplicita¶

    1. Errore su task di branch A:
    2. blocca solo branch A se block_scope='BRANCH'.
    3. blocca tutto se block_scope='GLOBAL'.
    4. stato_operativo lotto:
    5. transizioni autorizzate solo da punti di controllo espliciti (no update casuali da task interni).
    6. stato_esecuzione righe attivita:
    7. aggiornato dal runner/executor, non da API CRUD standard.

    Migrazioni e retrofit dati¶

    4. attivita_fatturabili_lotti.stato_operativo='APERTO' dove null.

    5.6 Decisioni sorgenti e scope operativo (22-02-2026)¶

    Decisione confermata: avanzare prima sul dominio attivita_fatturabili e gestire l'upstream in fasi successive, con scope sorgenti controllato.

    Sorgenti in scope (fase corrente)¶

    1. PREVENTIVO
    2. CONTRATTO
    3. ORDINE_VENDITA
    4. ATTIVITA
    5. ATTIVITA_CONSUMI

    Regola lotto attivita: - convergenza nello stesso lotto solo se coerente con perimetro fiscale/operativo (competenza, utility, tipo_doc, emittente; opzionale BA); - la pipeline/policy decide quali branch possono convivere nello stesso lotto.

    Sorgenti temporaneamente escluse (posticipate)¶

    1. Tutte le sorgenti *_RIGA
    2. motivo: fase iniziale orientata a livello testata/documento;
    3. rischio: duplicazioni e deduplica prematura complessa.
    4. FATTURA e FATTURA_RIGA
    5. motivo: nel flusso target le fatture sono output, non input di alimentazione standard;
    6. possibile riuso futuro su canali dedicati (rettifiche/import esterni/reconciliation).
    7. DDT_VENDITA e DDT_VENDITA_RIGA
    8. motivo: sovrapposizione frequente con ORDINE_VENDITA e rischio doppio conteggio;
    9. riattivazione solo con policy esplicita di precedenza/deduplica.

    Backlog esplicito da riprendere¶

    1. Definire policy di precedenza tra ORDINE_VENDITA e DDT_VENDITA.
    2. Valutare reintroduzione selettiva delle sorgenti *_RIGA per casi a granularita` articolo.
    3. Definire se e come usare FATTURA* come sorgente eccezionale fuori pipeline standard.

    7. sorgenti in scope abilitate (PREVENTIVO, CONTRATTO, ORDINE_VENDITA, ATTIVITA, ATTIVITA_CONSUMI);
    8. sorgenti posticipate marcate abilitata=false (*_RIGA, DDT*, FATTURA*).
    9. Registry task dominio ATTIVITA_FATTURABILI seedato in dbops:

    Implementare il runtime dominio ATTIVITA_FATTURABILI con semantica branch-first:

    2. AttivitaPipelineRunner
    3. AttivitaPipelineStepExecutor
    4. AttivitaPipelineRepository

    7. esecuzione indipendente per branch_code;
    8. blocco perimetrale su block_scope:
      • BRANCH: blocca solo il branch corrente;
      • GLOBAL: interrompe l'intero run.
    9. Stato runtime:
    10. aggiornare attivita_fatturabili.stato_esecuzione solo da runner/executor;
    11. sincronizzare stati lotto con funzioni DB dedicate (fn_set_attivita_lotto_stato, fn_sync_attivita_stato_esecuzione).
    12. Error handling:
    13. envelope standard con scope=ATTIVITA_FATTURABILI;
    14. distinzione errori tecnici bloccanti vs non bloccanti coerente con policy.

    Acceptance BE-1: - run multi-branch nello stesso lotto senza blocchi incrociati in modalitaBRANCH; - tracing task persistito suattivita_fatturabili_lotti_task_runs`; - rerun/resume branch isolato funzionante.

    9.2 BE-2 API Operative (obbligatorio)¶

    Esporre API minime per uso UI/ops:

    1. POST /attivita-fatturabili/pipeline/run
    2. input: lotto o criteri creazione lotto + filtro sorgenti/branch opzionale;
    3. output: id run/lotto + stato iniziale per branch.
    4. GET /attivita-fatturabili/pipeline/{lottoId}/status
    5. output: stato_lotto, stato_operativo, riepilogo stato_esecuzione per branch.
    6. GET /attivita-fatturabili/pipeline/{lottoId}/task-runs
    7. output: lista task run ordinata per sequenza/tentativo con esito e dettagli errore.

    Regole API: - nessun mapping hardcoded sorgente->branch lato Python: usare solo resolver DB; - error envelope uniforme e tracciabile (code, scope, severity, context).

    Acceptance BE-2: - endpoint run/status/task-runs disponibili e coerenti con dati DB runtime; - contratti DTO stabili per UI (branch-level visibility).
