ZeroERP – Modulo Pagamenti/Incassi¶

Analisi e Proposta Struttura DB¶

1. Obiettivo Funzionale¶

Gestire flussi di incasso provenienti da enti esterni (banche, poste, PSP, ecc.) con:

  • Importazione flusso (testata contabile)
  • Gestione righe di incasso
  • Matching verso fatture
  • Generazione movimenti contabili su fatture
  • Gestione sospesi
  • Tracciabilità completa

Il modello deve garantire:

  • Separazione tra flusso e movimento fattura
  • Riconciliazione differita
  • Integrità referenziale
  • Audit completo
  • Coerenza date contabili

2. Architettura Concettuale¶

Oggetti Principali¶

  1. vendite_contabili → Testata flusso
  2. vendite_contabili_righe → Singole disposizioni
  3. vendite_movimenti → Movimenti su fatture
  4. enti_incasso → Anagrafica canali/enti
  5. Tabelle lookup stati → Governance lifecycle

3. Logica Relazionale¶

vendite_contabili (1) ─── (N) vendite_contabili_righe (1) ─── (0/1) vendite_movimenti

Caratteristiche:

  • Una testata contiene più righe.
  • Una riga può generare al massimo un movimento.
  • Il movimento è l'atto di contabilizzazione verso fattura.
  • Le righe possono rimanere sospese senza generare movimenti.

4. Date – Modello Coerente¶

Testata (flusso)¶

  • data_registrazione → Data registrazione flusso
  • data_contabile → Data contabile flusso

Riga¶

  • data_pagamento → Data effettiva pagamento
  • data_valuta → Data valuta banca
  • data_operazione → Data operazione (opzionale)

Movimento¶

  • data_effettiva → Riga.data_pagamento
  • data_valuta → Riga.data_valuta (fallback data_contabile)
  • data_contabile → Testata.data_contabile
  • data_registrazione → Testata.data_registrazione
  • data_contabilizzazione → Data posting

Regola: definire una sola policy stabile e riutilizzarla sempre.

5. Tabella: enti_incasso¶

Gestisce i canali di provenienza del flusso.

CREATE TABLE pagamenti.enti_incasso (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  codice text NOT NULL UNIQUE,
  descrizione text NOT NULL,
  tipo text NOT NULL,                -- BANCA, POSTE, PSP, ALTRO
  attivo boolean NOT NULL DEFAULT true,
  centro_riscossione_id bigint
    REFERENCES pagamenti.centri_riscossione(id),
  formato_flusso text,
  regole_match jsonb NOT NULL DEFAULT '{}'::jsonb,
  meta jsonb NOT NULL DEFAULT '{}'::jsonb,
  data_insert timestamptz NOT NULL DEFAULT now(),
  user_insert text NOT NULL DEFAULT CURRENT_USER,
  data_update timestamptz NOT NULL DEFAULT now(),
  user_update text NOT NULL DEFAULT CURRENT_USER,
  tx_id uuid
);

Utilità:

  • Normalizzazione ente
  • Parametri di import
  • Regole di matching
  • Governance tecnica

6. Tabella: vendite_contabili (Testata)¶

Estensione proposta:

ALTER TABLE pagamenti.vendite_contabili
ADD COLUMN stato_id smallint
  REFERENCES pagamenti.lu_vendite_contabili_stati(id),
ADD COLUMN data_conferma timestamptz,
ADD COLUMN user_conferma text;

Motivazione:

  • Stato lifecycle (BOZZA, IMPORTATA, VALIDATA, CHIUSA, ANNULLATA)
  • data_conferma come evento

Chiusura flusso ≠ riconciliazione righe.

7. Tabella: vendite_contabili_righe¶

CREATE TABLE pagamenti.vendite_contabili_righe (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  contabile_id bigint NOT NULL
    REFERENCES pagamenti.vendite_contabili(id),
  ente_incasso_id bigint NOT NULL
    REFERENCES pagamenti.enti_incasso(id),
  riferimento_ente text,
  descrizione text,
  data_pagamento date,
  data_valuta date,
  data_operazione date,
  importo numeric NOT NULL,
  fattura_id bigint
    REFERENCES vendite.fatture(id),
  billing_account_id bigint
    REFERENCES anagrafiche.billing_account(id),
  stato_id smallint NOT NULL
    REFERENCES pagamenti.lu_vendite_contabili_righe_stati(id),
  motivo_sospeso text,
  meta jsonb NOT NULL DEFAULT '{}'::jsonb,
  attivo boolean NOT NULL DEFAULT true,
  data_insert timestamptz NOT NULL DEFAULT now(),
  user_insert text NOT NULL DEFAULT CURRENT_USER,
  data_update timestamptz NOT NULL DEFAULT now(),
  user_update text NOT NULL DEFAULT CURRENT_USER,
  tx_id uuid
);

Indici:

  • contabile_id
  • fattura_id
  • ente_incasso_id + riferimento_ente
  • stato_id

8. Tabella: vendite_movimenti (estensione)¶

Aggiunta collegamento riga + data_valuta.

ALTER TABLE pagamenti.vendite_movimenti
ADD COLUMN contabile_riga_id bigint
  REFERENCES pagamenti.vendite_contabili_righe(id);

CREATE UNIQUE INDEX uq_vm_contabile_riga
ON pagamenti.vendite_movimenti(contabile_riga_id)
WHERE contabile_riga_id IS NOT NULL;

ALTER TABLE pagamenti.vendite_movimenti
ADD COLUMN data_valuta date;

Policy:

  • contabile_id mantenuto ma derivato dalla riga
  • coerenza garantita tramite trigger

9. Lookup Stati¶

Stati Testata¶

CREATE TABLE pagamenti.lu_vendite_contabili_stati (
  id smallint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  codice text NOT NULL UNIQUE,
  descrizione text NOT NULL,
  is_final boolean NOT NULL DEFAULT false,
  ordine smallint NOT NULL DEFAULT 0,
  attivo boolean NOT NULL DEFAULT true,
  meta jsonb NOT NULL DEFAULT '{}'::jsonb
);

Stati Riga¶

CREATE TABLE pagamenti.lu_vendite_contabili_righe_stati (
  id smallint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  codice text NOT NULL UNIQUE,
  descrizione text NOT NULL,
  is_postabile boolean NOT NULL DEFAULT false,
  is_final boolean NOT NULL DEFAULT false,
  ordine smallint NOT NULL DEFAULT 0,
  attivo boolean NOT NULL DEFAULT true,
  meta jsonb NOT NULL DEFAULT '{}'::jsonb
);

10. Gestione Sospesi¶

  • Riga senza fattura → stato SOSPESA
  • Non genera vendite_movimenti
  • Testata può essere CHIUSA
  • Successivo matching → genera movimento

Separazione netta tra:

  • Chiusura flusso
  • Riconciliazione fatture

11. Regole di Integrità Fondamentali¶

  1. Una riga genera al massimo un movimento.
  2. Movimento con contabile_riga_id deve avere contabile_id coerente.
  3. Riga POSTATA deve avere fattura_id valorizzato.
  4. Riga SOSPESA deve avere motivo_sospeso.
  5. Le date devono seguire policy univoca di mapping.

12. Vantaggi del Modello¶

  • Alta tracciabilità
  • Separazione flusso/movimento
  • Supporto sospesi
  • Governance stati strutturata
  • Estendibilità futura
  • Nessuna duplicazione incoerente

13. Conclusione¶

Il modello risultante è coerente con:

  • ERP enterprise pattern
  • Gestione flussi bancari reali
  • Riconciliazione differita
  • Audit completo
  • Performance su reporting

Architettura stabile e scalabile per evoluzioni future (multi-assegnazione, split pagamenti, compensazioni complesse, ecc.).
