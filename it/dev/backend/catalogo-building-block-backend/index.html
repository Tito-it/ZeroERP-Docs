Catalogo Building Block — Backend¶

Inventario dei componenti riutilizzabili nel backend Django. Prima di implementare logica nuova, verificare se esiste già un building block adatto.

Documento vivo — aggiornare ogni volta che si aggiunge un building block.

Anagrafiche — Billing Account (apps/anagrafiche/)¶

Building Block File Descrizione
BillingAccountRepository.search_lookup billing_account_repository.py Ricerca ricca BA (codice, ragione sociale, id fiscale, PDP) con JOIN a istanze_utilities/pdp, vw_soggetti_ruoli_dettaglio, config.utilities. Filtri: utility_id, validita' temporale (valid_at), scope emittente via emittenti_fiscali_billing_account. Ordinamento alfabetico. Restituisce (rows, total_count)
BillingAccountRepository.get_lookup_by_id billing_account_repository.py Restore singolo BA arricchito per ricostruire _obj dell'AutoComplete in modalita' edit senza round-trip
BillingAccountRepository.get_emittente_fiscale_id billing_account_repository.py Wrapper su anagrafiche.fn_get_emittente_fiscale_pk: ritorna la PK reale emittenti_fiscali.id (catena specifico → default globale, filtro ef.attivo). Usato per check di scope emittente su singolo BA. Importante: ritorna PK, non soggetto_ruolo_id (vedi memoria progetto feedback_emittente_pk_vs_soggetto_ruolo)
BillingAccountRepository.exists billing_account_repository.py Esistenza BA per check 404 prima di scope/lookup. Usato dal flusso list_utilities_for_ba per non leakare 403 su id non esistenti
BillingAccountService.search_lookup billing_account_service.py Facade lookup BA: valida q >= 2 char, cap limit a 50 (default 20), delega a repository. Restituisce {results, total_count, limit} per gestione UI "affina la ricerca"
BillingAccountService.get_lookup_by_id billing_account_service.py Facade restore BA per edit. Solleva E_ANAG_NOT_FOUND se inesistente
BillingAccountService.list_utilities_for_ba billing_account_service.py Lista utility "guidate da emittente" per un BA (refactor operatore-emittenti, sez. 3 del WIP). Whitelist ruolo ∈ {CL, FO, GE}. Scope check applicativo confronta user_emittente_id con l'emittente del BA (bypass per superuser e admin globale user_emittente_id is None). Solleva E_ANAG_NOT_FOUND/E_PERMESSO_NEGATO. Delega lookup riga a LookupRepository.list_utilities_per_billing_account. Restituisce {results: [...]}

Endpoint: - GET /api/v1/anagrafiche/billing-account/lookup/?q=<min2>&utility_id=&solo_validi=&valid_at=&limit= — autocomplete - GET /api/v1/anagrafiche/billing-account/<id>/lookup/ — restore per edit - GET /api/v1/anagrafiche/billing-account/<id>/utilities/?ruolo=CL — utility BA-driven (refactor operatore-emittenti)

Scope emittente lookup: applicato automaticamente dalla view via PermissionResolver.get_emittenti_sr_ids (ritorna soggetto_ruolo_id). Un operatore vede solo i BA mappati al suo emittente fiscale + quelli del gestore globale (is_default=true in emittenti_fiscali_billing_account).

Scope emittente per list_utilities_for_ba: usa il pattern 1-a-1 del refactor operatore-emittenti (PermissionResolver.get_emittente_for_user → PK reale, vedi sotto). Semantica diversa da get_emittenti_sr_ids: il primo ritorna l'unico EF assegnato all'utente (o None per admin globale), il secondo ritorna la lista soggetto_ruolo_id filtrata per scope.

Building Block File Descrizione
PricingRepository.resolve_prezzo_listino_v2 pricing_repository.py Wrapper vendite.fn_resolve_prezzo_listino_v2(uuid,bigint,date,bigint,integer,bigint,integer). Resolver a 3 stadi (promo → contratto → categoria). Ritorna 1 riga con prezzo + metadati snapshot.
PricingRepository.resolve_prezzo_composito pricing_repository.py Wrapper vendite.fn_resolve_prezzo_composito(...). BoM ibrido A/B1/B2: ritorna N righe (CASO A) o 1 riga (B1/B2) secondo esposizione in fattura dei componenti.

Fallback E_VENDITE_PRICING_FAILED. emittente_soggetto_ruolo_id deve essere gia' risolto dal caller (derivato dal JWT).
PricingService.resolve_prezzo_composito pricing_service.py Facade fn_resolve_prezzo_composito: stessa policy di validazione e traduzione errori. Caller tipico: pipeline di espansione attivita' commessa (F2-BE-12).
PromoArticoliRepository promo_articoli_repository.py CRUD su vendite.promo_articoli (STADIO 0 resolver). Lista arricchita con JOIN articolo/uom.
PromoArticoliService promo_articoli_service.py Service admin promo. PayloadValidator + map_integrity_error. Ammette tipo_variazione=PREZZO_FISSO (vietato in listini e matrice categoria). Coerenza tipo/valore anticipata lato service.
CatalogoRepository.ARTICOLI_CREATE_COLUMNS.listino_tipologia_id catalogo_repository.py Colonna smallint nullable (FK config.listini_tipologie). Ereditata da ARTICOLI_UPDATE_COLUMNS e proiettata in ARTICOLI_DETAIL_COLUMNS insieme ai decode tipologia_listino_codice/tipologia_listino_descrizione via vw_articoli_dettaglio. Coerenza articolo↔riga listino imposta dal trigger DB trgfn_listini_righe_guard_tipologia (§7.2 v5).
CatalogoRepository.list_articoli(listino_tipologia_id=) catalogo_repository.py Filtro opzionale sulla lista articoli. Esposto via query param listino_tipologia_id su GET /api/v1/catalogo/articoli/.
CatalogoBomRepository.COMPONENTE_WRITE_COLUMNS.esposto_in_fattura catalogo_bom_repository.py Flag bool (DDL default false) che decide la modalita' A/B1/B2 del fn_resolve_prezzo_composito (§8 v5): se almeno un componente ha esposto_in_fattura=true, il resolver emette N righe (una per componente) e la pipeline di creazione attivita' espande in commesse_attivita.
PricingResolveView views_pricing.py Endpoint POST /api/v1/vendite/pricing/resolve/. Esposizione REST di PricingService.resolve_prezzo per UI di debug, smoke test e supporto operativo. emittente_soggetto_ruolo_id derivato automaticamente dal JWT operatore (override opzionale nel payload per diagnostica). Area vendite livello LETTURA. Nessun side-effect: solo lettura.

Consumer previsti — PricingService.resolve_prezzo e' il building block centrale per qualsiasi calcolo prezzo in domini downstream. Al posto di duplicare logica (lookup listino / matrice / contratto) chiamare sempre il service:

Consumer Stato Dove chiamarlo
commesse_attivita (snapshot audit) Done (F2-BE-11) Il DB fn_upsert_commessa_attivita popola gia' le 8 colonne snapshot
preventivi_service.calcola_prezzo_riga Da integrare Al momento della creazione/modifica riga preventivo, sostituire lookup manuale con PricingService.resolve_prezzo
ordini_vendita (riga ordine) Da integrare Stesso pattern preventivi
pipeline fatturazione compositi (F2-BE-12) Bloccato Scope separato, usera' resolve_prezzo_composito
Endpoint diagnostico /pricing/resolve/ Done Vedi PricingResolveView

Regola pratica: mai leggere direttamente listini_righe.prezzo o categorie_clienti_listini in un service di dominio. Sempre passare per PricingService: garantisce i 3 stadi del resolver, la traduzione errori uniforme e lo snapshot dei metadati (origine, listino, contratto, promo, categoria).
