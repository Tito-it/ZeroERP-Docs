Principi di progettazione¶

Zero ERP espone azioni di dominio, non operazioni CRUD generiche.

Principio Regola
DB-first Il database el'autorita su stato, vincoli e regole. L'API non replica logica gia` garantita dal DB
Azioni atomiche Ogni endpoint POST rappresenta un'unita` di lavoro completa, eseguita in un'unica transazione
Separazione read/write GET = consultazione (nessun side-effect). POST = comando (modifica stato). PATCH = aggiornamento parziale controllato
Nessun CRUD esposto Non si usano ModelViewSet nerouter DRF automatici. Ogni endpoint e una APIView esplicita

Grammatica URL — Regole vincolanti¶

CRUD standard — nessun verbo nel path¶

Il metodo HTTP determina l'operazione. Il path identifica solo la risorsa.

GET    /api/v1/{modulo}/{risorsa}/            → lista
POST   /api/v1/{modulo}/{risorsa}/            → crea
GET    /api/v1/{modulo}/{risorsa}/{id}/       → dettaglio
PATCH  /api/v1/{modulo}/{risorsa}/{id}/       → aggiorna
Esempio Perche'
OK POST /toponomastica/ Il metodo POST dice "crea"
NO POST /toponomastica/crea/ Il verbo e' nel metodo HTTP, non nel path
NO PATCH /toponomastica/5/aggiorna/ Idem

Azioni di dominio — verbo ammesso come ultimo segmento¶

Operazioni non-CRUD (cambio stato, sospensione, esecuzione pipeline) usano un verbo breve come ultimo segmento. Il verbo nomina cosa e', non descrive come si fa.

Esempio Perche'
OK POST /pratiche/3/stato/ stato e' la sotto-risorsa che cambia
OK POST /pratiche/3/sospendi/ Azione atomica, nome diretto
NO POST /pratiche/3/aggiorna-stato/ Descrizione dell'azione, non nome della risorsa
NO POST /pratiche/3/esegui-sospensione/ Descrive l'azione invece di nominarla

Lookup — due pattern, una regola¶

Per i dropdown/select nel frontend esistono due pattern complementari:

1. Lookup generico — per tabelle config con struttura id, codice, descrizione:

GET /api/v1/core/lookup/codici/?rel=config.qualifiche
GET /api/v1/core/lookup/codici/?rel=config.stati_pratiche&search=ape

Un'unica API, parametro rel con whitelist (83 tabelle su 9 schemi, 2026-07-02). Restituisce sempre id, codice, codice_interno, descrizione, attivo, codice_stabile con paginazione e search. Variante specializzata (config _LOOKUP_SPECIALIZZATE): stessa API e contratto + UNA colonna extra per relazione (es. pratiche.tipi_prestazione → categoria, catalogo.unita_misura → tipo_uom_id) — preferirla a un endpoint dedicato quando serve un solo campo in piu'. Dettagli: docs/it/backend/core/manual/api_lookup_codici.md.

2. Lookup dedicato — quando servono JOIN o campi extra non riducibili a id, codice, descrizione:

GET /api/v1/anagrafiche/province/lookup/     → sigla + regione_descrizione
GET /api/v1/anagrafiche/regioni/lookup/      → stato_descrizione
GET /api/v1/anagrafiche/stati/lookup/        → codice_iso2
GET /api/v1/vendite/famiglie/lookup/         → prefisso_default, lunghezza_default,
                                               gestisce_serie, ammette_regole_fiscali

⭐ Il lookup famiglie documento e' l'esempio di quando un dedicato e' giustificato: dbops.fn_get_lookup_codici torna id/codice/descrizione/attivo e non puo' portare i default della forma del numero ne' le due colonne di natura, che sono esattamente cio' che il drawer dei registri deve sapere per precompilare il prefisso e decidere quali campi mostrare. ⛔ Non e' dietro il cancello dell'amministratore: lo chiama una schermata di dominio, e chiuderlo spegnerebbe quei campi per tutti gli altri, in silenzio.

Suffisso /lookup/ sulla risorsa, senza paginazione.

3. Parameters — per valori default e gestione override personali:

GET  /api/v1/core/parameters/defaults/?codes=DEFAULT_IVA_ID,DEFAULT_CURRENCY
GET  /api/v1/core/parameters/settings/
POST /api/v1/core/parameters/settings/override/
DELETE /api/v1/core/parameters/settings/override/{id}/

defaults/ risolve N parametri con override (user → group → emittente → default). settings/ lista completa con valori a ogni livello di scope. override/ CRUD override personale utente (UPSERT + DELETE). Vedi: api_parameter_settings.md per dettagli completi. Max 20 codici per chiamata su defaults/.

Regola: usare il lookup generico quando la tabella ha la struttura standard (id, codice/codice_interno, descrizione). Creare un lookup dedicato solo se servono colonne aggiuntive da JOIN o campi non standard.

Criterio Lookup generico Lookup dedicato
Struttura id, codice, descrizione Campi custom, JOIN
Endpoint GET /core/lookup/codici/?rel=... GET /{risorsa}/lookup/
Paginazione Si' No (lista completa)
Quando usare Tabelle config standard Province, regioni, stati, UO con gerarchia

⛔ L'ENVELOPE DI UN LOOKUP — {"results": [...]}, non la lista nuda¶

Un lookup dedicato risponde {"data": {"results": [...]}}. success_response({"results": ...}), mai success_response(<lista>).

⚠️ Ed e' un difetto che non da' nessun errore. I due composable del frontend — useLookup e useGlobalLookup — trasformano ogni risposta con r.data.data.results di default. Su una lista nuda quella espressione vale undefined: il ref delle opzioni passa da [] a undefined, il primo .map() in un computed solleva, e Vue svuota il sottoalbero. A video resta una schermata bianca, con il backend che ha risposto 200, nessuna riga nei log e la suite verde.

⭐ Successo reale, 2026-09-08: GET /api/v1/vendite/famiglie/lookup/ tornava la lista nuda ed era l'unica coppia disallineata in tutto il progetto (verificate tutte le altre: 17 endpoint /lookup/ su 20 gia' conformi). Il drawer dei registri di numerazione si apriva vuoto — in creazione e in modifica — e l'unica traccia del difetto stava nella console del browser.

L'eccezione, ed e' dichiarata: i tre lookup enum statici di vendite (/vendite/lookup/tipi-variazione-*, /ambiti-contratto/) tornano la lista nuda per ragioni storiche. ⚠️ Chi li consuma deve passare il transform esplicito — :transform="(r) => r.data.data" — e tutti i 6 call site lo fanno. ⛔ Non e' un modello da imitare: un endpoint nuovo usa {"results": [...]}, e cosi' non ha bisogno di nessun transform da ricordarsi.

Il presidio: un test che guarda la forma della risposta, non solo lo status — test_il_lookup_torna_l_envelope_results in apps/vendite/tests/api/test_famiglie_api.py e' il modello. Uno status 200 non dice niente su un campo che il frontend legge e non trova.

Architettura a tre layer¶

Ogni richiesta attraversa tre livelli con responsabilita` distinte:

APIView  (api/views.py)         — parsing, validazione input, envelope risposta
  |
Service  (services/*.py)        — orchestrazione, transazioni, regole Python
  |
Repository  (db/*.py)           — accesso DB via cursor, chiamate a funzioni PG
  |
PostgreSQL                      — stato, vincoli, trigger, funzioni di dominio

Nessun livello replica la logica di un altro. Il service non riscrive vincoli gia` nel DB; la view non contiene logica di business.

Struttura tipo per app¶

apps/<dominio>/
  api/
    views.py          # APIView per ogni endpoint
    urls.py           # Route unversioned (diagnostics/test)
    urls_v1.py        # Route canoniche /api/v1/<dominio>/
  services/           # Orchestrazione e logica Python
  db/                 # Repository con raw SQL (cursor)
  types.py            # TypedDict per tipizzare le righe DB
  tests/
    api/              # Test endpoint HTTP
    services/         # Test logica service

Base classes per view¶

Quattro base class in apps/core/api/base_views.py eliminano il boilerplate auth/permission:

from apps.core.api.base_views import (
    AdminAPIView,
    DomainAPIView,
    PortaleAPIView,
    ShopAPIView,
)

# Per endpoint di dominio (anagrafiche, vendite, pratiche...)
class ToponomasticaView(DomainAPIView):
    area_funzionale = "anagrafiche"
    is_search_endpoint = True        # opzionale, per throttling ricerca

    def get(self, request): ...      # lista
    def post(self, request): ...     # crea

# Per endpoint riservati ad amministratori (amm-software)
class UtentiListView(AdminAPIView):
    is_search_endpoint = True

    def get(self, request): ...
    def post(self, request): ...

# Per endpoint del portale clienti/fornitori (/api/portale/*)
class PortaleFattureListView(PortaleAPIView):
    def get(self, request): ...

# Per endpoint del negozio online (/api/shop/*, anche pubblici)
class ShopCatalogoView(ShopAPIView):
    def get(self, request): ...
Base class Auth Permessi Uso
DomainAPIView JWT ZeroERPPermission + area_funzionale Endpoint di dominio
AdminAPIView JWT IsAdminZeroERP (check binding SUPER_ADMIN) Amm. Software
PortaleAPIView JWT PortaleBasePermission (ruolo_applicativo ∈ {CLIENTE_PORTALE, FORNITORE_PORTALE}) Portale clienti/fornitori
ShopAPIView JWT opzionale ShopBasePermission (anonimo oppure SHOP_CUSTOMER) Negozio online

Attributi di classe¶

Attributo Scopo Obbligatorio
area_funzionale Schema DB dell'area (es. "vendite", "anagrafiche") Si' su DomainAPIView
is_search_endpoint Abilita SearchBurstRateThrottle No
post_permission Codename azione di processo (per comandi specifici) No
skip_area_check Salta il check area — ammesso solo per endpoint cross-dominio (profilo, sessioni, lookup). ⛔ Non convive con area_funzionale: la catena lo legge solo se l'area non si risolve, quindi una view che dichiara entrambi ha lo skip muto e vince l'area in silenzio (trovato il 2026-09-12 su 15 view). ⚠️ E una view con lo skip che scrive (post/patch/put/delete) senza il <metodo>_permission è aperta a chiunque sia autenticato: lecito solo se agisce su sé stessa. Presidio: core/tests/test_skip_area_check_registro.py No

PortaleAPIView e ShopAPIView dichiarano skip_area_check = True implicitamente: il set di endpoint portale/shop e' ristretto e non passa per la catena livello area. Lo scope dati e' applicato a livello DB via scope_policy + RLS (vedi docs/it/guide/architettura-multi-face-auth.md).

Pattern Dual-Class (ELIMINATO)¶

Il pattern Base + V1 e' stato eliminato il 15 marzo 2026. Tutti i moduli usano ora DomainAPIView, AdminAPIView, PortaleAPIView o ShopAPIView direttamente:

class ApiRunLottoPipeline(DomainAPIView):
    area_funzionale = "vendite"
    post_permission = "genera_fatture_lotti"

    def post(self, request): ...

Non creare classi V1 per nuovi endpoint.

La risoluzione permessi segue la catena: superuser bypass → ruolo_applicativo = DISABILITATO → bypass SUPER_ADMIN → azione processo → livello area/oggetto CRUD. Vedi apps/core/api/permissions.py.

Endpoint POST (Command API)¶

handle_post_json — helper obbligatorio¶

Tutti gli endpoint POST usano handle_post_json da apps.core.api.endpoint_helpers. Il helper gestisce in modo centralizzato:

  1. Parsing JSON del body (parse_json_body)
  2. Validazione Idempotency-Key (se require_idempotency_key=True)
  3. Idempotency strong mode (claim/replay/in_progress su dbops.idempotency_keys)
  4. Esecuzione handler e wrap in success_response
  5. Gestione errori con exception_to_error_response
from apps.core.api.endpoint_helpers import handle_post_json

class ApiPraticaStato(APIView):
    # Scopo: Gestisce la richiesta HTTP POST per cambiare stato pratica.
    def post(self, request: Request, pratica_id: int) -> JsonResponse:
        def _handler(payload: dict\[str, object\]) -> dict\[str, object\]:
            pratiche_service.cambia_stato_pratica(pratica_id, str(payload\["nuovo_stato"\]))
            return {"status": "ok"}

        return handle_post_json(request, handler=_handler)

Validazione parametri¶

I parametri del payload si estraggono con i validator di apps.core.api.payload_validators:

Funzione Scopo
optional_int(payload, "key") Estrae int o None, errore se non convertibile
optional_bool(payload, "key", default=False) Estrae bool con default
optional_iso_date(payload, "key") Estrae date da stringa ISO
optional_uuid(payload, "key") Estrae UUID

Idempotency-Key¶

Regola Dettaglio
Header Idempotency-Key (stringa libera, tipicamente UUID)
Obbligatorieta|require_idempotency_key=True` su tutti gli endpoint che modificano stato
Strong mode Attivabile con DJANGO_API_STRONG_IDEMPOTENCY_ENABLED=1
Store Tabella dbops.idempotency_keys
Replay Key giacompletata: restituisce risposta cached con headerX-Idempotency-Replayed: 1`
In-progress Key giain elaborazione:409con codiceE_IDEMPOTENCY_IN_PROGRESS`

Endpoint GET (Read API)¶

Gli endpoint di lettura restituiscono dati senza modificare lo stato.

class ApiLottiList(APIView):
    is_search_endpoint = True                           # abilita throttling

    # Scopo: Restituisce via GET l'elenco paginato dei lotti fatturazione.
    def get(self, request: Request) -> JsonResponse:
        competenza_mese = optional_iso_date(
            {"competenza_mese": request.query_params.get("competenza_mese")},
            "competenza_mese",
        )
        page = optional_int({"page": request.query_params.get("page", "1")}, "page")
        page_size = optional_int(
            {"page_size": request.query_params.get("page_size", "50")}, "page_size"
        )
        auth_user_id = get_scope_user_id(request)       # None per superuser

        data = fn_list_lotti(
            competenza_mese=competenza_mese,
            auth_user_id=auth_user_id,
            page=page,
            page_size=page_size,
        )
        return success_response(data)

Query params (filtri lista)¶

I filtri opzionali da query string si normalizzano con gli helper di apps.core.api.payload_validators (passati per valore, es. qp_bool_optional(qp.get("attivo"), "attivo")):

Funzione Scopo
qp_str(raw) stringa o None se assente/vuota (strip)
qp_int(raw, default) int con default; fallback silenzioso al default se non numerico
qp_int_strict(raw, name, default) int con default; 400 se presente ma non numerico
qp_int_optional(raw, name) int opzionale strict: None se assente/vuoto, 400 se non numerico
qp_bool(raw, default=True) bool con default (False solo su 0/false/no/n/off)

⛔ Il count non si deriva MAI dalle righe che stai consegnando¶

Regola scritta il 2026-09-02, dopo averla vista rotta due volte nello stesso giorno e in due forme diverse.

Un endpoint di lista deve calcolare count con una valutazione indipendente dalle righe che ritorna:

  • paginato → COUNT(*) OVER () nella stessa query, tramite il building block fetch_paged_with_total (apps/core/db/_helpers.py), che fa pagina e totale in una valutazione e ha il fallback per il rientro su una pagina stantia;
  • non paginato → una SELECT count(*) sua, con lo stesso perimetro della lista.

⛔ len(results) non è un conteggio: è un'eco. Un numero derivato dalle righe non può dire niente sulle righe — vale rows.length == rows.length, sempre vero. Il client che lo usa per verificare di aver ricevuto tutto sta confrontando una cosa con se stessa.

⚠️ E la forma sbagliata somiglia moltissimo a quella giusta: uno dei due casi del 02-09 era già scritto {"count": len(atti), "results": atti}. Leggendolo sembra a posto — c'è un count, c'è un results. Non lo è.

Chi lo consuma e perché conta. <ListaConfigurabile> in modalità :paginata="false" tratta rows come il dataset completo: se il backend paginasse senza dirlo, la lista mostrerebbe un sottoinsieme senza paginator e senza errore. Il building block confronta rows.length con total e si rifiuta di disegnare la tabella se divergono — ma quel confronto vale solo se il total è indipendente.

⚠️ Il perimetro del conteggio deve essere quello della lista, JOIN compresi. Con INNER JOIN che possono togliere righe, un count(*) sulla sola tabella madre conta di più di quanto la lista consegna e fa scattare il guard su un troncamento che non esiste. ⇒ Si condivide il frammento FROM+WHERE fra le due query, non lo si riscrive.

⚠️ parse_list_params normalizza order_dir ad "asc": non è mai None¶

parse_list_params(qp) fa order_dir = qp.get("order_dir") or "asc". Quindi annulla il default_desc=True dei repository, che si accende solo su None.

🔴 Il difetto che produce è muto: una lista che deve aprirsi dal più grave (o dal più recente) si apre al contrario, senza nessun errore. ⇒ Per le liste con un default DESC si passa il valore grezzo, che è il pattern già in uso in pagamenti:

p = parse_list_params(qp, default_order="eccedenza")
dati = service.list_x(
    limit=p\["limit"\], offset=p\["offset"\], order_by=p\["order_by"\],
    order_dir=qp_str(qp.get("order_dir")),   # ⛔ non p\["order_dir"\]
)

La whitelist di ordinamento si chiava sul campo_sorgente FISICO¶

<ListaConfigurabile> monta le Column con :field="col.campo_sorgente", quindi order_by porta il nome fisico del catalogo, non il codice logico.

⚠️ E il valore della whitelist è la colonna per cui si ordina davvero: si ordina la colonna che si vede. Una chiave centro_descrizione mappata su centro_codice ordina per un campo che a video non c'è, e se i due non sono correlati l'ordine sembra arbitrario a chi guarda (corretto il 2026-09-02).

⚠️ Se la colonna è un'espressione della SELECT (un CASE, una sottrazione), si ordina per il suo alias — PostgreSQL lo ammette in ORDER BY — e non riscrivendo l'espressione: una copia riscritta può divergere dall'originale, e la lista si ordinerebbe diversamente da come si legge.

⭐ Capability di riga — come viaggia il motivo di un'azione spenta¶

La regola non nasce qui, e questa sezione non la riscrive: sta in linee-guida-sql §12 per chi la produce e in frontend-standards per chi la rende. Qui c'è la faccia che mancava — il trasporto — perché una regola scritta su due lati di tre si perde nel mezzo, ed è successo davvero: il pulsante «Annulla l'accredito» e il cestino del mapping billing account erano accesi su gesti che il database avrebbe rifiutato.

Permesso ⇒ nascondi. Stato ⇒ disabilita col motivo. Ne discende che la risposta deve portare due cose, non una: se dice solo «non si può», il client ha un pulsante grigio che non spiega niente — indistinguibile da un bug.

Ruolo del campo Tipo Cosa porta
il flag bool false = azione da disabilitare, non da nascondere
il motivo string | null codice macchina del primo motivo. null = ammesso
la chiave string | null chiave i18n del tooltip

⚠️ Sui NOMI non c'è ancora una forma unica, e questa tabella non ne inventa una. Le famiglie in servizio sono tre, e nessuna è il calco delle altre:

Superficie Flag Motivo Chiave i18n
dettaglio documento can_push_commessa can_push_commessa_reason can_push_commessa_reason_key
riga mapping BA can_remove rimozione_blocco_reason rimozione_blocco_reason_key
righe reso · coda accrediti — annullo_blocco_codice · blocco_codice —

⭐ Solo la prima è una terna coerente: motivo e chiave si ricavano dal nome del flag, quindi chi ne legge uno sa già come si chiamano gli altri due. La seconda ha il motivo che non discende dal flag; la terza non ha flag e porta due nomi diversi per la stessa cosa su due superfici.

⇒ Ciò che vale in tutte è la proprietà, non il template: il nome dice quale verbo blocca, e motivo e chiave viaggiano in coppia. Un blocco_reason generico su una riga che ha due azioni bloccabili le confonde al primo che si aggiunge (linee-guida-sql §12.5.4).

⛔ Unificare i nomi è una decisione che nessuno ha preso, e non va presa di straforo rinominando: finché non c'è, si segue la famiglia della superficie su cui si sta lavorando invece di coniarne una quarta.

⛔ Il testo del motivo non viaggia mai nel payload. Va la chiave: il messaggio è multilingua e vive nei locales, e una frase composta in SQL sarebbe una traduzione che nessuno può cambiare. ⚠️ Il client usa la chiave con un ripiego sul codice (labelOrCode): chiave mancante ⇒ si vede il codice macchina, non un tooltip vuoto.

⛔ Il backend TRASPORTA, non deduce. Il flag si deriva dal motivo (reason is None), e il motivo lo produce la stessa funzione che il database usa per rifiutare — script.fn_check_<azione>, chiamata sia dalla madre che solleva l'errore sia dalla query di lista. Così tooltip e rifiuto non «coincidono oggi»: non possono divergere. Ricalcolare la condizione in Python è la forma in cui i due si sfilano in silenzio.

⚠️ E l'errore resta, non viene sostituito: la capability è cosa si propone, il guard è cosa si ammette. Un client che non legge la capability prende il 409 e ha ragione lui.

Due forme, e non sono intercambiabili:

Azione di documento Azione per riga
dove sta blob available_actions[] nel dettaglio colonne della riga di lista
esempio fn_available_actions_preventivo can_remove + rimozione_blocco_reason su …/billing-account/

⛔ Una capability di dettaglio non risponde per una riga: il blob non sa niente delle righe. È l'errore in cui si cade per primo, perché la forma di dettaglio è quella già scritta.

⚠️ Il nome del campo dice QUALE verbo, e non si riusa quello di un altro: su una riga possono esistere due azioni bloccabili per motivi diversi, e un blocco_reason generico le confonde al primo che si aggiunge.

⭐ Prima di dichiarare fatta una capability, verificare che il client la LEGGA. Un campo dichiarato e mai letto sembra presidiato e non presidia niente: nel 2026 il motivo di un pulsante spento non era mai stato reso a video, perché il frontend leggeva un nome di campo diverso da quello emesso — e niente falliva.

Endpoint PATCH (aggiornamento parziale)¶

Usato quando un'entita` ammette modifica di campi specifici senza che questo costituisca un'azione di dominio distinta (es. aggiornare descrizione o scadenza di una pratica).

class ApiPraticaDetail(APIView):
    # Scopo: Gestisce la richiesta HTTP PATCH per aggiornare una pratica.
    def patch(self, request: Request, pratica_id: int) -> JsonResponse:
        def _handler(payload: dict\[str, object\]) -> dict\[str, object\]:
            pratiche_service.aggiorna_pratica(pratica_id, dict(payload))
            return {"status": "ok"}

        return handle_post_json(request, handler=_handler)

Quando usare handle_post_json vs request.data¶

Metodo Protocollo Motivo
POST (create, azioni) handle_post_json Parsing JSON raw, supporto idempotency, error envelope uniforme
PATCH/PUT (update, replace) request.data diretto DRF ha gia' parsato il body; handle_post_json chiama json.loads() su body raw che in PATCH puo' essere gia' consumato da DRF, causando errori nei test

Esempio PATCH corretto (pattern adottato):

class UtentiDetailView(AdminAPIView):
    def patch(self, request, auth_user_id):
        result = AmmSoftwareService().update_utente(auth_user_id, request.data)
        return success_response(result)

La view resta sottile (una riga). L'error handling e' garantito dal service (ServiceError) e dal middleware (ApiExceptionMiddleware), non serve il wrapper handle_post_json.

Eccezione: se il PATCH richiede Idempotency-Key (operazione critica), usare handle_post_json con require_idempotency_key=True.

Sono gli stessi tre in cui message è già sostituito dalla policy e detail da _sanitize_public_detail: il suggerimento accompagna il messaggio, e dove il messaggio non è più quello dell'errore il suggerimento accompagnerebbe un'altra frase.

⚠️ E la regola NON è quella del bersaglio, che guarda anche lo status. Su un codice di classe TECNICO registrato a catalogo il bersaglio non esce e la soluzione sì: su un 500 non c'è nessun gesto da offrire, ma «segnalare al supporto citando il request_id» è esattamente ciò che chi legge può fare. Due campi, due regole, e la differenza è scritta nei test (test_error_translator_soluzione.py, casi 5 e 6).

⚠️ Escono solo i nomi, e solo dalla chiave field. Il context è una borsa diagnostica destinata a dbops.error_log: contiene anche lotto_id, contratto_id, order_dir, che non sono campi di un form — mandarli direbbe al client di evidenziare cose che sullo schermo non esistono. E il valore non esce mai: è il dato che l'operatore ha appena scritto.

⭐ targets — dal 2026-08-24. È l'altra metà di fields, e la differenza vale la riga: fields dice quale campo correggere dentro la pagina in cui l'operatore già si trova; targets dice a quale altra cosa deve andare. Il primo evidenzia un input, il secondo fa disegnare un gesto — «Apri la fattura 820».

Forma: un array di {type, id}, al massimo cinque. type è un codice di config.tipi_entita (FATTURA, COMMESSA, LOTTO…), mai un nome di tabella — il catalogo dei messaggi serve anche il portale cliente e lo shop, e lì i nomi delle tabelle sarebbero ricognizione regalata.

⚠️ È un'offerta, non una promessa. Il bersaglio può puntare a qualcosa che chi legge non può aprire (permessi, perimetro emittente, record cancellato): il messaggio si mostra lo stesso, il pulsante non compare. Mai un pulsante che porta in un vicolo cieco.

⛔ Mai su un codice TECNICO. Su un 500 l'operatore non ha niente da fare, quindi non c'è nessun gesto da offrirgli: _apply_policy lo toglie, anche se il database ce l'avesse messo.

Scope emittente¶

Due pattern disponibili in base al dominio:

  1. Vendite — get_scope_user_id(request) passa auth_user_id alle funzioni SQL che risolvono lo scope internamente via fn_get_emittenti_scope_sr_ids.
  2. Search / Anagrafiche — PermissionResolver.get_emittenti_sr_ids(request.user) risolve in Python i soggetto_ruolo_id degli emittenti autorizzati e li passa come array bigint[] alle query SQL.

Usare get_emittenti_sr_ids (filtra su *_soggetto_ruolo_id, convenzione SR) o get_emittenti_pk_ids (filtra su emittente_fiscale_id PK) secondo la colonna. ⛔ Sono i soli due nomi: l'alias get_emittenti_ids — dichiarato deprecato dal 2026-05-02 e arrivato a nove chiamanti, più dell'originale — è stato tolto il 2026-09-12 (analisi-software-per-dati-morti §2.7). Un nome deprecato che non cala è un nome in servizio; il presidio è il grep a zero.

Enforcement RLS (operatori) — dal 2026-06. Lo scope emittente degli OPERATORI è applicato anche a livello DB via Row Level Security sulle tabelle sensibili (vendite.fatture / fatture_scadenze / fatturazione_lotti / ordini / preventivi / contratti / offerte_commerciali, documenti.documenti_generati, pratiche.pratiche, anagrafiche.billing_account). I filtri applicativi (get_emittenti_*) restano come defense-in-depth e si sommano. Conseguenze per il consumer API:

  • le liste restituiscono solo le righe degli emittenti in whitelist dell'operatore (filtro automatico, anche dove il filtro applicativo non c'era);
  • un dettaglio by-id di un record fuori scope torna 404 (E_*_NOT_FOUND), identico a un id inesistente — il FE lo gestisce come "non trovato/non accessibile" (composable useDrawerDetailLoad: toast + chiusura drawer);
  • una connessione senza GUC vede 0 righe (fail-closed); i ruoli tecnici BYPASSRLS (migrazioni, job batch owner) restano esenti.

Decisioni architetturali¶

Validazione input¶

La validazione vive nel service layer, tramite helper procedurali:

descrizione = _require_str(payload, "descrizione", "Descrizione obbligatoria.")
sigla = _optional_str(payload, "sigla", "Sigla non puo' essere vuota.")

Non si usano serializer DRF ne' Pydantic — gli helper _require_str, _optional_str, optional_int, optional_bool sono sufficienti per il volume attuale. Rivalutare se i payload distinti superano 20-30.

Comunicazione cross-modulo¶

I service possono chiamare direttamente service/repository di anelli interni (es. anagrafiche chiama core). NON sono ammesse chiamate laterali tra moduli allo stesso livello (es. vendite non chiama pratiche direttamente).

Quando servira' comunicazione laterale, introdurre un dispatcher sincrono interno. Non prima.

Letture vs scritture¶

Separazione logica, non fisica. Nei repository:

  • Letture: SQL diretto su view PostgreSQL, ottimizzate per proiezioni
  • Scritture: stored functions PostgreSQL, transazionali con trigger

Non creare sottodirectory commands/ e queries/. La separazione nei commenti e nelle sezioni del file e' sufficiente.

Atomicità e composizione di scritture¶

Un endpoint che modifica stato è un'unità di lavoro atomica. Quando l'operazione compone più scritture (INSERT/UPDATE o SELECT fn_... di mutazione), decidere dove vive la transazione — non lasciarle in autocommit una dietro l'altra (se la 2ª fallisce, la 1ª resta committata → stato parziale / orfani).

L'operazione... Meccanismo
compone solo scritture/fn DB una sola SELECT fn_madre(...) nel repository — atomica per costruzione (preferito, DB-first)
richiede orchestrazione Python (lock, dispatch handler, control-flow) with transaction.atomic() esplicito nel service
ha un side-effect esterno (email/SMTP) pattern outbox/saga, mai dentro la transazione

⚠️ Non affidarsi a ATOMIC_REQUESTS. Sarebbe inefficace qui: handle_post_json cattura l'eccezione e restituisce una Response, quindi non esce mai dalla view → il rollback a livello di request non scatta e il parziale viene committato (e su IntegrityError il 4xx diventa 500). with transaction.atomic() esplicito è invece sicuro: fa rollback al confine del blocco (nel suo __exit__), prima che handle_post_json catturi l'eccezione. È l'attrezzo corretto.

Guardrail: «una azione = una unità atomica». Un metodo service che compone 2+ scritture con side-effect deve avvolgerle in un solo transaction.atomic() oppure delegare a una singola funzione madre DB. Domini con natura mista (es. pratiche): le operazioni pure-dato → madre DB (pratiche.fn_crea_pratica); il motore-flussi-con-handler → transaction.atomic().

Enforcement CI. Un test AST — apps/core/tests/test_transaction_atomicity_guardrail.py (gira senza DB) — fallisce se un metodo compone 2+ scritture non tutte in un transaction.atomic(). Copertura v1 = livello repository (cursor.execute di scrittura, con ALLOWLIST motivata per i casi deliberati come il protocollo idempotency); il livello service (2+ chiamate a metodi-write del repo) è un follow-up v2 (richiede euristiche receiver-aware per non generare falsi positivi). La regola sopra vale comunque per intero: il check automatico ne presidia oggi il sottoinsieme più verificabile, non sostituisce la disciplina in review.

Faccia DB della stessa regola (come scrivere la funzione madre): linee-guida-sql §5b. Caso di studio, criterio esteso e catalogo dei finding: analisi-fix-transazioni (docs/it/dev/work-done/analisi-fix-transazioni).

⭐ Registrare un codice = dargli una classe (dal 2026-08-07)¶

⚠️ Non si scrive più lo status. Fino al 2026-08-07 registrare un codice voleva dire aggiungere una riga con http_status, ui_action e messaggio a un dizionario di 659 voci. Ora si dichiara che cosa è l'errore — la sua classe — e status e ui_action si derivano.

classe HTTP Quando
DATO_ERRATO 400 la richiesta è malformata o il valore è sbagliato
CONFLITTO_STATO 409 in conflitto con lo stato attuale della risorsa
NON_TROVATO 404 la cosa indicata non esiste
TECNICO 500 guasto o pezzo non configurato: l'operatore non può farci niente
NON_PERMESSO 403 il diritto manca, e non dipende dallo stato
NON_ESEGUIBILE 422 si capisce ma non si può eseguire
NON_DISPONIBILE 501 funzione presente ma non servita (disattivata)
NON_AUTENTICATO 401 non autenticato (≠ 403: autenticato ma senza diritto)
ERRORE_ESTERNO 502 un provider esterno ha risposto male

Il vocabolario è lo stesso di config.classi_errore. La mappa classe → HTTP resta lato backend, ed è una scelta: è trasporto, non dominio — il database non deve sapere cosa sia un 409.

⭐ Le classi erano otto fino al 2026-08-07, e le due arrivate dopo dicono qualcosa. 401 e 502 erano dichiarati «fuori dal vocabolario di dominio, da mappare a mano nel backend». Non lo erano: sono righe del catalogo come tutte le altre, quindi con classe NOT NULL una classe la vogliono. Con NON_AUTENTICATO ed ERRORE_ESTERNO a vocabolario l'eccezione dei cinque codici sparisce: non c'è più nessuna mappa per codice nel backend, si deriva tutto dalla classe — e il prossimo codice di autenticazione prenderà il suo 401 senza che nessuno lo scriva.

Dove si mette cosa — quattro moduli in apps/core/services/, separati per quando cambiano e non per contenuto:

Modulo Cosa Chi lo scrive

# 2. lato backend:
./manage-env.sh genera_error_policies          # riscrive il modulo

Ma nessun punto di chiamata nuovo deve nominarli: lo presidia test_error_codes_declared_guardrail, e per la stessa ragione ErrorPolicyRegistry.has() oggi risponde «lo conosco», non «è buono». ⛔ Il rubinetto degli accumulatori: riusare un codice per una condizione nuova¶

scripts/codici-errore-baseline.sh (CI) confronta, per ogni codice, le famiglie di condizione su cui viene sollevato — lette dalla riga di guardia in pg_proc:

guardia famiglia
EXCEPTION WHEN … ECCEZIONE
IF NOT FOUND NOT_FOUND
IS NULL / <= 0 su un p_* PARAMETRO
NOT IN (…) ENUM
x <> 'LETTERALE' VALORE_ATTESO — dal 2026-09-07
tutto il resto IGNOTO — la misura dichiara di non saper leggere

⚠️ L'ordine conta: un NOT IN resta ENUM, e una guardia su un parametro nullo resta PARAMETRO anche se confronta un letterale.

Un codice che acquista una famiglia che non aveva ferma la CI.

⭐ Non è pedanteria: è il modo in cui gli accumulatori si formano davvero. Nessuno crea un codice generico di proposito. Si prende quello che c'è già e lo si usa «anche per questo caso qui», una volta sola, e sembra ragionevole. La sessantottesima volta è E_GENERICO.

⛔ La baseline non si aggiorna per far passare la CI. Il rosso è la richiesta di una decisione, e le uscite sono due: o il codice nuovo va creato, o l'uso è legittimo e allora la baseline si aggiorna con la ragione nel messaggio di commit.

Il caso vero, 2026-09-06. config.fn_chiudi_email_sistema sollevava E_VALIDAZIONE su tre condizioni diverse, e una era IF NOT FOUND — «nessuna email con questo identificativo». ⇒ La CI si è fermata.

La decisione non è stata aggiornare la baseline: E_VALIDAZIONE è di classe DATO_ERRATO, cioè «hai sbagliato i dati», ma quell'identificativo non arriva mai da una persona — è l'id che il backend ha scritto un istante prima. ⇒ Codice nuovo, E_EMAIL_LOG_INESISTENTE, classe TECNICO.

⚠️ E non NON_TROVATO, che sarebbe stata la scelta d'istinto: quella classe porta un 404, giusto quando è una persona a chiedere una cosa che non c'è. Qui chi chiede è il backend, e un 404 manderebbe a cercare una risorsa mancante invece di un difetto di codice. ⇒ La famiglia della condizione non decide la classe: la prima dice com'è fatta la guardia, la seconda chi ha sbagliato.

⚠️ Un codice nuovo vuole anche il suo ripiego. error_messages_fallback.py deve avere una frase senza segnaposto per ogni codice vivo — lo presidia test_ogni_codice_vivo_ha_un_messaggio_di_ripiego. Senza, l'operatore vede una frase neutra che non parla del suo problema.

⭐ Il seguito, 2026-09-07: quando cambia il metro e non il misurato¶

Il giorno dopo, un changeSet ha insegnato al classificatore una quinta famiglia — VALORE_ATTESO, cioè x <> 'LETTERALE': la forma di ogni guardia di stato o di perimetro, che prima cadeva tutta in IGNOTO. ⇒ Il rubinetto si è fermato su otto codici in una volta.

⛔ Sette non erano accumuli, e l'ha detto il conteggio: per tutti e sette i punti di sollevamento erano identici alla baseline. Nessuno aveva allargato niente — era il metro a essere cambiato sotto. ⇒ Ri-base, con la ragione nel commit.

⭐ L'ottavo sì, ed è il caso che vale. E_VALIDAZIONE guadagnava un punto sulla terza guardia della stessa fn_chiudi_email_sistema: «la riga esiste ma non è di ambito SISTEMA». Non è un dato sbagliato — è la porta sbagliata, e E_VALIDAZIONE è DATO_ERRATO. ⇒ Codice nuovo, E_EMAIL_LOG_NON_DI_SISTEMA, TECNICO — la stessa decisione del giorno prima, sulla guardia accanto.

⚠️ La lezione operativa, e serve la prossima volta che nasce una famiglia. Una famiglia nuova produce due effetti che si assomigliano e vanno separati uno per uno: cambia il metro su chi già usava quel codice, e rende visibile ciò che prima era illeggibile. ⛔ Il primo si ri-basa, il secondo no: è una segnalazione vera arrivata in ritardo. ⚠️ Il suffisso NON decide lo status: decide il punto che solleva¶

La tabella sopra è una convenzione di naming, non una regola di mapping. Usarla per assegnare uno status è il modo più rapido di sbagliare, e non è un'ipotesi: assegnando 91 policy in un giorno (2026-08-06) il nome ha mentito tre volte.

Codice Cosa suggerisce il nome Cosa fa davvero il punto che solleva Status
E_SNAPSHOT_ID_NOT_FOUND 404 EXCEPTION WHEN OTHERS nella storicizzazione: non manca un record, fallisce la lettura della chiave 500
E_DELETE_NOT_ALLOWED 409 (stato sfavorevole) blocca sempre, sbloccabile solo da una GUC di sistema: è un diritto che manca 403
E_FULFILL_NOT_FOUND «manca un legame» la riga indicata non esiste (SELECT INTO → NULL) 404

E in senso opposto: E_PARAMETRO_INVALIDO viene sollevato in due punti su un IF NOT FOUND, dove la verità è 404 — ma non si corregge cambiando la sua policy: 113 funzioni lo nominano e per 111 il 400 è giusto. Un codice usato per due cose si spezza a monte, non si rimappa a valle.

Regola operativa: leggere la funzione che solleva, non il nome del codice. Se il codice è sollevato da più punti con verità diverse, lo status giusto è il denominatore sicuro (quello che non fa danno in nessuno dei punti), e il codice va segnalato al team DB come candidato allo split.

Due corollari, pagati entrambi sul campo (2026-08-07):

  • ⚠️ conta il ramo, non la funzione. Due IF adiacenti nella stessa funzione possono avere verità opposte: in dbops.fn_accoda_lavoro, E_JOB_TYPE_NON_TROVATO è 500 (tipo mai registrato: difetto di deploy) e E_JOB_TYPE_NON_ATTIVO è 501 (tipo esistente, disattivato di proposito). In fn_push_offerta_a_contratto due guardie quasi identiche hanno richiesto codici diversi, e la prima misura le aveva confuse;
  • ⚠️ se la funzione ha gemelle per dominio, il perimetro sono tutte. fn_contratto_riga_componenti_init ha tre gemelle (ddt, ordine, preventivo): lo stesso difetto stava in tutte e quattro, ma è stato corretto su una sola e le altre tre sono tornate al giro dopo. Nello stesso file, nello stesso giorno, un altro difetto era già stato trattato come famiglia.

⚠️ Non introdurre codici generici nuovi. Un codice che serve a due punti diversi è due codici. E_PARAMETRO_INVALIDO è nominato da 177 punti ed E_VALIDAZIONE da 13: nessuno dei due è stato scelto per mancanza di alternative, erano generici e a portata di mano, e in un caso il commento nel DB confessa di aver scelto il codice per il numero di %s del messaggio.

⭐ Ma «generico» e «accumulatore» non sono la stessa cosa, e questo documento lo diceva sbagliato fino al 2026-08-07. Diceva che i due erano «la prova di dove si finisce», contando le funzioni che li nominano — 113 e 10, «cinque domini». Contate invece le condizioni che li sollevano (team DB, eseguendo lo split che questa misura aveva reso urgente):

Codice Punti Guard di parametro (IS NULL OR <= 0 e simili) Altro
E_VALIDAZIONE 13 13 0
E_PARAMETRO_INVALIDO 177 160 (90%) 17

E_VALIDAZIONE non è un accumulatore: tutti e 13 i punti sono la guard di parametro che AGENTS.md (.codex/AGENTS.md) prescrive. Lo split programmato è stato chiuso senza fare niente. Il caso che sembrava dimostrare il contrario — «fn_annulla_reso che rifiuta un annullamento è un conflitto di stato» — non esiste: lì E_VALIDAZIONE scatta su p_reso_id IS NULL OR p_reso_id <= 0, e non rifiuta nessun annullamento.

La regola che ne esce, e vale oltre questi due: un codice è un accumulatore quando copre condizioni diverse, non quando è usato in domini diversi. «10 funzioni, 5 domini» era un numero vero che misurava la cosa sbagliata — le funzioni erano eterogenee, la condizione no. Prima di proporre uno split, contare le condizioni ai punti che sollevano.

Quando spezzare un codice e quando no. Un codice a più significati si spezza quando i significati portano a reazioni diverse della pagina, non perché sono più d'uno: E_STATO_SCONOSCIUTO diceva «stato di workflow inesistente» (404, la pagina torna indietro) e «nazione dell'indirizzo non risolta» (400, si evidenzia il campo) — reazioni opposte, spezzato. E_SOGGETTI_RUOLI ne copre tre, ma tutte e tre chiedono un 400: tenuto insieme, con la ragione scritta nella policy.

Gli status in uso, tutti — e cosa è standard e cosa è nostro¶

⚠️ Gli status HTTP non li abbiamo inventati noi. Sono uno standard IETF: RFC 9110 «HTTP Semantics» (giugno 2022, che ha sostituito RFC 7231/7235), e il registro ufficiale dei codici è quello IANA. Quando questo documento dice «404 = non esiste» sta citando lo standard, non una convenzione di progetto.

Nostro è invece tutto il resto, e conviene sapere dove passa il confine:

Cosa Chi lo stabilisce
il significato di 400/403/404/409/500… RFC 9110 (standard)
il nome dei codici (E_MODULO_TIPO) noi
quale codice mappa su quale status noi — è la decisione di dominio
il vocabolario ui_action noi, non esiste nulla di standard

⚠️ Il criterio che distingue un 404 da un 500: chi può rimediare¶

Prima di scrivere 404 su un «non trovato», chiedersi chi può fare qualcosa:

  • l'operatore, cambiando la richiesta → 404 («quel documento non c'è»);
  • nessuno, finché qualcuno non configura → 500. «Non trovato» detto a chi non può trovarlo lo manda a cercare una cosa che per lui non esiste.

L'audit del 2026-08-06 sui 404 ha spostato cinque codici per questa ragione: E_PIPELINE_NOT_FOUND, E_PIPELINE_TASK_HANDLER_NOT_FOUND, E_TASK_IMPLEMENTATION_NOT_FOUND ed E_EMITTENTE_DEFAULT_MISSING → 500 (pipeline, handler, implementazioni e default mai configurati; uno era già loggato internamente con severity="C" mentre l'HTTP diceva «non trovato»); E_LISTINO_VERSIONE_NON_ATTIVA → 422, perché non era affatto un non-trovato — il listino c'è, manca una versione valida alla data — e il fratello E_CONTRATTO_LISTINO_SENZA_VERSIONE_ATTIVA era già 422.

⚠️ Tre candidati sono stati risparmiati leggendo il codice, e vale più dei cinque spostati: E_PARAMETER_NOT_FOUND sembrava configurazione mancante, ma è usato anche per l'override_id nell'URL di una DELETE, dove il 404 è corretto (semmai è da spezzare); E_PREV_STATO_CORRENTE_NON_TROVATO nasce da una JOIN che fallisce sia quando il preventivo non esiste (404 giusto) sia quando il suo stato è rotto; E_INDIRIZZO_SNAPSHOT_NOT_FOUND è un IF NOT FOUND su un id referenziato, cioè il 404 «largo» qui sotto. Otto candidati dal messaggio, cinque veri dopo la lettura.

⚠️ Il nostro 404 è più largo di quello dell'RFC. Nello standard il 404 riguarda la risorsa indirizzata dall'URI; noi lo usiamo anche quando l'URI esiste ma un'entità referenziata nel payload non c'è (E_FULFILL_NOT_FOUND, E_GESTORE_SOGGETTO_RUOLO_MANCANTE). È un'estensione diffusa e in questa app è innocua — nessun interceptor reagisce globalmente al 404 — ma è una scelta, non la lettura letterale dello standard. L'alternativa RFC-stretta sarebbe 422.

Scegliere fra 409 e 400: chi ha scelto il valore in conflitto¶

È il dubbio più frequente quando due entità «non vanno d'accordo». Il criterio:

  • 409 · show_error_banner — l'operatore non ha un campo da correggere: il conflitto è fra righe che non ha scelto lui (legami creati dal sistema, stato del documento cambiato sotto). Il messaggio è «rileggi lo stato»;
  • 400 · highlight_form_fields — il valore in conflitto l'ha scelto lui in un form (un parent, un soggetto, un conto). Il messaggio è «correggi quel campo».

Stesso difetto apparente, status diverso: E_ARTICOLO_MISMATCH (riga ordine vs riga DDT, legami di sistema) è 409; E_ID_FISCALI_DIVERSI (parent account scelto a mano) è 400.

Come il codice arriva dal DB al backend (dal 2026-08-05)¶

Gli errori di dominio nascono in PostgreSQL, da script.fn_log_and_raise_error. Il contratto di trasporto è uno solo:

SQLSTATE P0001 + campo CONSTRAINT valorizzato = errore di dominio, e il contenuto di CONSTRAINT è il codice di config.messaggi_errore.

Il codice viaggia quindi in un campo strutturato dell'eccezione (diag.constraint_name lato psycopg), non nel testo. Gli altri campi restano dove erano: DETAIL = causa, HINT = soluzione, e il messaggio è il testo localizzato per l'operatore. Il codice non compare nel messaggio, ed è una scelta: il messaggio è per l'utente.

⚠️ La condizione su P0001 non è prudenza, è necessaria. Su una violazione di vincolo vera (classe 23xxx) constraint_name contiene il nome del vincolo DB (uq_..., fk_...): leggerlo come codice applicativo scavalcherebbe map_integrity_error, che quei vincoli li traduce già. E se il campo è vuoto va trattato come assente (... or None): quando il codice arriva da un'espressione che vale NULL, PostgreSQL lo consegna come stringa vuota, non NULL.

⚠️ Il fallback a regex sul testo resta. Nel DB ci sono 135 RAISE EXCEPTION diretti in 46 funzioni PL/pgSQL che non passano dall'helper: per quelle il campo esce vuoto. Si potrà togliere il giorno in cui quel numero sarà zero — non prima.

Presidio: scripts/sql/guardrail_codice_errore_strutturato.sql (in CI) verifica che nessun altro RAISE scriva CONSTRAINT. Un secondo mittente su quel canale non farebbe fallire niente: farebbe rispondere sbagliato.

Lato backend la lettura è una sola, in apps/core/services/db_error_fields.py (structured_db_error_code → campo, db_error_code → campo con ripiego al testo). Non leggere diag.constraint_name a mano: prima del 2026-08-05 la stessa estrazione era riscritta in quattro punti, ognuno col suo modo, ed è così che si sono sfilati. I quattro delegano tutti al modulo:

Punto Cosa fa col codice

payload_helpers.translate_db_errors lo usa al posto del fallback_code di dominio
ErrorManager.raise_from_database_error lo accetta solo se dichiarato nei known_markers del chiamante (message vs fallback_message dipendono da «riconosciuto o no»)

  1. Creare la view ereditando da DomainAPIView (o AdminAPIView per amm-software)
  2. Definire area_funzionale sulla classe
  3. List + Create sulla stessa URL: def get + def post
  4. Detail + Update sulla stessa URL: def get + def patch

  6. Per GET: usare success_response() e paginated_envelope() per le liste

Disattivazione record — ordine UPDATE e trigger¶

Il database usa trigger trgfn_prevent_deactivate_if_children sulle tabelle con campo attivo. Il trigger impedisce di disattivare un padre se ha figli attivi.

Questo vale per tutte le relazioni padre-figlio dove entrambi hanno attivo: risorse_umane → l'identita' OPERATORE della stessa persona in anagrafiche.identita_digitali, e future relazioni analoghe.

⚠️ Fino al 2026-09-12 l'esempio qui sotto scriveva su risorse_umane_auth_user: e' il nome vecchio del ponte, oggi una vista di sola lettura che il DB ritira (analisi-software-per-dati-morti §2.1) — chi scrive passa da identita_digitali. Il guard sulla madre, per ora, legge ancora quella vista: e' un fatto del DB e cambia con lo DROP VIEW, non con il chiamante.

Regola: disattivare dal basso verso l'alto, riattivare dall'alto verso il basso¶

Disattivazione — prima i figli, poi il padre:

# 1. Disattiva figlio
UPDATE anagrafiche.identita_digitali SET attivo = false WHERE ...
# 2. Disattiva padre (trigger OK: figlio gia' inattivo)
UPDATE anagrafiche.risorse_umane SET attivo = false WHERE ...

Riattivazione — prima il padre, poi i figli:

# 1. Riattiva padre
UPDATE anagrafiche.risorse_umane SET attivo = true WHERE ...
# 2. Riattiva figlio (padre gia' attivo)
UPDATE anagrafiche.identita_digitali SET attivo = true WHERE ...

Perche'¶

Il trigger e' una guardia di integrita': un figlio attivo senza padre attivo non ha senso nel dominio. Se il codice Python non rispetta l'ordine, il trigger blocca l'operazione con errore E_ATTIVO_BLOCK_CHILDREN_EXIST.

Questa regola si applica a qualsiasi operazione di disattivazione/riattivazione nel sistema, non solo agli operatori. Quando si implementa un nuovo endpoint disabilita/riattiva, verificare le relazioni padre-figlio e rispettare l'ordine.
