ZeroERP — Standard Frontend¶

Questo documento definisce le regole di progettazione e sviluppo dell'interfaccia utente di ZeroERP. È vincolante per qualsiasi contributo al frontend. Le deroghe devono essere documentate e motivate.

Struttura del progetto¶

La struttura delle cartelle rispecchia i domini del database. Chi conosce il backend riconosce immediatamente il frontend.

src/
  core/               ← client API, composables, componenti riutilizzabili, utilities
  amministrazione/    ← dominio amm-software (solo ADMIN)
  anagrafiche/        ← dominio anagrafiche (gestione geografica, soggetti)
  catalogo/           ← dominio catalogo
  pratiche/           ← dominio pratiche
  vendite/            ← dominio vendite
  acquisti/           ← dominio acquisti
  magazzino/          ← dominio magazzino
  pagamenti/          ← dominio pagamenti
  contabilita/        ← dominio contabilita'
  strumenti/          ← viste operative trasversali. Dominio SENZA `schemaDb`
                        (dal 2026-09-26): le voci sono di aree diverse e
                        ognuna porta la sua con `requireArea` — code di lavoro
                        (`strumenti`), giornale eventi (`vendite`: vista e
                        client restano in `vendite/`), email dell'operatore
                        (nessuna: `skip_area_check` BE, la vede ogni operatore)
  documenti/          ← MOTORE: generazione ed emissione dei documenti (PDF,
                        scelta template), condivisa dai domini che stampano
  config/             ← configurazione (tabelle, impostazioni, modelli documenti)
  ui/                 ← personalizzazione delle liste (definizioni, colonne, preset)
  portale/            ← portale esterno (attivazione, profilo)
  shop/               ← shop esterno (attivazione)
  router/             ← definizione rotte
  stores/             ← store Pinia globali (auth, ui, tabs, navigation, context,
                        ai, parameters)
  locales/            ← file i18n (it.json, en.json)
  assets/             ← stili globali (theme.css, main.css)

Ogni cartella di dominio contiene:

anagrafiche/
  api/                ← client API per gli endpoint del dominio
  stores/             ← store Pinia per il dominio
  views/              ← pagine intere (lista, dettaglio, tab)
  components/         ← componenti specifici del dominio
  composables/        ← logica riusabile del dominio
  iscrizioni.js       ← cio' che il dominio aggiunge ai registri di `core` e dei
                        motori (facoltativo; lo carica `main.js` all'avvio)

pratiche/ e documenti/ sono motori: ogni dominio li usa, e loro non nominano nessun dominio (§«Confini fra domini»).

core/ e' l'equivalente frontend di dbops e script: nessun dominio lo chiama esplicitamente, ma tutti dipendono da lui.

Principio di omogenita' UI¶

L'operatore deve sentirsi a casa in ogni schermata.

Tutte le UI seguono gli stessi pattern visivi e comportamentali. Non esistono eccezioni per dominio. Se un pattern viene migliorato, il miglioramento si applica a tutte le schermate — mai a una sola.

Le regole di consistenza sono:

  1. Un solo modo di fare ogni cosa — lista, form, filtri, paginazione, notifiche
  2. Stesso layout ovunque — toolbar + tabella + drawer, senza varianti
  3. Stessi componenti ovunque — PageActionsBar, RowActionsMenu, FormFooter, useSearchTable, Tag per stati
  4. Stesse classi CSS ovunque — app-page, app-datatable, form-grid, mai CSS scoped per layout
  5. Nessun testo hardcoded — tutto via $t(), sempre
  6. Modifiche al pattern devono essere globali — se cambi il paginator, cambi useSearchTable una volta e tutte le liste si aggiornano

⛔ Regola zero della lista — <ListaConfigurabile>, non DataTable grezza¶

Una lista si monta con <ListaConfigurabile codice="...">. Importare primevue/datatable in una view è l'ECCEZIONE, e va motivata.

⚠️ Questa regola non era scritta da nessuna parte fino al 2026-08-30, e si è visto: nel mese di agosto i file con DataTable grezza sono tornati a crescere. Nel frattempo questo stesso documento spiegava come configurare una DataTable (poco più sotto) senza dire prima di non scriverla: chi legge in buona fede trova le istruzioni per fare la cosa sbagliata.

Cosa si guadagna, e vale anche se non si cambierà mai libreria:

  • colonne, ordine, larghezze, visibilità e permessi arrivano dal catalogo (ui.lista_colonna, risolto da ui.fn_resolve_lista_config) invece che da <Column> scritte a mano;
  • l'operatore può personalizzare le colonne, e la preferenza è sua;
  • ritiro dinamico, export, azioni di utility e paginazione arrivano gratis;
  • il file della view smette di nominare PrimeVue — e il giorno di un cambio libreria si tocca un building block invece di N view.

Come si fa, e non serve aspettare nessuno: la lista ha bisogno del suo codice — una riga in ui.lista_definizione più N righe in ui.lista_colonna. ⭐ È dato, non DDL: si crea dall'amministrazione in-app (ListaDefinizionePanel, ListaColonnaPanel), oppure con scripts/gen_seed_lista.py. Nessun brief, nessun blocco.

Le eccezioni legittime — le uniche:

Caso Cosa si usa
Dettaglio espanso di un risultato della ricerca universale SearchDetailTable (core/components/details/), non il BB
Matrice slot/override (la popolazione la decide il catalogo, l'operatore imposta l'override sulla riga) MatriceOverride, non il BB
Tabella di anteprima dentro un dialog, non paginata e non configurabile DataTable grezza, con il motivo scritto in un commento sopra l'import

⛔ Le righe di un documento NON sono un'eccezione, dal 2026-09-28 (decisione di Tid, brief-db-liste-righe-documento). Fino a quel giorno lo erano, e su tablet le 9-10 colonne di un preventivo uscivano in uno scroll orizzontale che col touch non si usa. Un documento ha un numero arbitrario di righe con molti attributi: e' una lista. RigheMasterDetailTable monta <DrawerTabLista> con la macchina del form useFormInline; chi ha ancora una DataTable di righe (BoM, fattura, contratto: lotti C e D) sta nel registro del debito, non fra le eccezioni.

⛔ «È dentro un drawer» NON è un'eccezione, ed è l'errore che si fa più spesso. Una lista su un tab di drawer — un'entità con endpoint suo, popolazione arbitraria e ciclo di vita indipendente dal padre — è una lista: le manca il paginator, non la natura. Si monta con useDrawerTabLista + <DrawerTabLista> (2026-09-01), che sono useListaConfigurabilePage + <ListaConfigurabile> più il legame col padre. ⭐ Il criterio in tre domande sta nel piano PrimeVue 5 §Gruppo B (docs/it/dev/work-in-progress/piano-migrazione-primevue-5.md), riscritto il giorno in cui il secondo caso è emerso.

⭐ La matrice slot/override ha il suo building block: MatriceOverride (regola del 2, estrazione approvata da Tid il 2026-09-05; primo consumatore OperatorePermessiTab). Non pagina per scelta di modello: la popolazione è limitata dal catalogo e la schermata esiste per farla vedere tutta. 🔴 Il pattern è nato sul tab Utilities degli emittenti (EmittenteFiscaleUtilitiesTab), che però monta ancora una DataTable grezza: debito dichiarato, non eccezione.

⛔ Non sono eccezioni: «è una lista piccola», «è solo per l'admin», «tanto non la guarda nessuno», «faccio prima». Una lista che nessuno guarda non è una lista senza problemi: è una lista che nessuno ha ancora aperto.

Come si verifica, prima di dire che una view è finita:

cd frontend && npm run guard:datatable

Il presidio (scripts/check-datatable-baseline.mjs) confronta gli import di primevue/datatable con il registro scripts/datatable.baseline.json, che elenca i file: se ne compare uno nuovo è rosso e lo nomina — hai aggiunto una lista fuori standard, o un'eccezione senza il commento che la motiva. È un cricchetto: rosso anche quando il numero cala, perché la baseline va abbassata nello stesso giro.

Regole fisse¶

ℹ️ Le regole qui sotto valgono dentro <ListaConfigurabile> (che le applica da sé) e nelle due eccezioni sopra. ⛔ Non sono un invito a montare una DataTable a mano: quella decisione la prende la regola zero.

  • Paginazione SOPRA la tabella (paginatorPosition: 'top')
  • Righe per pagina: ⭐ misure e default stanno nel DATABASE (catalogo ui.misure_pagina, dal 2026-09-30, decisioni di Tid del 29-09) e si leggono dal BB core/misurePagina.js: misureOpzioni() per il selettore, misuraDefault(USO_MISURA.PAGINA | USO_MISURA.COMPATTA) per la partenza. Le carica il guard del router una volta per sessione, attese, prima di qualunque rotta sotto AppLayout per l'operatore (anche 404 e forbidden: le legge anche il layout); se la chiamata fallisce si apre la pagina «Avvio non riuscito», che sta fuori dal layout, ⛔ senza ripiego scritto nel FE (sarebbe una copia del catalogo). ⛔ Nessun numero di righe e nessun array di opzioni scritto in un componente o in uno store: fino al 2026-09-30 erano PAGINATION in constants.js più due array a mano, e un preset a 15 lasciava il selettore vuoto senza errore. Una lista standard parte dalla misura PAGINA, adattata al viewport da useSearchTable (la COMPATTA sotto BREAKPOINTS.TABLET, regola unica in misuraPerViewport). ⭐ Dentro un drawer o un dialog la lista parte dalla COMPATTA (decisione di Tid del 2026-09-28): lo dichiara lo store con l'uso, misura: USO_MISURA.COMPATTA in useListaStoreCore/createListaStore/createCrudStore (e in usePagedDashFetch) — ⛔ mai il numero: le opzioni di uno store si scrivono a livello di modulo, e un numero letto lì verrebbe letto prima che il guard carichi il catalogo (la vecchia opzione limit è ritirata e solleva). Il preset di sistema della lista lo dichiara a DB (ui.lista_preset.pagina_dimensione), che rifiuta una misura fuori catalogo (E_UI_MISURA_PAGINA_NON_AMMESSA).
  • Indicatore pagina: 1/5 con JumpToPageDropdown per salto diretto. ⭐ Su tablet e schermo stretto ((hover: none), (max-width: 1023.98px)) il JumpToPageDropdown è nascosto via CSS in main.css (2026-09-28): doppia la navigazione ◀ 1 2 3 ▶, e 1/5 resta visibile
  • Font compatto sul paginator (0.8rem)
  • Azioni pagina/lista: building block PageActionsBar — refresh, nuovo e azioni utility/secondarie con comportamento responsive unico
  • Click riga → apre drawer in edit (modifica = interazione principale)
  • Colonna azioni riservata alle azioni secondarie (apri sub-drawer, disattiva, ecc.) — mai mettere la modifica tra le azioni: e' il click riga. Vedi sotto "Colonna azioni di riga".
  • Filtri sopra la tabella nella toolbar, dentro <FiltriLista> (vedi §«Filtri della lista» qui sotto): in linea su desktop, in un drawer dal basso in modalità compatta. Flex-wrap per il responsive della riga in linea

  • Scroll orizzontale gestito globalmente da .app-datatable — non impostare table-style="min-width: ..." nelle singole liste salvo eccezioni documentate. Filtri della lista — FiltriLista (drawer dal basso in modalità compatta)¶

✅ Adozione COMPLETA dal 2026-09-23 (lotti L2 e L3 chiusi): nessuna view scrive più app-page-filters a mano, nessuna coppia di date è scritta a mano, nessuna larghezza di filtro sta in un tag. I tre registri di npm run guard:filtri sono a zero e da qui in avanti dicono una cosa sola: una lista nuova fuori standard li fa risalire. Decisioni e cronaca: brief-fe-filtri-lista-su-schermo-compatto.md (docs/it/dev/work-done/brief-fe-filtri-lista-su-schermo-compatto.md).

La regola: un filtro è stato della lista, non decorazione della view. Ne discende che dove i filtri si rendono — e il segno che sono attivi — appartengono al building block della lista, come il paginator, il ritiro delle colonne e le azioni di testata.

<FiltriLista :store="store" :inert="perimetroBloccato">
  <template #sempre>
    <InputText v-model="searchText" :placeholder="…" />
  </template>
  <LookupSelect … @change="onStatoChange" />
  <FiltroPeriodo :periodo="periodo" />
</FiltriLista>

⚠️ L'esempio non mostra due <DatePicker> con @date-select: quel cablaggio è il difetto che <FiltroPeriodo> esiste per togliere (§«Il periodo è UN filtro»).

Modalità Resa
Desktop #sempre + slot di default in linea, dentro app-page-filters
Compatta (< 1024px o touch senza hover) #sempre in linea + icona filtro col segno; al click lo stesso slot dentro un Drawer position="bottom", su una griglia di al massimo due filtri per riga (§sotto), «Pulisci filtri» in fondo

⭐ «Pulisci filtri» vive su entrambe le rese (A3, Tid 2026-09-23): nel drawer compatto col nome per esteso, nella toolbar desktop come icona sola col tooltip, come ogni altro comando di quella riga. Compare quando c'è qualcosa da riportare al default — non quando c'è un segno: le due domande divergono da quando esistono i valori neutri.

Il segno ha tre stati, e dal 2026-09-23 il numero c'è sempre: niente (niente sta restringendo) · numero grigio (qualcosa restringe, tutto al suo default) · numero blu (almeno uno diverso dal default). ⛔ Prima lo stato «tutto al default» era un pallino senza numero, e a video si leggeva «0 → 2» toccando una cosa sola: il filtro già attivo valeva zero un istante e uno quello dopo. Il conteggio non è mai cambiato — era la forma a nasconderlo, e un segno che nasconde ciò che conta fa sembrare sbagliato un conto giusto.

La ricerca non è un filtro e resta sempre a video (slot #sempre): è il gesto principale di una lista, gli altri filtri la restringono.

⭐ Ma solo se la lista cerca (Tid, 2026-09-23 — brief-be-ricerca-full-liste-residue §7-bis). La configurazione della lista porta ricerca_full: vero se il catalogo accende almeno una colonna in cui l'operatore può cercare. Lo scaffolding (useListaConfigurabilePage, quindi anche useDrawerTabLista) lo scrive in store.ricercaFull, e <FiltriLista> non rende #sempre quando è false. La chiave la dichiara useListaEmptyStateFetch (dal 2026-09-24), quindi la ha ogni store-lista, anche quelli scritti a mano: nessuno store la dichiara per conto suo. Nessuna view lo scrive a mano: la casella e il catalogo non possono più dire due cose diverse. ⚠️ Solo false la toglie — null («non si sa ancora») la lascia, così non lampeggia a ogni apertura. ⛔ Le caselle senza lista a catalogo (ConfigTablePanel, i drawer di BoM e righe del contratto) e la casella della dashboard gruppi, fuori da FiltriLista, restano come sono: non hanno un catalogo da leggere.

I filtri si applicano subito, a ogni cambio, anche col drawer aperto: useStoreFilterBindings scrive diretto sullo store, che è la sede del filtro.

⛔ Un filtro si lega con un binder, mai con un ref che spinge e basta¶

// ⛔ NO — spinge nello store e non torna indietro
const attivoFilter = ref(true)
function onAttivoChange() { store.filters.attivo = attivoFilter.value; applyFilters() }

// ✅ SÌ — `bindSelect` porta con sé il `watch` store → widget
const { bindSelect } = useStoreFilterBindings(store, applyFilters)
const { value: attivoFilter, onChange: onAttivoChange } = bindSelect('attivo')

Perché è una regola e non uno stile: dal 2026-09-22 i filtri si possono cambiare da fuori il widget — «Pulisci filtri» del drawer compatto (azzeraFiltri), un deep-link ?search= che azzera i default data, un reset. Un ref a senso unico resta a mostrare il valore di prima su una lista che non ce l'ha più: la casella dice una cosa e l'elenco ne dice un'altra, e nessuno fallisce. ⚠️ Si vede solo sotto i 1024px, perché è lì che vive il pulsante che pulisce.

🔴 Non era teorico: i filtri a senso unico sono stati sanati il 2026-09-23. E la forma del difetto si vedeva dentro un file solo — PraticheSearchTable aveva il watch scritto a mano per uno dei quattro filtri e non per gli altri tre: non una policy, una dimenticanza. Presidio: il controllo 2-bis di npm run guard:filtri verifica che dietro un :store ci sia davvero il contratto; per il verso store → widget la difesa è questa regola.

⭐ Dove un binder non arriva, ci arriva un computed sullo store — che è la stessa cosa detta meglio, perché lo stato non si copia affatto: scadenza_mese dei contratti (lo store tiene YYYY-MM, il widget una Date: è un punto che traduce) e i tre criteri di RatePickerDialog. ⛔ Ciò che non va bene è la terza forma: un ref che scrive nello store e non lo rilegge. ⛔ Nessun pulsante «Applica»: vorrebbe una copia temporanea dei filtri accanto a quella vera, e quella copia diverge alla prima cosa che la tocca da fuori (un deep-link ?search=, un reset(), un cambio di emittente).

Il segno dei filtri attivi — tre stati¶

Stato dei filtri Segno
Nessun filtro con valore niente
Filtri con valore, tutti al loro default numero grigio = quanti filtri limitano la lista
Almeno un filtro diverso dal default numero blu = quanti filtri limitano la lista, default compresi

⭐ Perché i default contano: data_da a «oggi-60gg al primo del mese» restringe esattamente come un filtro scelto a mano — che nessuno l'abbia digitato non lo rende meno vero. Nel momento in cui i filtri non sono più sempre a video, una lista ristretta e una lista vuota si assomigliano, e l'operatore attribuisce il buco al sistema («il documento non c'è»). ⚠️ Il colore esiste perché un segno sempre uguale smette di essere un segno: il grigio distingue «ristretta come nasce» dal blu «ristretta da te». Il numero, invece, c'è in entrambi i casi (§sopra: il pallino senza numero è ritirato il 2026-09-23).

⛔ Il grigio non copre i default risolti a RUNTIME, ed è deciso (D9, Tid 2026-09-22). I default sono il letterale filterDefaults dello store, cioè la fotografia scattata alla nascita della lista: un default che arriva dopo il mount — UtilityPerRuoloSelect apply-default — lì non c'è, quindi il numero esce blu e non grigio. La regola è una sola: si contano sempre i filtri, default compresi. L'eccezione non starebbe in piedi da sola — il caso gemello (l'operatore che svuota un filtro di default) vorrebbe la regola opposta, e il conteggio risponderebbe a due domande diverse a seconda di come il valore ci è arrivato. Il numero resta vero comunque: dice quante cose stanno restringendo l'elenco.

⛔ Il conteggio non si calcola nelle view. Nasce in useListaStoreCore, che già conosce l'elenco dei filtri di quella lista (filterDefaults) e i loro valori di partenza (filtriDiPartenza()), e passa da una funzione pura con il suo .spec.js (core/utils/segnoFiltri.js). Una lista che «dimentica» di contare direbbe «nessun filtro» mentre filtra, senza nessun errore.

Nel drawer: al massimo DUE filtri per riga¶

┌──────────────────────── Filtri ────────────────────────┐
│ \[ Servizi                                     ▼ \]      │  ← combo: riga intera
│ \[ Data da   📅 \]  \[ Data a   📅 \]                       │  ← il periodo: sempre in coppia
│ \[ ◉ Mostra non attivi                          \]       │  ← interruttore: riga intera
│ Pulisci filtri                                         │
└────────────────────────────────────────────────────────┘
        ↑ drawer ≥ 27rem: anche le combo si affiancano, due per riga

Regola (Tid, 2026-09-22): su una riga non stanno più di due elementi. Tre filtri in fila su un telefono sono tre filtri illeggibili, e un tablet non è una ragione per cambiare la forma della maschera. La griglia ha due colonne, sempre.

Il periodo sta su una riga sola, e non per via del layout. data_da/data_a non sono due filtri, sono un filtro con due estremi: si montano con il building block del periodo (§sotto), che è una cella della griglia e si divide in due. Spezzarli su due righe rompe la cosa che l'operatore legge come una.

Tutto il resto prende la riga intera finché due non ci stanno LEGGIBILI. La soglia è una @container (min-width 27rem = 2 × --app-filtro-min-combo + gap), non una @media: dipende dalla larghezza del drawer, non della finestra. ⛔ L'interruttore (FiltroToggle) prende la riga intera anche sopra la soglia: la sua etichetta sta fuori dal controllo e non sa degradare in ellissi. ⭐ Il filtro che a mezza riga non si legge nemmeno lì ha una leva dichiarata, class="app-filtro-largo", valida solo dentro il drawer. ⚠️ È una leva, non un default: se la mettessero tutti, la griglia tornerebbe una pila.

<script setup>

⭐ La ragione meno visibile per cui il BB esiste è il verso degli eventi. Nelle liste che scrivevano la coppia a mano il cablaggio era divergente: @date-select + @clear-click in quasi tutte, @update:modelValue nei contratti. Non sono equivalenti — col primo una data digitata nella casella non applica il filtro: l'operatore vede la data che ha scritto e una lista che non l'ha ricevuta, senza nessun errore. Il BB usa @update:model-value, che copre calendario, digitazione e svuotamento.

⚠️ bindPeriodo espone setDa/setA, non i ref nudi: il componente legge periodo.da.value e chiede il cambio. Un v-model su un ref che arriva in una prop scrive in casa d'altri — funziona e nasconde chi possiede lo stato (lo respinge vue/no-mutating-props).

⛔ Un intervallo invertito non è un periodo¶

da > a non può esistere (Tid, 2026-09-22). Non è una validazione di comodo: da > a descrive un insieme vuoto, e una lista che torna vuota per questo non lo dice a nessuno — l'operatore legge «non ci sono documenti» invece di «hai chiesto un intervallo che non esiste».

Il meccanismo: l'estremo che tocchi vince, l'altro si apre. Chi sposta da oltre a sta dicendo dove comincia la finestra; il vecchio a non descrive più niente, quindi si svuota — e un estremo vuoto è «aperto da quella parte», che è un periodo legittimo. Simmetrico nei due versi (feedback_normalize_guard_simmetrico), e in una sola fetch.

Strada Perché no
min-date/max-date incrociati trappola d'uso: legando un estremo all'altro, spostare la finestra in avanti diventa impossibile finché non tocchi prima l'altra data
scambiare i due estremi inventa un periodo che nessuno ha chiesto, e in silenzio
rifiutare con un avviso un filtro non è un form: blocca un gesto che ha una lettura ovvia

⚠️ La correzione porta l'altro estremo a null, mai al suo clearTo: il floor è la risposta al gesto «svuoto io», e qui il gesto è un altro — per giunta un floor può essere a sua volta invertito rispetto alla data appena scelta, e si tornerebbe al punto di partenza. ⚠️ Il guard vive in bindPeriodo: una coppia di date scritta a mano non ce l'ha, ed è una delle ragioni per cui il quinto controllo di npm run guard:filtri la respinge (registro a zero dal 2026-09-23). Presidio: useStoreFilterBindings.spec.js (senza la correzione, i casi dell'intervallo invertito vanno rossi).

Quanto si può stringere una combo con le descrizioni¶

Il minimo riguarda la lettura di ciò che è GIÀ scelto, non la scelta.

È la domanda che sembra senza risposta («quanto stretta può stare una combo che mostra descrizioni?») e ne ha una precisa, che sta nel comportamento di PrimeVue:

  • il pannello delle opzioni riceve min-width = larghezza del trigger (alignOverlay), e le opzioni hanno white-space: nowrap ⇒ il pannello cresce col contenuto: un trigger stretto non taglia le descrizioni, e la scelta si legge per intero;
  • il valore selezionato degrada in ellissi (.p-select-label ce l'ha nel tema) ⇒ stringere non rompe niente, rende solo meno riconoscibile ciò che è attivo.

⇒ Il pavimento è quindi una soglia di riconoscibilità, e si dichiara una volta: --app-filtro-unita: 8rem ≈ 13 caratteri al font della toolbar — cioè 31/12/2026 intero più l'icona, e per una combo il punto in cui «Energia el…» si legge ancora e «Ene…» no. ✅ Il testo intero sta nel title (A4 del brief, 2026-09-24): PrimeVue non lo fa da sé, e fino a quel giorno una selezione troncata non si rileggeva senza riaprire il pannello. Lo fanno le due combo md dei filtri — LookupSelect e UtilityPerRuoloSelect — con il BB etichettaSelezionata, come fa .app-lista-cella per le celle: il title dice ciò che si legge a video (anche descrizione (codice) con show-code), e senza selezione l'attributo non c'è. ⚠️ Serve solo al desktop: su touch non c'è hover. ⛔ Le Select con opzioni scritte in pagina (sm) non lo portano, e non per dimenticanza: le loro etichette sono corte per costruzione, lo stesso criterio che le fa sm.

La zona sinistra della toolbar che filtri NON porta — app-page-toolbar-start¶

Una toolbar di lista ha due zone: a sinistra i filtri, a destra le azioni. Quando a sinistra non ci sono filtri — il titolo di una pagina, un pulsante «torna alla lista» — la classe è app-page-toolbar-start, non app-page-filters.

⛔ Non è un alias di comodo, ed è presidiato: app-page-filters significa «gruppo filtri», e il registro di npm run guard:filtri la conta come debito da portare in <FiltriLista>. ⭐ E una toolbar senza zona sinistra non ha bisogno di niente: le azioni restano a destra per regola di foglio (.app-page-toolbar > .app-page-actions:first-child). Fino al 2026-09-23 lo faceva uno spaziatore scritto nel markup — <div class="app-page-filters" /> — cioè un gruppo filtri senza filtri: la spaziatura è del foglio, non del markup.

⛔ Il valore che NON restringe si dichiara (filtriNeutri)¶

filterDefaults: { solo_ultima_revisione: true, … },
// «mostra storico» scrive `false`, che DEVE viaggiare (il BE è `default=True`)
// ma è lo stato più largo possibile: non deve contare nel segno.
filtriNeutri: { solo_ultima_revisione: false },

Il segno conta un filtro quando restringe. Sapeva riconoscere un solo «tutto» — l'assenza (null/'') — e per la maggior parte dei filtri basta. Non per quelli il cui «tutto» è un valore vero:

Filtro Neutro Perché non può essere null
solo_ultima_revisione (offerte, preventivi) false il BE è qp_bool(..., default=True): assente significa true
ambito (code di lavoro) 'tutti' il parametro parte solo a «tutti»: sul filo il verso è rovesciato
ampiezza (task del lotto) 'TUTTI' è una ref, non va sul filo (→ neutro in useContrattoFiltriLocali)
archiviate (code), annullati (lotti), scartate (righe distinta) true acceso chiede in più: il parametro parte e l'elenco diventa il più largo

⛔ Senza, il numero SALE quando l'operatore ALLARGA la lista.

⭐ La regola che li trova tutti, e va guardata prima del valore: un interruttore «mostra anche X» ha SEMPRE un valore neutro, ed è quello acceso. Spento nasconde qualcosa — restringe, e conta a ragione; acceso apre l'elenco al massimo che quella lista sappia mostrare. ⚠️ Il dominio lo dichiara già: un interruttore che allarga porta il conteggio di ciò che nasconde (archiviate_count, scartate_count, annullati_count), uno che restringe («solo negativa», «solo interne») non ha niente da contare. Se il count c'è, il neutro esiste. 🔴 Scritta il 2026-09-23 dopo che il primo censimento, fatto filtro per filtro, ne aveva mancati più della metà — uno nello store che stava modificando (brief §11.10).

⛔ Non si deriva e non si indovina: archiviate: false — l'interruttore spento — nasconde le righe archiviate, quindi conta a ragione. È lo stesso filtro del neutro qui sopra, guardato dall'altro verso: è conoscenza del filtro, come paramNames e gateKeys. ⭐ E se il neutro può essere null, si usa quello: su pratiche il BE legge «falso» e «assente» allo stesso modo, quindi il rimedio non è dichiarare il neutro ma smettere di mandare il parametro (default null, bindToggle senza off). ⛔ Un interruttore non è un filtro se ACCENDE un altro filtro: nel drawer BoM «tutte le versioni» spegne valido_al, e dichiararlo come chiave a sé contava 2 per una restrizione sola e 1 su un elenco intero. Lì la chiave è una, e il legame vive nel computed scrivibile — come data_da/data_a sono un periodo e non due date. ⚠️ Niente cancello, ed è dichiarato: un controllo statico non può sapere se un valore restringe — boccerebbe archiviate: false. Il presidio è la spec di segnoFiltri (i casi sui neutri) e la regola qui sopra, che si applica leggendo il count.

⛔ Un filtro che l'operatore non può togliere è un difetto¶

Se un filtro nasce valorizzato, ci dev'essere un gesto per riportarlo a «tutti»: la terna dal BB buildAttivoOptions(t) (o buildBoolOptions(t), che è la stessa con Sì/No), show-clear, oppure — forma migliore per i booleani — bindToggle('attivo', { on: null, off: true }), dove accendere «mostra non attivi» porta il filtro a null e lo fa smettere di contare. ⛔ La terna non si riscrive a mano, ed è la lezione del 2026-09-23: era copiata in più sedi e ne bastava una senza la voce «tutti» per avere un filtro che non si spegne. Due di quelle copie scrivevano già nella tendina una parola diversa da quella della loro stessa colonna. ⚠️ Senza, il segno conta un'unità su cui non c'è nessuna azione possibile. Trovato il 2026-09-23 su /catalogo/articoli (nessun «Tutti») e, peggio, sulle conversioni UoM, dove il filtro attivo: true non aveva nessun widget: la lista era ristretta e non lo diceva a nessuno. 🟡 Restano per scelta i floor data con clearTo (contratti, code di lavoro): non si tolgono, ma restringono davvero.

⭐ E c'è una terza risposta, che non è un widget: non era un filtro. Se il valore non lo decide l'operatore ma il dominio — «la rata di una bozza non è un credito» — allora non va in filterDefaults affatto: è un perimetro, e la sua sede è il backend (api.md §«Un PERIMETRO non è un filtro»). ⛔ Tenerlo qui fa due danni insieme: il segno conta un'unità su cui non c'è nessun gesto, e la regola di dominio vale solo per il client che si ricorda di mandarla. ⇒ La domanda è una: «se domani un altro client chiamasse lo stesso endpoint, questa regola dovrebbe valere anche per lui?» Se sì, non è un filtro. Successo reale: solo_numerate del picker delle rate, spostato nel backend il 2026-09-23 (decisione di Tid).

Le larghezze dei filtri stanno in una classe, non nel tag¶

<DatePicker class="app-filter-w-sm" />   <!-- ✅ -->
<DatePicker style="width: 150px;" />     <!-- ⛔ -->

Tre taglie, dichiarate in theme.css come multipli dell'unità del filtro: app-filter-w-sm (10rem: date, stati, codici brevi), app-filter-w-md (13rem: combo con descrizioni), app-filter-w-lg (16rem: ricerca, lookup ricchi). 🔵 Valgono per la toolbar in linea; nel drawer la larghezza la decide la griglia (§sotto). ✅ Al 2026-09-23 nessun tag porta più un numero, e npm run guard:filtri tiene il registro a zero — in px come in rem, e anche sull'input-style di un InputNumber: l'unità non cambia il difetto, e un criterio che ne guarda una sola è cieco sull'altra.

Come si sceglie la taglia (§A1 del brief, decisa convertendo tutte le liste): lg alla ricerca e ai lookup ricchi (articolo, billing account, comune); md alle combo con descrizioni che vengono da un catalogo (LookupSelect su un rel, UtilityPerRuoloSelect); sm alle date, agli stati e alle liste di opzioni scritte in pagina (attivo, sì/no, super admin), che portano etichette corte.

Una larghezza scritta nel tag vince su qualunque foglio di stile: nel drawer dal basso, dove ogni filtro deve occupare la riga intera, resta quella. Non dà nessun errore — si vede solo guardando il telefono. ⭐ Vale anche su desktop: al 2026-09-22 i filtri portavano larghezze inline con decine di valori distinti (150px, 160px, 120px, 200px, 220px, 260px…), cioè lo stesso filtro largo in modo diverso da una schermata all'altra. Non era una scelta: era una sedimentazione — e con le tre taglie è finita.

⭐ Un involucro non spegne le regole del drawer (corretto il 2026-09-23): le regole della griglia — la taglia che si annulla, l'interruttore e il periodo che prendono la riga intera — parlano del filtro, non della forma del markup che lo avvolge. Erano scritte come figli diretti (>), quindi un filtro dentro un <div class="form-field"> con la sua etichetta — markup legittimo, e nel repo ce n'è — le perdeva in silenzio: la taglia sopravviveva dentro la cella e l'interruttore restava a mezza riga. Ora sono descendant + :has(). ⚠️ Si vedeva solo sotto i 1024px.

Ritiro dinamico colonne — useResponsiveColumns (responsive, ResizeObserver)¶

Le liste configurabili (<ListaConfigurabile>) ritirano dinamicamente le colonne meno prioritarie in una riga di espansione quando lo spazio non basta (tipicamente all'apertura della sidebar), invece di attivare la scrollbar orizzontale. È attivo di default (prop responsive, default true): tutte le liste configurabili ne beneficiano (omogeneità UI). Building block: src/core/composables/useResponsiveColumns.js.

Come funziona (packing a somma): ogni colonna contribuisce con la sua larghezza_default (catalogo); quando la somma supera la larghezza reale del contenitore si ritira la colonna a priorita più bassa (catalogo ui.lista_colonna.priorita, esposta da fn_resolve_lista_config; tiebreaker ordine_default = la più a destra per prima), finché la somma rientra. Le colonne tipo_colonna IN ('identificatore','azione') e quelle fissata non si ritirano mai. Le ritirate finiscono nell'expansion row riusando gli slot cell-{codice} del caller (zero dati persi, resa identica). Niente larghezza_min: la soglia riusa larghezza_default. Le liste responsive sono escluse dalle soglie min-width 8/10/12 colonne (.app-datatable--responsive in main.css): il packing garantisce già che le colonne entrino.

⛔ La larghezza di catalogo è un TETTO, non un minimo (2026-09-18)¶

Regola: su una lista responsive non compare mai una scrollbar orizzontale, e la colonna azioni è sempre l'ultima a video. Le colonne che non entrano stanno nella riga di espansione, e «Espandi tutte» le apre tutte insieme. (Decisione di Tid, rilievo in-app sui preventivi.)

🔴 Il difetto che questa regola chiude era controintuitivo: la scrollbar compariva a sidebar chiusa, non aperta. Il packing somma le larghezze dichiarate, ma la tabella è width: max-content — ogni colonna era larga quanto il suo contenuto più lungo, e la larghezza di catalogo era solo un minimo. A sidebar aperta il ritiro compensava per caso; con più spazio il packing diceva «entra tutto» sui numeri dichiarati, il browser rendeva quelli veri, e la differenza usciva come scrollbar. Il packing faceva una promessa che il rendering non manteneva.

Come si chiude: <ListaConfigurabile> passa la larghezza anche come tetto della cella e dell'intestazione (--col-w + .app-lista-cella, main.css §liste responsive). Un contenuto più lungo va in ellissi su una riga, col testo intero nel title. Così la somma resa è quella dichiarata: la scrollbar non può comparire, e la colonna azioni — alla sua larghezza naturale, mai tagliata — resta l'ultima.

⭐ Ne discende che una larghezza di catalogo troppo stretta si VEDE (una colonna piena di «…») invece di produrre una scrollbar muta: si corregge dall'amministrazione, è un dato di ui.lista_colonna, non un intervento sul codice.

⚠️ L'unica larghezza che il catalogo non conosce è quella dei pulsanti inline della colonna azioni, e la dichiara il chiamante: prop azioni-inline (default 4). Fino a quel giorno era una costante — 130px, «~3-4 pulsanti» — che copriva tre pulsanti (2rem + 0.25rem di gap): diverse liste ne hanno di più, e la differenza usciva dal contenitore senza che il packing lo sapesse. Un numero più basso del vero non taglia niente, ma riporta la scrollbar: chi aggiunge una quinta azione di riga alza la prop.

⚠️ Nello stesso giro sono entrate nel conto le colonne di chrome che il packing ignorava: la checkbox di selezione e l'expander sempre presente delle liste con dettaglio inline (48px l'una).

Presidio: useResponsiveColumns.spec.js.

⚠️ DEROGA DOCUMENTATA allo standard "responsive CSS-first, niente JS di detection". Le media query CSS reagiscono solo a window.innerWidth, ma l'apertura della sidebar non cambia la larghezza della finestra — restringe solo l'area contenuto. Le media query sono cieche a questo evento, e la scrollbar appare proprio lì. L'unico modo per reagire alla larghezza reale del contenitore (che cambia sia col viewport sia con la sidebar) è osservarla con un ResizeObserver. Non è una scelta di comodo: l'alternativa puramente-CSS per questo caso non esiste. La deroga è circoscritta a questo building block; non legittima JS-detection altrove.

Colonna azioni di riga — RowActionsMenu (responsive)¶

Le azioni secondarie su una riga (apri sub-drawer, disattiva, clona, ecc.) vanno sempre renderizzate tramite il building block RowActionsMenu (src/core/components/RowActionsMenu.vue). La modifica del record NON va tra le azioni: e' gestita dal click sulla riga del DataTable.

Comportamento responsive (CSS-first, nessun JS di detection):

Contesto Variante Dettaglio
Desktop hover + viewport >=1024px Inline Pulsanti icon-only con tooltip, un click = una azione
Tablet / touch / viewport <1024px Compact Kebab ⋮ che apre un menu popup con label esplicite

Lo switch e' realizzato da @media (hover: none), (max-width: 1023.98px) in main.css sulle classi .app-row-actions-inline / .app-row-actions-compact. Il componente renderizza entrambe le varianti, il CSS ne mostra una sola. Il breakpoint hover: none intercetta esplicitamente i dispositivi touch (es. iPad Pro) indipendentemente dalla larghezza del viewport.

Perche': su touch i tooltip non funzionano; con 3-4 azioni inline la colonna ruba larghezza; sul desktop c'e' spazio e il mouse hover — l'inline resta piu' veloce. La soluzione responsive combina il meglio di entrambe senza compromessi.

Un campo dichiarato e non letto è peggio della sua assenza: sembra presidiato. Il gate vero resta il backend; questo è il non-proporre.

Permesso ⇒ nascondi, stato ⇒ disabilita col motivo. Il permesso non è qualcosa che l'operatore possa risolvere dal kebab, quindi una voce grigia sarebbe una promessa che non si mantiene; ciò che invece dipende dallo stato del record può cambiare, e lì disabled + tooltip spiega e resta a video.

⭐ E la regola vale prima di tutto per il DATABASE, che è chi decide se un'azione è proposta, spenta o assente: sono le script.fn_available_actions_* a emettere enabled / reason / reason_key, e il frontend le rende. La stessa regola è scritta per chi lavora in SQL in linee-guida-sql §12. ⚠️ Le due copie vanno tenute allineate: il 2026-08-20 una decisione DB è stata presa ignorando questa pagina, perché chi scrive SQL non la legge.

⭐ E per le azioni PER RIGA il motivo lo deve dare il database lo stesso (linee-guida-sql §12.5, dal 2026-08-26). Le capability stanno sul dettaglio, quindi una riga non le ha: il motivo arriva come colonna della vista di riga, prodotta da una script.fn_check_* che la madre chiama per rifiutare — così il tooltip e l'errore non possono dire due cose diverse. ⛔ Non ricalcolare la regola qui: fra «riscriverla nel frontend» e «non dirla affatto» la terza strada è chiederla al DB. È il difetto trovato in app sul pulsante «Annulla l'accredito», acceso su un annullo che sarebbe stato rifiutato dopo aver fatto scrivere all'operatore un motivo obbligatorio.

⛔ E il campo si chiama tooltip, non motivo. RowActionsMenu legge action.tooltip e da lì ricava da solo il tooltip inline e la riga sotto la voce nel kebab (actionMotivo). Un motivo: sull'azione non lo legge nessuno: misurato il 2026-08-26, il motivo di un pulsante spento non era mai stato reso — ed è anche il motivo per cui la chiave i18n mancante non si era mai vista a video, perché l'etichetta non veniva proprio chiesta. Filtro data standard (obbligatorio su liste con date)¶

Ogni SearchTable che mostra dati con data di apertura/creazione deve avere il filtro data:

  • Un periodo "Dal" (data_da) – "Al" (data_a) nella toolbar filtri, montato con <FiltroPeriodo> (§«Il periodo è UN filtro»), mai con due <DatePicker> scritti a mano
  • Default data_da solo frontend: oggi - 60 giorni, riportato al primo giorno del mese risultante (es. oggi 15-08-2026 -> 01-06-2026). Il calcolo NON si riscrive nello store: si chiama defaultFiltroDataDaString() da core/utils/date
  • data_a: null (nessun limite superiore di default)
  • Il filtro si applica su data_insert (o colonna data apertura dedicata se esiste)
  • Backend: applica WHERE data_insert >= data_da::date AND data_insert < (data_a::date + INTERVAL '1 day') solo se i parametri arrivano dalla request; non deve applicare default temporali impliciti
  • Il tiebreaker id nell'ORDER BY garantisce paginazione deterministica

Il default temporale e' una scelta UX, non una regola backend. Va impostato nello store/componente solo quando il filtro e' visibile nella toolbar (<FiltroPeriodo>): l'operatore deve poter vedere, modificare o cancellare il valore che limita la lista. Se una lista non espone il periodo data_da/data_a, non deve inviare data_da di default e il backend non deve inventarlo.

Perche' allineato al primo del mese e non "oggi - 60 giorni" secco: cosi' il default e' stabile dentro il mese — non scorre di un giorno ogni giorno, quindi l'operatore non vede la lista cambiare da sola — e il mese piu' vecchio del periodo si vede sempre per intero, che e' come si legge un archivio operativo.

Storico: fino al 2026-08-01 il default era il 1° gennaio dell'anno-1. Era troppo largo: su liste popolate significava scorrere fino a due anni di documenti per arrivare a quelli di ieri. La formula viveva copiata a mano in più punti; ora e' una funzione sola.

Implementazione nello store — si importa, non si ricalcola:

import { defaultFiltroDataDaString } from '../../core/utils/date'

const filters = ref({
  // ... altri filtri ...
  data_da: defaultFiltroDataDaString(),
  data_a: null,
})

Se serve una Date invece della stringa (es. il clearTo di useStoreFilterBindings, o un filtro tenuto in reactive come nelle code di lavoro), la variante e' defaultFiltroDataDa(). Le due condividono la formula: cambiare i 60 giorni e' una riga in core/utils/date (LISTE_FILTRO_DATA_GIORNI).

Implementazione nella SearchTable — ⛔ non due <DatePicker>: il periodo è UN filtro con due estremi, e si monta col suo building block (§«Il periodo è UN filtro»).

<script setup>
const { bindPeriodo } = useStoreFilterBindings(store, applyFilters)
const periodo = bindPeriodo()                    // 'data_da' / 'data_a'
</script>

<FiltroPeriodo :periodo="periodo" />

⚠️ Fino al 2026-09-23 questo paragrafo mostrava esattamente la forma sbagliata — due DatePicker con @date-select + @clear-click e style="width: 150px" — cioè le istruzioni per riprodurre due difetti muti: una data digitata che non applica il filtro, e una larghezza nel tag che vince sul drawer. È la stessa lezione della «regola zero della lista»: chi legge in buona fede trova le istruzioni per fare la cosa sbagliata.

Le chiavi i18n common.data_da ("Dal") e common.data_a ("Al") sono condivise da tutte le liste.

Interruttore di filtro — FiltroToggle + bindToggle¶

Un filtro acceso/spento nella toolbar di una lista («Mostra storico», «Solo interne», «Solo negativa», «Mostra annullati») è il BB FiltroToggle: [switch] Etichetta. ⛔ Non un ToggleSwitch + <label> scritti in pagina: il 2026-09-18 erano più copie, con lo stile inline ricopiato e un id inventato a mano per non collidere fra due schede — il root del BB è un <label>, e non ha bisogno di nessun id.

Il legame con lo store non si scrive nel componente: useStoreFilterBindings.bindToggle(storeKey, { on, off }). Quelle stesse copie avevano tre forme del legame (un ref + handler, un computed invertito, un computed che scrive true | null): on/off sono i due valori che lo store porta, e coprono tutte e tre.

  • ⚠️ off è null di default, non false: il core manda ogni filtro != null, e un false sul filo sarebbe un parametro che il backend legge senza che filtri niente. Chi ha false come default dello store lo dichiara;
  • il filtro invertito («mostra storico» acceso ⇔ solo_ultima_revisione = false) si scrive bindToggle('solo_ultima_revisione', { on: false, off: true }), non con un computed a mano;
  • il cambio ricarica da pagina 1 (applyFilters): la pagina 3 dell'insieme piccolo può non esistere in quello grande, e viceversa.

Quando l'interruttore ALLARGA la lista — rimette dentro elementi che esistono e che di default restano fuori (righe archiviate, lotti annullati) — porta anche il numero: [switch] Mostra annullati (3), prop count. Il numero lo dichiara il backend (archiviate_count, annullati_count): spento e senza numero, «elenco pulito» e «tre righe messe via» si leggono uguali — è la stessa regola di ritirate_count sul giornale. La forma è Etichetta (N) (decisione di Tid, 2026-09-12), non una frase plurale: la chiave i18n è una. Un interruttore che restringe non ha niente da contare e non passa count.

Fino al 2026-09-18 il BB si chiamava ToggleNascoste e copriva il solo caso col conteggio: le copie senza conteggio erano lo stesso componente, e si è ritirato nel giro che le ha assorbite.

Esempio di consumatore: LottiListView (col conteggio). Dettaglio nel catalogo.

Filtro con lookup ricco — bindLookup¶

Quando il filtro è un lookup ricco (ArticoloLookup, BillingAccountLookup…) il widget tiene l'oggetto scelto e lo store l'id: il legame è useStoreFilterBindings.bindLookup(storeKey, { idField }), con onChange su @update:model-value (i lookup ricchi lo emettono su select e su clear). ⛔ Non un watch sul widget con un guard anti-giro-a-vuoto: erano due copie identiche (registro e disponibilità di magazzino, 2026-09-18). ⭐ L'oggetto scelto si ricorda nello store (<storeKey>_obj, come il _obj del form per il restore dell'AutoComplete): un widget che rimonta — la scheda di un <Tabs lazy> — lo ritrova, invece di mostrare un picker vuoto sopra una lista filtrata. ⚠️ Un id messo da fuori senza l'oggetto (deep-link col solo id) non si rende: da colmare con un'opzione risolvi il giorno che un deep-link lo chiederà.

Nessun componente lista deve implementare onPage/onSort/debounce manualmente.

⛔ Paginazione corretta: una sola sorgente per rows e first¶

🔴 Il difetto che questa regola evita: cambi la dimensione di pagina, poi vai da pagina 1 a pagina 2 e ti ritrovi su pagina 3. Non è un bug di PrimeVue: è la dimensione di pagina contata da due parti diverse.

La regola, in una riga: rows e first li possiede il caller — è lui che ha fatto la fetch, e solo lui sa con quale dimensione. Chi disegna il paginator li legge, non li ricalcola.

<ListaConfigurabile> applica questa cascata, in quest'ordine:

  1. paginatorOptions.rows / .first del caller — lo stato vero;
  2. config.pagina_dimensione — il preset a catalogo, finché il caller non ha uno stato suo;
  3. la misura PAGINA del catalogo (misuraDefault(USO_MISURA.PAGINA)).

⛔ Fino al 2026-08-28 il caller non era nella cascata: rows veniva dalla sola config e sovrascriveva quello che il caller dichiarava. La scelta «righe per pagina» dell'operatore non arrivava mai al paginator: lui sceglieva 10, il caller rifaceva la fetch con 10, e al render successivo il paginator tornava a disegnarsi con i 25 del catalogo. Poi PrimeVue calcolava l'offset del «vai a pagina 2» con 25 e il caller lo interpretava con 10: 25/10 + 1 = 3.

Come si scrive una lista che pagina bene:

Lista Cosa usare
lista di ricerca standard useSearchTable(store) — paginatorProps porta già rows/first dallo store, e onPage ha le due guardie (evento che non cambia niente → esci; fetch in volo → ignora)
cruscotti / drawer (che useSearchTable non può servire: pretende uno store «ricerca + sort + limit») usePagedDashFetch + paginatorOptions che dichiara sempre rows e first calcolati con la stessa dimensione della fetch

⚠️ Il difetto si nasconde dove i numeri combaciano. Sulla Lente 1 saltavano tre liste su quattro: gli errori hanno pagina_dimensione = 10 a catalogo, uguale alla misura compatta di allora, quindi lì i due numeri coincidevano per caso e non succedeva niente. Sembrava il problema di una lista sola.

⚠️ Conseguenza da conoscere: con la cascata, pagina_dimensione del preset vale come valore iniziale solo per le liste il cui caller si allinea alla config (@config-loaded, che quasi tutti i consumatori agganciano). Per le altre il preset resta dichiarato e non applicato — è una divergenza aperta, non un difetto di questa regola.

Pattern: Ricerca universale → lista filtrata¶

Quando l'utente seleziona un risultato dalla ricerca universale (SearchDrawer), il sistema:

  1. Imposta il contesto globale (contextStore.setContext con searchTerm)
  2. Naviga alla rotta lista corrispondente
  3. useSearchTable legge automaticamente il termine da route.query.search o contextStore.searchTerm

Nessuna configurazione necessaria nelle singole SearchTable — useSearchTable centralizza la risoluzione del termine di ricerca iniziale. Le SearchTable si usano esattamente come prima:

const { searchText, onPage, onSort, paginatorProps } = useSearchTable(store, {
  defaultSortField: 'ragione_sociale_completa'
})

Nella View serve solo il watcher per auto-apertura drawer da contesto:

import { useContextStore } from '../../stores/context'
const ctx = useContextStore()

watch(() => route.fullPath, () => {
  if (route.name === 'anagrafiche-clienti' && ctx.entitaId) {
    nextTick(() => drawer.editRow({ id: ctx.entitaId }, 'id'))
  }
}, { immediate: true })

Compatibilita' con empty state: le liste che partono vuote (vedi sezione "Empty state") usano onMounted(() => { if (searchText.value) store.fetchList() }) per garantire che il termine precaricato da ricerca universale o AI venga eseguito al mount. Senza questo onMounted condizionale, la lista resta vuota anche con search precaricata.

Per aggiungere una nuova lista:

  • Aggiungere la rotta nella mappa TIPO_RUOLO_ROUTES in SearchDrawer.vue
  • Implementare il watcher ctx → drawer.editRow nella View se supporta auto-apertura
  • Se la lista usa empty state: aggiungere onMounted condizionale (vedi sezione "Empty state")
  • Nient'altro: useSearchTable fa il resto

⚠️ REGOLA CRITICA: Paginazione deterministica (backend)¶

Ogni query SQL paginata (LIMIT/OFFSET) DEVE avere id come tiebreaker nell'ORDER BY.

-- ❌ SBAGLIATO — ordine non deterministico, pagine duplicate a offset alti
ORDER BY descrizione ASC
LIMIT 25 OFFSET 700

-- ✅ CORRETTO — id garantisce ordine unico per ogni riga
ORDER BY descrizione ASC, c.id
LIMIT 25 OFFSET 700

Perche': senza tiebreaker, PostgreSQL non garantisce l'ordine tra righe con lo stesso valore nella colonna di sort. Con OFFSET alto il planner puo' restituire righe gia' viste nelle pagine precedenti, causando dati duplicati e pagine "bloccate".

Stesso principio dei subfile AS/400 dove il RRN nascosto garantiva la posizione del cursore.

Dove applicare: TUTTE le query repository che usano LIMIT %s OFFSET %s — nessuna eccezione.

Regole (Tabs)¶

I componenti da usare sono Tabs, TabList, Tab, TabPanels, TabPanel. TabView (l'API della generazione precedente di PrimeVue) è eliminato dal repo — migrazione completata il 2026-07-22, zero residui: se lo trovi in un esempio, l'esempio è vecchio. ⚠️ La versione di PrimeVue in uso si legge in frontend/package.json, non qui: ciò che questa sezione fissa è quale API si usa, e quella non cambia con la patch. Il salto alla generazione successiva ha un piano suo (piano-migrazione-primevue-5.md (docs/it/dev/work-in-progress/piano-migrazione-primevue-5.md)).

  • Usare Tabs con lazy (carica il contenuto solo quando il tab è attivo)
  • Il div root della vista ha class="app-page" — Tabs si espande in altezza
  • NON mettere app-tab-content sul contenitore <Tabs>: quella classe, come figlia diretta di .app-page, applica flex:1; overflow:hidden pensati per un pannello di contenuto. Sul contenitore fa sì che i pannelli comprimano la TabList fuori vista appena il contenuto cresce — sintomo insidioso perché dipende dalla quantità di righe: chi vede pochi record non nota nulla, chi ne vede molti «perde» i tab (bug reale, 2026-07-22).
  • class="app-tab-content" va sul div root del componente dentro ogni TabPanel
  • La DataTable dentro il tab vuole scrollable + scroll-height="flex" (§Regole liste): senza, la catena flex esiste ma la tabella non scrolla
  • ⚠️ Con lazy ogni attivazione del tab è un mount: il primo caricamento va in onMounted (il solo onActivated non scatta per un discendente montato dopo l'attivazione della rotta → tab vuoto per sempre). Vedi CodaLavoriTab.vue.
  • Ogni tab contiene un SearchTable riutilizzabile (non logica inline nella vista)
  • I drawer sono dichiarati nella vista, fuori da Tabs
  • Le chiavi value sono stringhe stabili e parlanti (indirizzi, comuni…), mai indici numerici: sono ciò che rende il tab attivo deep-linkabile
  • ⚠️ Tab condizionali (v-if su permesso/modo): il value iniziale va calcolato sul primo tab effettivamente reso, non fissato al primo in ordine. TabView attivava da sé il primo pannello presente; Tabs no — un value="preset" fisso lascia la pagina senza alcun pannello per chi non ha quel tab. Vedi GestionePersonalizzazioniListeView.vue.
  • ⚠️ Tab dentro un drawer: il tab attivo va riportato al primo a ogni riapertura (v-model:value nel watch su visible), altrimenti si riapre sul tab dell'ultima consultazione — e se quel tab era condizionale al modo (es. «Permessi» solo in modifica) il pannello risulta vuoto. Vedi OperatoreDrawer.vue, PraticaDrawer.vue.

Componente FormFooter¶

Footer standard del drawer — mai duplicare i pulsanti inline. Due modalita':

1. Default (form di add/edit): Annulla + Salva.

<FormFooter :loading="loading" :disabled="!canSave" @save="handleSave" @cancel="close" />

2. close-only (drawer di lista / sola visualizzazione): solo "Chiudi". Obbligatorio in qualsiasi drawer che mostra una lista di sub-entita' (vedi pattern Master-Detail inline §"Regole del pattern" punto 12). Senza esso, l'operatore deve raggiungere la X in alto per uscire — UX storta su touch e violazione di Fitts's law.

<FormFooter v-if="!formMode" close-only @cancel="onClose" />

Regola di visibilita': nascondere il close-only quando il drawer e' in form mode (v-if="!formMode" o v-if="!adding"). Motivi:

  • il form ha gia' Annulla/Salva: il footer "Chiudi" duplicherebbe l'azione
  • senza v-if, il "Chiudi" spinge il form sotto il fold

Pattern di riferimento: ContrattoRigheDrawer.vue (o il BB NoteDrawer.vue).

Handler standard di chiusura: usare il composable useDrawerClose(emit) da core/composables/useDrawerClose.js (centralizza il pattern, evita le copie identiche). Per drawer che notificano il parent della chiusura con un evento secondario (es. cancelled in pratiche/anagrafiche, annullato in SoggettoResolver), passare il nome come secondo argomento:

import { useDrawerClose } from '../../core/composables/useDrawerClose'
const onClose = useDrawerClose(emit)              // base
const onClose = useDrawerClose(emit, 'cancelled') // con notifica al parent

Note: la X in alto del drawer PrimeVue resta come escape rapido (semantica diversa da "Chiudi"): X = dismiss/escape, Chiudi = completion deliberata. Non sono duplicati, vanno tenuti entrambi. ⚠️ Vale per il drawer, NON per il dialog (2026-09-18): nel drawer il footer di un form lungo sta sotto il fold e la X in alto ha un ruolo; nel dialog il footer è sempre visibile, e la X è un doppione — vedi §AppDialog, «Chrome».

Componente AppDialog (OBBLIGATORIO per le dialog modali)¶

Regola: ogni Dialog modale "azione" (conferma, form one-shot, registrazione esito) DEVE usare il building block AppDialog — mai <Dialog> PrimeVue grezzo con <template #footer> hand-rolled. AppDialog è il mirror di AppDrawer per le Dialog: incapsula chrome uniforme + FormFooter integrato.

⛔ import Dialog from 'primevue/dialog' è lecito in un solo file, core/components/AppDialog.vue — presidiato da frontend/scripts/check-dialog-chrome.mjs (npm run guards, in CI).

Cosa centralizza:

  • chrome: modal/closable/closeOnEscape/dismissableMask con i default di DIALOG_CHROME (core/constants.js) — la sede unica, condivisa con la ConfirmDialog globale (vedi §«Chrome» qui sotto e §«Conferma azioni»);
  • width: da scala centralizzata DIALOG_WIDTH (sm/md/lg/xl) — mai più px hardcoded ('480px', '90vw', ecc.);
  • footer: FormFooter integrato (icone ←/✓, collapse responsive icon-only sotto 1024px, Ctrl+S, readonly-aware);
  • v-model:visible uniforme;
  • una via d'uscita sola: Annulla/Chiudi ed ESC passano dallo stesso handler ed emettono cancel e poi update:visible=false. Un consumer che pulisce stato su @cancel lo vede da qualunque uscita.

Chrome — le regole (decisione di Tid, 2026-09-18)¶

Regola Perché
⛔ Niente X in alto (closable: false) Il footer di un dialog è sempre visibile (max-height: 90%, footer in coda): ogni dialog ha già Annulla o Chiudi, e la X era un doppione con una semantica sua (chiude senza cancel). Nel drawer la X resta, per la ragione opposta — il footer di un form lungo sta sotto il fold (§FormFooter)
⭐ header obbligatorio (prop required) Un Dialog PrimeVue senza titolo rende comunque la riga di testa, e con justify-content: space-between l'unico figlio — le azioni — finiva a sinistra: era la «X a sinistra» vista in-app, non un secondo chrome. Il titolo è un fatto dell'azione, non un ornamento
ESC = Annulla, e si spegne mentre lavora (closeOnEscape && !loading) La direzione sicura resta aperta da tastiera; a salvataggio in volo il dialog non si chiude sotto la risposta. Era riscritto a mano in due dialog (ExportDialog, AttivaVersioneDialog): ora lo fa il BB
⭐ ESC chiude SOLO il dialog in cima, mai il drawer sotto In PrimeVue Dialog e Drawer hanno ciascuno un listener keydown su document e si chiudono per conto proprio: un ESC in un dialog aperto da un drawer chiudeva entrambi (rilievo di Tid, 2026-09-18). Il BB gestisce ESC sulla propria radice (pt.root.onKeydown, prima di document nella risalita) e tiene spento il listener di PrimeVue; core/utils/escapeSoloInCima — installato in main.js prima di ogni Drawer — ingoia l'ESC che sfugge alla radice quando c'è un dialog aperto. Il dialog vede l'ESC per primo (fase capture) e lo cede solo a un campo con la tendina aperta — segnale ARIA aria-expanded="true" sul controllo a fuoco (AutoComplete della lookup, Select, DatePicker): lì l'ESC chiude la tendina, il dialog resta. ⛔ Non defaultPrevented: l'AutoComplete di PrimeVue lo fa sempre, anche a tendina chiusa — con quel criterio ESC in «Abbina fattura» non chiudeva niente (rilievo di Tid, stesso giorno). Stessa forma sulla ConfirmDialog in App.vue. ⏳ Due drawer impilati si chiudono ancora insieme: chrome del drawer, fuori da questa regola
Click fuori non chiude (dismissableMask: false) Terza via d'uscita accidentale, stessa ragione della X
Un footer c'è sempre Nessuna prop hide-footer: senza X, un dialog senza footer non avrebbe nessuna uscita visibile. Il caso speciale (wizard, terzo bottone) è lo slot #footer, che il chrome lo mantiene

L'unico oggi è EmittenteAttivoDialog (:close-on-escape="false": la scelta dell'emittente non è rimandabile con un tasto). ⛔ Non si rimette :closable per un dialog «che ce l'aveva»: il default è la regola, e un cambio di layout deve restare una riga in DIALOG_CHROME, non un giro su tutti i file di dialog.

Componenti riutilizzabili (building block)¶

Principio¶

Ogni sotto-area che potrebbe essere usata in piu' di un contesto deve essere un componente autonomo. Dove vive lo decide di che cosa parla, non quanti la usano: un pezzo generico (layout, form, UI) sta in core/components/; un pezzo che parla di un'entita' sta nel dominio di quell'entita', e gli altri domini lo importano secondo §«Confini fra domini».

Dove collocare un componente¶

Criterio Collocazione Esempio
Componente di layout, form o UI generico (non parla di un'entita' di dominio) core/components/ PageActionsBar, FormFooter, TagList, EntityFormDrawer
Componente che parla di un'entita' di dominio, anche se lo usano piu' domini <dominio dell'entita'>/components/ SoggettoForm, ComuneDrawer (anagrafiche), ArticoloLookup (catalogo), FatturaLookup (vendite)
Pezzo che un dominio A VALLE aggiunge alla schermata di un'entita' A MONTE il dominio a valle, iscritto a un punto di estensione la sezione Lotti della scheda articolo (magazzino)

Confini fra domini — chi puo' importare chi¶

Decisione di Tid, 2026-09-26 (analisi (docs/it/dev/work-done/analisi-fe-regole-standard-violate-dal-codice.md) R-1/R-2). Sostituisce la regola «un dominio importa solo da core/» e l'eccezione dei componenti geografici.

🔴 Perché la regola vecchia era sbagliata. «Un dominio non importa un altro dominio» contraddiceva il modello: pagamenti deve cercare le fatture, vendite deve scegliere un articolo. Per rispettarla, i pezzi finivano in core/ — e allora era core/ a importare i domini: SoggettoForm e i componenti geografici importavano anagrafiche, FatturaLookup importava vendite, il motore delle pratiche nominava i drawer di vendite, e il registro «tipo → drawer» che core/bersagli.js legge stava dentro vendite/. La regola produceva la violazione che voleva impedire.

La regola, sul modello — il verso delle FK:

  1. Un dominio importa un altro dominio solo se le sue tabelle puntano a un'entità di quello. vendite.contratti punta a billing_account: vendite può usare i componenti di anagrafiche. magazzino.lotti punta a catalogo.articoli: magazzino può usare ArticoloLookup. Si guarda l'entità, non lo schema: fra schemi le FK vanno in tutti e due i versi (anagrafiche.soggetti_titoli_iva_ambiti punta agli articoli).
  2. Il verso opposto passa da un punto di estensione. La scheda articolo non importa magazzino: offre il punto ARTICOLO_DRAWER_SEZIONI, e magazzino ci contribuisce la sezione Lotti dal suo iscrizioni.js. Così per i contratti nella lista clienti, gli accessi web nell'anteprima del soggetto, il saldo nel drawer della fattura (core/estensioni.js).
  3. I motori (pratiche, documenti) li usano tutti e non nominano nessuno. Il motore possiede il registro; il dominio si iscrive (iscriviAttivitaUi, iscriviDrawerEntita…). È lo specchio del backend, dove vendite iscrive i suoi handler in HANDLER_MAP da apps.py:ready().
  4. core/ non importa mai un dominio. Ciò che un dominio aggiunge a core si iscrive (core/registri.js, core/drawerEntita.js); una funzione API che serve a tutti (la lookup degli emittenti, la testata dei presidi) sta in core/api/, anche se l'endpoint lo serve un'app di dominio. ⛔ Nemmeno dalla porta di servizio del router: router/index.js è la radice dell'app e nomina tutti i domini (view e vocabolari), quindi core/ e gli store globali non ne importano il modulo. Chi deve navigare fuori da un setup (l'interceptor HTTP, un bersaglio, l'assistente) usa routerApp() di core/routerApp.js, a cui main.js consegna l'istanza prima del mount; dentro un componente, useRouter().

main.js carica ogni <dominio>/iscrizioni.js con import.meta.glob, prima del mount, senza nominarne nessuno: un dominio nuovo — acquisti — si aggiunge scrivendo il proprio file, senza toccare i motori.

Presidio: npm run guards → check-confini-domini.mjs. L'elenco degli archi ammessi porta accanto la FK che li giustifica. ⛔ Un arco non si aggiunge per far passare il guard: se la FK non c'è, quello che serve è un punto di estensione.

Checklist prima di creare un componente¶

  1. Esiste gia'? — controllare core/components/ e core/composables/
  2. Di che cosa parla? — se e' generico, in core/; se parla di un'entita', nel dominio di quell'entita' (anche se lo useranno altri domini: §«Confini fra domini»)
  3. Props minimali — esporre solo cio' che varia tra i contesti
  4. Emits chiari — @saved, @changed, @row-click, @new, update:modelValue

⭐ saved e changed non sono sinonimi, e il drawer deve sceglierne uno. saved dice «il lavoro su questo documento è finito» — la lista si ricarica e il drawer si chiude. changed dice «la riga è cambiata, ma sto ancora lavorando qui dentro» — la lista si ricarica e il drawer resta aperto. È il caso di ogni verbo che genera un documento senza concludere il proprio: genera DDT da un ordine, genera reso da un DDT, smista un preventivo, ri-consegna un reso.

Li implementa entrambi useDrawerSavedListRefresh: la vista scrive @saved="onDrawerSaved" @changed="onDrawerChanged" e non riscrive nulla.

🔴 Perché la regola è scritta qui: al 2026-09-01 quel momento esisteva in quattro domini con tre comportamenti diversi — due drawer non avvisavano nessuno (la lista restava ferma, e l'operatore ricaricava a mano senza sapere perché), uno avvisava solo un'altra tab, uno emetteva saved e si chiudeva addosso a chi stava ancora lavorando. Nessuno dei quattro falliva: è la classe di difetto che nessun test vede, perché la pagina non sbaglia — è solo ferma. 5. i18n — tutti i testi tramite $t(), mai hardcoded 6. Responsive — testare su mobile (flex-wrap, no larghezze fisse)

L'informazione di stato — prop infoKey¶

Una lista di azioni vuota e' indistinguibile da un errore di caricamento. Se da uno stato non si puo' fare nulla, la barra deve dirlo — e dire cosa si fa invece.

E' la faccia a video della regola R3 del brief vie d'uscita per l'operatore (docs/it/dev/work-done/brief-db-vie-uscita-operatore.md): per ogni stato, o la via d'uscita c'e', o c'e' scritto perche' non c'e'. Il testo non e' una scelta del componente: e' un dato, la chiave i18n seminata nel meta della riga di config.stati_doc_*, che le capability script.fn_available_actions_* espongono nel campo stato_info_key. Cambiare il messaggio e' cambiare un seed, non toccare il frontend.

Transizione a stato terminale con data (CESSATO / CHIUSO / TERMINATO)¶

Regola standard: per le entità il cui workflow include uno stato terminale (es. contratto CESSATO, listino-versione CHIUSA, soggetto ESTINTO) accompagnato da una data finale (valido_al, data_chiusura, data_cessazione), la chiusura non si fa modificando la data nel form: si fa con un pulsante dedicato che apre un dialog di conferma con DatePicker (default oggi). La data e il cambio stato vengono applicati in transazione atomica dal BE.

Motivazione¶

  • Evita lo stato incoerente "stato terminale + data NULL" (resolver/processi che dipendono dalla data continuerebbero a considerare l'entità operativa)
  • Rende l'azione esplicita e auditabile (1 click intenzionale, non 2 modifiche separate)
  • Previene errori dell'operatore (dimentica data, oppure imposta data senza cambiare stato)
  • Allinea l'esperienza fra domini: l'utente impara una volta sola "Chiudi/Cessa = dialog con data"

Cessazione immediata vs programmata (regola data-driven)¶

Quando l'utente sceglie nel dialog la data, il comportamento si differenzia:

Data scelta Cessazione Effetto
oggi o passata immediata Service applica PATCH valido_al + UPDATE stato CESSATO (atomico)
futura (>= today) programmata Service applica solo PATCH valido_al. Stato resta ATTIVO/SOSPESO. Job notturno DB allineerà a CESSATO quando la data scade

Rationale (allineato col principio fail-safe): un contratto con stato CESSATO ma valido_al futuro è incoerente — il resolver/processi che dipendono da validita @> CURRENT_DATE continuano correttamente a considerarlo operativo, ma chi legge lo stato vede "cessato". Lo evitiamo per costruzione: il cambio stato avviene solo quando la realtà operativa lo conferma.

Dialog adattivo: titolo, severity, label conferma e toast variano in base a cessazioneProgrammata:

const cessazioneProgrammata = computed(() => {
  if (!cessaDialogData.value) return false
  const oggi = new Date(); oggi.setHours(0, 0, 0, 0)
  const scelta = new Date(cessaDialogData.value); scelta.setHours(0, 0, 0, 0)
  return scelta >= oggi
})

Cessazione programmata visibile in stato intermedio: in ATTIVO/SOSPESO con valido_al valorizzato, il drawer mostra il campo readonly come "Cessazione programmata al {data}" — l'operatore vede che il contratto è in attesa di scadenza.

Pattern BE — service cambia_stato¶

Estendere il service per accettare valido_al opzionale e applicare la regola data-driven:

def cambia_stato(
    self, contratto_id: int, *, codice_interno: str, valido_al: date | None = None,
) -> dict\[str, Any\]:
    target_stato_id = self._repo.get_stato_id_by_codice(codice_interno)
    cessazione_programmata = False
    if codice_interno == "CESSATO":
        # data obbligatoria + valido_al >= valido_dal (errore parlante anti CHK constraint)
        ErrorManager.require(valido_al is not None, ...)
        existing = self._repo.get(contratto_id)
        if isinstance(existing.get("valido_dal"), date):
            ErrorManager.require(valido_al >= existing\["valido_dal"\], ...)
        # Regola fail-safe: data futura -> programmata (no cambio stato)
        if valido_al >= date.today():
            cessazione_programmata = True
    with transaction.atomic():
        if valido_al is not None:
            self._repo.update_contratto(contratto_id, {"valido_al": valido_al})
        if not cessazione_programmata:
            self._repo.update_stato(contratto_id, target_stato_id)
    return self.get_contratto(contratto_id)

Struttura chiavi — radici dei namespace¶

La chiave i18n è un contratto fra tre livelli, non una faccenda del solo frontend. Il database emette l'indirizzo di una traduzione (label_key, reason_key nelle capability script.fn_available_actions_* e nel meta dei seed config.transizioni_stati_*), il backend lo trasporta senza interpretarlo, il frontend lo risolve. Se l'indirizzo non esiste il frontend non segnala un errore: mostra testo mancante — il difetto è silenzioso e si scopre solo guardando la schermata. È già costato due difetti in produzione-dev (offerte, ordini), entrambi da chiavi emesse in una radice inesistente.

La regola (una sola):

Se una stringa appartiene a un modulo che vive in una cartella d'area di frontend/src/ (vendite, anagrafiche, catalogo, amministrazione, config, ui, portale, shop, …), il suo indirizzo parte da quell'area: vendite.ordini.*, anagrafiche.clienti.*, amministrazione.emittenti_fiscali.*. Se è vocabolario trasversale, riusato da più aree o che vive in core/, resta in cima: common.*, errors.*, validation.*, nav.*, search.*, confirm.*.

Corollari operativi:

  • L'ancora è la cartella del codice, non lo schema DB: listini sta in vendite/, clienti in anagrafiche/ — l'indirizzo segue il codice.
  • La foglia non ripete l'area: amministrazione.emittenti_fiscali, non amministrazione.amm_emittenti_fiscali.
  • Niente radici piatte di dominio in cima (preventivi.*, clienti.*): sono esattamente la forma che ha generato i difetti. Una radice nuova in cima si crea solo per vocabolario d'interfaccia trasversale.
  • Vale identica per le chiavi emesse dal DB: una reason_key di un ordine deve iniziare per vendite.ordini., non ordini..
  • Ogni stringa va aggiunta in entrambi i file (it.json e en.json) contemporaneamente: la parità è verificata.

Controllo automatico (obbligatorio prima di toccare chiavi o namespace): python3 scripts/check_i18n_keys.py [--strict-roots] — rende rumoroso l'errore silenzioso: chiavi citate ma assenti, chiavi emesse dal DB (capability + seed) non risolvibili, parità it/en, radici di dominio in cima, e chiavi definite due volte nello stesso oggetto. Va tenuto verde.

⚠️ Una chiave scritta due volte non è un errore di sintassi: in JSON è lecito, e ogni parser tiene l'ultima — JSON.parse come json.load. La prima è quindi morta, senza errori e senza test rossi, e il file mostra una frase che a video non compare. ⭐ Fa danno quando i consumatori sono due con contratti diversi: il 2026-08-26 vendite.lotti.numera_esito era definita due volte, e la numerazione di massa — che passa {numerati} — riceveva la frase del singolo lotto, perdendo il conteggio. Un segnaposto che non compare non si vede. ⛔ E il cancello era cieco al proprio difetto fino a quel giorno: faceva json.load, cioè leggeva il dizionario già collassato — guardava il risultato invece del difetto. Ora usa un object_pairs_hook, che vede le coppie prima che si schiaccino. Un presidio che parsifica il formato eredita la tolleranza del formato.

Procedura di classificazione e inventario (come si decide dove va una radice esistente, soglia del 70%, casi «due indirizzi con lo stesso nome»): i18n-namespace-radici.md — riferimento di dettaglio, subordinato a questa sezione.

Icone: un nome di significato, in un punto solo¶

⛔ Nessuna icona PrimeIcons si scrive a mano ('pi pi-...', icon="pi pi-...", class="pi pi-...") fuori da src/core/constants.js e src/core/navigation.js (censimento icone per significato, approvato da Tid il 2026-09-27). Il presidio è src/core/icone.spec.js. Fa due controlli:

  • fallisce se un letterale compare altrove;
  • fallisce se una costante punta a un glifo che PrimeIcons non ha. Una classe inesistente non dà errore: l'icona semplicemente non c'è.

Il nome dice il significato, non il disegno: STAMPA, SOSPENDI, RIPROVA, non PRINT, PAUSE, REPLAY. Due regole ne discendono:

Una voce che porta a una cosa con un'icona sua ripete l'icona della cosa (FATTURE, SOGGETTO, NAV_ICONS.PRATICHE). Il generico VAI_A è solo un ripiego.

Pattern toggle dinamico: EXPAND / COLLAPSE¶

Per accordion, expansion row di DataTable, tree e qualsiasi azione che apre/chiude contenuto, usare la coppia dinamica MANAGE_ICONS.EXPAND (pi pi-chevron-down, stato collassato — invita ad aprire) e MANAGE_ICONS.COLLAPSE (pi pi-chevron-up, stato espanso — invita a chiudere). Standard PrimeVue/Material allineato.

Eccezione — expansion row di DataTable (2026-09-27): il toggler di riga PrimeVue usa chevron-right (chiusa) / chevron-down (aperta). Il toggle «espandi tutte» della lista usa la stessa coppia, MANAGE_ICONS.ROW_EXPAND / MANAGE_ICONS.ROW_COLLAPSE, così riga e lista portano lo stesso segno. Stessa coppia per i gruppi annidati della sidebar e per i toggler di riga scritti a mano nei drawer (isExpanded(data) ? ROW_COLLAPSE : ROW_EXPAND). ⛔ Mai il glifo pi pi-chevron-* cablato per un toggle di espansione. EXPAND/COLLAPSE restano per accordion, pannelli e tree.

⛔ Su una <ListaConfigurabile> il toggle «espandi tutte» NON si scrive in pagina (2026-09-18): è l'azione standard di useListaAzioni, accanto a «Personalizza colonne» ed «Esporta», e compare da sé solo quando c'è qualcosa da espandere (colonne ritirate o dettaglio inline). L'esempio qui sotto vale per le superfici che non sono liste configurabili. I listini avevano il proprio toggle-all-versioni: era la prima copia, ritirata alla seconda.

// In toolbar globale (PageActionsBar) — toggle di tutte le righe

Glifo vs controllo — icone decorative/indicative¶

Non tutte le icone sono pulsanti. Un'icona decorativa/indicativa (una freccia di direzione, un ↩ di ramo, il glifo accanto a un titolo di sezione) non deve mai sembrare cliccabile; un'icona azione deve esserlo senza ambiguità. La distinzione si gioca sul chrome, non sulla tinta.

Icona azione (controllo) Icona glifo (decorativa)
Hit-area (padding/box) sì no — inline nel flusso
Hover sì no
cursor pointer default
Colore semantico saturo via classe app-*-btn (blu azione e gestisci / rosso distruttivo / arancio cautela) --app-text-muted

Regole:

  • Il colore non è l'affordance principale: lo è il chrome. Un glifo senza hit-area, senza hover e con cursor: default non viene letto come pulsante qualunque sia la sua tinta.
  • Mai un colore nuovo (teal, viola, ecc.) per dire "non sono cliccabile": nella palette il colore È semantica, un 6° colore sarebbe l'unico senza significato e, per essere distinguibile, dovrebbe essere saturo → avanza invece di arretrare. Pacchiano per costruzione.
  • Mai uno sfondo/chip per un glifo: è il segnale più forte di "sono un bottone" — l'opposto dell'obiettivo.
  • Per il glifo usare --app-text-muted (arretra). Attenzione: ha lo stesso valore di --app-btn-disabled-color, quindi da solo direbbe "bottone disabilitato" — è il chrome assente a chiarire che è decorativo. La differenza --app-text-color vs --app-text-muted su un glifo piccolo (≈0.8rem) è impercettibile: non usarla come leva.
  • opacity non è un segnale semantico. Non usarla per "attenuare" un elemento: si somma ai veli dei contenitori (es. .app-readonly a 0.85 nei drawer post-DRAFT → 0.85 × 0.75 ≈ 0.64, area illeggibile) e smorza anche i dati veri dentro la riga (codici, Tag stato). Se un ramo/stato va segnalato, farlo con icona + label esplicita, non con opacity.

Primo consumatore: LineagePassaggiContenuto (corpo "Passaggi", in dialog dai chip di DocumentoCollegamentiBar) — frecce direzione e ↩ ramo inverso come glifi muted.

⭐ Dove vive il NOME di un'icona — la regola del 2 applicata al significato¶

Decisa con Tid il 2026-09-02, dopo che una revisione aveva proposto di portare tutte le icone scritte a mano dentro MANAGE_ICONS.

Le due sezioni sopra dicono com'è fatta un'icona (glifo o controllo) e quali icone sono composite (le entità di dominio). Restava senza risposta la terza domanda, ed è quella che si pone chi scrive una cella: il nome dell'icona lo scrivo sul posto o lo metto in una costante?

La regola, e non è nuova — è la regola del 2, applicata al significato:

Un'icona che porta un senso ripetuto in più di un punto è un concetto: va in MANAGE_ICONS e i consumatori la referenziano. Un'icona usata una volta sola, decorativa, resta letterale sul posto.

⛔ La regola generale «ogni icona da MANAGE_ICONS» è stata VALUTATA E RIFIUTATA, e non per il costo delle modifiche — per il merito. Una costante serve a dare un nome a un concetto: darlo a un glifo con un solo lettore obbliga chi legge la pagina ad aprire un altro file per sapere cosa mostra, e produce un nome che deriva dal suo unico uso alla prima modifica. Una costante con un consumatore solo non centralizza niente: sposta.

⭐ E il rischio vero non è la centralizzazione, è la DIVERGENZA DI SIGNIFICATO. Se «bloccato» si scrive a mano in sei punti, sei punti possono derivare a sei icone diverse per lo stesso stato — e quello è un difetto che l'operatore vede, che nessun test prende e che nessuno attribuisce alla causa. È questo che la costante previene, non il numero di righe.

Come si applica, in una domanda:

Chiedersi Se sì Se no
«Questa icona dice una cosa che l'applicazione dice anche altrove?» concetto → MANAGE_ICONS, e si sistemano tutte le occorrenze di quel senso letterale sul posto

⚠️ Il criterio è il SENSO, non la stringa. Due pi pi-check che significano cose diverse (una «riga valida», l'altra «preset di default») sono due casi da una volta, non un concetto da due: unirli sotto una costante sola creerebbe un legame falso, e il giorno in cui una delle due cambia icona cambierebbe anche l'altra.

⚠️ E vale nei due versi: una costante in MANAGE_ICONS che è rimasta con un consumatore solo va riportata sul posto, non tenuta per simmetria.

Come si misura il perimetro (la misura trova i candidati, non decide la regola — che reggerebbe identica con qualunque numero):

cd frontend
# icone scritte a mano nei template
grep -rho 'class="pi pi-\[a-z0-9-\]*"' src --include=*.vue | sort | uniq -c | sort -rn
# quante passano gia' dalla costante
grep -rho 'MANAGE_ICONS\.\[A-Z_\]*' src --include=*.vue --include=*.js | wc -l

Le icone usate una volta sola non sono candidate per costruzione; il perimetro da guardare sono le ripetute, e solo quelle in cui la ripetizione è davvero lo stesso senso.

⛔ Non è una campagna da fare in un colpo. Si consuma come l'inventario delle liste: quando si tocca un file per altri motivi, e partendo dai sensi più ripetuti.

Iconografia di dominio — base documento + overlay-tipo¶

Le icone delle entità vendite (preventivi, offerte, ordini, ddt, resi, contratti, fatture) sono icone composite definite in main.css come .app-nav-icon-<entita> con due pseudo-elementi, e referenziate da NAV_ICONS (navigation.js), non da PrimeIcons singole.

Il principio (deciso con Tid 2026-07-09): nessun glifo "si spiega da solo" per un nome proprio (un calculator significa "calcolo" ovunque, non "preventivo"). Il riconoscimento nasce da famiglia coerente, differenziatore ed etichetta (l'icona ha sempre label o tooltip accanto). Quindi:

  • ::before = base documento (pi-file \e958) → il marcatore di famiglia/area: "questo è un documento vendite" (mai un glifo generico che potrebbe significare altro).
  • ::after = overlay del TIPO → il differenziatore, grande, dentro l'angolo in basso a destra del foglio, che è aperto come quello di pi-file-edit (Tid 2026-09-27; lo si ottiene ritagliando pi-file con clip-path, perché il font non ha un foglio aperto senza simbolo proprio). ⭐ Misure di base e simbolo in una regola sola per tutta la famiglia, in main.css: ogni documento dichiara solo il content del suo ::after.

Il pezzo che varia (l'overlay) è quello che deve distinguere; l'euro resta solo su Fattura, dove finalmente significa qualcosa di specifico. ⚠️ La regola vale dentro la famiglia documento (base \e958): su un'altra base l'euro è un altro segno.   • Due elementi, non tre. Base (famiglia) + overlay (tipo). Non aggiungere un terzo marcatore "area": la base È già l'area → sarebbe solo ingombrante.
  • Niente collisioni di dominio/azione: l'icona del dominio Vendite è il carrello intero (pi-shopping-cart pieno) → l'ordine usa il carrello come badge su documento, non collide. Mai pi-replay/pi-refresh per i Resi (si leggono come "ricarica").

Sicurezza¶

Autenticazione JWT¶

⛔ Nessun token in localStorage (dal 2026-09-28, brief sicurezza (docs/it/dev/work-in-progress/brief-be-fe-sicurezza-header-token-mfa.md) §2). Il refresh sta in un cookie HttpOnly che il JavaScript non vede: lo scrivono e lo leggono il backend e il browser. L'access (10 minuti) vive solo in memoria, in core/sessione.js. Al ricaricamento della pagina l'access non c'è mai: la sessione si ritrova rinnovando dal cookie.

Meccanismo Dove Descrizione
Access in memoria core/sessione.js Unica sede dell'access; reattivo (accessTokenRef)
Route guard router/index.js Rotte protette di default; auth.ripristinaSessione() prima di ogni rotta
Rinnovo core/api.js rinnovaAccess Corpo vuoto + header X-Requested-With; il cookie lo porta il browser
Una scheda alla volta core/sessione.js rinnovaCoordinato Lock del browser + BroadcastChannel: rinnova una scheda, le altre ricevono l'access
Accodamento core/sessione.js Chiamate concorrenti della stessa scheda aspettano la stessa promise
Protezione loop core/api.js Chiamate a /token/ escluse dal rinnovo
Redirect LoginView Rotta originale salvata in ?redirect=
Motivo del ritorno core/sessione.js MOTIVO_USCITA ?reason=: sessione scaduta o logout da un'altra scheda, ognuno con la sua frase
Logout stores/auth.js Backend cancella il cookie; clearTokens() pulisce; le altre schede escono

⭐ Più schede. Ogni rinnovo ruota il refresh e mette in blacklist il precedente: due schede che rinnovano insieme presenterebbero lo stesso cookie, e la seconda verrebbe buttata fuori. Il rinnovo gira quindi dentro un lock (navigator.locks): una scheda alla volta, e il cookie (condiviso) è già quello ruotato da chi è uscito dal lock. L'access nuovo si annuncia sul canale zeroerp-sessione. Gli altri due eventi — logout (tutte le schede escono) e sessione nuova (login o cambio emittente in un'altra scheda: questa riparte dal boot) — li gestisce lo store auth. ⛔ Nessun altro modulo chiama l'endpoint di refresh: passa da rinnovaAccess, altrimenti il coordinamento ha un buco.

Regole di sicurezza¶

  • Mai accedere a localStorage direttamente — passa da core/storage.js; e ⛔ mai un token lì dentro
  • Mai window.location per redirect — usare il router. ⭐ Una sola eccezione dichiarata, e non è un redirect: l'azione ripartiDalBoot di stores/auth.js fa window.location.assign(...) per ripartire dal boot. La usano due casi con la stessa esigenza: cambiaEmittenteAttivo (cambiare emittente cambia ciò che si vede ovunque) e l'apertura di una sessione nuova in un'altra scheda (login o cambio emittente: il cookie ora è di un'altra sessione). L'applicazione tiene stato in cache fuori dagli store (KeepAlive delle viste, cache di modulo dei lookup): solo un ricaricamento completo garantisce che non restino a video dati della sessione precedente. Un terzo caso passa dalla stessa azione, non scrive un secondo window.location
  • Mai esporre dati sensibili in log, template o attributi HTML
  • Mai costruire URL con interpolazione da input utente — usare parametri Axios

Gestione errori API¶

I componenti non gestiscono errori manualmente. Il composable useApiHandler intercetta, estrae il messaggio dall'envelope backend e mostra il toast.

// Caricamento (toast solo su errore) — la funzione viene dal modulo api/
const data = await execute(() => listConfigRecords(rel, params))

// Salvataggio (toast su successo e errore)
const result = await execute(
  () => store.create(payload),
  { successMessage: t('notifications.save_success') }
)

// Polling silenzioso (nessun toast)
const sessioni = await execute(() => listSessioni(), { silent: true })

⭐ Campi in errore dal backend — campiErrati (dal 2026-08-08)¶

Quando il backend sa quale campo l'operatore deve correggere, lo dice: l'envelope d'errore porta error.fields, un array di nomi (mai i valori — vedi api.md §Envelope risposte). useApiHandler li espone gia' pronti da legare agli input:

const { execute, loading, campiErrati } = useApiHandler()

<InputText v-model="form.codice" :invalid="campiErrati.includes('codice')" />

Non sostituisce la validazione client, la completa: canSave copre le regole che il frontend conosce (obbligatorieta', formato), campiErrati copre quelle che stanno nel service — unicita', coerenza fra entita', vincoli di stato. Prima l'operatore leggeva «Campo 'ordinamento' non valido» nel toast e doveva cercarselo da solo nel form.

si azzera a ogni execute descrive l'ultimo errore, non la storia del drawer. Il campo resta rosso finche' non si riprova a salvare
si legge anche in silent il chiamante puo' voler evidenziare senza toast
nessun messaggio sotto il campo il testo sta gia' nel toast; ripeterlo sotto l'input e' rumore. Il bordo rosso dice dove, il toast dice cosa
il nome e' quello del payload API, non del v-model se il form rinomina un campo, il legame va scritto a mano — :invalid="campiErrati.includes('nome_api')"

È lo standard, non un caso isolato: dal 2026-08-08 i drawer lo legano. La regola per un drawer nuovo: se un campo del form ha lo stesso nome della chiave che mandi nel payload, legalo — costa una riga e il giorno in cui il service comincia a rifiutarlo l'operatore vede dove.

⚠️ Non si lega tutto: la lista dei nomi che il backend può davvero mandare è finita (si ricava dai context={"field": …} e dalle chiavi passate ai validator). Legare un campo fuori da quella lista non fa danno ma non fa niente: è una riga che non decide.

✅ Dal 2026-08-24 lo popolano anche gli errori nati in PL/pgSQL, e la storia merita una riga perché è un difetto che si vedeva solo dal lato che riceve. Il canale del database (RAISE … USING COLUMN) viaggiava dall'08/08 ed era valorizzato da quasi tutti i punti di sollevamento — ma il backend lo perdeva appena un service traduceva l'errore, cioè quasi sempre. Il nome arrivava all'envelope da una strada su cinque, e a video non si illuminava niente. Ora la lettura è una sola (diagnostica_db) e il campo viaggia fino in fondo: vedi api.md §I cinque punti di traduzione.

⭐ Il bersaglio dell'errore — bersagli (dal 2026-08-24)¶

campiErrati dice quale campo correggere nella pagina dove l'operatore già si trova. Il bersaglio dice a quale altra cosa deve andare — ed è la differenza fra evidenziare un input e disegnare un gesto.

messaggio:  «Non si può numerare il documento 835: la fattura che
             rettifica non è ancora numerata (documento 820).»
gesto:      \[ Apri Fattura 820 \]

⭐ Perché esiste: all'operatore non serve il nome del record, gli serve arrivarci. Un identificativo dentro una frase, per quanto umano, resta una cosa da ricopiare a mano in un campo di ricerca.

Non c'è niente da scrivere nei componenti. Il gesto lo compone useApiHandler e lo consegna al toast: tutti i file che usano execute lo hanno già.

// Serve solo a chi ha una superficie PROPRIA dove metterlo.
const { execute, bersagli } = useApiHandler()
Regola Perché
il toast con un gesto è persistente un pulsante che sparisce dopo cinque secondi non è un gesto. life: 0, come systemError
bersaglio irraggiungibile → nessun pulsante è un'offerta, non una promessa: permessi, area bloccata, tipo senza destinazione. Il messaggio si mostra lo stesso. ⛔ Mai un pulsante che porta in un vicolo cieco
mai su un errore tecnico su un 500 l'operatore non ha niente da fare. Lo toglie il backend, in _apply_policy
al massimo cinque oltre, non è più un gesto ma un elenco — e quanti sono lo dice già la frase

Le tre superfici, e il resolver è uno solo:

Da dove arriva l'errore Chi disegna il gesto
envelope error.targets (una chiamata fallita) il toast, via useApiHandler — automatico
errore.targets dentro un 200 del runner di pipeline useLottoAzioni, stesso toast
errore_bersagli di una riga (giro asincrono, errore persistito) ErroreRigaInfo, il popover dell'icona di riga

⚠️ Un resolver solo — core/bersagli.js — per tutte e tre. Se divergessero, lo stesso errore direbbe due cose diverse a seconda di come è arrivato a video.

⭐ E la terza riga è quella che conta di più. Un giro di fatturazione può partire da solo — worker, batch notturno — e fallire quando davanti allo schermo non c'è nessuno: chi legge quell'errore lo legge ore dopo, dall'icona di riga. Il toast è il caso facile.

Aggiungere un tipo raggiungibile = una riga in DESTINAZIONI (core/bersagli.js) più la sua etichetta config.tipi_entita.<codice> in it.json/en.json. ⚠️ L'indirizzo i18n lo dichiara il database (config.tipi_entita.etichetta_key): qui si ripete quella chiave, non se ne inventa una — è lo stesso patto dei tre livelli già descritto sopra.

⚠️ Oggi TASK_RUN non è raggiungibile, ed è deliberato: è a catalogo perché serve al giornale degli eventi, e nessuna schermata mostra un giro per id.

⭐ La soluzione — hint, cioè cosa fare adesso (dal 2026-09-09)¶

campiErrati dice quale campo correggere, il bersaglio dice a quale altra cosa andare. La soluzione dice cosa fare adesso — ed è la terza metà, quella che mancava.

messaggio:   «Non si può numerare il documento 835: la fattura che
              rettifica non è ancora numerata (documento 820).»
soluzione:   «Numerare prima i documenti che questo rettifica, poi ripetere.»
gesto:       \[ Apri Fattura 820 \]

⭐ La frase non la scrive il frontend, e nemmeno il backend: è la soluzione che il team DB scrive a catalogo per ogni codice, quindi è multilingua e cambia con un seed. Viaggia nell'envelope come error.hint.

Non c'è niente da scrivere nei componenti. La estrae useApiHandler e la consegna al toast, che la rende sotto il messaggio — esattamente come per il gesto:

// Serve solo a chi ha una superficie PROPRIA dove metterla.
const { execute, soluzione } = useApiHandler()
Regola Perché
va nel detail del toast, mai concatenata al messaggio sono due frasi con due ruoli — cosa è successo, cosa fare — e il tema le rende una sotto l'altra con pesi diversi. Unirle produce un periodo unico in cui l'istruzione si perde dentro la diagnosi
il toast che la porta dura di più (TOAST_DURATION.ERROR_CON_SOLUZIONE) la durata si calibra su quanto c'è da leggere, e qui il testo è il doppio. ⛔ Non è persistente come quello col gesto: la soluzione è a catalogo per ogni codice, e life: 0 farebbe di ogni errore di dominio un toast da chiudere a mano
su un errore tecnico non arriva, e non è il frontend a deciderlo lo toglie _apply_policy sui tre codici in cui il canale HINT non porta una soluzione a catalogo ma il testo che PostgreSQL scrive per lo sviluppatore. ⛔ Ri-deciderlo qui sarebbe una seconda sede della stessa regola
il rifiuto confermabile non la mostra, ed è voluto lì la frase «cosa fare adesso» è il dialog che sta comparendo (useForzaturaConfermata): ripeterla sotto sarebbe dire due volte la stessa cosa

⛔ Chi chiama notify.error(...) a mano non ce l'ha, ed è la stessa asimmetria che già vale per il gesto: il canale è execute, e un secondo percorso che legge l'envelope per conto proprio è la forma in cui i due divergono. Se una schermata mostra un errore senza passare da useApiHandler, la domanda da farsi è perché.

⚠️ ui_action: un valore su sette, e gli altri sei sono SERVITI. useApiHandler lo espone come azioneUi; l'unico componente che ci ramifica è useForzaturaConfermata, su confirm_and_retry. ⭐ Non è una lacuna, ed è dichiarato (decisione di Tid, 2026-09-09): highlight_form_fields lo serve campiErrati, redirect_login lo serve lo status 401 in core/api.js, e i restanti quattro li serve il toast — che ora porta anche la soluzione e, dove c'è un bersaglio, il gesto. ⚠️ Prima di dare un comportamento al settimo vanno rilette le righe di override, decise quando nessuno poteva verificarle a video. Modalita' sola lettura e accesso — pattern "protect"¶

Principio¶

Le autorizzazioni utente prevedono tre livelli di accesso (TUTTO, LETTURA, BLOCCATO) su tre granularita' diverse. Tutti i form e le view devono supportare nativamente le modalita' ridotte senza duplicare componenti o creare varianti separate.

Piramide permessi¶

Livello Cosa controlla Trigger FE Enforcement BE
Area (schema DB) Accesso all'intero dominio useReadonlyMode(schemaDb) + route guard su BLOCCATO ZeroERPPermission via area_funzionale
Azione processo Singola operazione (es. "genera fatture") action su PageActionsBar / FormFooter permission_codename sulla view
Oggetto / model (v2) Singola entita' dentro un'area useReadonlyMode(schemaDb, modelName) model_permission = (app_label, model_name) sulla view

Composable useReadonlyMode(schemaDb, modelName?)¶

Il provider va chiamato nella View (parent della SearchTable e dei drawer). I figli iniettano con useInjectReadonly() / useInjectBlocked().

// Livello area (classico)
useReadonlyMode(READONLY_DOMAINS.ANAGRAFICHE)

// Livello oggetto (permessi v2) — richiede model_permission sulla view BE
useReadonlyMode(READONLY_DOMAINS.ANAGRAFICHE, READONLY_MODELS.CLIENTE)

Semantica di isReadonly / isBlocked dopo la risoluzione:

Contesto Livello risolto isReadonly isBlocked
Area TUTTO false false
Area LETTURA true false
Area BLOCCATO — (route guard interviene prima) —
Oggetto TUTTO false false
Oggetto LETTURA true false
Oggetto BLOCCATO true true

A livello oggetto BLOCCATO implica anche isReadonly (l'utente non deve poter attivare form o inviare POST).

Tecnica CSS "pannello protect"¶

Ispirata al formato protect AS/400: un unico overlay CSS blocca ogni interazione sul contenuto, senza toccare i componenti interni. Non si creano componenti *ReadOnly.vue separati.

.app-readonly {
  pointer-events: none;     /* blocca ogni click, hover, focus */
  user-select: text;        /* permetti copia testo */
  opacity: 0.85;            /* feedback visivo: stai consultando */
}

Wrap del contenuto:

<div :class="{ 'app-readonly': isReadonly }">
  <!-- form, DataTable, drawer content — tutto normale -->
</div>

  • Non mostrare toolbar, filtri o tabella: sostituisci con <AccessoBloccatoPanel />

Drawer di entita' con sub-drawer (catena readonly)¶

Regola d'oro: il readonly non si calcola mai nei sub-drawer. Lo calcola il drawer di entita' (parent) e lo propaga via provide(READONLY_KEY, ...). I sub-drawer (note, righe, utility, conti, ecc.) usano solo useInjectReadonly() senza nessuna logica locale.

I drawer di entita' (es. ContrattoDrawer, PreventiviDrawer) sono il punto unico dove si combinano i 3 ingredienti del readonly:

  1. Permessi area/oggetto dell'utente — via useInjectReadonly() dal provider della View
  2. Stato workflow del documento (DRAFT vs stati post-DRAFT) — derivato da detail.stato_codice*
  3. Contesto — props.readonly (split-view), is_attiva=false (revisione superseded), ecc.

Il computed risultante isReadonly viene provide-ato con READONLY_KEY ai sub-drawer, che lo ricevono "gia' cotto" tramite useInjectReadonly().

Template drawer di entita' (parent provider):

// ContrattoDrawer.vue / PreventiviDrawer.vue
import { computed, provide } from 'vue'
import { useInjectReadonly, READONLY_KEY } from '@/core/composables/useReadonlyMode'

const parentReadonly = useInjectReadonly()                  // (1) permessi area
const isWorkflowLocked = computed(                          // (2) stato post-DRAFT
  () => props.mode === 'edit'
     && detail.value
     && detail.value.stato_codice !== 'DRAFT',
)
const isSuperseded = computed(                              // (3) contesto entita'
  () => detail.value !== null && detail.value.is_attiva === false,
)

const isReadonly = computed(() =>
  parentReadonly.value
  || props.readonly
  || isWorkflowLocked.value
  || isSuperseded.value,
)
provide(READONLY_KEY, isReadonly)

Template sub-drawer (figlio puro consumer) — zero logica locale:

// ContrattoRigheDrawer.vue / PreventivoNoteDrawer.vue / ContrattoNoteDrawer.vue
import { useInjectReadonly } from '@/core/composables/useReadonlyMode'

const isReadonly = useInjectReadonly()  // ← solo lettura. STOP.

Anti-pattern (DA NON FARE) nel sub-drawer:

// ❌ NO: logica locale che ricalcola lo stato workflow
const parentReadonly = useInjectReadonly()
const isReadonly = computed(
  () => parentReadonly.value || props.contrattoStatoCodice !== 'DRAFT',
)

Perche' e' sbagliato:

  • duplica la regola del modello UX in 2 posti (parent + figlio) — drift garantito
  • nasconde una props (contrattoStatoCodice) che il sub-drawer non dovrebbe nemmeno conoscere
  • se la regola cambia (es. CESSATO ammette modifica meta), va aggiornata in N posti
  • rompe il pattern "Provider → Consumer" su cui si fonda il sistema permessi

Se il sub-drawer ha bisogno di un readonly diverso dal parent (caso raro: il padre e' editabile ma il figlio no per ragioni di dominio), allora il PARENT estende il proprio isReadonly con quella regola e la propaga. Il sub-drawer resta agnostico.

Azioni di stato in drawer readonly — i pulsanti di transizione (Emetti, Accetta, Cessa, ecc.) restano cliccabili anche dentro app-readonly perche' DrawerActionsBar applica automaticamente .app-escape a tutti i suoi pulsanti. Non filtrare la lista actions per isReadonly (allineato a ContrattoDrawer.drawerActions / PreventiviDrawer.drawerActions): la sicurezza e' garantita dal BE che rifiuta i comandi senza permesso.

Azioni di processo su selezione righe → dialog, non pannello in coda (2026-07-25, decisione Tid). Le attività che generano un documento a valle selezionando righe (evasione ordine → DDT, smistamento preventivo → ordine/commessa, crea reso da DDT, ri-spedizione reso) si aprono da un pulsante nella DrawerActionsBar — con l'icona del documento che si genera (NAV_ICONS.DDT, NAV_ICONS.RESI, MANAGE_ICONS.SEND) e kind: 'manage' — e vivono in un AppDialog dedicato. Non più come pannello sempre montato in fondo al drawer: allungava il contenuto e faceva la fetch delle righe anche a chi non stava lavorando quel processo.

Regole del dialog d'azione:

  • fetch lazy su watch([visible, id]) — all'apertura e a ogni riapertura (i residui devono essere freschi dopo un'azione appena eseguita), mai al mount;
  • :readonly esplicito = il readonly PURO del chiamante (permessi/split/superseded), NON quello combinato col lock-di-stato: il dialog è lanciato da un drawer post-DRAFT app-readonly e senza override FormFooter erediterebbe readonly=true nascondendo il pulsante di conferma — è la stessa ragione per cui il pannello, quando viveva nel drawer, stava in app-escape (vedi AppDialog.readonly);
  • :close-only quando non c'è nulla da fare (readonly puro o nessuna riga lavorabile): il dialog resta consultabile come consuntivo;
  • chiusura a conferma riuscita, con emit al drawer padre che ricarica detail e capability. Un lavoro parziale si riprende riaprendo il dialog.

Riferimento: DdtResoDialog, OrdineEvasioneDialog, PreventiviSmistamentoDialog.

⚠️ La X del drawer NON ha bisogno di una regola (verificato 2026-09-18): app-readonly sta sul wrapper del contenuto (app-drawer-content), e la testa del Drawer — con la sua X — è fuori da quel wrapper. Fino a quel giorno qui stavano due selettori in più, .p-drawer-close e .p-dialog-close, che in PrimeVue non esistono (le classi sono p-drawer-close-button / p-dialog-close-button): CSS morto che descriveva un meccanismo mai attivo. Il dialog una X non ce l'ha più (§AppDialog, «Chrome»).

Regola: in sola lettura si puo' solo chiudere/uscire, mai aprire/creare/modificare.

  • DrawerTitle: auto-include ReadonlyBadge a destra del titolo
  • FormFooter: Salva nascosto se readonly (v-if="!isReadonly")
  • PageActionsBar: nasconde le azioni con hideWhenReadonly, mantiene il refresh in LETTURA e usa il kebab su touch/tablet/mobile
  • ReadonlyBadge: visibile solo se readonly e non bloccato
  • AccessoBloccatoPanel: sostituisce il contenuto lista se bloccato (livello oggetto)
  • DataTable row-click: in sola lettura apre il drawer in modalita' consultazione (protect attivo)
  • Copia testo: user-select: text garantisce che l'operatore possa sempre copiare dati con Ctrl+C

Enum centralizzati cross-cutting (constants.js)¶

Principio¶

Le stringhe identificative condivise tra producer e consumer (readonly area/model, chiavi cross-tab refresh) NON si scrivono mai come literal. Vivono come costanti in src/core/constants.js e si importano dove servono.

Rationale: un typo silenzioso ('contratoo' vs 'contratto') rompe il binding senza errori runtime — il producer emette, nessun consumer ascolta, auto-refresh morto. L'enum toglie il problema alla radice (IDE autocompletion + grep facile).

I tre enum¶

import { READONLY_DOMAINS, READONLY_MODELS, TAB_ENTITIES } from '@/core/constants'
Enum Scopo Esempi
READONLY_DOMAINS Area (schema DB) passata come primo arg a useReadonlyMode AMM_SOFTWARE, ANAGRAFICHE, CATALOGO, CONFIG, DOCUMENTI, MAGAZZINO, PAGAMENTI, PRATICHE, STRUMENTI, VENDITE (elenco completo al 2026-09-26; PAGAMENTI e' entrato quel giorno, prima le view di pagamenti passavano la stringa)
READONLY_MODELS Model specifico (permessi v2) come secondo arg opzionale a useReadonlyMode CONTRATTO, CLIENTE, FORNITORE, ARTICOLO, UNITA_MISURA, CONTO_BANCARIO, SOGGETTO, PROMO_ARTICOLO
TAB_ENTITIES Chiave cross-tab per emitDataChanged + useTabFreshness / onDataChanged CONTRATTO, PRATICA, ARTICOLO, FORNITORE, PREVENTIVO, PROMO_ARTICOLI, ...

Regola operativa¶

// NO — literal vietato
useReadonlyMode('vendite', 'contratto')
emitDataChanged('contratto', id)
useTabFreshness(store, 'contratto')

// SI — costante
useReadonlyMode(READONLY_DOMAINS.VENDITE, READONLY_MODELS.CONTRATTO)
emitDataChanged(TAB_ENTITIES.CONTRATTO, id)
useTabFreshness(store, TAB_ENTITIES.CONTRATTO)

Il primo (literal) funziona ma non è mai accettato in PR di nuovo codice: il pattern enum è la fonte di verità per tutti i call site.

Consumer cross-tab: due pattern¶

Entrambi validi, ambedue usano TAB_ENTITIES:

// Pattern A — standard per SearchTable paginata
useTabFreshness(store, TAB_ENTITIES.CONTRATTO)
// Se un altro tab emette CONTRATTO, lo store fa fetchList() automatico

// Pattern B — hook custom (es. pannelli senza SearchTable, view di profilo)
const { onDataChanged } = useTabEvents()
onMounted(() => {
  onDataChanged('profilo-reparto', () => store.fetchList())
})

Pattern A è la default. Pattern B si usa quando la view non ha uno store standard con fetchList o quando serve un handler custom.

Producer cross-tab¶

Sta sempre nello store, dopo ogni operazione di scrittura:

// Store Pinia
async function create(payload) {
  const res = await api.create(payload)
  emitDataChanged(TAB_ENTITIES.CONTRATTO, res.data.data.id)  // emit post-write
  return res.data.data
}

async function update(id, payload) {
  const res = await api.update(id, payload)
  emitDataChanged(TAB_ENTITIES.CONTRATTO, id)
  return res.data.data
}

Entità read-only (es. log immutabili): non emettono mai, e nessun consumer deve ascoltarle.

⭐ Un verbo che fa nascere un'altra entità avvisa le DUE entità, dallo store del verbo. Generare un DDT da un ordine scrive sull'ordine (residui, stato) e crea il DDT; lo smistamento di un preventivo scrive sul preventivo e crea l'ordine. L'azione dello store che chiama l'endpoint emette per entrambe:

// store ordini
async function generaDdt(ordineId, righe = null) {
  const res = await generaDdtFromOrdine(ordineId, righe)
  emitDataChanged(TAB_ENTITIES.ORDINE, ordineId)
  if (res.data.data?.ddt_id) emitDataChanged(TAB_ENTITIES.DDT, res.data.data.ddt_id)
  return res.data.data
}

⛔ Mai l'emissione nella dialog o nel drawer che ha lanciato il verbo: un'altra superficie che chiama lo stesso endpoint (un flusso di pratica, un'azione di massa) non avviserebbe nessuno, e la lista dell'entità nata resterebbe ferma senza errori. Fino al 2026-09-26 facevano così OrdineEvasioneDialog e PreventiviDrawer (smistamento); generaRiconsegna dello store resi era già nella forma giusta. Il changed del drawer resta: è il contratto verso chi lo ha aperto, non l'avviso alle liste.

Aggiungere una nuova entità¶

  1. Aggiungere la chiave in constants.js:

Naming¶

  • READONLY_MODELS usa singolare snake_case (contratto, promo_articolo) — matcha app_label.model_name del BE Django per ZeroERPPermission.
  • TAB_ENTITIES può usare plurale dove è più naturale per la feature (promo_articoli, categorie_clienti) — è una chiave FE-only, non vincolata al BE.
  • READONLY_DOMAINS corrisponde 1:1 agli schema DB backend.

Una stessa parola può comparire in entrambi (es. PROMO_ARTICOLO singolare in READONLY_MODELS + PROMO_ARTICOLI plurale in TAB_ENTITIES): è volontario, i due ruoli sono distinti.

Store Pinia — user-scoped + reset al logout¶

Principio¶

Qualsiasi store Pinia che contenga dati specifici dell'utente loggato (filtri lista, cache di lookup user-aware, override personali, contesto selezionato, ecc.) DEVE dichiararsi userScoped: true come terzo parametro di defineStore. Il plugin autoResetPlugin (src/core/pinia-plugins/auto-reset.js) lo intercetta e:

  1. al login successivo / al logout chiama resetAllUserScopedStores() da auth.js
  2. per ogni store user-scoped invoca clearUserState() se esposto come action, altrimenti fa fallback su $resetToInitial() (snapshot dello state al primo init)

Razionale: senza questo flag uno stesso browser usato in sequenza da utenti diversi (caso "computer in ufficio condiviso") rischia che l'utente B veda i filtri / la cache / gli override dell'utente A. Bug di sicurezza silenzioso.

Pattern store user-scoped¶

export const useMyStore = defineStore('my-store', () => {
  const items = ref(\[\])
  const filters = ref({ ... })

  function clearUserState() {
    // Solo se serve logica custom oltre al snapshot:
    // es. clear di Map/Set/cache module-level interna,
    // disconnect di BroadcastChannel, ecc.
    items.value = \[\]
    filters.value = { ... }
  }

  return { items, filters, clearUserState }
}, {
  // Reset automatico al logout via autoResetPlugin.
  userScoped: true,
})
Quando serve clearUserState() esplicito Quando basta lo snapshot
Lo state contiene Map / Set / Date / function (non JSON-serializable) State con primitives, oggetti/array piani
Lo store legge da localStorage all'init (snapshot fotografa già i dati utente); per auth vale per l'access in memoria di core/sessione, che lo snapshot non azzera State puro in-memory
Servono side-effect aggiuntivi (chiudere BroadcastChannel, abortire fetch in volo) Nessun side-effect

Pattern composable user-scoped (cache module-level)¶

I composable possono mantenere cache module-scope (es. useGlobalLookup._cache). Anche queste vanno azzerate al logout. Pattern:

import { registerUserScopedResetter } from '@/core/pinia-plugins/auto-reset'

const _cache = new Map()
registerUserScopedResetter(() => _cache.clear())

export function useMioCompose() { ... }

registerUserScopedResetter accetta una function di reset ed è idempotente. Va chiamata al top-level del modulo (non dentro la setup function).

Store globale parameters — cache condivisa per config.parameters¶

Single source of truth per i valori risolti (con override) dei parametri di sistema. Sostituisce la cache per-istanza che useParameterDefaults aveva pre-2026-05-02:

import { useParametersStore } from '@/stores/parameters'

const params = useParametersStore()
await params.ensure(\['DEFAULT_IVA_ID', 'DEFAULT_UTILITY'\])  // single-flight per code
const iva = params.get('DEFAULT_IVA_ID')                     // sync getter, null se mancante

API¶

Metodo Scopo
ensure(codes) Garantisce che i codes siano in cache. Single-flight per code: chiamate concorrenti convergono su una sola fetch. Idempotente.
get(code) Sync getter del valore risolto. Ritorna null sia se non in cache sia se BE non ha valore. Per distinguere usare has(code).
has(code) True se il code è già stato fetchato (anche con valore null).
invalidate(codes) Rimuove i codes dalla cache + broadcast cross-tab. La prossima ensure ri-fetcha.
setOverride(code, value, scope) Upsert override personale o emittente + invalidate automatico del code.
removeOverride(overrideId, code, scope) Delete override + invalidate. Il code serve per identificare cosa invalidare (l'API delete usa solo l'id).

Cosa risolve rispetto al composable per-istanza¶

Problema pre-2026-05-02 Soluzione store
4 drawer aperti = 4 fetch identiche per DEFAULT_UTILITY Single-flight per code: 1 sola fetch
Admin cambia override → drawer mostrano valore vecchio finché non F5 setOverride invalida la cache → tutti i computed reattivi si aggiornano
Cambio override in tab A non visibile in tab B BroadcastChannel('zeroerp-parameters') propaga gli invalidate cross-tab
Cache parametri persiste tra utenti diversi sullo stesso browser userScoped: true + clearUserState() azzera la cache al logout

useParameterDefaults come thin wrapper¶

Il composable useParameterDefaults esiste ancora come API ergonomica per i drawer:

const { defaults, load } = useParameterDefaults(\['DEFAULT_IVA_ID', 'CATALOGO_BOM_DEFAULT_OBBLIGATORIO'\])
await load()
form.iva_id = defaults.value.DEFAULT_IVA_ID   // string — convertire se serve

Internamente delega a useParametersStore: cache, single-flight, invalidation, cross-tab sync, reset al logout sono tutti gestiti dallo store. Il composable espone un computed defaults reattivo allo store.

Quando usare lo store direttamente vs il composable¶

  • Composable useParameterDefaults: drawer/form che leggono N parametri all'apertura e li usano in defaultForm(). È la scelta di default.
  • Store useParametersStore direttamente: pagine che fanno mutation di override (admin / impostazioni utente), o che devono reagire a invalidate cross-tab. Es. useParameterSettings.saveOverride delega a store.setOverride per ottenere invalidate gratis.

Convenzione codice_interno per parametri FK-surrogata¶

I parametri che referenziano tabelle di catalogo dotate di codice_interno (UNIQUE + immutabile via script.trgfn_lock_columns) stoccano il codice_interno, non l'id. La risoluzione codice→id è applicativa e va fatta lato FE incrociando il valore con la lookup della tabella target. Esempio: DEFAULT_UTILITY (codice_interno di config.utilities) risolto da useUtilityDefaultId.

Vedi anche linee-guida-sql §6b per il principio generale e il framework DB config.parameter_fk_surrogate.

Azioni processo — Livello 2 (pattern "action gate")¶

Principio¶

Le azioni di processo controllano singole operazioni (es. "crea soggetto", "genera fatture") dentro un'area a cui l'operatore ha gia' accesso. Sono il livello di granularita' sotto TUTTO/LETTURA/BLOCCATO.

Collocazione nel modello permessi¶

Livello 1: Area (TUTTO / LETTURA / BLOCCATO)  → sidebar + route guard + .app-readonly
Livello 2: Azione processo (abilitata / negata) → `action` su `PageActionsBar` / `FormFooter`

Come funziona¶

L'endpoint /me/ ritorna azioni_abilitate: { codename: boolean } per tutte le azioni attive. Lo store auth.js espone isActionAllowed(codename).

I componenti PageActionsBar e FormFooter accettano una prop opzionale action: - Se assente (default): il componente funziona come prima (solo check readonly) - Se presente: il componente si nasconde se l'azione non e' abilitata

// Azione "Nuovo" visibile solo se l'azione e' abilitata
{ key: 'new', kind: 'primary', action: 'crea_soggetto', label: t('common.new'), command: onNew }

<!-- Footer Salva visibile solo se l'azione e' abilitata -->
<FormFooter action="modifica_soggetto" @save="..." @cancel="..." />

Come aggiungere un'azione¶

  1. DB: inserire riga in config.azioni_processo (seed CSV)
  2. Backend: aggiungere post_permission = "codename" sulla view API
  3. Frontend: aggiungere action: 'codename' sull'azione PageActionsBar o prop action su FormFooter
  4. Configurazione: da Amm. Software → Profili reparto, abilitare per reparto

Composable per casi avanzati¶

Per logica condizionale oltre ai componenti standard:

import { useActionPermission } from '@/core/composables/useActionPermission'

const { isAllowed } = useActionPermission('genera_fatture_lotti')
// <Button v-if="isAllowed" ... />

Regole¶

  • Mai hardcodare codename nei componenti — usare costanti se ripetuti
  • Il backend blocca sempre con 403 anche se il frontend non nasconde il bottone (defense-in-depth)
  • ADMIN ha tutte le azioni abilitate — il check frontend lo gestisce automaticamente
  • La prop action e' cumulativa con readonly: se readonly=true, il componente e' nascosto a prescindere

Test — le tre altezze, e come si sceglie¶

⭐ Dal 2026-09-23 si montano i componenti (@vue/test-utils + jsdom, ok di Tid). Fino a quel giorno il frontend provava solo funzioni pure: quel confine ha presentato il conto tre volte in una settimana — rate, filtri di lista, barra del drawer di magazzino — e i filtri ne hanno pagati due difetti in un giorno, entrambi invisibili a qualunque funzione pura.

Altezza Ambiente Vede Costo
funzione pura (composable, utility) node — il default logica, calcoli, contratti di dato il più basso: si scrive sempre per primo
componente montato (// @vitest-environment jsdom) jsdom che cosa esiste nel DOM: quali pulsanti, acceso/spento, dove sta un attributo medio: vuole l'impalcatura, e parte più lento
a video un browser vero, cioè una persona come è disegnato: media query, ingombri, il telefono il più alto, e non si automatizza oggi

La regola di scelta: si scende di un'altezza solo quando quella sopra non può vedere il difetto. ⛔ Un componente montato per provare un if che sta in un composable è un test lento che prova la cosa sbagliata.

Come si monta¶

// @vitest-environment jsdom        ← in cima al file, prima di tutto
import { monta } from '../../../test/montaggio'

const w = monta(Componente, { prop: 'x' }, { provide: { [CHIAVE]: ref(true) } })
expect(w.findAll('button').map(b => b.text())).toContain('Conferma')
  • frontend/test/montaggio.js è l'impalcatura: installa i plugin che main.js installa sull'app vera (Pinia, PrimeVue + i suoi servizi, i18n, la direttiva tooltip) e colma le lacune di jsdom (matchMedia). Vive fuori da src/: non è codice applicativo e non deve finire in un bundle.
  • ⛔ Il DOM non si accende globalmente: chi ne ha bisogno lo dichiara in testa al proprio file. Accenderlo per tutti rallenterebbe i test puri — che sono la maggioranza — e nasconderebbe quali file toccano il DOM.
  • ⭐ Si monta il componente vero, si fingono solo i suoi contorni (un'API, la config che arriva dal server). Un test che stubba ciò che deve provare prova lo stub.
  • t rende la chiave, non la frase: le asserzioni parlano di chiavi i18n. Le frasi vivono nei locales, si riscrivono quando cambia il tono, e un test che le pinna diventa rosso per una virgola.
  • ⚠️ Le media query non si provano: jsdom non calcola il CSS. La variante compatta sotto i 1024px resta materia di collaudo a video, e va detto invece che sottinteso.

⛔ Un test verde al primo colpo si prova per mutazione¶

Si rompe di proposito il codice sotto esame e si guarda se il test diventa rosso. Un test che resta verde su un codice rotto non presidia niente.

🔴 Non è teoria: è già servito due volte lo stesso giorno. Sul mapper delle azioni, quattro mutazioni su cinque venivano viste e la quinta no — il ramo «motivo senza reason_key» non era coperto, e un dominio che perdesse la chiave avrebbe mostrato un tooltip vuoto su un pulsante spento, cioè il caso peggiore.   1. Ogni componente e' autonomo — logica nei composables (di core/ se generici, del dominio se parlano di un'entita')
  2. Un componente non parla HTTP: l'URL di un endpoint vive in un modulo api/ (del dominio o core/api/) o dietro uno store, e il componente chiama quella funzione dentro execute di useApiHandler.   3. Toast via useNotify() — mai useToast() direttamente
  4. Dialog conferma via useConfirmAction() — mai useConfirm() direttamente; sempre con header (il nome dell'azione)
  5. Drawer usano PrimeVue Drawer + FormFooter — mai pulsanti inline
  6. Testi visibili via $t() — mai stringhe hardcoded 6-bis. Un test si scrive all'altezza più bassa che vede il difetto (§Test), e se passa al primo colpo si prova per mutazione
  7. Nessun console.log in produzione
  8. Un dominio importa un altro dominio solo nel verso delle FK; il verso opposto passa da un punto di estensione, e core/ non importa mai un dominio (§«Confini fra domini»; presidio check-confini-domini.mjs)
  9. Larghezze drawer da constants.js — mai hardcoded
  10. Navigazione da navigation.js — mai duplicata
  11. Paginazione/sort/search da useSearchTable — mai implementata manualmente
  12. Inter-tab freshness di una lista da useTabFreshness — mai un onDataChanged scritto a mano accanto a uno store-lista. useTabEvents diretto solo per emettere (nello store, §«Producer cross-tab») o per il Pattern B (view senza store-lista standard, §«Consumer cross-tab»)

  14. CSS layout da main.css — mai <style scoped> per layout form/pagina
  15. Sola lettura da classe .app-readonly sul container — mai componenti duplicati
  16. Azioni processo via action su PageActionsBar/FormFooter — mai v-if manuali per permessi
  17. ConfirmDialog solo globale in App.vue — mai dentro Drawer (interferenza overlay) 18-bis.
