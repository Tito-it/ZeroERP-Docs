Sviluppo — Multi-Face Auth (Portale Clienti, Portale Fornitori, Shop Online)¶

Documento di pianificazione implementazione per il modello multi-face auth. Data creazione: 2026-04-18 Stato: Pianificazione iniziale — da rivedere ed evadere in fasi

1. Contesto¶

Oggi l'accesso al software e' modellato solo sul dipendente interno (risorsa umana). Vogliamo estendere il modello per supportare:

  • Clienti che accedono a un portale per vedere i propri documenti
  • Fornitori che accedono a un portale per vedere ordini e pagamenti
  • Clienti del negozio online con registrazione self-service

La guida architetturale spiega il come (nuovo bridge, profili generalizzati, scope policy, RLS, namespace API separati). Questo WIP elenca cosa fare concretamente, in ordine di dipendenza, con checkbox per tracciare l'avanzamento.

2. Principi guida per lo sviluppo¶

  • Additive, non distruttivo: risorse_umane_auth_user resta in produzione fino a fine migrazione. Nuove tabelle convivono con quelle vecchie
  • DB-first: le regole di scope vivono in funzioni SQL + RLS, non nel backend
  • Sviluppo concentrico: DB → backend → frontend, per fascia di maturita' (vedi docs/it/sviluppo-concentrico.md)
  • Nessun hardcoded: usare codici e lookup, mai ID numerici
  • Test prima di attivare: ogni fase ha una suite pgTAP + Django + smoke prima di essere dichiarata chiusa

4.6 Cutover operatori — da risorse_umane_auth_user a identita_digitali¶

Design deciso 2026-04-19: ADMIN modellato come profilo SUPER_ADMIN (nuovo valore in config.tipo_profilo_accesso) + binding su identita_digitali, NON come colonna boolean. Il bypass e' un privilegio bindato che riusa l'infrastruttura §4.3 (audit, storico, guard coerenza, finestra temporale). DISABILITATO legacy assorbito da ruolo_applicativo = DISABILITATO OPPURE identita_digitali.attivo = false. OPERATIVO legacy = default implicito (assenza di binding SUPER_ADMIN).
