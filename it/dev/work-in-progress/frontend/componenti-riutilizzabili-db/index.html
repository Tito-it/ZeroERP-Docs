Architettura indirizzi — catena completa¶

Riferimento: Guida Gestione degli Indirizzi

L'indirizzo in ZeroERP non e' un campo di testo: e' un dato strutturato normalizzato. La modalita' normalizzata (via indirizzo_dettaglio_id) e' sempre preferita. L'indirizzo_libero e' riservato a eccezioni (migrazioni, indirizzi esteri non normalizzabili).

Catena di normalizzazione (dal basso verso l'alto):

config.toponomastica          (Via, Piazza, Corso, Largo...)
       ↓
config.stradario_generale     (toponimo + denominazione via)
       ↓
config.stradario              (via locale = stradario_generale + comune + CAP)
       ↓
anagrafiche.indirizzi_dettaglio  (civico normalizzato: stradario + civico + estensione + palazzina + scala + piano + interno)
       ↓
anagrafiche.indirizzi_soggetti   (soggetto_id + tipo_indirizzo_id + indirizzo_dettaglio_id)

Gerarchia geografica: 

config.stati → config.regioni → config.province → config.comuni → config.codici_postali
                                                        ↓
                                                  config.stradario

Regole chiave (dalla guida): - R1 — XOR: o normalizzato (indirizzo_dettaglio_id) o libero (indirizzo_libero), mai entrambi - R2 — Unicita': un solo indirizzo per tipo per soggetto (UNIQUE soggetto_id, tipo_indirizzo_id) - R3 — Completezza libero: se libero, obbligatori indirizzo_libero + stato_id + (comune_id + codice_postale_id) oppure (locality + postal_box) - R6 — Guard tipo: trigger verifica tipo_indirizzo contro matrice config.tipi_soggetto_dettaglio_tipi_indirizzo - R7 — Unicita' civico: vincolo uq_indirizzi_dettaglio_norm su (stradario_id, civico, estensione, palazzina, scala, piano, interno)

Funzioni di ricerca gia' esistenti: - anagrafiche.fn_search_indirizzi_dettaglio(...) — ricerca per stradario+civico o fuzzy su indirizzo_normalizzato - script.fn_get_indirizzo(p_soggetto_ruolo_id, p_tipo_codice) — risoluzione master/fallback - script.fn_get_indirizzo_by_soggetto(p_soggetto_id, p_tipo_codice) — layer soggetto con fallback

Stato: COMPLETATO (2026-03-13) Prerequisiti: nessuno Schema: anagrafiche Tipo: building block riusabile

Funzione upsert: cerca un civico esistente per chiave naturale, se non esiste lo crea. Il vincolo uq_indirizzi_dettaglio_norm garantisce la deduplicazione.

Implementato in: - Changeset: db/changelog/migrations_v2/20_code/anagrafiche/20260313-12-create-fn-get-or-create-indirizzo-dettaglio-mctit.yaml - Doc manuale: docs/it/dbzero/anagrafiche/manual/fn_get_or_create_indirizzo_dettaglio.md - Test pgTAP: db/pgtap/anagrafiche/test-fn-get-or-create-indirizzo-dettaglio.sql (9 test)

Firma proposta: 

CREATE OR REPLACE FUNCTION anagrafiche.fn_get_or_create_indirizzo_dettaglio(
    p_stradario_id        config.stradario.id%TYPE,
    p_civico              anagrafiche.indirizzi_dettaglio.civico%TYPE         DEFAULT NULL,
    p_estensione_civico   anagrafiche.indirizzi_dettaglio.estensione_civico%TYPE DEFAULT NULL,
    p_palazzina           anagrafiche.indirizzi_dettaglio.palazzina%TYPE      DEFAULT NULL,
    p_scala               anagrafiche.indirizzi_dettaglio.scala%TYPE          DEFAULT NULL,
    p_piano               anagrafiche.indirizzi_dettaglio.piano%TYPE          DEFAULT NULL,
    p_interno             anagrafiche.indirizzi_dettaglio.interno%TYPE        DEFAULT NULL
)
RETURNS anagrafiche.indirizzi_dettaglio.id%TYPE

Logica: 1. Guard: p_stradario_id obbligatorio, verificare che esista e sia attivo in config.stradario 2. Cercare per chiave naturale (stradario_id, civico, estensione, palazzina, scala, piano, interno) con COALESCE su nullable 3. Se trovato → RETURN id esistente 4. Se non trovato → INSERT + RETURNING id (il trigger trgfn_indirizzi_dettaglio_normalize calcola indirizzo_normalizzato, via_norm, civico_norm) 5. Gestire unique_violation (race condition) con retry

Nota: questa funzione NON gestisce la creazione dello stradario. Se lo stradario non esiste, il chiamante (o il frontend) deve prima crearlo o selezionarlo. Vedi DB-1b.

DB-2 — Building block fn_crea_indirizzo_soggetto ✅ COMPLETATO¶

Stato: COMPLETATO (2026-03-13) Prerequisiti: DB-1 (se normalizzato) oppure nessuno (se libero) Schema: anagrafiche

Implementato in: - Changeset: db/changelog/migrations_v2/20_code/anagrafiche/20260313-14-create-fn-crea-indirizzo-soggetto-mctit.yaml - Doc manuale: docs/it/dbzero/anagrafiche/manual/fn_crea_indirizzo_soggetto.md - Test pgTAP: db/pgtap/anagrafiche/test-fn-crea-indirizzo-soggetto.sql (11 test) Tipo: building block riusabile

Crea un record in anagrafiche.indirizzi_soggetti. Supporta entrambe le modalita': - Normalizzata (standard): riceve p_indirizzo_dettaglio_id - Libera (eccezione): riceve p_indirizzo_libero + campi geografici

Firma proposta: 

CREATE OR REPLACE FUNCTION anagrafiche.fn_crea_indirizzo_soggetto(
    -- Obbligatori
    p_soggetto_id             anagrafiche.soggetti.id%TYPE,
    p_tipo_indirizzo_codice   config.tipi_indirizzi.codice_interno%TYPE,
    -- Modalita' normalizzata (preferita)
    p_indirizzo_dettaglio_id  anagrafiche.indirizzi_dettaglio.id%TYPE   DEFAULT NULL,
    -- Modalita' libera (eccezione)
    p_indirizzo_libero        text                                     DEFAULT NULL,
    p_stato_id                config.stati.id%TYPE                     DEFAULT NULL,
    p_comune_id               config.comuni.id%TYPE                    DEFAULT NULL,
    p_codice_postale_id       config.codici_postali.id%TYPE            DEFAULT NULL
)
RETURNS anagrafiche.indirizzi_soggetti.id%TYPE

Logica: 1. Guard XOR: o p_indirizzo_dettaglio_id o p_indirizzo_libero, mai entrambi (R1) 2. Lookup tipo_indirizzo_id da p_tipo_indirizzo_codice in config.tipi_indirizzi 3. Se modalita' libera: guard completezza (R3) — stato_id + (comune_id + codice_postale_id) 4. INSERT in anagrafiche.indirizzi_soggetti 5. I trigger si occupano di: guard tipo (R6), normalizzazione (R8), sync geoloc, audit, tx_id

Nota: il trigger trgfn_indirizzi_soggetti_guard_tipo_indirizzo verifica automaticamente che il tipo indirizzo sia ammesso per il tipo_soggetto_dettaglio del soggetto (matrice config).

DB-7 — Funzione fn_search_stradario (ricerca vie per autocomplete) ✅ COMPLETATO¶

Stato: COMPLETATO (2026-03-13) Prerequisiti: nessuno Schema: script (funzione di lettura cross-dominio, come le altre fn_search_*) Tipo: funzione STABLE di lettura ottimizzata

Implementato in: - Changeset: db/changelog/migrations_v2/20_code/script/20260313-11-create-fn-search-stradario-mctit.yaml - Doc manuale: docs/it/dbzero/script/manual/fn_search_stradario.md - Test pgTAP: db/pgtap/script/test-fn-search-stradario.sql (8 test)

Il frontend cerca VIE (stradario) per comune, non civici. L'utente: 1. Seleziona un comune (autocomplete comuni, BE-3) 2. Cerca una via nel comune selezionato (autocomplete stradario, questa funzione) 3. Inserisce il civico manualmente (campo numerico + dettagli) 4. Il backend chiama fn_get_or_create_indirizzo_dettaglio (DB-1) per ottenere/creare il civico

Firma proposta: 

CREATE OR REPLACE FUNCTION script.fn_search_stradario(
    p_comune_id    config.comuni.id%TYPE        DEFAULT NULL,
    p_search       text                         DEFAULT NULL,
    p_limit        integer                      DEFAULT 30
)
RETURNS TABLE (
    stradario_id           config.stradario.id%TYPE,
    toponimo               config.toponomastica.descrizione%TYPE,
    denominazione          config.stradario_generale.denominazione_norm%TYPE,
    via_completa           text,    -- es. "Via Roma"
    comune_id              config.comuni.id%TYPE,
    comune_descrizione     config.comuni.denominazione%TYPE,
    provincia_sigla        config.province.sigla%TYPE,
    codice_postale_id      config.codici_postali.id%TYPE,
    cap                    config.codici_postali.cap%TYPE
)
LANGUAGE plpgsql
STABLE
PARALLEL SAFE

Logica: 1. Guard: almeno p_comune_id o p_search deve essere valorizzato 2. Se p_comune_id fornito: filtra per comune (caso principale — autocomplete dopo selezione comune) 3. Se p_search fornito: ricerca ILIKE su toponimo || ' ' || denominazione_norm 4. JOIN: stradario → stradario_generale → toponomastica + comuni → province + codici_postali 5. Filtro stradario.attivo = true (se presente), ORDER BY via_completa, LIMIT p_limit 6. Campo calcolato via_completa = toponimo || ' ' || denominazione_norm (es. "Via Roma", "Piazza Garibaldi")

Nota sulle performance: con p_comune_id + p_search il numero di righe e' contenuto (un comune ha mediamente poche centinaia di vie). Se necessario, aggiungere indice trigram su stradario_generale.denominazione_norm.

Pattern coerente con il progetto: stessa struttura di fn_search_soggetti_universale e fn_search_indirizzi_dettaglio — funzione STABLE in script, usata dal backend come entry point.

TRACK BACKEND¶

BE-1 — Refactoring lookup: eliminare duplicati da amm-software¶

Prerequisiti: nessuno Principio: le tabelle config sono trasversali, i lookup vanno in core

Tabelle compatibili con lookup-codici (struttura id/codice/descrizione/attivo):

Verificare e registrare nella whitelist di dbops.fn_get_lookup_codici: * config.qualifiche * config.unita_organizzative * script.aree_funzionali * script.azioni_processo * config.emittenti_fiscali (potrebbe avere campi extra — verificare)

Azioni:

  1. Verificare quali tabelle sono gia' nella whitelist di fn_get_lookup_codici
  2. Aggiungere le mancanti (se la struttura e' compatibile)

FE-4 — Composable useSoggettoForm¶

Prerequisiti: FE-1, FE-2 File: src/core/composables/useSoggettoForm.js

Un unico composable che gestisce PF + PG + ENTE (non separare PF e PG):

export function useSoggettoForm(options = {}) {
  const { tipoForzato = null } = options
  // tipoForzato: se impostato (es. 1 per PR), il select tipo non appare

  const form = reactive({
    tipo_soggetto_dettaglio_id: tipoForzato || null,
    // PF
    cognome: '', nome: '', sesso: 'M', data_nascita: null, comune_nascita_id: null,
    // PG
    ragione_sociale: '',
    // Comuni
    codice_fiscale: '', partita_iva: '',
    // Contatto default
    email: '',
    // Indirizzo obbligatorio (il primo della matrice)
    indirizzo: { indirizzo_libero: '', comune_id: null, codice_postale_id: null }
  })

  // Computed guidati dalla matrice DB
  const tipiSoggetto = useLookup(lookupTipiSoggettoDettaglio)
  const tipoCorrente = computed(() => tipiSoggetto.find(t => t.id === form.tipo_soggetto_dettaglio_id))
  const isPF = computed(() => ['PF'].includes(tipoCorrente.natura_soggetto))
  const showPartitaIva = computed(() => tipoCorrente.piva_obbligatoria)
  const showDatiSocietari = computed(() => tipoCorrente.dati_societari_policy !== 'NONE')
  const requireDatiSocietari = computed(() => tipoCorrente.dati_societari_policy === 'REQUIRED')

  // Matrice indirizzi: ricaricata quando cambia tipo
  const matriceIndirizzi = ref([])
  const indirizziObbligatori = computed(() => matriceIndirizzi.filter(m => m.obbligatorio))

  watch(() => form.tipo_soggetto_dettaglio_id, async (id) => {
    if (id) matriceIndirizzi.value = await lookupMatriceIndirizzi(id)
  })

  function validate() { /* validazione campi in base al tipo corrente */ }
  function reset() { /* reset form */ }

  return { form, isPF, showPartitaIva, showDatiSocietari, requireDatiSocietari,
           indirizziObbligatori, matriceIndirizzi, tipiSoggetto, validate, reset }
}
