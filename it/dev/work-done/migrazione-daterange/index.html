Migrazione a daterange nativo PostgreSQL — Analisi di impatto e piano DB¶

Stato: COMPLETATA — Fase 1, 2, 3 applicate

Ultima revisione: 12 aprile 2026

Scopo: censimento di tutte le tabelle sviluppate che usano il pattern valido_dal / valido_al (o data_inizio / data_fine) con due colonne DATE separate, e analisi di impatto per la migrazione al tipo nativo daterange di PostgreSQL.

Riferimenti:

  • linee-guida-sql.md — convenzioni SQL di progetto
  • dbops/automazione_overlap — infrastruttura GIST exclusion corrente
  • anagrafiche/trgfn_clienti_set_periodo — modello di riferimento gia` in produzione

1) Contesto¶

PostgreSQL supporta nativamente il tipo daterange (e tstzrange per timestamp). Oggi nel progetto tutte le tabelle con validitatemporale usano **due colonne separate** (valido_dal DATE,valido_al DATE`) e ricostruiscono il range al volo nei vincoli GIST e nelle query:

daterange(valido_dal, COALESCE(valido_al, 'infinity'::date), '[]')

Esiste giaun **precedente funzionante**: la tabellaanagrafiche.clientimantiene le colonnedata_attivazioneedata_chiusuracome input, e un trigger (trgfn_clienti_set_periodo) popola una colonna calcolataperiodo daterange. Questo e il modello di riferimento.

Vantaggi della migrazione¶

Aspetto Due colonne separate Colonna daterange nativa
Vincoli anti-overlap daterange(col1, COALESCE(col2, 'infinity')) al volo EXCLUDE USING GIST (col WITH &&) diretto
Query "data X enel periodo?" |x >= valido_dal AND (valido_al IS NULL OR x <= valido_al)|col @> x::date`
Indici GiST Su espressione calcolata Sulla colonna nativa
Gestione infinity (aperto) COALESCE ovunque Nativo nel bound superiore
Operatori set (overlap, intersezione, differenza) Non disponibili &&, *, - nativi
Estrazione bound Giadisponibile |lower(col),upper(col)`

2) Censimento tabelle con validita` temporale¶

Legenda colonna "Stack sviluppato"¶

  • FULL = DB + Backend (repository, service, API) + Frontend (componenti Vue)
  • DB + BE = DB + Backend sviluppato, nessun componente frontend
  • DB only = Solo DDL e seed, nessun codice applicativo Python/Vue

Legenda colonna "GIST"¶

  • Si = Ha gia` un vincolo EXCLUDE USING GIST con daterange costruito al volo
  • No = Solo CHECK constraint sulle date

2.3 Modello di riferimento gia` implementato¶

La tabella anagrafiche.clienti usa gia` il pattern target:

  • Colonne input: data_attivazione, data_chiusura (DATE)
  • Colonna calcolata: periodo (daterange, bounds [))
  • Trigger: trgfn_clienti_set_periodo popola periodo ad ogni INSERT/UPDATE
  • Vincoli GIST sulla colonna periodo

Questo dimostra che il pattern egia validato nel progetto.

3) Decisioni architetturali — RISOLTE¶

Questa sezione documenta le decisioni prese dopo l'analisi critica di aprile 2026. Ogni decisione ha la motivazione esplicita per consentire valutazioni future.

D1 — Bounds standard: [] nel trigger (PG canonicalizza in [))¶

Decisione: usare '[]' nella costruzione del daterange nei trigger sync.

Motivazione: le colonne valido_dal / valido_al hanno semantica inclusiva-inclusiva nel dominio (es. "valido dal 1 gennaio al 31 dicembre" = entrambi i giorni inclusi). Scrivere daterange(valido_dal, COALESCE(valido_al, 'infinity'::date), '[]') riflette esattamente questa semantica.

Comportamento PG: PostgreSQL canonicalizza automaticamente i daterange [] in [) internamente perchele date sono un tipo discreto. Quindidaterange('2026-01-01', '2026-12-31', '[]')viene memorizzato come[2026-01-01, 2027-01-01). Questo e corretto e trasparente.

Invariante da documentare: upper(validita) restituisce valido_al + 1 (non valido_al). Per estrarre il bound originale usare upper(validita) - 1 oppure continuare a leggere valido_al.

Coerenza con clienti.periodo: il trigger di clienti usa [) esplicitamente, ma il risultato eidentico quando si parte da[]` — PG produce lo stesso range. Nessuna incoerenza reale.

D2 — Approccio: SEMPRE A (mantieni colonne + range calcolato) per tutte le tabelle¶

Decisione: approccio A anche per le tabelle DB only, senza eccezioni.

Motivazione:

  • Coerenza: un solo pattern in tutto il progetto, zero ambiguita` nelle convenzioni
  • Preparazione futura: quando backend/frontend verranno sviluppati per le tabelle DB only, il contratto API (valido_dal / valido_al come campi separati) egia pronto
  • Costo marginale: una colonna in piu` + trigger per tabella — trascurabile
  • Rischio evitato: due modelli diversi nello stesso progetto complicano le convenzioni e aumentano il carico cognitivo

D3 — Nome colonna range: validita standard¶

Decisione: validita come nome standard per tutte le tabelle con pattern valido_dal / valido_al. Nomi dominio-specifici solo dove le colonne sorgente non si chiamano valido_dal / valido_al.

Dominio Colonne sorgente Nome colonna range
Validitagenerica |valido_dal/valido_al|validita`
Pratiche (timestamp) data_inizio / data_fine periodo_sospensione / periodo_calcolo
Clienti (esistente) data_attivazione / data_chiusura periodo (gia` in uso)

D4 — Drop colonne originali: NO in questa fase¶

Decisione: le colonne valido_dal / valido_al restano. Non si droppano.

Motivazione: servono come interfaccia di input (API, frontend, INSERT diretti). Valutare il drop solo dopo che tutto il codice (DB, backend, frontend) usa esclusivamente validita per le letture — oggi non eil caso e non e l'obiettivo di questa migrazione.

D5 — Pratiche: tstzrange¶

Decisione: usare tstzrange per pratiche.sospensioni e pratiche.calcoli_tempo.

Motivazione: le colonne sorgente sono TIMESTAMP WITH TIME ZONE e la chiusura usa data_fine = NOW() — la granularitae sub-giornaliera. Usare daterange perderebbe informazione temporale.

D6 — Semantica di valido_dal IS NULL: usa -infinity (RIVISTA)¶

Decisione: valido_dal IS NULL → validita usa -infinity come lower bound. validita non e` mai NULL. Il trigger calcola sempre:

daterange(COALESCE(valido_dal, '-infinity'), COALESCE(valido_al, 'infinity'), '[]')

Motivazione (revisione post-analisi critica):

La decisione originale (validita = NULL quando valido_dal IS NULL) aveva un bug semantico: se valido_dal IS NULL e valido_al = '2025-12-31', il range NULL veniva trattato come "sempre valido" nelle query (validita IS NULL OR validita @> CURRENT_DATE), ignorando la scadenza valido_al. Con -infinity il range diventa [-infinity, 2026-01-01) e l'operatore @> rispetta correttamente la scadenza.

Vantaggi:

  • validita e` NOT NULL su tutte le tabelle (uniforme con Fase 1)
  • Le query usano sempre e solo validita @> CURRENT_DATE — nessun check NULL
  • Semantica corretta per tutti i casi: entrambi NULL, uno solo NULL, nessuno NULL

4) Analisi di impatto — Modifiche DB¶

Questa sezione descrive le modifiche da apportare esclusivamente lato database (DDL, funzioni, trigger, vincoli). Il DB ha la proprieta` del modello dati: tutte le modifiche partono da qui.

4.1 Strategia di migrazione per tabella¶

Per ogni tabella la sequenza Liquibase e`:

  1. Aggiungere colonna validita daterange (nullable inizialmente)
  2. Creare trigger sync (modello template §4.3) — BEFORE INSERT OR UPDATE
  3. Popolare la colonna per le righe esistenti: 
    UPDATE schema.tabella
SET validita = daterange(valido_dal, COALESCE(valido_al, 'infinity'::date), '[]')
WHERE valido_dal IS NOT NULL;
    (il trigger si attiva sull'UPDATE e ricalcola — ma l'UPDATE esplicito epiu chiaro)
  4. Impostare NOT NULL sulla colonna validita (dove valido_dal e` NOT NULL)
  5. Drop vecchio vincolo GIST (dove esiste)
  6. Creare nuovo vincolo GIST sulla colonna validita nativa
  7. Aggiornare funzioni che costruiscono daterange() al volo → usare validita direttamente
  8. Aggiornare query nelle funzioni/trigger che filtrano con doppio confronto → validita @> x::date

Nota sui dati esistenti: non c'e` produzione. Se i dati esistenti in sviluppo causano problemi durante la migrazione (es. righe con date incoerenti), si cancellano e si reinseriscono. Non servono script di migrazione dati difensivi.

4.2 Invariante del trigger sync: sovrascrittura incondizionata¶

Il trigger sync deve sempre sovrascrivere la colonna validita ad ogni INSERT/UPDATE, ignorando eventuali valori passati dall'utente. Questo previene il disallineamento tra valido_dal/valido_al e validita.

PostgreSQL non supporta GENERATED ALWAYS STORED per espressioni con COALESCE su range, quindi il trigger el'unico meccanismo disponibile. L'invariante e:

validita eSEMPRE una funzione deterministica divalido_dalevalido_al. Nessun codice applicativo deve mai scrivere direttamente suvalidita`.

4.3 Template trigger sync¶

Trigger function riutilizzabile, da istanziare per ogni tabella. Basata sul modello trgfn_clienti_set_periodo gia` in produzione.

-- Template: trigger sync validita` per tabelle con valido_dal / valido_al
-- Adattare: schema, nome funzione, gestione NULL su valido_dal

CREATE OR REPLACE FUNCTION <schema>.trgfn_<tabella>_set_validita()
RETURNS trigger
LANGUAGE plpgsql
AS $fn$
BEGIN
    -- Calcola validita` daterange da valido_dal / valido_al
    -- Bounds '[]' (PG canonicalizza in '[)' per date)
    IF NEW.valido_dal IS NOT NULL THEN
        NEW.validita := daterange(
            NEW.valido_dal,
            COALESCE(NEW.valido_al, 'infinity'::date),
            '[]'
        );
    ELSE
        NEW.validita := NULL;
    END IF;

    RETURN NEW;
END;
$fn$;

CREATE TRIGGER trg_<tabella>_a20_set_validita_ins_upd
    BEFORE INSERT OR UPDATE OF valido_dal, valido_al
    ON <schema>.<tabella>
    FOR EACH ROW
    EXECUTE FUNCTION <schema>.trgfn_<tabella>_set_validita();

Note sul template:

  • Fase _a20_: dopo i guard (_a10_) ma prima della logica applicativa
  • UPDATE OF valido_dal, valido_al: il trigger si attiva solo quando cambiano le colonne sorgente, non su ogni UPDATE della riga (performance)
  • Per tabelle dove valido_dal eNOT NULL, il ramoELSE` non si raggiunge mai — mantenerlo comunque per robustezza
  • Per tabelle con colonne diverse (es. data_inizio/data_fine): adattare i nomi
  • Per tstzrange (pratiche): sostituire daterange con tstzrange e i cast di tipo

4.4 Aggiornamento infrastruttura dbops.automazione_overlap¶

La funzione dbops.fn_apply_automazione_overlap costruisce vincoli GIST usando:

daterange(%I, COALESCE(%I, 'infinity'::date), %L) WITH &&

Dopo la migrazione, per le tabelle migrate dovrapuntare direttamente alla colonnavalidita`.

Modifiche alla tabella dbops.automazione_overlap:

  • Aggiungere colonna range_col TEXT DEFAULT NULL — nome della colonna daterange nativa
  • Se range_col IS NOT NULL → la funzione genera %I WITH && (colonna diretta)
  • Se range_col IS NULL → comportamento attuale (espressione calcolata, retrocompatibile)

Modifiche a dbops.fn_apply_automazione_overlap:

-- Nuovo codepath per colonna range nativa
IF rconf.range_col IS NOT NULL THEN
    v_range_expr := format('%I WITH &&', rconf.range_col);
ELSE
    v_range_expr := format(
        'daterange(%I, COALESCE(%I, ''infinity''::date), %L) WITH &&',
        rconf.valido_dal_col,
        rconf.valido_al_col,
        v_bounds
    );
END IF;

Modifiche a dbops.fn_seed_automazione_overlap:

  • Aggiungere detection: se la tabella ha una colonna validita di tipo daterange, popolare automaticamente range_col = 'validita'

Vincoli con WHERE personalizzate (#1 listini_versioni, #2 listini_associazioni):

Dall'analisi risulta che questi vincoli sono stati creati manualmente (non via automazione) perchehanno clausole WHERE filtrate (attivo IS TRUE AND stato = 'ATTIVA'). L'infrastrutturaautomazione_overlap` non gestisce filtri WHERE.

Questi vincoli restano manuali anche dopo la migrazione: la migration Liquibase li ricrea esplicitamente con la colonna validita nativa. L'automazione si occupa solo dei casi standard (#2, #4, #5 tramite automazione_overlap).

Correzione: listini_associazioni (#2) egestito sia manualmente che via automazione. Verificare quale dei due e autorevole e consolidare.

8) Strategia di rollback¶

Con l'approccio A il rollback esemplice perche le colonne originali restano intatte:

  1. Drop colonna validita
  2. Drop trigger sync
  3. Ricrea vecchi vincoli GIST (con espressione daterange(valido_dal, COALESCE(...)))
  4. Ripristina funzioni alle versioni precedenti (Liquibase runOnChange con il codice precedente)

Non enecessario uno script di rollback automatico — in sviluppo il rollback Liquibase standard (liquibase rollback) e sufficiente se i changeset hanno rollback definito.
