Analisi refactor frontend anagrafiche¶

Obiettivo: identificare cosa nei drawer/store anagrafiche e' logica di dominio mascherata da codice di presentazione, e quindi va spostata su backend/DB (filosofia DB-first: il frontend e' solo presentazione + UX).

L'analisi distingue tre categorie: A. Da spostare davvero (logica di business in JS) B. Casi controversi (sfumature, UX defense-in-depth, refactor di pulizia) C. Bug logici di modello (incoerenze tra componenti causate da ambiguita' del dominio)

A. Logica di business da spostare a backend/DB¶

A1. API contract: ruoli JSONB normalizzato a valle (PRIORITA' ALTA, quick win)¶

  • frontend/src/anagrafiche/stores/soggetti.js:70
  • frontend/src/core/components/SoggettoResolver.vue:52

Entrambi i punti fanno la stessa cosa: il backend ritorna ruoli come stringa JSON (a volte) invece che come array. Il frontend e' costretto a fare JSON.parse con try/catch.

E' un bug del contratto API, non del frontend. La fix sta nel serializer/repository backend: la colonna JSONB va sempre castata e serializzata come array JSON. Una volta sistemato il backend, le due normalizzazioni nel frontend spariscono.

A2. Normalizzazioni payload pagamento/fiscali (PRIORITA' ALTA)¶

  • frontend/src/anagrafiche/components/ClienteDrawer.vue:286
nr_giorni_scadenza: ['G', 'F'].includes(f.tipo_gg_scadenza_ft) ? (f.nr_giorni_scadenza || 0) : null

Regola: "se il tipo scadenza non e' G o F, i giorni scadenza non hanno senso → NULL".

  • frontend/src/anagrafiche/components/FornitoreDrawer.vue:135
ritenuta_aliquota: f.ritenuta_acconto ? f.ritenuta_aliquota : null

Regola: "se non c'e' ritenuta, l'aliquota va a NULL".

Sono regole di dominio (pagamenti / fiscalita' fornitore) replicate in JS. Vanno applicate nei service backend (clienti_service, fornitori_service) e idealmente da trigger DB di consistenza, esattamente come gia' fatto per contratti / promo articoli (ref: pattern data-driven cessazione). Il pre-clean frontend e' duplicazione che drifta non appena la regola backend cambia.

A3. Default tipo soggetto cablato in JS (PRIORITA' ALTA)¶

  • frontend/src/core/components/SoggettoResolver.vue:80
const privato = dettagli.find(d => d.codice_interno === 'PR')
return privato ? privato.id : dettagli[0].id

La scelta "default privato" e' una decisione di dominio cablata nel componente. Va esposta come campo nella response di getConfigResolver:

{
  "tipi_soggetto_dettaglio": [...],
  "nature_ammesse": [...],
  "default_tipo_soggetto_id": 42
}

Senza questo, cambiare la policy richiede deploy frontend.

A4. Stato operativo cliente calcolato lato Vue (PRIORITA' MEDIA)¶

  • frontend/src/anagrafiche/components/ClienteDrawer.vue:367
return sosp > riatt
  ? { label: t('clienti.col_sospeso_il'), date: sosp }
  : { label: t('clienti.col_riattivato_il'), date: riatt }

Lo "stato corrente" (sospeso vs riattivato) e' un calcolo di dominio. Il pattern gia' adottato per cessazione data-driven (contratti, listini-versioni, promo articoli — vedi work-done) prevede che il backend esponga sul detail:

  • evento_stato_corrente (es. SOSPESO, ATTIVO)
  • data_evento_stato
  • tipo_evento_stato

Il frontend si limita a mostrare i campi gia' risolti.

A5. Config-resolver da arricchire (mancante nel doc originale)¶

getConfigResolver(tipoRuolo) oggi ritorna tipi_soggetto_dettaglio e nature_ammesse. E' insufficiente: il frontend deve cablare ulteriori scelte (default tipo, soglia min_search_length = 3, ecc.). Aggiungere all'API:

  • default_tipo_soggetto_id (vedi A3)
  • min_search_length (oggi cablato a 3 in SoggettoResolver:41)
  • eventualmente editable_in_edit (vedi B3)

B. Casi controversi (sfumature, refactor di pulizia)¶

B1. Filtro nature_ammesse e marker ruolo duplicato (refactor cosmetico)¶

  • frontend/src/core/components/SoggettoResolver.vue:50

Il dato nature_ammesse arriva gia' dal backend (config-resolver). Il frontend lo usa per decorare visivamente la lista (icona ban, opacity 50%, warning ruolo gia' presente).

Non viola la filosofia DB-first: e' presentation che si appoggia a dati backend. La proposta architetturalmente piu' pulita ("API ritorna selectable + reason per ogni hit") e' migliore ma richiede di rendere listSoggetti role-aware. Refactor di pulizia, non di principio. Bassa priorita'.

L'unico vero problema in questo punto e' la duplicazione della normalizzazione ruoli, che si risolve da sola con A1.

B2. canSave (categoria + admin globale) — DEFENSE-IN-DEPTH, NON DUPLICAZIONE¶

  • frontend/src/anagrafiche/components/ClienteDrawer.vue:355

Qui l'analisi originale e' troppo aggressiva. Sono due cose diverse:

  • ba_categoria_cliente_id obbligatoria in create: e' validazione UX che disabilita il pulsante. Il backend valida comunque. Il commento del file lo dichiara: "F3-FE-04: categoria cliente obbligatoria in creazione".
  • auth.isAdminGlobale blocca save: e' UX guard su un'autorizzazione che il backend rifiuta gia' (guard service + trigger DB). Il commento lo dichiara esplicitamente: "defense-in-depth UI: il guard backend e il trigger DB sono comunque la difesa primaria".

Non e' un punto da spostare. E' UX legittima e va mantenuta. Spostarla significherebbe far diventare il pulsante salvabile finche' la chiamata API non torna errore, peggiorando l'esperienza utente per zero guadagno architetturale.

B3. Mutabilita' tipo soggetto in edit (refactor opzionale)¶

  • frontend/src/core/components/SoggettoForm.vue:42

La regola "in edit puoi cambiare tipo soggetto solo verso la stessa natura_soggetto" e' un invariante di dominio probabilmente gia' enforciato da trigger DB. Il pre-filtro frontend e' UX corretta MA duplica la regola silenziosamente.

Due strade:

  • Pulita: backend espone, sul detail soggetto, l'array tipi_modificabili. Il frontend filtra con quello (no duplicazione regola).
  • Pragmatica: rimuovi il filtro, lascia che il backend rifiuti. Costo UX: l'utente scopre il vincolo solo al salvataggio.

Non urgente. Se lasci il pre-filtro, almeno aggiungi un commento che cita il trigger DB di riferimento per evitare drift silenziosi.

B4. Immutabilita' CF/PIVA in edit (mancante nel doc originale)¶

  • frontend/src/core/components/SoggettoForm.vue:39-40
const cfDisabled = computed(() => props.isEdit && !!props.form.codice_fiscale?.trim())
const pivaDisabled = computed(() => props.isEdit && !!props.form.partita_iva?.trim())

Stessa natura di B3: regola di immutabilita' di dominio (analoga a Profilo A contratti) cablata in JS. Andrebbe esposta come metadata editable_fields dal backend, almeno per uniformita' con il pattern di immutabilita' adottato altrove. Bassa priorita'.

C. Bug logici di modello (priorita' MASSIMA — non e' "solo frontend")¶

C1. Definizione di "contatto compilato" incoerente tra i drawer anagrafiche¶

Stato verificato sul codice (3 drawer + 1 caso a parte):

Drawer Riga Regola attuale Diagnosi
ClienteDrawer :313-320 "qualunque campo valorizzato → contatto in compilazione" OK (regola A)
FornitoreDrawer :162 "solo nominativo conta" Bug: scarta dati silenziosamente
SoggettoDrawer :292 Invia SEMPRE contatto: {...} nel payload Funziona "per caso" grazie all'auto-fill nominativo
ContattiSoggettoDrawer (drawer dedicato) Entry esplicita "Aggiungi contatto" OK, non e' caso ambiguo

Conseguenza pratica del bug Fornitore: se l'utente scrive solo l'email del contatto e clicca Salva, l'email viene scartata senza alcun avviso. Sul Cliente la stessa azione produce una validazione che chiede i campi obbligatori mancanti. Tre drawer fratelli, tre comportamenti diversi.

Il composable frontend/src/core/composables/useContattoForm.js esiste gia' ed e' usato da tutti e quattro i drawer, MA non espone la regola "il contatto e' vuoto / parziale / valido". Ogni drawer la reinventa nella sua onSave().

Non e' "incoerenza frontend": e' ambiguita' del modello dominio. Nessuno ha definito cosa significa "l'utente ha iniziato a compilare un contatto".

Decisione (confermata)¶

Regola canonica: versione Cliente. Se almeno un campo (nominativo, tipo_contatto_id, email, telefono, cellulare, pec) e' valorizzato → il contatto e' in compilazione → richiede gli obbligatori (nominativo + tipo_contatto_id).

Implementazione: pattern A + A2 (defense-in-depth).

Piano implementativo¶

Backend — nuovo metodo classificatore in apps/anagrafiche/services/contatti_service.py

def classify_contatto_payload(data) -> str:
    """Ritorna 'EMPTY' | 'PARTIAL' | 'VALID'."""

Regola:

  • EMPTY = tutti i campi (nominativo, email, telefono, cellulare, pec, tipo_contatto_id) sono None o stringa vuota
  • PARTIAL = almeno un campo valorizzato MA mancano nominativo o tipo_contatto_id
  • VALID = nominativo + tipo_contatto_id presenti + email/pec con formato valido (se compilati)

Le API che ricevono un contatto inline (create cliente, fornitore, soggetto) applicano la classificazione:

  • EMPTY → ignora il blocco contatto, non crearlo (no errore)
  • PARTIAL → ritorna errore strutturato (es. code: CONTATTO_INCOMPLETO, missing: ["nominativo", "tipo_contatto_id"])
  • VALID → crea il contatto

Frontend — estendere useContattoForm

Aggiungere al composable:

function classify()  // 'EMPTY' | 'PARTIAL' | 'VALID'
function isEmpty()
function isFilled()  // !isEmpty()

Stessa regola del backend. Serve per UX immediata (disabilita Salva, mostra errori) — il backend resta la verita' unica.

Aggiornare i 3 drawer:

  • ClienteDrawer: sostituire hasAnyContatto (inline) con contatto.isFilled()
  • FornitoreDrawer: stesso, si allinea automaticamente alla regola corretta
  • SoggettoDrawer: prima di includere contatto: {...} nel payload, verificare contatto.isFilled(). Se isEmpty(), non includere affatto il blocco contatto

Bonus UX: aggiungere in tutti e tre i drawer un pulsantino "pulisci contatto" (icona x) per svuotare la sezione contatto senza perdere il resto del form. Necessario perche' con la regola A "qualunque campo" e' facile attivare per sbaglio la sezione contatto.

Perche' A + A2 e non solo A¶

La regola scritta solo nel composable frontend si dimentica appena un nuovo endpoint backend riceve un payload contatto (es. import massivo, API esterna). Scriverla nel service backend la rende patrimonio del dominio: qualunque ingresso di dati viene classificato in modo coerente.

Priorita' di refactor (ordine concentrico)¶

  1. A1 — Fix API contract ruoli JSONB. Quick win, elimina due punti di duplicazione frontend in un colpo solo.
  2. A2 — Normalizzazioni payload (nr_giorni_scadenza, ritenuta_aliquota) nei service backend + trigger DB di consistenza.
  3. A3 + A5 — Arricchire la response getConfigResolver (default_tipo_soggetto_id, min_search_length, ecc.) e rimuovere i cablati frontend.
  4. A4 — Stato corrente cliente esposto dal detail backend (evento_stato_corrente, data_evento_stato).
  5. C1 — Decidere e centralizzare la regola "contatto compilato" (bug logico modello: priorita' massima sul piano architetturale, anche se tecnicamente "piccolo").
  6. B3 — Mutabilita' tipo soggetto: refactor opzionale, basso valore se trigger DB c'e' gia'.
  7. B4 — Immutabilita' CF/PIVA come metadata: refactor di pulizia, basso valore.
  8. B1 — Marker resolver: refactor cosmetico, valore bassissimo.

Da NON spostare: B2 (canSave). E' UX defense-in-depth corretta. Toccarla peggiora l'esperienza utente per zero guadagno architetturale.

Nota di metodo¶

Tre punti del documento originale — A2 (#4 e #7 della lista vecchia), A4 (#6), A3 (#2) — sono esattamente lo stesso pattern gia' applicato con successo su contratti / listini-versioni / promo articoli (cessazione data-driven, vedi work-done/). Riusare lo stesso schema:

  • backend espone fields gia' risolti (stato corrente, data evento, default configurazione)
  • service normalizza il payload coerentemente
  • trigger DB enforcing l'invariante

evita di reinventare la ruota e mantiene coerenza tra domini.

D. Piano di sviluppo (suddivisione DB / Backend / Frontend)¶

Ordine di esecuzione: concentrico bottom-up. Per ogni fase si parte dal DB (trigger/viste/funzioni), poi il backend Django (service/API), infine il frontend (rimozione duplicazioni). Le azioni DB sono di competenza del team DB su dev/db-tid — il backend agent NON esegue DDL/trigger/migrations.

Fase 1 — Fix API contract ruoli JSONB (A1, quick win) — LANDED 2026-04-27¶

Stato: chiusa BE+FE il 2026-04-27. DB nessuna modifica (caso A).

DB (dev/db-tid) — CHIUSO (caso A): nessuna modifica

  • Verificato 2026-04-27: la lista ruoli non passa per una vista o funzione DB dedicata. E' costruita in SQL inline dal repository soggetti (soggetti_repository.py:51-97) tramite (SELECT COALESCE(jsonb_agg(jsonb_build_object(...) ORDER BY ...), '[]'::jsonb) FROM anagrafiche.soggetti_ruoli sr ...) AS ruoli. Il DB ritorna gia' un valore jsonb ben formato con shape [{soggetto_ruolo_id, codice, descrizione}, ...].
  • Causa del bug: il driver psycopg in alcune configurazioni ritorna jsonb come stringa Python invece che dict/list (cfr. commento in auth_helpers.py:70 e helper esistente email_repository._parse_jsonb_field).
  • Nessun DDL/trigger/funzione DB richiesta.

Backend Django

  • In apps/anagrafiche/db/soggetti_repository.py::list_soggetti(), dopo extract_paginated(cursor), parsare il campo ruoli se arriva come stringa: if isinstance(r["ruoli"], str): r["ruoli"] = json.loads(...). Pattern gia' usato in email_repository._parse_jsonb_field().
  • Aggiungere test API che verifichi il tipo della risposta (isinstance(data["ruoli"], list)).
  • (Nota futura, fuori scope A1): valutare promozione di _parse_jsonb_field da email_repository a apps/core/db/_helpers.py come helper condiviso per tutti i repository che restituiscono campi jsonb aggregati.

Frontend

  • Rimuovere normalizzazioni in stores/soggetti.js:70 e SoggettoResolver.vue:52. Solo dopo che backend e' a posto.

Dipendenze: nessuna verso altre fasi. Si chiude da sola.
