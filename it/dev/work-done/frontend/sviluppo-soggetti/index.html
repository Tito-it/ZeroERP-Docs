Gestione Soggetti — WIP¶

Documento di lavoro per pianificazione e avanzamento della gestione soggetti completa. Data: 2026-03-15 | Stato: DA INIZIARE

Documenti di riferimento:

  • Guida Soggetti e Ruoli Anagrafici — modello dati, trigger, matrici
  • Guida Gestione degli Indirizzi — due layer, normalizzato/libero
  • Guida Gestione dei Contatti — tre livelli contesto, default
  • Guida Generazione Cliente — flusso soggetto → ruolo → cliente
  • Architettura Building Block — building block DB/BE/FE

  • Frontend Standards — regole UI vincolanti

Posizionamento nello Sviluppo Concentrico¶

La gestione soggetti appartiene all'Anello 1 — Dati Base. E' il nucleo anagrafico su cui tutti i domini costruiscono: clienti, fornitori, operatori, vettori, banche.

    Anello 1 (Dati Base)
    ┌────────────────────────────────────────────────────────────┐
    │  Gestione Soggetti (NUOVO)                                 │
    │                                                            │
    │  + CRUD soggetti PF/PG/ENTE con tipo dinamico             │
    │  + Gestione contatti obbligatori (guard DEFERRED)          │
    │  + Gestione indirizzi soggetto (layer identita')           │
    │  + Dati societari per SC/ENC                               │
    │  + Assegnazione ruoli (cliente, fornitore, ecc.)           │
    │  + Frontend: area Anagrafiche > Soggetti                   │
    └────────────────────────────────────────────────────────────┘
           ↑ usa
    Gestione Geografica (COMPLETATO)
    ┌────────────────────────────────────────────────────────────┐
    │  Indirizzi, Toponomastica, Comuni, CAP, Province,          │
    │  Regioni, Stati — CRUD completo, 7 tab                     │
    └────────────────────────────────────────────────────────────┘

Strategia: dal piccolo al grande¶

L'approccio e' bottom-up: iniziare dagli elementi atomici piu' piccoli (config tables, form building block) che generano componenti riutilizzabili, poi comporli nelle viste complesse.

Fase 0 — Config tables manutenzione (tipi_contatti, forme_giuridiche, ecc.)
Fase 1 — Building block form (ContattoForm, IndirizzoForm, DatiSocietariForm)
Fase 2 — Backend API soggetti (repository, service, views)
Fase 3 — Frontend vista soggetti (SoggettoDrawer, SoggettiSearchTable)
Fase 4 — Integrazione ruoli (collegamento con domini futuri)

BB-2 — IndirizzoSoggettoForm.vue + useIndirizzoSoggettoForm.js¶

Scopo: form indirizzo per layer soggetto (identita': residenza, sede legale, domicilio fiscale). Supporta modalita' normalizzata (ComuneAutocomplete + StradarioAutocomplete + civico) e modalita' libera (indirizzo_libero + stato + comune/locality).

Campi modalita' normalizzata:

Campo Tipo Obbligatorio
tipo_indirizzo_id Select Si (filtrato da matrice)
comune_id ComuneAutocomplete Si
stradario / via nuova StradarioAutocomplete o switch Si
civico, estensione, palazzina, scala, piano, interno InputText/Number No (civico consigliato)

Campi modalita' libera:

Campo Tipo Obbligatorio
tipo_indirizzo_id Select Si
indirizzo_libero InputText Si
stato_id Select Si
comune_id / locality InputText Si (uno dei due)

Props: 

defineProps({
  form: { type: Object, required: true },
  tipiIndirizzo: { type: Array, default: () => [] }, // filtrati dalla matrice
  disabled: { type: Boolean, default: false }

Nota: questo form e' diverso da IndirizzoDrawer (che gestisce indirizzi_dettaglio standalone). Qui gestiamo indirizzi_soggetti — l'assegnazione di un indirizzo a un soggetto con tipo.

Collocazione: core/components/ Prerequisiti: BB-1 non richiesto, ma ComuneAutocomplete, StradarioAutocomplete gia' esistenti Effort: 1-2 sessioni

Dipendenza DB — fn_crea_soggetto_pg¶

L'unica dipendenza DB bloccante e' la funzione anagrafiche.fn_crea_soggetto_pg(). Deve essere creata sul server DB (migration Liquibase) prima di iniziare la Fase 2.

Firma prevista: 

fn_crea_soggetto_pg(
  p_ragione_sociale text,
  p_codice_fiscale text,
  p_partita_iva text,
  p_tipo_soggetto_dettaglio_id bigint,
  p_email text,
  p_stato_iso2 varchar DEFAULT 'IT',
  p_forma_giuridica_id bigint DEFAULT NULL,
  p_rea text DEFAULT NULL,
  p_capitale_sociale numeric DEFAULT NULL
) RETURNS uuid  -- soggetti.id

Deve: 1. INSERT in anagrafiche.soggetti con tipo PG 2. INSERT in anagrafiche.contatti (contatto default con email) 3. INSERT in anagrafiche.dati_societari (se tipo richiede: SC, ENC) 4. Chiamare fn_get_or_create_soggetto_ruolo se ruolo specificato

Vincoli DEFERRED — cosa il frontend deve garantire¶

Il DB verifica al COMMIT della transazione:

Trigger Errore Cosa serve nel form
trgfn_soggetti_guard_soggetto_contatti E_SOGGETTO_NO_CONTATTI Almeno un contatto con nominativo
trgfn_soggetti_guard_indirizzi_required E_SOGGETTO_NO_INDIRIZZI Indirizzi obbligatori dalla matrice tipo

Note aperte — Tracciamento pratiche¶

Le operazioni CRUD anagrafiche (crea/modifica soggetto, contatto, indirizzo) non passano dal sistema pratiche (Anello 2).

Il tracciamento attuale e' puramente tecnico (Anello 0): - Audit DB: data_insert, user_insert, data_update, user_update (trigger automatico) - tx_id: correla tutte le scritture nella stessa transazione - Storicizzazione: snapshot JSONB su UPDATE/DELETE in storico.<tabella> - Request log: ogni chiamata API in dbops.request_log

Non viene scritto il giornale di bordo (pratiche.giornale).

Quando si vorranno orchestrare le operazioni anagrafiche tramite pratica (es. "Onboarding cliente", "Variazione dati societari"), il service dovra': 1. Aprire una pratica con tipo e flusso appropriato 2. Scrivere nel giornale di bordo ad ogni step significativo 3. Chiudere la pratica al completamento

Questa integrazione e' prevista per Anello 2/3, non per Anello 1 (dati base).
