Architettura Building Block — DB, Backend, Frontend¶

Documento master per la scomposizione in building block riutilizzabili su tutti i livelli. Data: 2026-03-12 | Aggiornato: 2026-03-14 Stato: Backend COMPLETATO — Frontend PARZIALMENTE COMPLETATO (FE-1..FE-9, FE-11)

Documenti correlati:

  • Building Block Repository (backend) — piano backend completato
  • Amministrazione Utenti — Sprint 2 originale completato

Guide di riferimento:

  • Guida Soggetti e Ruoli Anagrafici
  • Guida Gestione dei Contatti
  • Guida Generazione di un Cliente
  • Guida Sviluppo Frontend

Motivazione¶

Il modulo Amministrazione (Sprint 2) ha prodotto componenti monolitici come UtenteDrawer.vue che contengono form per persona, accesso, contatto e collocazione in un unico blocco. Lo stesso form "persona fisica" servira' per creare un cliente PF, un fornitore PF, un referente. Lo stesso form "contatto" servira' ovunque si crei un soggetto (vincolo DEFERRED E_SOGGETTO_NO_CONTATTI).

Senza scomposizione, ogni dominio riduplica gli stessi form con varianti minime.

Principio guida¶

Il frontend rispecchia l'architettura DB: cosi' come il database ha building block SQL riutilizzabili (fn_crea_soggetto_pf, fn_crea_auth_user, fn_get_or_create_soggetto_ruolo), il frontend ha componenti Vue atomici che si compongono nelle view di dominio.

Stato attuale per livello¶

L'architettura building block si sviluppa su 3 livelli. Ogni livello ha il proprio documento di dettaglio; questa sezione riassume lo stato complessivo.

DB — Building block SQL (completato)¶

Il DB ha scomposto la funzione monolitica fn_crea_operatore in building block atomici:

Funzione Scopo Riusabile da
fn_crea_auth_user(...) Crea solo auth_user operatore, admin, qualsiasi utente
fn_crea_soggetto_pf(...) Crea soggetto PF + contatto default operatore, cliente PF, fornitore PF
fn_get_or_create_soggetto_ruolo(...) Crea/recupera ruolo soggetto tutti
fn_crea_risorsa_umana(...) Crea risorsa_umana + bridge auth_user operatore, admin, dipendenti
fn_crea_operatore(...) Orchestratore — chiama i building block solo operatore

Gestito sul server DB. Dettagli nelle guide di schema.

Backend — Repository core (completato)¶

I repository Python mappano 1:1 i building block SQL. Dettaglio completo: Building Block Repository

Repository Metodo In apps/core/db/
AuthRepository crea_auth_user() auth_repository.py
AnagraficheCoreRepository crea_soggetto_pf() anagrafiche_core_repository.py
RisorseUmaneCoreRepository crea_risorsa_umana() risorse_umane_core_repository.py

L'orchestratore resta in apps/amm_software/db/amm_software_repository.py → crea_operatore().

52 test backend OK + smoke test.

Frontend — Componenti atomici (parzialmente completato)¶

I componenti Vue mappano i building block come descritto nelle sezioni seguenti. Primo consumer: refactor di UtenteDrawer.vue — completato (Sprint 3, 2026-03-14).

Implementati:

  • SoggettoForm.vue — form universale PF/PG/ENTE (unificato, non separato PF+PG)
  • AuthUserForm.vue — form credenziali di accesso
  • ComuneAutocomplete.vue — autocomplete comuni con ricerca server-side
  • StradarioAutocomplete.vue — autocomplete stradario per comune
  • useSoggettoForm.js — composable universale con matrice tipi soggetto
  • useAuthUser.js — composable credenziali con password match
  • useLookup.js — cache generica per lookup API
  • useServerAutocomplete.js — composable ricerca server-side con debounce

Da implementare (domini futuri: clienti, fornitori):

  • ContattoForm.vue — form contatto (obbligatorio per guard DEFERRED)
  • IndirizzoForm.vue — form indirizzo normalizzato/libero
  • DatiSocietariForm.vue — form dati camerali SC/ENC
  • UOSelect.vue — select unita' organizzativa con gerarchia

Vincoli dal modello dati¶

Prima di definire i componenti, e' fondamentale capire cosa il DB richiede al COMMIT di una transazione che crea un soggetto.

Vincoli DEFERRED (scattano al COMMIT)¶

Trigger Tabella Errore Cosa richiede
trgfn_soggetti_guard_soggetto_contatti soggetti E_SOGGETTO_NO_CONTATTI Almeno un contatto default per ogni soggetto
trgfn_soggetti_guard_indirizzi_required soggetti E_SOGGETTO_NO_INDIRIZZI Indirizzi obbligatori in base a tipi_soggetto_dettaglio_tipi_indirizzo
trgfn_soggetti_guard_dati_societari_required soggetti E_DATI_SOCIETARI_REQUIRED Dati societari per SC/ENC (non per PF)

Implicazioni per i form¶

  • Creare un soggetto senza contatto = errore garantito al COMMIT
  • Creare un soggetto PG senza dati societari = errore per SC/ENC
  • Indirizzi = dipendono dalla matrice config; per PR (Privato) potrebbe non essere obbligatorio

Questo significa che i form "Soggetto" e "Contatto" sono inseparabili: ogni view che crea un soggetto DEVE includere anche il form contatto.

Catena completa — dal DB al frontend¶

DB (building block SQL)        Backend (repository core)          Frontend (componenti Vue)
──────────────────────         ────────────────────────           ─────────────────────────
fn_crea_auth_user         →    AuthRepository                →    AuthUserForm.vue
fn_crea_soggetto_pf       →    AnagraficheCoreRepository     →    SoggettoPFForm.vue + ContattoForm.vue
fn_get_or_create_soggetto_ruolo  (auto — chiamato dai building block, nessun form)
fn_crea_risorsa_umana     →    RisorseUmaneCoreRepository    →    CollocazioneForm.vue (UO + qualifica)

fn_crea_operatore         →    AmmSoftwareRepository         →    UtenteDrawer.vue (compone i form)
(futuro) fn_crea_cliente  →    (futuro) ClienteRepository    →    ClienteDrawer.vue (compone diversi)

Flusso dati: il frontend manda un payload unificato → il backend (service/view) scompone e chiama i building block SQL nella sequenza corretta → tutto in una transazione.

I repository core (apps/core/db/) sono gia' implementati e testati. I domini futuri (clienti, fornitori) li riuseranno senza modificarli.

4. useLookup(fetchFn, options) — COMPLETATO¶

// Cache generica per lookup (UO, qualifiche, tipi contatto, ecc.)
export function useLookup(fetchFn, options = {}) {
  const { immediate = false } = options
  const items = ref([])
  const loading = ref(false)

  async function load() {
    if (items.value.length > 0) return // gia' caricato
    loading.value = true
    items.value = await fetchFn()
    loading.value = false
  }

  if (immediate) load()

  return { items, loading, load, reload: () => { items.value = []; load() } }
}

Regole di implementazione¶

R1 — Nessuna logica di business nei componenti form¶

I componenti atomici fanno solo:

  • Rendere i campi con binding v-model
  • Validazione UX locale (campo vuoto, formato email, lunghezza CF)
  • Emettere eventi

Non chiamano API, non gestiscono transazioni, non conoscono il contesto d'uso.

R2 — Il composable gestisce lo state, il componente lo rende¶

Il composable (useSoggettoPF) possiede il reactive() e la funzione validate(). Il componente (SoggettoPFForm) riceve il form via v-model e mostra i campi. La view (UtenteDrawer) li compone e gestisce il submit.

R3 — Il backend assembla, il frontend compone¶

Il frontend manda un payload unico al backend (es. POST /api/v1/amm-software/operatori/). Il backend (service layer) scompone il payload e chiama i building block SQL nella sequenza corretta. Il frontend non chiama mai i building block singolarmente — l'orchestrazione e' responsabilita' del backend.

R4 — Lookup via useLookup, mai duplicati¶

Ogni select che carica opzioni da API usa useLookup(fetchFn). Le opzioni vengono caricate una volta e cachate nel composable. Non duplicare le stesse chiamate API in componenti diversi della stessa view.

R5 — i18n sempre, stringhe hardcoded mai¶

Tutti i label dei form usano $t('chiave'). Le chiavi per i componenti core vanno nel namespace common dei file locale:

{
  "common": {
    "cognome": "Cognome",
    "nome": "Nome",
    "codiceFiscale": "Codice Fiscale",
    "email": "Email",
    "telefono": "Telefono"
  }
}

Architettura indirizzi — catena completa¶

Riferimento: Guida Gestione degli Indirizzi

L'indirizzo in ZeroERP non e' un campo di testo: e' un dato strutturato normalizzato. La modalita' normalizzata (via indirizzo_dettaglio_id) e' sempre preferita. L'indirizzo_libero e' riservato a eccezioni (migrazioni, indirizzi esteri non normalizzabili).

Catena di normalizzazione (dal basso verso l'alto):

config.toponomastica          (Via, Piazza, Corso, Largo...)
       ↓
config.stradario_generale     (toponimo + denominazione via)
       ↓
config.stradario              (via locale = stradario_generale + comune + CAP)
       ↓
anagrafiche.indirizzi_dettaglio  (civico normalizzato: stradario + civico + estensione + palazzina + scala + piano + interno)
       ↓
anagrafiche.indirizzi_soggetti   (soggetto_id + tipo_indirizzo_id + indirizzo_dettaglio_id)

Gerarchia geografica: 

config.stati → config.regioni → config.province → config.comuni → config.codici_postali
                                                        ↓
                                                  config.stradario

Regole chiave (dalla guida): - R1 — XOR: o normalizzato (indirizzo_dettaglio_id) o libero (indirizzo_libero), mai entrambi - R2 — Unicita': un solo indirizzo per tipo per soggetto (UNIQUE soggetto_id, tipo_indirizzo_id) - R3 — Completezza libero: se libero, obbligatori indirizzo_libero + stato_id + (comune_id + codice_postale_id) oppure (locality + postal_box) - R6 — Guard tipo: trigger verifica tipo_indirizzo contro matrice config.tipi_soggetto_dettaglio_tipi_indirizzo - R7 — Unicita' civico: vincolo uq_indirizzi_dettaglio_norm su (stradario_id, civico, estensione, palazzina, scala, piano, interno)

Funzioni di ricerca gia' esistenti: - anagrafiche.fn_search_indirizzi_dettaglio(...) — ricerca per stradario+civico o fuzzy su indirizzo_normalizzato - script.fn_get_indirizzo(p_soggetto_ruolo_id, p_tipo_codice) — risoluzione master/fallback - script.fn_get_indirizzo_by_soggetto(p_soggetto_id, p_tipo_codice) — layer soggetto con fallback

DB-1 — Building block fn_get_or_create_indirizzo_dettaglio¶

Prerequisiti: nessuno Schema: anagrafiche Tipo: building block riusabile

Funzione upsert: cerca un civico esistente per chiave naturale, se non esiste lo crea. Il vincolo uq_indirizzi_dettaglio_norm garantisce la deduplicazione.

Firma proposta: 

CREATE OR REPLACE FUNCTION anagrafiche.fn_get_or_create_indirizzo_dettaglio(
    p_stradario_id        config.stradario.id%TYPE,
    p_civico              anagrafiche.indirizzi_dettaglio.civico%TYPE         DEFAULT NULL,
    p_estensione_civico   anagrafiche.indirizzi_dettaglio.estensione_civico%TYPE DEFAULT NULL,
    p_palazzina           anagrafiche.indirizzi_dettaglio.palazzina%TYPE      DEFAULT NULL,
    p_scala               anagrafiche.indirizzi_dettaglio.scala%TYPE          DEFAULT NULL,
    p_piano               anagrafiche.indirizzi_dettaglio.piano%TYPE          DEFAULT NULL,
    p_interno             anagrafiche.indirizzi_dettaglio.interno%TYPE        DEFAULT NULL
)
RETURNS anagrafiche.indirizzi_dettaglio.id%TYPE

Logica: 1. Guard: p_stradario_id obbligatorio, verificare che esista e sia attivo in config.stradario 2. Cercare per chiave naturale (stradario_id, civico, estensione, palazzina, scala, piano, interno) con COALESCE su nullable 3. Se trovato → RETURN id esistente 4. Se non trovato → INSERT + RETURNING id (il trigger trgfn_indirizzi_dettaglio_normalize calcola indirizzo_normalizzato, via_norm, civico_norm) 5. Gestire unique_violation (race condition) con retry

Nota: questa funzione NON gestisce la creazione dello stradario. Se lo stradario non esiste, il chiamante (o il frontend) deve prima crearlo o selezionarlo. Vedi DB-1b.

DB-2 — Building block fn_crea_indirizzo_soggetto¶

Prerequisiti: DB-1 (se normalizzato) oppure nessuno (se libero) Schema: anagrafiche Tipo: building block riusabile

Crea un record in anagrafiche.indirizzi_soggetti. Supporta entrambe le modalita': - Normalizzata (standard): riceve p_indirizzo_dettaglio_id - Libera (eccezione): riceve p_indirizzo_libero + campi geografici

Firma proposta: 

CREATE OR REPLACE FUNCTION anagrafiche.fn_crea_indirizzo_soggetto(
    -- Obbligatori
    p_soggetto_id             anagrafiche.soggetti.id%TYPE,
    p_tipo_indirizzo_codice   config.tipi_indirizzi.codice_interno%TYPE,
    -- Modalita' normalizzata (preferita)
    p_indirizzo_dettaglio_id  anagrafiche.indirizzi_dettaglio.id%TYPE   DEFAULT NULL,
    -- Modalita' libera (eccezione)
    p_indirizzo_libero        text                                     DEFAULT NULL,
    p_stato_id                config.stati.id%TYPE                     DEFAULT NULL,
    p_comune_id               config.comuni.id%TYPE                    DEFAULT NULL,
    p_codice_postale_id       config.codici_postali.id%TYPE            DEFAULT NULL
)
RETURNS anagrafiche.indirizzi_soggetti.id%TYPE

Logica: 1. Guard XOR: o p_indirizzo_dettaglio_id o p_indirizzo_libero, mai entrambi (R1) 2. Lookup tipo_indirizzo_id da p_tipo_indirizzo_codice in config.tipi_indirizzi 3. Se modalita' libera: guard completezza (R3) — stato_id + (comune_id + codice_postale_id) 4. INSERT in anagrafiche.indirizzi_soggetti 5. I trigger si occupano di: guard tipo (R6), normalizzazione (R8), sync geoloc, audit, tx_id

DB-7 — Funzione fn_search_stradario (ricerca vie per autocomplete)¶

Prerequisiti: nessuno Schema: script (funzione di lettura cross-dominio, come le altre fn_search_*) Tipo: funzione STABLE di lettura ottimizzata

Il frontend cerca VIE (stradario) per comune, non civici. L'utente: 1. Seleziona un comune (autocomplete comuni, BE-3) 2. Cerca una via nel comune selezionato (autocomplete stradario, questa funzione) 3. Inserisce il civico manualmente (campo numerico + dettagli) 4. Il backend chiama fn_get_or_create_indirizzo_dettaglio (DB-1) per ottenere/creare il civico

Firma proposta: 

CREATE OR REPLACE FUNCTION script.fn_search_stradario(
    p_comune_id    config.comuni.id%TYPE        DEFAULT NULL,
    p_search       text                         DEFAULT NULL,
    p_limit        integer                      DEFAULT 30
)
RETURNS TABLE (
    stradario_id           config.stradario.id%TYPE,
    toponimo               config.toponomastica.descrizione%TYPE,
    denominazione          config.stradario_generale.denominazione_norm%TYPE,
    via_completa           text,    -- es. "Via Roma"
    comune_id              config.comuni.id%TYPE,
    comune_descrizione     config.comuni.denominazione%TYPE,
    provincia_sigla        config.province.sigla%TYPE,
    codice_postale_id      config.codici_postali.id%TYPE,
    cap                    config.codici_postali.cap%TYPE
)
LANGUAGE plpgsql
STABLE
PARALLEL SAFE

Logica: 1. Guard: almeno p_comune_id o p_search deve essere valorizzato 2. Se p_comune_id fornito: filtra per comune (caso principale — autocomplete dopo selezione comune) 3. Se p_search fornito: ricerca ILIKE su toponimo || ' ' || denominazione_norm 4. JOIN: stradario → stradario_generale → toponomastica + comuni → province + codici_postali 5. Filtro stradario.attivo = true (se presente), ORDER BY via_completa, LIMIT p_limit 6. Campo calcolato via_completa = toponimo || ' ' || denominazione_norm (es. "Via Roma", "Piazza Garibaldi")

Nota sulle performance: con p_comune_id + p_search il numero di righe e' contenuto (un comune ha mediamente poche centinaia di vie). Se necessario, aggiungere indice trigram su stradario_generale.denominazione_norm.

Pattern coerente con il progetto: stessa struttura di fn_search_soggetti_universale e fn_search_indirizzi_dettaglio — funzione STABLE in script, usata dal backend come entry point.
