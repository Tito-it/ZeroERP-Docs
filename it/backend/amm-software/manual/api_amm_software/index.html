API Amministrazione Software¶

Scopo¶

Documentazione completa delle API REST del modulo Amm. Software (Amministrazione). Questi endpoint gestiscono utenti (operatori), permessi individuali, profili reparto e lookup di supporto.

Contesto¶

Il modulo Amm. Software e' il pannello di controllo per l'amministratore di sistema. Permette di creare operatori, assegnare ruoli, configurare override di permessi per singolo utente e definire profili di accesso per reparto (unita' organizzativa).

Tutti gli endpoint richiedono autenticazione JWT con ruolo ADMIN (AdminAPIView). Post-cutover multi-face il check ADMIN delega a PermissionResolver.is_super_admin (binding SUPER_ADMIN su config.profili_accesso_bindings, profilo seed id 9100). L'endpoint lista utenti ha throttling search attivo (is_search_endpoint = True).

Le risposte seguono l'envelope standard { "data": {...}, "meta": {...} }.

Base URL: /api/v1/amm-software/

  • PATCH/POST /operatori/: contratto pubblico rifiuta ruolo_sistema legacy → usa is_super_admin + attivo (vedi §1.2 e §1.4).
  • GET dettaglio: 6 nuovi campi capability (can_invite/invite_reason, can_disable/disable_reason, can_demote_super_admin/demote_reason) piu' is_super_admin, ruolo_applicativo, last_login, invito_inviato_at, deve_cambiare_password, emittenti_descrizione.

1. Utenti¶

1.1 GET /api/v1/amm-software/operatori/ -- Lista utenti¶

Restituisce la lista paginata degli operatori con filtri opzionali.

Parametri query string:

Parametro Tipo Obbligatorio Descrizione
search string no Ricerca libera su username, nome, cognome, email (ILIKE)
ruolo_sistema string no Filtra per ruolo: ADMIN, OPERATIVO, DISABILITATO
unita_organizzativa_id int no Filtra per unita' organizzativa
is_active bool no Filtra per stato attivo (true/false/1/0)
limit int no Numero massimo risultati (default 50, max 200)
offset int no Offset per paginazione (default 0)
order_by string no Colonna di ordinamento: last_name, username, ruolo_sistema, is_active, unita_organizzativa_nome, data_insert
order_dir string no Direzione ordinamento: ASC o DESC

Risposta:

{
  "data": {
    "count": 42,
    "results": [
      {
        "auth_user_id": 1,
        "username": "mtitini",
        "email": "m.titini@example.com",
        "first_name": "Michele",
        "last_name": "Titini",
        "ruolo_sistema": "ADMIN",
        "is_active": true,
        "unita_organizzativa_id": 2,
        "unita_organizzativa_nome": "Sviluppo",
        "risorsa_umana_id": 5,
        "attivo": true,
        "valido_al": null,
        "data_insert": "2026-01-15 10:30:00+00"
      }
    ]
  },
  "meta": { "request_id": "..." }
}

Esempio curl:

curl -H "Authorization: Bearer <token>" \
  "https://host/api/v1/amm-software/operatori/?search=titini&ruolo_sistema=ADMIN&limit=10"

1.2 POST /api/v1/amm-software/operatori/ -- Crea utente¶

Crea un nuovo operatore completo: utente Django, soggetto persona fisica, risorsa umana. La creazione e' orchestrata dalla funzione DB anagrafiche.fn_crea_operatore.

Contract Fase 1 multi-face: il payload accetta is_super_admin (booleano). Il campo legacy ruolo_sistema e' rifiutato con E_AMM_VALIDAZIONE. Il service traduce internamente is_super_admin -> ruolo_sistema legacy per la fn DB fn_crea_operatore (compat layer interno mentre il refactor write-path DB e' in transizione).

Payload JSON:

Campo Tipo Obbligatorio Descrizione
cognome string si* Cognome operatore (*solo se soggetto_id non valorizzato)
nome string si* Nome operatore (*solo se soggetto_id non valorizzato)
codice_fiscale string si* Codice fiscale italiano (*solo se soggetto_id non valorizzato)
username string si Username per login
email string si Email operatore
password string si Password in chiaro (viene hashata lato backend)
qualifica_id int si ID qualifica (da lookup)
is_super_admin bool no true per binding profilo SUPER_ADMIN, default false
soggetto_id UUID no Se valorizzato: associa soggetto esistente (flusso B). Se assente: crea soggetto PF nuovo (flusso A)
unita_organizzativa_id int no ID unita' organizzativa di appartenenza
data_nascita string no Data nascita (formato YYYY-MM-DD)
sesso string no M o F (default M)
valido_dal string no Data inizio validita' (default data corrente)
valido_al string no Data fine validita'
comune_nascita_id int no ID comune di nascita
indirizzo_resid_dettaglio_id int no ID dettaglio indirizzo residenza
indirizzo_domfisc_dettaglio_id int no ID dettaglio indirizzo domicilio fiscale

Note sul contract:

  • Niente ruolo_sistema: il payload con la chiave legacy viene rifiutato prima di chiamare il repo. La promotion ad ADMIN passa da is_super_admin: true.
  • Niente attivo su POST: l'operatore e' sempre creato attivo. La disabilitazione passa dal comando dedicato /disabilita/ (vedi §1.5).
  • Niente ruolo_applicativo: per il drawer admin-software e' implicitamente OPERATORE. Le vesti CLIENTE_PORTALE, FORNITORE_PORTALE, SHOP_CUSTOMER nascono da flussi di invito dedicati (vedi api_invito_portale_shop.md).

Risposta: dettaglio utente creato (stesso formato di GET dettaglio §1.3).

Esempio curl:

curl -X POST -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "cognome": "Rossi",
    "nome": "Mario",
    "codice_fiscale": "RSSMRA85M01H501Z",
    "username": "mrossi",
    "email": "m.rossi@example.com",
    "password": "SecurePass123!",
    "qualifica_id": 1,
    "is_super_admin": false,
    "unita_organizzativa_id": 2
  }' \
  "https://host/api/v1/amm-software/operatori/"

Il dettaglio e' generato da script.fn_get_operatore_detail(p_auth_user_id) (single source of truth lato DB, idioma lookup-by-id: 0 righe per id non valido).

Parametri path: id (int) -- auth_user_id dell'utente.

    "soggetto_id": "8a1f...uuid",
    "ragione_sociale_completa": "Titini Michele",
    "codice_fiscale": "TTNMHL75A01H501Z",
    "ruolo_sistema": "ADMIN",
    "is_super_admin": true,
    "ruolo_applicativo": "OPERATORE",
    "is_active": true,
    "attivo": true,
    "unita_organizzativa_id": 2,
    "unita_organizzativa_nome": "Sviluppo",
    "risorsa_umana_id": 5,
    "valido_dal": "2026-01-15",
    "valido_al": null,
    "last_login": "2026-04-29T08:30:00+00:00",
    "invito_inviato_at": "2026-01-15T09:15:00+00:00",
    "deve_cambiare_password": false,

  "meta": { "request_id": "..." }
}

Campi multi-face (Fase 1):

Campo Tipo Descrizione
is_super_admin bool true se l'identita ha binding SUPER_ADMIN attivo (config.profili_accesso_bindings, profilo seed id 9100)
ruolo_applicativo string OPERATORE / CLIENTE_PORTALE / FORNITORE_PORTALE / SHOP_CUSTOMER / API_CLIENT / DISABILITATO
last_login timestamptz | null Ultimo login (auth_user.last_login); NULL se mai loggato
invito_inviato_at timestamptz | null Quando e' stato spedito l'ultimo invito (identita_digitali.invito_inviato_at)
deve_cambiare_password bool Force-reset password al prossimo login
emittenti_descrizione string | null Lista descrizioni emittenti scope, concatenate con virgola+spazio

Capability data-driven (Fase 1):

Campo Tipo Descrizione
can_invite bool True se l'operatore e' invitabile (mai loggato, attivo, email valida). Delega a script.fn_check_operatore_invitabile
invite_reason string | null Motivo it-IT free-form quando can_invite=false; NULL altrimenti
can_disable bool False se e' l'unico super admin attivo. Preview di script.fn_check_ultimo_super_admin_attivo; non e' una garanzia (race tra sessioni: il trigger DB resta l'autorita')
disable_reason string | null Motivo quando can_disable=false
can_demote_super_admin bool | null Stesso check di can_disable ma per la rimozione del binding SUPER_ADMIN. NULL se l'operatore non e' SUPER_ADMIN (azione non applicabile -> il FE nasconde l'azione)
demote_reason string | null Motivo quando can_demote_super_admin=false

Nota sui reason it-IT free-form: i campi *_reason sono stringhe visualizzabili direttamente come tooltip dal FE. Coerente col pattern esistente di fn_check_operatore_invitabile. Eventuale futura migrazione a codici stabili (es. E_LAST_SUPER_ADMIN_DISABLE) richiederebbe un passaggio coordinato BE+DB+FE.

Esempio curl:

curl -H "Authorization: Bearer <token>" \
  "https://host/api/v1/amm-software/operatori/1/"

1.4 PATCH /api/v1/amm-software/operatori/{id}/ -- Aggiorna utente¶

Aggiorna i campi modificabili di un utente. Solo i campi presenti nel payload vengono modificati. Dopo la modifica, la cache permessi dell'utente viene invalidata.

Contract Fase 1 multi-face: il payload accetta is_super_admin + attivo. Il campo legacy ruolo_sistema e' rifiutato con E_AMM_VALIDAZIONE. Il service traduce internamente la coppia in ruolo_sistema legacy per il repo (compat layer interno) secondo la regola:

  • attivo=False → DISABILITATO (a prescindere da is_super_admin)
  • attivo=True, is_super_admin=True → ADMIN
  • attivo=True, is_super_admin=False → OPERATIVO
  • payload senza is_super_admin ne' attivo → NO-OP sul ruolo (solo altri campi)

Parametri path: id (int) -- auth_user_id dell'utente.

Payload JSON (tutti opzionali):

Campo Tipo Descrizione
email string Nuovo indirizzo email
first_name string Nuovo nome (auth_user)
last_name string Nuovo cognome (auth_user)
is_super_admin bool true per binding profilo SUPER_ADMIN, false per rimuoverlo
attivo bool Stato attivo identita digitale + risorsa umana
unita_organizzativa_id int Nuova unita' organizzativa
valido_al string Data fine validita' (formato YYYY-MM-DD)

Regole:

  • Il payload con ruolo_sistema viene rifiutato con E_AMM_VALIDAZIONE (HTTP 400).
  • Se la modifica equivale alla rimozione dell'ultimo super admin attivo, il trigger DB trgfn_profili_accesso_bindings_guard_ultimo_super_admin blocca con E_PROFILO_ULTIMO_SUPER_ADMIN (HTTP 409) — vedi sezione "Errori".
  • Se is_super_admin o attivo vengono modificati, viene chiamata anagrafiche.fn_sync_auth_user_is_active per sincronizzare auth_user.is_active
  • La cache permessi dell'utente viene invalidata dopo ogni modifica

Risposta: dettaglio utente aggiornato (stesso formato di GET §1.3).

Esempio curl:

curl -X PATCH -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"is_super_admin": true, "attivo": true, "unita_organizzativa_id": 3}' \
  "https://host/api/v1/amm-software/operatori/1/"

1.5 POST /api/v1/amm-software/operatori/{id}/disabilita/ -- Disabilita utente¶

Disabilita un utente: identita digitale attivo=false, ruolo_applicativo='DISABILITATO', risorsa umana attivo=false+valido_al=oggi. Sincronizza auth_user.is_active, invalida la cache permessi e inserisce tutti i token JWT dell'utente nella blacklist (SimpleJWT), impedendo ulteriori accessi.

Parametri path: id (int) -- auth_user_id dell'utente.

Payload: nessuno.

Guard "ultimo super admin": il preview lato Python legge can_disable dal detail (Fase 1) ed evita il round-trip se l'utente e' l'unico SA attivo (short-circuit con E_PROFILO_ULTIMO_SUPER_ADMIN). In caso di race tra sessioni, il trigger DB trgfn_profili_accesso_bindings_guard_ultimo_super_admin e' l'autorita' finale: il service traduce il DatabaseError in ServiceError(E_PROFILO_ULTIMO_SUPER_ADMIN) preservando il code per l'envelope errore (HTTP 409).

Regole:

  • Ordine disattivazione: figlio (identita_digitali) prima del padre (risorse_umane) per rispettare il framework ATTIVO del DB.
  • Chiama anagrafiche.fn_sync_auth_user_is_active per sincronizzare auth_user.is_active.
  • Invalida la cache permessi dell'utente.
  • Blacklist di tutti i token JWT outstanding (best-effort).

Risposta: dettaglio utente aggiornato (con is_active=false, attivo=false, ruolo_applicativo="DISABILITATO").

Esempio curl:

curl -X POST -H "Authorization: Bearer <token>" \
  "https://host/api/v1/amm-software/operatori/1/disabilita/"

1.6 POST /api/v1/amm-software/operatori/{id}/riattiva/ -- Riattiva utente¶

Riattiva un utente precedentemente disabilitato. Ordine inverso rispetto a /disabilita/: padre (risorse_umane) prima del figlio (identita_digitali) per rispettare il framework ATTIVO (un figlio attivo richiede padre attivo).

Parametri path: id (int) -- auth_user_id dell'utente.

Payload: nessuno.

Regole:

  • risorse_umane: attivo=true, valido_dal=oggi, valido_al=NULL.
  • identita_digitali: attivo=true, ruolo_applicativo='OPERATORE'.
  • Sync auth_user.is_active.
  • Invalida la cache permessi dell'utente.
  • Non riattiva il binding SUPER_ADMIN: se l'utente era stato precedentemente promosso e poi disabilitato, l'eventuale binding va ri-impostato via PATCH is_super_admin: true (azione esplicita).

Risposta: dettaglio utente aggiornato (con is_active=true, attivo=true, ruolo_applicativo="OPERATORE").

Esempio curl:

curl -X POST -H "Authorization: Bearer <token>" \
  "https://host/api/v1/amm-software/operatori/1/riattiva/"

  "meta": { "request_id": "..." }
}

2.7 GET /api/v1/amm-software/operatori/{id}/permessi-ereditati/ -- Livelli ereditati dal profilo¶

Restituisce i livelli che l'operatore eredita dal profilo, cioe' cosa avrebbe senza nessun override individuale. Sola lettura: non cambia niente e non tocca la semantica dei permessi.

⭐ A cosa serve. Alimenta la colonna «ereditato» del pannello permessi. Un override che ripete il valore del profilo non e' rumore innocuo: congela la riga, perche' da quel momento quell'utente non segue piu' il reparto se il reparto cambia livello. Vedere l'ereditato accanto all'override e' cio' che evita di scriverlo.

⛔ Non e' GET /reparti/{uo_id}/profilo/, e la differenza non e' cosmetica. Quello legge il solo binding REPARTO per unita_organizzativa_id. I bindings sono tre e i resolver prendono il primo per priorita':

Priorita' Tipo Legato a
1 AD_HOC l'identita' digitale dell'utente
2 PORTALE il ruolo applicativo dell'identita'
2 REPARTO l'unita' organizzativa

Per un utente con un binding AD_HOC la lettura per reparto darebbe un valore plausibile e sbagliato, su una schermata di sicurezza. Questo endpoint legge invece da script.fn_get_profili_accesso_applicabili, la stessa funzione che usano fn_resolve_livello_area e fn_check_azione_processo.

Parametri path: id (int) -- auth_user_id dell'utente.

Risposta:

{
  "data": {
    "aree": [
      {
        "area_id": 2,
        "area_codice": "vendite",
        "area_descrizione": "Vendite",
        "livello": "LETTURA",
        "profilo_nome": "Profilo reparto Amministrazione",
        "profilo_tipo": "REPARTO"
      }
    ],
    "azioni": [
      {
        "azione_id": 3,
        "permission_codename": "genera_fatture_lotti",
        "azione_descrizione": "Genera fatture lotti",
        "area_codice": "vendite",
        "abilitata": true,
        "profilo_nome": "Profilo reparto Amministrazione",
        "profilo_tipo": "REPARTO"
      }
    ]
  }
}

⚠️ Una voce ASSENTE e' un dato, non un buco: significa che nessun profilo copre quell'area o quell'azione, quindi vale il default — BLOCCATO per le aree, azione negata per le azioni. Un utente senza profili applicabili riceve due liste vuote, e va rappresentato come «default», non come «vuoto».

ℹ️ Nessuna chiave oggetti, ed e' voluto: config.profili_accesso_oggetti non esiste. La catena di un model e' override oggetto -> override area -> profilo dell'area -> BLOCCATO, quindi l'ereditato di un oggetto e' il livello della sua area, che il chiamante ha gia' nella chiave aree. Restituirlo anche qui sarebbe una seconda risposta alla stessa domanda, con due posti in cui sbagliarla.

Esempio curl:

curl -H "Authorization: Bearer <token>" \
  "https://host/api/v1/amm-software/operatori/1/permessi-ereditati/"

5. Form-defaults emittente fiscale (Fase 3)¶

5.1 GET /api/v1/amm-software/emittenti-fiscali/form-defaults/¶

Defaults pre-compilazione del form di creazione anagrafica emittente fiscale. Centralizza il consumo di config.parameters (EMITTENTE_DEFAULT_BOLLO_AUTO, EMITTENTE_DEFAULT_BOLLO_SOGLIA, EMITTENTE_DEFAULT_ROUNDING_POLICY) con cast tipi gia' applicato lato BE: il FE non duplica il cast generico di /core/parameters/defaults/. Pattern allineato a ApiArticoliFormDefaults (catalogo Fase 8 -- A5).

Cascata: user -> group -> emittente -> default via script.fn_get_parameter_full. In creazione emittente_fiscale_id e' None (cascata effettiva user->group->default).

Cast applicati:

Campo response Codice parameter Cast Convenzione
defaults.bollo_auto EMITTENTE_DEFAULT_BOLLO_AUTO bool 'true'/'false' case-insensitive; altro -> false (default-safe)
defaults.bollo_soglia EMITTENTE_DEFAULT_BOLLO_SOGLIA Decimal o null Stringa vuota = nessuna soglia -> null; non parsabile -> null (best-effort)
defaults.rounding_policy EMITTENTE_DEFAULT_ROUNDING_POLICY str o null Validato vs _ROUNDING_MODE_VALIDI_EMITTENTE (4 valori, no HALF_EVEN); fuori enum -> null

Note:

  • Il campo attivo non passa per parameters: la colonna anagrafiche.emittenti_fiscali.attivo ha gia' DEFAULT true. Il FE non lo include nei defaults.
  • non_editable_fields ritornato statico oggi (['codice', 'soggetto_id']). In attesa che dbops.vw_non_editable_fields (Fase 5) includa anche le tabelle anagrafiche, il FE legge gia' la chiave per non avere breaking change quando la fonte diventera' DB-driven.
  • Best-effort sui cast: parameters mancanti, malformati o fuori enum non sollevano errore. Il form mostra comunque, l'utente compila/seleziona manualmente.

      "bollo_soglia": null,

6. Processi automatici — i presidi¶

⚠️ Di questa famiglia qui c'e' solo l'endpoint dei presidi. Le altre cinque rotte (GET processi/, GET processi/{codice}/, POST processi/{codice}/run/, GET|POST processi/{codice}/identita/, POST .../identita/riattiva/) esistono e non sono documentate: e' un debito dichiarato, non un'omissione da leggere come «non ci sono». Contratto vivo: /api/docs/.

6.1 GET /api/v1/amm-software/processi/presidi/¶

Lo stato di tutte le viste-presidio del cantiere «nessun processo senza operatore», in un round-trip: per ognuna il conteggio, le prime righe e la descrizione.

⭐ La natura di ogni presidio la dichiara il DATABASE, non il backend. È il COMMENT della vista a dire se «deve restare VUOTA» oppure se è «un registro di DEBITO che deve CALARE», e il backend lo consegna in descrizione leggendolo con obj_description. ⛔ Un elenco di eccezioni scritto nel backend o nel frontend sarebbe la seconda sede della stessa decisione, e la seconda diverge.

⛔ Quante siano non è scritto da nessuna parte, ed è una scelta. L'elenco è PRESIDI_PROCESSI in apps/core/db/processi_repository.py, qualificato collo schema (ci sono viste di dbops e di maintenance). Un numero copiato accanto a un elenco che cresce invecchia in silenzio: fino al 2026-09-07 il docstring della view diceva «i SEI presidi» e alla stessa data l'elenco ne contava dieci.

Response shape: presidi è una lista; con_righe è il numero che si guarda per primo.

{
  "data": {
    "presidi": [
      {
        "vista": "dbops.vw_processi_programmazione_da_guardare",
        "descrizione": "PRESIDIO: i processi automatici la cui sveglia e la cui ultima corsa non tornano. DEVE restare VUOTA. …",
        "conteggio": 1,
        "righe": [ { "processo_codice": "apply_storicizza_weekly", "stato": "GIRA_E_NON_REGISTRA", "…": "…" } ],
        "troncato": false
      }
    ],
    "con_righe": 4
  }
}
Campo Significato
vista nome qualificato collo schema: due schemi possono avere viste omonime, e mezzo nome manderebbe a guardare quella sbagliata
descrizione il COMMENT della vista — è lì che sta la differenza fra «deve essere zero» e «deve calare»
conteggio count(*) senza filtro e prima delle righe: dice quanto sta fuori dalle prime consegnate
righe le prime N righe, con le colonne che la vista ha (forme diverse per vista)
troncato le righe mostrate non sono tutte — senza, venti su duecento si leggerebbero come «sono venti»

⚠️ Le colonne di righe non sono un contratto fisso: ogni presidio ha la sua forma e il client le rende leggendo le chiavi che trova (PresidiProcessiPanel.vue). Un elenco di colonne per vista sarebbe un terzo posto in cui quella forma è scritta, e si romperebbe alla prima colonna aggiunta.

⚠️ conteggio > 0 non è sempre un errore, e per questo la descrizione va resa insieme al numero: alcune viste sono registri di debito. ⭐ Al 2026-09-07 dbops.vw_processi_programmazione_da_guardare nasce con una riga (apply_storicizza_weekly, che dal febbraio 2026 gira senza lasciare traccia sul giornale): il suo stesso COMMENT lo dichiara e dice quando va tolto. Brief: work-done/brief-db-sveglia-dei-processi.md §8.1.

Esempio curl:

curl -H "Authorization: Bearer <token>" \
  "https://host/api/v1/amm-software/processi/presidi/"

Regole trasversali¶

  • Autenticazione: tutti gli endpoint richiedono JWT Bearer token con ruolo ADMIN
  • Cache permessi: ogni PUT su permessi (override aree, override azioni, emittenti scope, profilo reparto) invalida la cache permessi dell'utente o del reparto interessato
  • Semantica replace: le PUT su permessi cancellano tutti i record esistenti e inseriscono i nuovi (non e' un merge/patch)
  • Ordinamento lista utenti: whitelist di colonne ammesse (last_name, username, ruolo_sistema, is_active, unita_organizzativa_nome, data_insert); colonne non valide vengono ignorate
  • Throttling: l'endpoint lista utenti ha throttling search attivo
