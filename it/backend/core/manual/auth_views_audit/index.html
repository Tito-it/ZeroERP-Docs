Auth Views Audit (Core Django)¶

Scopo¶

Override delle view SimpleJWT per agganciare: (a) l'audit login/refresh nella tabella dbops.sessioni_utente, (b) il controllo blocco utente per tentativi falliti, (c) il throttle IP, (d) il guard cross-namespace multi-veste (§8.3).

Per il contratto HTTP completo dei 6 endpoint (3 login + 3 refresh, uno per namespace), i claim JWT custom e i codici errore → vedi api_multi_veste_token.md. Questo documento descrive l'architettura interna delle view.

Contesto¶

File apps/core/api/auth_views.py. Post refactor multi-face §8.3, le view di login/refresh sono organizzate in 2 classi base astratte + 6 subclass namespace-specific.

Gerarchia delle classi¶

TokenObtainPairView  (SimpleJWT)
  └── AuditTokenObtainPairView       \[ASTRATTA\]  audit + throttle + blocco
        ├── AdminTokenView           → /api/v1/admin/token/    (OPERATORE)
        ├── PortaleTokenView         → /api/v1/portale/token/  (CLIENTE/FORNITORE_PORTALE)
        └── ShopTokenView            → /api/v1/shop/token/     (SHOP_CUSTOMER)

TokenRefreshView  (SimpleJWT)
  └── AuditTokenRefreshView          \[ASTRATTA\]  audit + guard cross-namespace
        ├── AdminTokenRefreshView    → /api/v1/admin/token/refresh/
        ├── PortaleTokenRefreshView  → /api/v1/portale/token/refresh/
        └── ShopTokenRefreshView     → /api/v1/shop/token/refresh/

AuditTokenObtainPairView (base astratta)¶

  • Astratta: serializer_class = None + assert guard in post(). Istanziarla direttamente → AssertionError. Le subclass DEVONO fornire un serializer_class sottoclasse di MultiVesteTokenSerializer.
  • Throttle: LoginRateThrottle (5 tentativi / 5 minuti per IP).
  • Blocco utente: prima del login chiama AuthRepository.check_blocco_login(auth_user_id) che solleva errore DB (E_UTENTE_BLOCCATO) se l'utente ha bloccato_fino_a > now().
  • Tentativi falliti: dopo login fallito chiama registra_tentativo_login(successo=False). Eccezione: VesteNonAttivaError (credenziali OK ma veste sbagliata) NON viene contato come tentativo.
  • Audit login: dopo login OK, popola le 5 GUC di sessione via set_jwt_gucs(username, user_id, identita_id, request) (l'identita_id e' estratto dal refresh appena emesso tramite _extract_identita_id_from_refresh), poi chiama session_audit_service.record_login(user_id, request, jti).
  • Flag password_change_required: se AuthRepository.get_deve_cambiare_password(user.id) ritorna True, aggiunge password_change_required: true alla response.

Subclass login (Admin/Portale/Shop)¶

Differiscono dalla base SOLO per serializer_class:

  • AdminTokenView.serializer_class = AdminTokenSerializer (veste OPERATORE)
  • PortaleTokenView.serializer_class = PortaleTokenSerializer (vesti portale)
  • ShopTokenView.serializer_class = ShopTokenSerializer (veste SHOP_CUSTOMER)

Il serializer concreto (subclass di MultiVesteTokenSerializer) risolve l'identita attiva dell'utente con ruolo_applicativo nel subset ammesso e inietta i claim identita_id + ruolo_applicativo nel JWT. Se l'utente non ha la veste richiesta dal namespace → VesteNonAttivaError (403).

AuditTokenRefreshView (base astratta)¶

  • Astratta: expected_ruoli_applicativi = () + assert guard in post(). Istanziarla direttamente → AssertionError.
  • Guard cross-namespace: estrae il claim ruolo_applicativo dal refresh token via _extract_ruolo_applicativo_from_refresh (decode non-verificato del payload JWT — firma gia' validata da SimpleJWT a monte) e rifiuta con VesteNonAttivaError se non rientra in expected_ruoli_applicativi.
  • Audit refresh: dopo refresh OK, risolve lo username dal user_id del claim (_resolve_username), popola le GUC e chiama session_audit_service.record_refresh.
  • Claim preservation: SimpleJWT con ROTATE_REFRESH_TOKENS=True ruota solo jti/exp/iat; i claim custom (identita_id, ruolo_applicativo, sid) sono preservati nel nuovo refresh.

Subclass refresh (Admin/Portale/Shop)¶

Differiscono dalla base SOLO per expected_ruoli_applicativi:

  • AdminTokenRefreshView.expected_ruoli_applicativi = ("OPERATORE",)
  • PortaleTokenRefreshView.expected_ruoli_applicativi = ("CLIENTE_PORTALE", "FORNITORE_PORTALE")
  • ShopTokenRefreshView.expected_ruoli_applicativi = ("SHOP_CUSTOMER",)

Input¶

Vedi api_multi_veste_token.md §Input. Tutti e 6 gli endpoint accettano JSON body standard SimpleJWT (username+password per login, refresh per refresh).

Output¶

Envelope SimpleJWT standard (access + refresh + eventuale password_change_required al login). Il JWT contiene i claim custom (identita_id, ruolo_applicativo, sid) documentati in api_multi_veste_token.md §Claim JWT custom.

Effetto aggiuntivo: INSERT in dbops.sessioni_utente (audit login/refresh).

Regole¶

  • Il logging sessione avviene solo dopo risposta con successo (status 200). Login/refresh falliti non generano record.
  • VesteNonAttivaError al login e' catturato prima di AuthenticationFailed per non incrementare tentativi falliti (no autoblock su errore "canale sbagliato").
  • set_jwt_gucs ritorna False se identita_id e' None o l'identita non e' attiva: in quel caso viene loggato security.{login,refresh}_guc_mancate e l'audit procede con GUC vuote (user_insert='zeroerp_app').
  • Le 6 view concrete sono registrate in zeroerp_backend/urls.py con permission_classes=[AllowAny] (endpoint pubblici di autenticazione).
  • Breaking change §8.3.1: il path legacy /api/v1/auth/token/ e' stato rimosso senza alias. Client pre-refactor devono essere aggiornati.

Dipendenze¶

Componente Ruolo
dbops.sessioni_utente INSERT via session_audit_service (login/refresh/logout)
anagrafiche.identita_digitali Source di identita_id + ruolo_applicativo iniettati nel JWT
script.fn_check_blocco_login Blocco utente per tentativi falliti
script.fn_registra_tentativo_login Incremento/reset contatore tentativi
MultiVesteTokenSerializer Iniezione claim custom + risoluzione veste
JwtAuditAuthentication Validazione claim + popolamento GUC a ogni request

Test¶

  • apps/core/tests/api/test_auth_views.py — test behavior login/refresh, guard astratta, cross-namespace (Admin/Portale/Shop), no-tentativo su VesteNonAttivaError, extract helpers.
  • apps/core/tests/api/test_multi_veste_token_serializer.py — test serializer, VesteNonAttivaError, claim injection.
  • apps/core/tests/api/test_jwt_audit_authentication.py — test authenticate multi-face (E_JWT_SENZA_IDENTITA, E_IDENTITA_NON_ATTIVA, CTE GUC).

Note di migrazione¶

  • Le view base AuditTokenObtainPairView / AuditTokenRefreshView sostituiscono TokenObtainPairView / TokenRefreshView nel routing tramite subclass concrete, mai direttamente.
  • Pre-§8.3: esistevano solo 2 route (/auth/token/ + /auth/token/refresh/) sulla base, senza guard cross-veste, senza claim custom.
  • Post-§8.3: 6 route + claim custom + guard cross-namespace + audit identita-aware. Il contratto HTTP esterno resta compatibile con client SimpleJWT standard (stesso input/output base), ma:
  • I client devono aggiornarsi al nuovo path (/admin/ etc.).
  • Il JWT contiene claim aggiuntivi — ignorati dai consumer che non li leggono, letti da /me/ e JwtAuditAuthentication.
