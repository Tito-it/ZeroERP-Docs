API Offerte commerciali vendite.offerte_commerciali¶

Scopo¶

CRUD operativo delle offerte commerciali, documento pre-contrattuale che propone al cliente le condizioni quadro per una specifica utility prima della formalizzazione in contratto. Espone sub-entita' eccezioni (mirror di contratti_righe) e utility 1:1 (estensione 1:1 con dati di utenza).

L'offerta e' specchio strutturale del contratto: stessa testata, stesso enum tipo_eccezione, stessa cardinalita' utility. La fedelta' garantisce che il push offerta -> contratto (in arrivo allo step DB 8) sia una copia 1:1 senza conversioni semantiche.

Modello (decisioni §5 chiuse 2026-05-23)¶

  • Mono-utility per offerta: istanza_utility_id e utility_id NOT NULL sulla testata. Cliente con piu' utility → N offerte distinte (un eventuale raggruppamento "pacchetto commerciale" e' fuori dal v1).
  • Versione listino fissata all'emissione: in BOZZA listino_versione_id puo' essere NULL; al passaggio BOZZA -> EMESSA il trigger guard rifiuta se NULL o versione non ATTIVA. Da EMESSA in poi e' immutabile.
  • Eccezioni come mirror di contratti_righe con i 5 CHECK constraint replicati (chk_offerte_eccezioni_*) e i gate prezzo L1/L2/L3 (refactor-prezzi 2026-06-01). Le colonne stato_approvazione_prezzo e pratica_approvazione_prezzo_id esistono su offerte_commerciali_eccezioni (migration 20260601-01): la proposta ha lo stesso workflow di approvazione prezzo del contratto. Al push lo stato approvazione viene copiato 1:1 sul contratto (non più NULL) — un override già autorizzato in offerta non va riapprovato. Vedi API approvazioni prezzo e refactor-prezzi (docs/it/backend/dev/work-in-progress/refactor-prezzi.md).
  • State machine asimmetrica (decisione operativa): annullamento da noi solo prima dell'emissione; rifiuto cliente solo dopo l'emissione.

Contesto¶

  • Il codice offerta OFC-* e' generato dal trigger DB trgfn_offerte_commerciali_gen_codice (BEFORE INSERT, step 5 brief DB atterrato 2026-05-25). Il campo codice non va nel payload in creazione: se inviato viene rifiutato come unknown_key. Lookup script.fn_generate_codice('offerta_commerciale') con prefisso OFC e lunghezza 7.
  • Lo stato iniziale di ogni offerta e' BOZZA (risolto dal service via config.stati_doc_offerte.codice_interno).
  • La state machine e' autoritativa lato DB tramite il trigger trgfn_offerte_commerciali_guard_transizione che:
  • verifica che la transizione sia in config.stati_doc_offerte_transizioni
  • valorizza data_emissione / data_accettazione / data_rifiuto / data_annullamento al passaggio
  • rifiuta BOZZA -> EMESSA con listino_versione_id NULL o versione non ATTIVA (codici E_OFFERTA_EMISSIONE_SENZA_VERSIONE_LISTINO / E_OFFERTA_EMISSIONE_VERSIONE_LISTINO_NON_ATTIVA)
  • I codici errore E_OFFERTA_* sollevati dal trigger sono estratti dal MESSAGE del trigger via regex (_DB_ERROR_CODE_RE) e propagati al client come ServiceError.code originale, non come E_VENDITE_VALIDATION generico. Il FE puo' fare routing UI specifico per codice.

State machine¶

Da A Chi la innesca Effetto laterale
BOZZA EMESSA operatore (/emetti/) Congela versione listino; valorizza data_emissione
BOZZA ANNULLATA operatore (/annulla/) Valorizza data_annullamento + motivazione_rifiuto
EMESSA ACCETTATA operatore (/registra-esito/) Valorizza data_accettazione
EMESSA RIFIUTATA operatore (/registra-esito/) Valorizza data_rifiuto + motivazione_rifiuto
EMESSA SUPERATA trigger revisione (Step 7 DB) Stato terminale tecnico; rev.N+1 diventa la nuova offerta corrente

Stati terminali immutabili: ACCETTATA, RIFIUTATA, SUPERATA, ANNULLATA. Transizioni NON ammesse (documentate per evitare ambiguita'):

  • BOZZA -> RIFIUTATA non esiste: RIFIUTATA e' il "no del cliente" e dal cliente non si arriva mai con un'offerta ancora in bozza.
  • EMESSA -> ANNULLATA non e' ammessa: una volta emessa, o accetta o rifiuta il cliente. Per correzioni interne dopo l'emissione si crea una revisione (che marcera' la corrente SUPERATA).

Perimetro D6 (BE completo, step DB 1-9 + addendum)¶

Tutti gli endpoint cablati:

  • testata + state machine + eccezioni + utility 1:1 (step 1-4)
  • motivazione_rifiuto (addendum 2026-05-24)
  • numerazione automatica OFC-* via trigger DB (step 5, 2026-05-25 AM)
  • POST /<id>/crea-revisione/ + GET /<id>/revisioni/ (step 6-7, 2026-05-25 AM)
  • POST /<id>/push-contratto/ (step 8, 2026-05-25 PM)
  • Suite pgTAP (step 9) confermata da team DB
  • POST /<id>/note/ + GET/PATCH/DELETE /<id>/note/<note_id>/ — cablaggio building block PartitionedNoteRepository per target_tipo='OFFERTA' (2026-05-26)

Perimetro D7 — capability layer + refactor atomico (2026-05-26)¶

Step migliorativo data-driven applicato dopo la consegna della fn DB script.fn_available_actions_offerta (migration 20260526-01):

  • Capability blob nel detail: get_offerta ora include available_actions[], can_edit_*, can_push_contratto, non_editable_fields, stato_codice letti da script.fn_available_actions_offerta. Il FE consuma con useEntityCapabilities + mapAvailableActionsToDrawerActions, rimuovendo lo state-machine FE hardcoded.
  • Contratto collegato: contratto_id + contratto_numero esposti via LEFT JOIN vendite.contratti.offerta_id. Il FE li usa per il dialog parlante post-E_OFFERTA_CONTRATTO_GIA_GENERATO (link al ContrattoDrawer) e per il deep-link ?open=<id> post-push.
  • Atomicita' utility 1:1 inline: crea_offerta (POST) e aggiorna_offerta (PATCH) accettano un sub-oggetto opzionale utility. Se valorizzato, il service esegue il create/update_utility nella stessa transaction.atomic() (eredita istanza_utility_id/utility_id dalla testata se non specificati). Mirror del pattern ContrattoDrawer, elimina il rischio "offerta orfana di utility" del flusso a 2 round-trip.
  • Alias display fields: il SELECT testata ora espone billing_account_display + utility_display (allineamento al piano FE+BE rev. f), evitando ricodifiche client-side.

Input¶

Form-defaults GET /api/v1/vendite/offerte/form-defaults/¶

Endpoint sola lettura per pre-popolare il form CREATE offerta. Riusato dal drawer FE all'apertura e al cambio billing_account_id. Simmetrico a vendite-contratto-form-defaults e vendite-preventivi-form-defaults.

Parametro Tipo Descrizione
billing_account_id int Opzionale. Se presente, popola i campi BA-derived (categoria_cliente, utility, valuta).

Risposta 200:

{
  "data": {
    "billing_account_id": 100,
    "categoria_cliente_id_snapshot": 7,
    "categoria_cliente_codice": "STANDARD",
    "categoria_cliente_descrizione": "Standard",
    "utility_id": 3,
    "istanza_utility_id": 200,
    "utility_codice": "GAS",
    "utility_descrizione": "Gas",
    "valuta_id": 1,
    "valuta_codice": "EUR",
    "valuta_descrizione": "Euro"
  }
}

Risoluzione valuta_id (BB resolve_valuta_default, allineato a vendite.fn_get_valuta_id):

  1. billing_account.valuta_id se valorizzato
  2. EF del BA via fn_get_emittente_fiscale_pk
  3. EF dell'utente loggato (con fallback gestore globale)
  4. anagrafiche.gestori.valuta_id (primo per id)
  5. null se nessuna sorgente

Senza billing_account_id i campi BA-derived restano null ma la catena valuta parte comunque dal livello 3.

Errori: E_VENDITE_NOT_FOUND (404) se billing_account_id non esiste.

Lista offerte GET /api/v1/vendite/offerte/¶

DEF-8 (2026-06-03): la lista legge dalla vista canonica self-contained vendite.vw_offerte_commerciali_lista (security_invoker=on) — lista configurabile vendite.offerte, ritiro dinamico colonne lato FE. La vista assorbe i JOIN prima nel repository (listino_codice, listino_versione_codice, valuta_codice) e materializza is_scaduta (validita_al < CURRENT_DATE; il gating per stato STATI_OFFERTA_SEGNALA_SCADENZA resta lato FE). Campi display con i nomi canonici: cliente = ragione_sociale_completa, id. fiscale = id_fiscale_univoco_cf_piva, codice account = ba_codice, stato = stato_descrizione + stato_codice_interno. Il dettaglio (GET .../<id>/) conserva i nomi storici (billing_account_display, utility_display): fonte diversa (JOIN su tabelle base). vw_offerte_commerciali_list deprecata (drop differito post-BE).

Parametro Tipo Descrizione
search string ILIKE su codice offerta e ragione_sociale_completa BA (minimo 3 char se valorizzato)
billing_account_id int Filtro cliente
stato_codice_interno string BOZZA | EMESSA | ACCETTATA | RIFIUTATA | ANNULLATA | SUPERATA
utility_id int Filtro utility
listino_id int Filtro listino di riferimento
validita_dal_min ISO date Filtro su validita_dal (range minimo). Nessun default backend
validita_dal_max ISO date Filtro su validita_dal (range massimo)
solo_attiva bool Default true: solo l'ultima revisione viva per lineage (vw_offerte_commerciali_lista.is_attiva). false = storico revisioni completo (2026-05-28)
limit int Default 25
offset int Default 0
order_by string campo_sorgente catalogo vendite.offerte: codice | ragione_sociale_completa | ba_codice | id_fiscale_univoco_cf_piva | utility_codice | utility_descrizione | listino_codice | validita_dal | validita_al | data_emissione | stato_descrizione | stato_codice_interno | data_insert. revisione_numero non ordinabile
order_dir string asc o desc (default)

search vuoto: stringa vuota o whitespace-only trattato come "no filter" (non solleva 422). Il minimo 3 char si applica solo a search non-vuota.

Export lista offerte GET /api/v1/vendite/offerte/export/¶

Genera un file CSV o Excel con le offerte filtrate (stessi parametri della lista). Renderer generico DEF-1 (ListaExportService); colonne coerenti con la DataTable a video (config runtime: preferenza + preset + permessi).

Parametro Tipo Descrizione
formato string csv (default) o xlsx. NB: formato (italiano), NON format (magic param DRF)
search, billing_account_id, stato_codice_interno, utility_id, listino_id, validita_dal_min, validita_dal_max, solo_attiva, order_by, order_dir — stessi della lista
  • Hard cap 10.000 righe: oltre → 422 E_UI_EXPORT_LIMIT_EXCEEDED.
  • formato non valido → 400 E_UI_EXPORT_FORMAT_INVALID.
  • Risposta binaria: Content-Disposition: attachment; filename="offerte.csv|xlsx"; i filtri attivi sono metadato nel file.
  • Coda condivisa: apps.ui.api.export_helpers.{parse_export_format,build_export_response} (building block DEF-1).

Note:

  • valuta_id opzionale (2026-05-29). Snapshot fissato al CREATE, immutabile in PATCH (simmetrico a preventivi). Se omesso, il trigger DB _a*_set_valuta_default_ins lo risolve via vendite.fn_get_valuta_id (catena BA → emittente → gestore). Il FE può pre-popolare il valore via GET /api/v1/vendite/offerte/form-defaults/?billing_account_id=... che usa il BB resolve_valuta_default.
  • codice non va nel payload (step 5 atterrato 2026-05-25): generato dal trigger DB trgfn_offerte_commerciali_gen_codice come OFC-NNNNNNN. Se inviato, rifiutato come unknown_key con E_VENDITE_VALIDATION.
  • stato_doc_offerta_id / uid / revisione_* / data_* di transizione NON vanno mai inviati (rifiutati come unknown_keys con E_VENDITE_VALIDATION).
  • istanza_utility_id e utility_id sono il riferimento "anagrafico" della utility (mono-utility per offerta). I campi business (tipo/classe utenza, parametri) vivono nel sub-record utility 1:1.
  • utility (sub-oggetto opzionale, atomicita' inline 2026-05-26): se valorizzato, il service crea il record utility 1:1 nella stessa transaction.atomic() della testata (mirror ContrattoDrawer pattern). istanza_utility_id/utility_id interni al sub-oggetto sono opzionali: vengono ereditati dalla testata se omessi (coerenza FK col BA scelto). Whitelist sub-payload: istanza_utility_id, utility_id, istanza_dati_precontrattuali_id, tipo_utenza_id, classe_utenza_id, param_1_num, param_2_txt, meta. Alternativa: chiamare POST /utility/ separato dopo (vedi §Utility 1:1) — sconsigliato perche' non atomico col create testata.
  • validita_dal obbligatorio; validita_al opzionale.
  • Coerenza coppia variazione globale: tipo_variazione_globale + valore_variazione_globale entrambi NULL o entrambi NOT NULL (CHECK DB chk_offerte_variazione_globale_coerenza).

  • Capability blob (da script.fn_available_actions_offerta, mergiato nel dict): available_actions[] lista azioni ammesse nello stato corrente (mappabili 1:1 a DrawerActionsBar via mapAvailableActionsToDrawerActions); can_edit_testata / can_edit_eccezioni / can_edit_utility flag editabilita'; can_change_state true se almeno un'azione disponibile; can_create_revisione / can_push_contratto / can_genera_ordine flag per azioni speciali non-cambio-stato. Crea revisione POST /api/v1/vendite/offerte/<id>/crea-revisione/¶

Body vuoto. Crea rev.N+1 in stato BOZZA a partire dall'offerta corrente (che deve essere in stato EMESSA). Effetti:

  1. Invoca vendite.fn_crea_revisione_offerta(offerta_id, user) (step 7 brief DB).
  2. La fn DB copia testata + eccezioni attive + utility 1:1 nella nuova revisione, con revisione_numero = N+1 e revisione_padre_id = <id>.

  • Stato corrente diverso da EMESSA → 422 E_OFFERTA_REVISIONE_STATO_NON_AMMESSO. La fn DB e' guard finale; il service applica anche un pre-check applicativo che ritorna E_VENDITE_VALIDATION parlante in caso di stato fuori scope.

Genera ordine POST /api/v1/vendite/offerte/<id>/genera-ordine/¶

Conversione upstream (§7.4 analisi-ordini-vendita, 2026-06-04): crea un ordine di vendita DRAFT dall'offerta, copiando testata + righe + componenti BoM e valorizzando documento_origine = ('OFFERTA', offerta_id) sull'ordine.

  • View ApiOffertaGeneraOrdine (area vendite) → delega a ordini_service.crea_ordine_da_offerta(offerta_id) (stesso app vendite).
  • Precondizione: offerta in stato ACCETTATA.
  • Righe: l'offerta non ha righe materializzate → le righe «effettive» sono prodotte dalla fn DB fn_offerta_righe_espanse (listino base + variazione globale + eccezioni OVERRIDE/ESCLUSIONE/AGGIUNTA, con BoM, IVA/uom risolte). Prezzi negoziati preservati (offerta accettata): non-composito = prezzo congelato; composito = componenti via componenti_overrides → il trigger DB ricompone il prezzo padre dai prezzi negoziati.
  • Testata: BA, utility, emittente, valuta (l'offerta non ha termine/modalità pagamento).
  • Univocità 1:1 (rev. 2026-06-07): un'offerta genera al massimo un ordine (l'offerta è una condizione quadro atomica, non ha righe selezionabili). Guard BE fail-fast E_ORD_OFFERTA_GIA_CONVERTITA (409) + rete strutturale UNIQUE parziale uq_ordini_v_documento_origine_offerta (mappata via map_integrity_error allo stesso codice per la race concorrente). È il reversal parziale di A1 «senza UNIQUE», solo per OFFERTA (PREVENTIVO resta 1:N). Specchio della guard data-driven can_genera_ordine.
  • Mutua esclusività contratto XOR ordine (rev. 2026-06-08): un'offerta ACCETTATA si materializza in una sola forma a valle — o contratto o ordine, mai entrambi, in modo permanente (anche se annullato; il recupero è una nuova offerta). Lato ordine: guard BE fail-fast E_OFFERTA_CONTRATTO_GIA_GENERATO se l'offerta ha già un contratto (testata.contratto_id dal LEFT JOIN, nessuna query nuova). Lato contratto: il guard è a DB in fn_push_offerta_a_contratto → E_OFFERTA_ORDINE_GIA_GENERATO. La capability riflette già l'XOR: can_push_contratto/can_genera_ordine sono abilitate solo se non esiste né l'una né l'altra materializzazione.
  • Output 200: { "ordine_id": int, "numero": str, "righe_create": int, "documento_origine": {"tipo": "OFFERTA", "id": int} }.
  • Errori: E_VENDITE_NOT_FOUND (404) se inesistente; E_ORD_ORIGINE_NON_CONVERTIBILE (409) se non ACCETTATA; E_ORD_OFFERTA_GIA_CONVERTITA (409) se un ordine è già stato generato da questa offerta; E_OFFERTA_CONTRATTO_GIA_GENERATO (409) se l'offerta ha già generato un contratto (mutua esclusività XOR).
  • FE: azione «Genera ordine» data-driven da available_actions (key genera_ordine, esposta dalla fn solo se can_genera_ordine): compare in ACCETTATA senza ordine e sparisce a conversione avvenuta (come push_contratto); confirm prima della generazione (requires_confirm).
  • Prerequisiti DB atterrati: brief db-brief-offerta-righe-espanse.md (docs/it/dev/work-done/db-brief-offerta-righe-espanse.md) (righe espanse) e brief-db-univocita-offerta-ordine.md (docs/it/dev/work-done/brief-db-univocita-offerta-ordine.md) (univocità 1:1 + azione genera_ordine).

Gate prezzo L1/L2/L3 (su create ed update di OVERRIDE/AGGIUNTA)¶

Quando un'eccezione OVERRIDE/AGGIUNTA non composita porta un prezzo manuale, il service applica gli stessi tre gate del contratto/preventivo (BB condiviso _pricing_gate_helpers, mirror contratti_service):

  • L1 — permesso: l'override del prezzo richiede l'azione di processo prezzo_override_manuale; in assenza → 403 E_PRICING_OVERRIDE_NON_AUTORIZZATO. Lo stesso gate L1 si applica agli override dei prezzi componenti (componenti_overrides) — allineamento a preventivi.
  • L2 — soglia: il delta % rispetto al prezzo suggerito (resolver pricing sul listino fissato/operativo dell'offerta) non può eccedere le soglie max_sconto_pct / max_maggiorazione_pct (cascata user → categoria_cliente → group → emittente → default). Oltre soglia, senza richiesta_approvazione → 422 E_PRICING_SCONTO_ECCESSIVO / E_PRICING_MAGGIORAZIONE_ECCESSIVA (retryable=true).
  • L3 — escalation: con richiesta_approvazione: true, una violazione L2 non solleva: crea una pratica APPROVAZIONE_PREZZO (sorgente offerta) e salva l'eccezione con stato_approvazione_prezzo = PENDING + pratica_approvazione_prezzo_id. L'eccezione PENDING è bloccata in modifica dal trigger DB trgfn_righe_guard_pending finché l'approver non risolve (vedi API approvazioni prezzo).

Note: - gate saltato per ESCLUSIONE (prezzo NULL) e per i compositi (il prezzo padre è la somma derivata dei figli; i componenti hanno il proprio audit). Saltato anche se l'offerta è senza listino_id (caso non standard: per le offerte è obbligatorio). - l'output dell'eccezione (su GET/detail) include ora stato_approvazione_prezzo e pratica_approvazione_prezzo_id (NULL = nessuna approvazione richiesta).

  4. Annullamento solo da BOZZA, rifiuto solo da EMESSA: state machine asimmetrica analoga ai contratti DRAFT/ATTIVO.
  5. Versione listino congelata all'emissione (Profilo A); da EMESSA in poi listino_versione_id immutabile.
  6. Mirror del contratto: enum tipo_eccezione, VARCHAR tipo_variazione_globale, cardinalita' utility 1:1, 5 CHECK su eccezioni — tutto identico a vendite.contratti_* per garantire push 1:1 senza conversioni (step 8 DB).
  7. Anti-tampering URL su sub-resource (eccezioni/<eid>/, utility/<uid>/): verifica ownership prima di ogni mutazione.
  8. Payload {} in PATCH rifiutato: niente no-op silenziosi.
  9. Motivazione obbligatoria per RIFIUTATA e ANNULLATA. Trim applicato; stringa whitespace-only rifiutata.

E_CONFIG_MANCANTE 500 DB P0001 — OFFERTA_COMMERCIALE o CONTRATTO non trovati in config.sorgenti; stato DRAFT non in config.stati_doc_contratti. Errore di configurazione sistema fn_push_offerta_a_contratto
E_CONTRATTO_OVERLAP_ESISTENTE 409 DB P0001 — push con contratto attivo sovrapposto e chiudi_esistente=false. Il FE legge il conflitto via contratto-sovrapposto/ e richiama con chiudi_esistente=true fn_push_offerta_a_contratto / fn_contratto_sovrapposto
E_CONTRATTO_SUCCESSIONE_DATA_INVALIDA 422 DB P0001 — successione con date incoerenti: il contratto esistente inizia dopo la decorrenza del nuovo (chiusura produrrebbe valido_al < valido_dal) fn_chiudi_contratto_per_successione

I codici E_OFFERTA_* sollevati dai trigger sono propagati al client come ServiceError.code originale (non rimpiazzati da E_VENDITE_VALIDATION), estratti via regex dal MESSAGE del trigger. Questo permette al FE di fare routing UI specifico per codice (es. dialog "versione listino non ATTIVA" diverso da "transizione non ammessa generica").

Dipendenze DB¶

Tabelle:

  • vendite.offerte_commerciali — testata
  • vendite.offerte_commerciali_eccezioni — mirror di contratti_righe
  • vendite.offerte_commerciali_utilities — estensione 1:1 (UNIQUE offerta_id)
  • vendite.note_offerte_commerciali — partizione del sistema note generico (target_tipo = 'OFFERTA'), cablata via building block apps.core.db.PartitionedNoteRepository (cablaggio differito, vedi piano BE/FE)

Funzioni:

  • script.fn_generate_codice('offerta_commerciale') — generazione codice OFC-* (step 5 atterrato 2026-05-25, invocata dal trigger BEFORE INSERT).
  • vendite.fn_crea_revisione_offerta(p_offerta_id, p_user) — step 7 atterrato 2026-05-25. Crea rev.N+1 da offerta EMESSA copiando testata + eccezioni attive + utility 1:1. Ritorna BIGINT (id nuova rev).
  • vendite.fn_push_offerta_a_contratto(p_offerta_id, p_pratica_id, p_chiudi_contratto_esistente) — step 8 atterrato 2026-05-25 PM, esteso 2026-05-31 con la successione su overlap. Crea contratto DRAFT da offerta ACCETTATA, copia 1:1 eccezioni e UPSERT utility (sovrascrive il record creato dal trigger snapshot precontrattuali). Idempotente per costruzione (UNIQUE uq_contratti_offerta_id). Pratica opzionale (collega via pratiche.pratiche_sorgenti). 3° param p_chiudi_contratto_esistente (default false): su contratto attivo sovrapposto solleva E_CONTRATTO_OVERLAP_ESISTENTE se false, esegue la successione se true. Ritorna BIGINT (id nuovo contratto).
  • vendite.fn_contratto_sovrapposto(...) — rilevamento read-only (STABLE) del contratto attivo sovrapposto sulla quintupla ex_contratti_no_overlap. Meccanismo generico di dominio contratti (riusabile da ogni percorso di creazione). Esposto via OfferteRepository.get_contratto_sovrapposto per l'endpoint GET /<id>/contratto-sovrapposto/.
  • vendite.fn_chiudi_contratto_per_successione(p_contratto_id, p_nuovo_valido_dal) — accorcia il contratto esistente (valido_al = nuovo valido_dal − 1); nessun cambio di stato (lo allinea il job notturno chiusura_scadenze_daily). Guard E_CONTRATTO_SUCCESSIONE_DATA_INVALIDA su date incoerenti.
  • script.fn_available_actions_offerta(p_offerta_id) — D7 atterrata 2026-05-26 (migration 20260526-01). Capability layer pure-read: ritorna jsonb con available_actions[] dalla matrice config.stati_doc_offerte_transizioni.meta (azioni manuali) + hardcode di crea_revisione (EMESSA) e push_contratto (ACCETTATA con check cross-dominio EXISTS vendite.contratti.offerta_id), oltre a can_edit_*, can_push_contratto_reason, non_editable_fields, stato_codice. Mergeata nel detail get_offerta per il FE data-driven.

Trigger autoritativi:

  • trgfn_offerte_commerciali_guard_transizione — state machine + guard versione listino + valorizzazione timestamp transizione.
  • trgfn_offerte_commerciali_gen_codice — generazione codice OFC-NNNNNNN (BEFORE INSERT) se codice IS NULL o vuoto.
  • trgfn_offerte_commerciali_revisione — AFTER INSERT: marca la rev.N come SUPERATA quando si inserisce la rev.N+1 (cascata sicura perche' la transizione EMESSA -> SUPERATA e' ammessa nel seed).

Stati gestiti via config.stati_doc_offerte (BOZZA / EMESSA / ACCETTATA / RIFIUTATA / ANNULLATA / SUPERATA).
