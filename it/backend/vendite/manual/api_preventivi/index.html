API Preventivi vendita (Django)¶

Scopo¶

Esporre via HTTP la gestione completa dei preventivi di vendita: CRUD testata, righe, indirizzi, cambio stato, revisioni, integrazione con commesse/fatturazione e pratiche.

Contesto¶

I preventivi vendita sono il punto d'ingresso del ciclo commerciale. Dopo accettazione, alimentano la pipeline commesse/attivita_fatturabili/fatturazione. Possono anche generare pratiche operative (installazione, sopralluogo, ecc.) via tabella ponte pratiche.pratiche_sorgenti.

Le tabelle DB esistono gia' (vendite.preventivi, preventivi_righe, preventivi_indirizzi, note_preventivo, config.stati_doc_preventivi). Alcune funzioni DB sono da creare (cambio stato, revisione, ricalcolo totali).

Endpoint¶

1. Lista preventivi¶

DEF-8 (2026-06-03): la lista legge dalla vista canonica vendite.vw_preventivi_lista (security_invoker=on, sorgente vw_preventivi per is_attiva derivata) — lista configurabile vendite.preventivi, ritiro dinamico colonne lato FE. I campi display usano i nomi canonici della vista: cliente = ragione_sociale_completa, id. fiscale = id_fiscale_univoco_cf_piva, codice account = ba_codice, stato = stato_descrizione + stato_codice_interno. Il dettaglio (GET .../<id>/) conserva i nomi storici (cliente_denominazione): è una fonte diversa (JOIN diretto, non la vista). Anche list_revisioni legge dalla vista canonica.

  • Metodo: GET
  • Path: /api/v1/vendite/preventivi/
  • Auth: JWT, area_funzionale = "vendite", is_search_endpoint = True
  • Query param (tutti opzionali):
  • stato (string) — codice_interno stato (es. DRAFT, EMESSO, ACCETTATO); filtro su stato_codice_interno
  • billing_account_id (int) — filtro per BA/cliente
  • utility_id (int) — filtro per utility
  • data_da (date ISO) — data minima (su data preventivo). Default: 1 gennaio anno-1 (regola standard liste con date, lato frontend)
  • data_al (date ISO) — data massima
  • search (string, min 3 char) — ILIKE su numero e ragione_sociale_completa
  • solo_attiva (bool, default true) — solo l'ultima revisione viva per numero (is_attiva); false = storico revisioni completo (toggle "Mostra storico")
  • page (int, default 1) — pagina
  • page_size (int, default 50, max 200) — righe per pagina
  • order_by (string, default data) — campo_sorgente colonna catalogo vendite.preventivi: numero data ragione_sociale_completa ba_codice id_fiscale_univoco_cf_piva utility_codice utility_descrizione istanza_utility_codice totale_documento totale_imponibile totale_iva validita_al validita_dal stato_descrizione stato_codice_interno valuta_codice emittente_fiscale_codice competenza_mese data_insert. rev non ordinabile. Valore fuori whitelist → fallback data
  • order_dir (string, default desc) — asc o desc
  • Output 200:

1b. Export lista preventivi GET /api/v1/vendite/preventivi/export/¶

Genera un file CSV o Excel con i preventivi filtrati (stessi parametri della lista). Renderer generico DEF-1 (ListaExportService); le colonne sono coerenti con la DataTable a video (config runtime: preferenza + preset + permessi — colonne nascoste escluse, ordine utente rispettato).

Parametro Tipo Descrizione
formato string csv (default) o xlsx. NB: parametro formato (italiano), NON format (magic param DRF)
search, stato, billing_account_id, utility_id, data_da, data_al, solo_attiva, order_by, order_dir — stessi della lista
  • Hard cap 10.000 righe: oltre → 422 E_UI_EXPORT_LIMIT_EXCEEDED.
  • formato non valido → 400 E_UI_EXPORT_FORMAT_INVALID.
  • Risposta binaria: Content-Disposition: attachment; filename="preventivi.csv|xlsx"; i filtri attivi sono inclusi come metadato nel file.
  • Coda condivisa: apps.ui.api.export_helpers.{parse_export_format,build_export_response} (building block DEF-1, gemello contratti/clienti/soggetti/fornitori).

2. Crea preventivo¶

  • Metodo: POST
  • Path: /api/v1/vendite/preventivi/
  • Body JSON:
  • utility_id (int, obbligatorio)
  • billing_account_id (int, opzionale)
  • istanza_utility_id (int, opzionale)
  • valuta_id (int, opzionale)
  • termine_pagamento_id (int, opzionale)
  • validita_dal (date, opzionale)
  • validita_al (date, opzionale)
  • competenza_mese (date, opzionale — primo del mese)
  • fatturazione_immediata (bool, default false)
  • Output 200: { "data": { "id": 1, "uid": "...", "numero": "P-0001" } }
  • Regole: crea sempre in stato BOZZA, numero generato da trigger trgfn_preventivi_gen_codice
  • Errori: E_PREV_VALIDAZIONE (400), E_CONFIG_MANCANTE (500 se BOZZA non configurato)

3. Dettaglio preventivo¶

  • Metodo: GET
  • Path: /api/v1/vendite/preventivi/{id}/
  • Output 200: testata completa con decodifiche (stato, cliente, utility, valuta, termini) + indirizzi[] + righe_count (summary leggero) + capabilities (Fase 1 refactor frontend vendite)
  • Fase 3.F6 refactor frontend vendite — il detail NON include piu' righe[] (decisione C2: detail = testata + summary, righe via endpoint autonomo /righe/). Il FE chiama GET /righe/ separatamente. Vantaggi: payload detail piu' leggero su lista refresh, mai mismatch con totali ricalcolati dai trigger DB. righe_count resta disponibile come badge UX.
  • Errori: E_PREV_NOT_FOUND (404)

Capabilities (spalmate top-level nel detail, da script.fn_available_actions_preventivo):

Campo Tipo Significato
available_actions[] array Azioni cambio stato disponibili: {key, target_state, label_key (i18n), severity, icon, requires_confirm}. Non include transizioni automatiche (job notturno SCADUTO)
can_edit_testata bool true solo in DRAFT
can_edit_righe bool true solo in DRAFT
can_create_revisione bool true per ACCETTATO (revisione = nuova rev del preventivo)
can_push_commessa bool true per ACCETTATO (push verso commesse)
can_push_commessa_reason string|null Codice tecnico ostativo (es. PREVENTIVO_NON_ACCETTATO)
can_push_commessa_reason_key string|null Chiave i18n pronta da tradurre, es. preventivi.push_commessa_reason.non_accettato
non_editable_fields[] string[] Whitelist campi immutabili nello stato corrente. utility_id sempre incluso (regola di dominio: utility immutabile post-create)

Il frontend (PreventiviDrawer.vue) consuma questi metadata direttamente: niente if (stato === 'DRAFT') cablato.

4. Aggiorna preventivo¶

  • Metodo: PATCH
  • Path: /api/v1/vendite/preventivi/{id}/
  • Body JSON: campi modificabili — billing_account_id, istanza_utility_id, valuta_id, termine_pagamento_id, validita_dal, validita_al, competenza_mese, fatturazione_immediata, meta. Passare null per azzerare campi nullable. utility_id non e' aggiornabile (regola di dominio, vedi non_editable_fields nel detail).
  • Regole: ammesso solo in stato BOZZA
  • Errori: E_PREV_NOT_FOUND (404), E_PREV_STATO_NON_MODIFICABILE (409)

5. Cambio stato¶

  • Metodo: POST
  • Path: /api/v1/vendite/preventivi/{id}/stato/
  • Auth: post_permission = "cambia_stato_preventivi"
  • Body JSON: { "nuovo_stato": "ACCETTATO" }
  • Regole: delega a vendite.fn_cambia_stato_preventivo() che valida transizioni e prerequisiti
  • Transizioni: EMESSO→ACCETTATO/RIFIUTATO/SCADUTO/ANNULLATO, BOZZA→ANNULLATO
  • Transizione BOZZA→EMESSO non ammessa da questo endpoint (refactor 2026-05-28): il service fail-fast con E_PREV_VALIDAZIONE (400) e indirizza all'endpoint dedicato POST /<id>/emetti/ (§5b). Motivo: l'emissione deve orchestrare atomicamente cambio stato + generazione documento + allegati per garantire l'invariante "stato EMESSO ⇒ esiste un documento PDF persistito".
  • Guard L3 verso ACCETTATO (Sprint E): il trigger DB trg_preventivi_a10_guard_transizione_approvazione_upd blocca la transizione verso ACCETTATO se esiste almeno una riga con stato_approvazione_prezzo='PENDING'. Errore E_PREVENTIVO_RIGHE_PRICING_PENDENTI (409). L'admin deve attendere esito approvazione (vedi api_approvazioni_prezzo.md) o annullare la richiesta prima di accettare.
  • Errori: E_PREV_STATO_TRANSIZIONE (409), E_PREV_NESSUNA_RIGA (400), E_PREVENTIVO_RIGHE_PRICING_PENDENTI (409), E_PREV_VALIDAZIONE (400 se nuovo_stato="EMESSO")

5b. Emissione BOZZA→EMESSO POST /api/v1/vendite/preventivi/{id}/emetti/¶

Nuovo endpoint multipart 2026-05-28. Mirror del flusso offerta POST /api/v1/vendite/offerte/<id>/emetti/. Sostituisce la transizione BOZZA→EMESSO precedentemente esposta via /stato/.

  • Metodo: POST
  • Path: /api/v1/vendite/preventivi/{id}/emetti/
  • Content-Type: multipart/form-data
  • Parser: MultiPartParser, FormParser (override del default DRF JSON-only)
  • Auth: JWT, area_funzionale = "vendite", post_permission = "cambia_stato_preventivi" (riusa lo stesso permesso del cambio stato — l'emissione è anch'essa una transizione di dominio)
  • Body multipart:
  • template_documento_id (int, opzionale) — id template documentale da usare. Se omesso, il motore documentale seleziona il template is_default=true per (sorgente=PREVENTIVO, emittente_fiscale_id, tipo_documento_output_id)
  • tipo_documento_output_id (int, opzionale) — id tipo output (PDF, ecc.). Se omesso, default del template
  • allegati (file ripetuto, opzionale) — file secondari da persistere assieme al PDF principale. MIME/size validati dal DocumentGenerationService
  • Output 200:
{
  "data": {
    "preventivo": { "...": "testata aggiornata dopo cambio stato" },
    "documento": {
      "documento_generato_id": 42,
      "uid": "...",
      "progressivo_sorgente": 1,
      "nome_file": "PREVENTIVO_P-0001_v1.pdf",
      "size_bytes": 23456,
      "allegati_count": 2
    }
  },
  "meta": { "request_id": "..." }
}
  • Semantica transazionale: la view apre transaction.atomic() che racchiude (in ordine): preventivi_service.emetti(preventivo_id) (cambio stato + valorizza data_emissione = now()) → _resolve_contesto_preventivo (entity + sorgente_tipo) → DocumentGenerationService.genera_documento(allegati=...) (render + persist su documenti.documenti_generati + evento GENERATO). Se il render fallisce o uno qualsiasi degli allegati viola MIME/size, l'eccezione propaga e l'atomic esterno fa rollback completo → il preventivo resta BOZZA, nessun record orfano. Invariante di dominio: stato='EMESSO' ⇒ esiste almeno un record documenti_generati con sorgente_tipo=PREVENTIVO, sorgente_id=preventivo.id.
  • Regole pre-emissione (validate dal service + trigger DB):
  • Preventivo in stato BOZZA con almeno una riga attiva
  • Righe senza prezzo PENDING (Guard L3, vedi §5)
  • Template documento applicabile (PUBBLICATA valido alla data)
  • Errori:
  • E_PREV_NOT_FOUND (404) — preventivo inesistente
  • E_PREV_STATO_TRANSIZIONE (409) — preventivo non in BOZZA
  • E_PREV_NESSUNA_RIGA (400) — nessuna riga attiva
  • E_DOCUMENTI_VALIDATION (400/422) — emittente non risolto / sorgente PREVENTIVO non attiva / template non trovato / MIME allegato non ammesso / size oltre limite
  • E_DOCUMENTI_NOT_FOUND (404) — entity attesa non trovata dal resolver di contesto

6. Nuova revisione¶

  • Metodo: POST
  • Path: /api/v1/vendite/preventivi/{id}/revisione/
  • Regole: delega a vendite.fn_crea_revisione_preventivo() — copia testata+righe, rev+1, nuova rev in BOZZA, disattiva precedente
  • Errori: E_PREV_REVISIONE_ATTIVA (409)

6b. Lista catena revisioni GET /api/v1/vendite/preventivi/{id}/revisioni/¶

Nuovo endpoint 2026-05-28. Mirror di GET /api/v1/vendite/offerte/<id>/revisioni/.

  • Metodo: GET
  • Path: /api/v1/vendite/preventivi/{id}/revisioni/
  • Auth: JWT, area_funzionale = "vendite". Lettura libera in ogni stato (utile per timeline UI revisioni anche su preventivi annullati/scaduti)
  • Scopo: ritorna tutte le revisioni che condividono lo stesso numero del preventivo passato, ordinate per rev ASC. Il frontend lo consuma per il tab "Revisioni" del drawer e per il deep-link revisione → revisione precedente
  • Output 200:
{
  "data": [
    {"id": 1,  "numero": "P-0001", "rev": 1,
     "stato_codice": "SUPERATO", "is_attiva": false,
     "data_emissione": "2026-04-10T09:15:00Z"},
    {"id": 7,  "numero": "P-0001", "rev": 2,
     "stato_codice": "SUPERATO", "is_attiva": false,
     "data_emissione": "2026-05-02T16:40:00Z"},
    {"id": 42, "numero": "P-0001", "rev": 3,
     "stato_codice": "EMESSO", "is_attiva": true,
     "data_emissione": "2026-05-25T11:00:00Z"}
  ]
}
  • Implementazione: query su vendite.preventivi filtrando per numero = (SELECT numero FROM preventivi WHERE id=<id>) con ORDER BY rev ASC. Indice esistente (numero, rev)
  • Errori: E_PREV_NOT_FOUND (404) se l'id passato non esiste

6c. Genera ordine da preventivo (smistamento MERCE) POST /api/v1/vendite/preventivi/{id}/genera-ordine/¶

Modello split per natura (brief brief-preventivi-ordini.md (docs/it/dev/work-done/brief-preventivi-ordini.md) D8 — sostituisce il vecchio copia-tutto 1:1). Smista a un ordine di vendita DRAFT solo le righe MERCE del preventivo (natura con destinazione_tipo='ORDINE'), valorizzando documento_origine = ('PREVENTIVO', preventivo_id) sull'ordine.

  • View ApiPreventivoGeneraOrdine (area vendite) → delega a ordini_service.crea_ordine_da_preventivo(preventivo_id, righe_ids), che a sua volta delega alla primitiva DB vendite.fn_push_preventivo_a_ordine.
  • Body JSON (opzionale): { "righe_ids": [int, ...] } — sottoinsieme di righe da smistare (smistamento selettivo). Assente/null = tutte le righe MERCE residue; lista vuota = E_PREV_VALIDAZIONE (non degrada a "tutte").
  • Cosa fa la fn DB (non più orchestrazione Python):
  • copia solo le righe natura ORDINE (i servizi una-tantum vanno a commessa via push commessa; il ricorrente è bloccato a monte, D9);
  • snapshot prezzi + componenti BoM (fn_ordine_riga_componenti_init);
  • scrive il link di riga ordini_righe.preventivo_riga_id → idempotenza di riga: una riga merce finisce su al massimo un ordine (le righe già allocate sono saltate, D5). Niente più doppio-ordine del vecchio copia-tutto.
  • Precondizione / guard (validati dalla fn DB, non più in Python): stato ACCETTATO → altrimenti E_VENDITA_PREVENTIVO_PUSH_STATO_NON_AMMESSO; almeno una riga merce residua → altrimenti E_VENDITA_PREVENTIVO_NESSUNA_RIGA_ORDINE.
  • Output 200: { "ordine_id": int, "numero": str, "documento_origine": {"tipo": "PREVENTIVO", "id": int} }. (Il campo righe_create non è più ritornato: il conteggio vive a DB.)
  • FE: il ramo merce vive nel Pannello Smistamento (PreventiviSmistamentoPanel, sostituisce il GeneraOrdineDialog dal 2026-06-12): l'operatore seleziona le righe residue (preselezionate tutte) e «Smista selezionate» instrada per natura — le righe merce finiscono su questo endpoint con righe_ids. La capability genera_ordine di script.fn_available_actions_preventivo (gate su residuo merce) resta esposta dal BE ma è filtrata dalla barra azioni del drawer.
  • Gate EVASO bi-ramo (§5b brief smistamento): dopo il push, se non resta residuo su nessun ramo (fn_preventivo_ha_residuo_ordine + fn_preventivo_ha_residuo_commessa), il service transita ACCETTATO→EVASO (warning-tolerant al deploy parziale, come il gemello su push-commessa §13).
  • Percorso pratica (bivio-per-esito rev.3): lo smistamento merce si esegue da qui (Pannello Smistamento); quando il preventivo è in una pratica, l'aggancio dell'ordine come pratiche_sorgenti COLLEGATO avviene alla chiusura di SMISTAMENTO via l'handler merce-only post_smistamento (esito MERCE_PRESENTE), non da un orchestratore monolitico. Il vecchio CONFERMA_VENDITA / vendita.push_preventivo è deprecato (solo tipi legacy 9002/9003). Vedi §14b (completa smistamento).

Offerta → ordine: non disponibile (l'offerta non ha righe materializzate, solo eccezioni su listino). Prerequisito DB: brief db-brief-offerta-righe-espanse.md (docs/it/dev/work-done/db-brief-offerta-righe-espanse.md).

6d. Righe merce smistabili a ordine GET /api/v1/vendite/preventivi/{id}/righe-smistabili-ordine/¶

  • Metodo: POST

  • Body JSON:

  • uom_operativa_id (int, opzionale)
  • ordine (int, opzionale)

  • componenti_overrides (object {componente_id: prezzo_string}, opzionale) — modello unificato componenti BoM 2026-05-13: mappa di prezzi manuali per i figli del padre composito. Solo se l'articolo is_composito=TRUE. Richiede l'azione prezzo_override_manuale come per il prezzo padre; altrimenti E_PRICING_OVERRIDE_NON_AUTORIZZATO (403). Per i componenti senza entry, il backend invoca il resolver bundle-aware (STADIO 0 listino bundle del padre, fallback STADIO 1 standalone). Vedi modello-componenti-bom.md.
  • componenti_attivazioni (object {componente_id: bool}, opzionale) — modello unificato: mappa per attivare/disattivare componenti opzionali. Default DB: obbligatori attivo=TRUE, opzionali attivo=FALSE. Inviare solo i delta. Disattivare componenti obbligatorio=TRUE e' bloccato dal trigger DB con E_DOC_COMPONENTE_OBBLIGATORIO (422). Nessun gate L1 dedicato — decisione operativa, non economica
  • Regole:
  • Ammesso solo in stato BOZZA
  • Auto-fill prezzo: se prezzo_unitario non e' nel payload e la testata ha BA+utility+data validi, il service chiama PricingService.resolve_prezzo e popola il prezzo dal resolver v5 (3 stadi: promo/contratto/categoria)
  • L1 override: se prezzo_unitario e' passato e differisce dal resolver, serve l'azione di processo prezzo_override_manuale; altrimenti E_PRICING_OVERRIDE_NON_AUTORIZZATO (403). Stessa autorizzazione per componenti_overrides non vuoto. Superuser bypassato
  • L2 limite variazione (Sprint D): dopo L1, se prezzo_resolver e' noto e non zero, calcola delta_pct firmato; sconto > VENDITE_MAX_SCONTO_PCT o maggiorazione > VENDITE_MAX_MAGGIORAZIONE_PCT -> E_PRICING_SCONTO_ECCESSIVO/E_PRICING_MAGGIORAZIONE_ECCESSIVA (403, retryable=True dopo Fase 5.B2: il FE puo' offrire CTA "richiedi approvazione" e ri-tentare con richiesta_approvazione=true). Parametri risolti via ParameterService con cascata estesa (refactor 2026-05-15): user → categoria_cliente → group → emittente → session → function → default. La categoria_cliente_id viene recuperata dal BA della testata preventivo (BillingAccountRepository.get_categoria_cliente_id) e propagata al risolutore: cosi' un'azienda puo' configurare soglie commerciali per categoria cliente (es. PREMIUM max sconto 5% indipendentemente dal seniority dell'operatore). Superuser bypass.
  • L3 workflow approvazione (Sprint E): se richiesta_approvazione=true e L2 viola, l'errore L2 viene catturato, viene creata pratica APPROVAZIONE_PREZZO (stato APERTA) e la riga inserita con stato_approvazione_prezzo='PENDING' + pratica_approvazione_prezzo_id. Email best-effort al recipient configurato in parameter VENDITE_APPROVAZIONE_PREZZO_RECIPIENT_EMAIL. La pratica e' visibile nella coda approver via GET /vendite/approvazioni-prezzo/.
  • Componenti BoM CASO composito: dopo create_riga, se l'articolo e' is_composito=TRUE, il service invoca fn_preventivo_riga_componenti_init che popola preventivi_righe_componenti per tutti i figli BoM validi alla data. Errori bloccanti: E_DOC_COMPOSITO_BOM_VUOTA (422) se la BoM e' vuota/scaduta alla data del documento; E_DOC_COMPONENTE_OBBLIGATORIO_PREZZO_ZERO (422) se un override mette prezzo 0 su un obbligatorio; E_DOC_COMPONENTE_LISTINO_MANCANTE (422) se il resolver fallisce per un componente senza override. Tutta la transazione e' atomica (init + UPDATE attivazioni avvengono in @transaction.atomic).
  • Meta audit: popolato sempre con origine_prezzo (PROMO/CONTRATTO_OVERRIDE/CONTRATTO_LISTINO/CATEGORIA/MANUALE/LISTINO_BUNDLE) + prezzo_resolver_context (listino/contratto/promo + variazione). Se override manuale: anche prezzo_base_resolver, delta_override, delta_override_pct, override_user_id. Se workflow L3: anche richiesta_approvazione_pending=true + violazione_l2 (tipo, variazione_abs_pct, limite_pct).
  • Ricalcolo totali automatico dopo insert (trigger DB). Per padri compositi il prezzo unitario padre viene immediatamente sovrascritto dal trigger _z90_ricalcola_padre come SUM(figli × coeff_qta_snapshot).
  • Errori: E_PREV_VALIDAZIONE (400), E_PREV_STATO_NON_MODIFICABILE (409), E_PRICING_OVERRIDE_NON_AUTORIZZATO (403), E_PRICING_SCONTO_ECCESSIVO (403), E_PRICING_MAGGIORAZIONE_ECCESSIVA (403), E_DOC_COMPOSITO_BOM_VUOTA (422), E_DOC_COMPONENTE_OBBLIGATORIO (422), E_DOC_COMPONENTE_OBBLIGATORIO_PREZZO_ZERO (422), E_DOC_COMPONENTE_LISTINO_MANCANTE (422)

13. Push in commessa (fatturazione)¶

  • Metodo: POST
  • Path: /api/v1/vendite/preventivi/{id}/push-commessa/
  • Auth: post_permission = "push_commessa_preventivi", Idempotency-Key obbligatoria
  • Body JSON (opzionale): { "righe_ids": [int, ...] } — sottoinsieme di righe servizio da pushare (smistamento selettivo dal Pannello Smistamento, brief-db-smistamento-preventivi.md (docs/it/dev/work-done/brief-db-smistamento-preventivi.md) C). Assente/null = tutte le righe servizio eleggibili; lista vuota = E_PREV_VALIDAZIONE (non degrada a "tutte" — stessa regola su /genera-ordine/, helper _parse_righe_ids). Il filtro arriva alla fn DB fn_list_preventivi_da_pushare(p_righe_ids) attraverso la catena push_a_commessa → pr_run_commesse_push_one → CommessaPushOrchestrator → handler → CommesseRepository.fetch_pushable_rows (5° parametro, supportato dalla sola sorgente PREVENTIVO — whitelist _SORGENTE_SUPPORTA_RIGHE_IDS).
  • Regole: ammesso solo in stato ACCETTATO, verifica righe eleggibili via fn_list_preventivi_da_pushare
  • Gate EVASO bi-ramo (D6 + brief smistamento §5b): a push COMPLETATO transita ACCETTATO→EVASO solo se non resta residuo su nessun ramo (fn_preventivo_ha_residuo_ordine e fn_preventivo_ha_residuo_commessa entrambe false). Il check commessa non è ridondante: con righe_ids COMPLETATO si riferisce al solo sottoinsieme. Lo stesso gate vive anche sul ramo ordine (ordini_service.crea_ordine_da_preventivo).
  • Aggancio pratica (ramo servizi dello split, bivio rev.3): se il preventivo appartiene a una pratica, a push COMPLETATO la commessa-servizi viene legata alla pratica come pratiche_sorgenti COLLEGATO (idempotente). È il punto d'aggancio del ramo servizi: l'handler post_smistamento è merce-only, quindi la commessa-servizi non passa da lì. No-op per i push standalone (preventivo non in pratica).
  • Semantica transazionale (fix analisi-fix-transazioni #5, 2026-07-08): push + transizione EVASO + aggancio commessa-servizi alla pratica avvengono in un unico transaction.atomic(). Un fallimento dell'aggancio-pratica rolla l'intero push (commesse + ponte emittibilità): non resta mai una commessa-servizi orfana senza link pratica (prima l'aggancio era una scrittura separata post-push). Il push è idempotente/ri-eseguibile (advisory lock + dedup segment_key) → retry sicuro. La sola transizione EVASO resta best-effort, isolata su un savepoint dedicato (un suo fallimento logga e prosegue, senza rollbackare push+aggancio).
  • Output 200: report orchestrator { stato, push_log_id, durata_ms, handlers, commesse_ids, righe_pushable, fatturazione_immediata }
  • Errori: E_PREV_STATO_TRANSIZIONE (409), E_PREV_NESSUNA_RIGA (400)

  • risolve la pratica del preventivo (ROOT per-flusso) → E_VENDITA_PREVENTIVO_NON_COLLEGATO (422) se il preventivo non nasce da una pratica;
  • guard bi-ramo: nessun residuo su ORDINE né COMMESSA (fn_preventivo_ha_residuo_ordine / _commessa) → E_VENDITA_SMISTAMENTO_NON_ESEGUITO (422) se resta merce/servizi da smistare;
  • esito di ramo: MERCE_PRESENTE se dal preventivo è nato un ordine (stesso lookup documento_origine dell'handler post_smistamento, così l'handler troverà l'ordine da agganciare), altrimenti SOLO_SERVIZI — copre anche il caso misto (c'è merce → MERCE_PRESENTE);
  • completa (o avvia+completa se lo step è ancora DA_ESEGUIRE) delegando al BB motore pratiche_service.completa_step_pratica.
  • Effetto sul percorso pratica:
  • MERCE_PRESENTE → i flussi ordine CONFERMA_ORDINE (9013) e INVIO_COMMESSA (9014) sono percorribili+obbligatori → la pratica resta APERTA finché non completati; nasce anche il retro-aggancio dell'ordine (handler post_smistamento);
  • SOLO_SERVIZI → 9013/9014 sono ramo morto (non bloccano) → la pratica si chiude subito (nessun lavoro pendente).
  • Idempotente: se lo step è già terminale → no-op, gia_completato=true.
  • Output 200:
{ "data": { "preventivo_id": 1, "pratica_id": 42, "flusso_id": 500,
            "esito": "MERCE_PRESENTE", "gia_completato": false } }
  • Errori: E_VENDITA_PREVENTIVO_NON_COLLEGATO (422), E_VENDITA_SMISTAMENTO_NON_ESEGUITO (422), E_PREV_VALIDAZIONE (400, flusso SMISTAMENTO non istanziato).

16b. Risoluzione preventivo ROOT (percorso pratica)¶

Due endpoint di lettura che risolvono il preventivo ROOT agganciato a una pratica (pratiche_sorgenti, ruolo_link ROOT). Alimentano gli step del percorso che aprono lo stesso PreventiviDrawer. Ritornano {"preventivo_id": <id|null>}.

  • Per flusso: GET /api/v1/vendite/preventivi/root-per-flusso/?flusso_id=<id> — ROOT agganciato a quel flusso (aggancio per-flusso). Usato dalla riapertura del flusso PREVENTIVAZIONE (azione_ui APRI_PREVENTIVO): se il ROOT esiste apre in EDIT, altrimenti CREATE. flusso_id obbligatorio (E_FLUSSO_ID_OBBLIGATORIO).
  • Per pratica: GET /api/v1/vendite/preventivi/root-per-pratica/?pratica_id=<id> — ROOT della pratica (non del flusso corrente). Usato dagli step a valle (es. azione_ui SMISTAMENTO, flusso che non possiede il ROOT: agganciato a monte da PREVENTIVAZIONE). pratica_id obbligatorio (E_PRATICA_ID_OBBLIGATORIO). Il FE non apre in CREATE se ritorna null (requiresExisting): lo step a valle richiede un preventivo già esistente.
  • Lettura libera (area vendite); l'apertura del documento applica comunque RLS sull'emittente.

    "preventivo_id": 53,

    "contratto_id": 23,

Integrazione pricing v5¶

Le righe preventivo usano il building block centralizzato PricingService.resolve_prezzo (catalogo backend §Vendite Pricing v5) per:

  • Auto-fill del prezzo quando il payload lo omette (endpoint 8) — resolver 3 stadi: PROMO → CONTRATTO → CATEGORIA
  • Suggerimento diagnostico pre-compilazione (endpoint 8b) — nessun side-effect
  • Audit override (endpoint 8/9) — meta JSONB popolato con origine del prezzo, contesto resolver e delta override manuale

Il resolver risolve il prezzo usando BA, utility, data della testata preventivo + emittente derivato dal JWT operatore. Se la testata manca di uno di questi campi (caso legacy), il wiring e' skippato: il prezzo passa come da payload senza check ne' audit.

Per la roadmap L2 (limite sconto via parametri) e L3 (approvazione out-of-policy via pratiche), vedi sviluppo-autorizzazioni-prezzi (docs/it/dev/work-in-progress/sviluppo-autorizzazioni-prezzi).

Form-defaults BA-aware (Fase 2.B4)¶

Il drawer FE preventivi popola valuta_id/termine_pagamento_id/iva_id automaticamente al cambio BA via GET /api/v1/vendite/preventivi/form-defaults/?billing_account_id=.... Risolve dal cliente associato al BA tramite tripletta (istanza_utility_id, soggetto_ruolo_id, utility_id). valuta_id segue la catena del BB resolve_valuta_default (BA → EF del BA → EF utente → fallback gestore globale), allineata 2026-05-29 alla fn DB vendite.fn_get_valuta_id. Vedi api_vendite_form_defaults.md.
