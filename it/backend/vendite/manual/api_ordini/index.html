API Ordini di vendita vendite.ordini¶

Scopo¶

CRUD operativo (scheletro) degli ordini di vendita, documento del ciclo attivo che raccoglie le righe articolo da evadere/fatturare. Espone testata, righe con componenti BoM (modello unificato), conferma (DRAFT -> CONFERMATO) e push singolo a commessa (chiusura del giro ordine → attività fatturabili → pipeline lotto → fattura), oltre a lista configurabile DEF-8 + export e note partizionate.

Clone strutturale della famiglia vendite (preventivi/offerte) — regola del 2: pricing via PricingService, componenti via fn_ordine_riga_componenti_*, note via PartitionedNoteRepository, lista/export via ListaExportService. Rispetto a preventivi/offerte l'ordine non ha revisioni né listino in testata.

Stato: scheletro BE (analisi analisi-ordini-vendita.md (docs/it/dev/work-done/analisi-ordini-vendita.md) §5) + stampa PDF (§Documenti) + conversione preventivo/offerta→ordine (2026-06-04, endpoint genera-ordine sui domini upstream — valorizza documento_origine A1). Fulfillment/DDT: vedi api_ddt.md (evasione genera-ddt). Indirizzi documento: vedi api_indirizzi_documento.md.

Modello¶

  • Identità: (anno, serie, numero) + uid. Il numero è generato dal trigger trgfn_ordini_gen_numero (BEFORE INSERT) via script.fn_generate_codice('ordine') — valorizzato già in BOZZA, immutabile dopo (lock colonne). Il campo numero non va nel payload.
  • Stato iniziale DRAFT (risolto dal service via config.stati_doc_ordini.codice_interno).
  • fatturazione_trigger (CONFERMATO | SPEDITO | CONSEGNATO): governa quando l'ordine pusha a commessa. Default ereditato da billing_account.fatturazione_ordini (trigger trgfn_ordini_normalize); sovrascrivibile sul payload.
  • canale_origine (ADMIN | PORTALE | SHOP): immutabile post-INSERT; in back-office sempre ADMIN.
  • Estensioni modello 2026-06-03: agente (agente_soggetto_ruolo_id, nullable) ed origine documento (A1: documento_origine_tipo ∈ {PREVENTIVO,OFFERTA} + documento_origine_id). Valorizzate dalla conversione upstream (fatte 2026-06-04): documento_origine = ('PREVENTIVO', id) da ordini_service.crea_ordine_da_preventivo (copia 1:1 righe piatte) e ('OFFERTA', id) da crea_ordine_da_offerta (righe espanse via fn DB fn_offerta_righe_espanse, prezzi negoziati preservati). Univocità (rev. 2026-06-07): per OFFERTA vale 1:1 — un'offerta genera al massimo un ordine (UNIQUE parziale uq_ordini_v_documento_origine_offerta + guard BE E_ORD_OFFERTA_GIA_CONVERTITA, reversal parziale di A1 «senza UNIQUE»); PREVENTIVO resta 1:N (split per riga, nessun vincolo). Endpoint sui domini upstream (vedi api_preventivi.md §6c e api_offerte). La CREATE diretta lascia le colonne NULL.
  • Pagamento/valuta: modalita_pagamento_id, termine_pagamento_id, valuta_id, tasso_cambio (default 1). giorni_pagamento/fine_mese e i campi trasporto non sono in testata (droppati 20251027-01; vivono su BA / DDT a valle).

State machine¶

Da A Chi la innesca Effetto
DRAFT CONFERMATO operatore (/emetti/) Abilita il push a commessa (se fatturazione_trigger=CONFERMATO)

Il flusso utente innesca la transizione via /emetti/ (conferma + generazione documento, vedi sezione Emetti); /conferma/ resta come API di sola transizione, riusata internamente da emetti. La transizione è autoritativa lato DB (trigger trgfn_ordini_guard_transizione_approvazione sull'UPDATE di stato_doc_ordine_id): il service applica solo il guard applicativo «origine DRAFT + almeno una riga». I codici E_ORDINE_* sollevati dai trigger sono estratti dal MESSAGE via regex (_DB_ERROR_CODE_RE) e propagati come ServiceError.code originale (routing UI specifico), con fallback E_VENDITE_VALIDATION.

Input¶

Tutti gli endpoint sotto DomainAPIView (area_funzionale='vendite', JWT + ZeroERPPermission). Liste/export con is_search_endpoint=True.

Lista ordini GET /api/v1/vendite/ordini/¶

Lista paginata dalla vista canonica vendite.vw_ordini_lista (DEF-8, lista configurabile vendite.ordini). Scope emittente automatico (RLS + fn_get_emittenti_scope_pk_ids su emittente_fiscale_id).

Query param Tipo Note

stato_codice_interno str codice_interno stato (DRAFT
billing_account_id int cliente
utility_id int
data_da / data_a str ISO filtro su data (default lato UI, non backend)
order_by str whitelist: numero | data | ragione_sociale_completa | ba_codice | utility_codice | totale_doc | fatturazione_trigger | stato_descrizione | stato_codice_interno | data_insert. Default data
order_dir str asc | desc (default desc), tiebreaker id
limit / offset int paginazione (limit cap 200)

Export lista GET /api/v1/vendite/ordini/export/?formato=csv|xlsx¶

Export DEF-1: stessi filtri della lista, ListaExportService + catalogo colonne vendite.ordini (ordine/visibilità/permessi utente rispettati). Cap EXPORT_MAX_ROWS. Parametro formato (italiano), MAI format. Errori: E_UI_EXPORT_FORMAT_INVALID (400), E_UI_EXPORT_LIMIT_EXCEEDED (422).

Create testata POST /api/v1/vendite/ordini/¶

Crea un ordine in DRAFT. handle_post_json.

Campo Tipo Note
billing_account_id int cliente; se presente, soggetto_ruolo_id è derivato dal BA
soggetto_ruolo_id int alternativa al BA (NOT NULL in testata)
utility_id int
emittente_fiscale_id int opzionale; se omesso, trigger lo valorizza da GUC
valuta_id, modalita_pagamento_id, termine_pagamento_id int opzionali

agente_soggetto_ruolo_id int opzionale (E)
data str ISO opzionale (default CURRENT_DATE)
meta obj opzionale

numero/canale_origine/stato_doc_ordine_id non vanno nel payload. Ritorna {id, uid, numero}.

Detail GET /api/v1/vendite/ordini/<id>/¶

Testata (dalla vista + meta/storicizza) + capability data-driven da script.fn_available_actions_ordine (matrice config.transizioni_stati_ordini): available_actions[] (azioni di stato con key/target_state/label_key/ severity/icon/requires_confirm — incl. conferma, annulla, e push_commessa come azione applicativa), can_edit_testata, can_edit_righe, can_push_commessa (+ can_push_commessa_reason/_reason_key), non_editable_fields, stato_codice, più righe_count. (can_conferma non è più un flag: la conferma è un'entry di available_actions.) 404 (E_ORD_NOT_FOUND) se inesistente o fuori scope (RLS).

Ordine per pratica GET /api/v1/vendite/ordini/per-pratica/?pratica_id=<id>¶

Risolve l'ordine COLLEGATO a una pratica (pratiche_sorgenti, sorgente ORDINE_VENDITA, ruolo COLLEGATO — aggancio fatto dal PostSmistamentoHandler alla chiusura di SMISTAMENTO). Alimenta gli step a valle del percorso pratica (azione_ui CONFERMA_ORDINE / INVIO_COMMESSA), che aprono l'OrdiniDrawer su quell'ordine. Ritorna {"ordine_id": <id|null>} (null se nessun ordine agganciato — preventivo tutto-servizi). pratica_id obbligatorio (E_PRATICA_ID_OBBLIGATORIO). Lettura libera (area vendite). Se più ordini (consegne parziali, 1:N) ritorna il più recente. Gemello di GET /vendite/preventivi/root-per-pratica/.

Riepilogo IVA GET /api/v1/vendite/ordini/<id>/riepilogo-iva/¶

Riepilogo IVA aggregato dell'ordine: una riga per aliquota con imponibile, imposta, arrotondamento, totale_riga (più decodifiche iva_codice/ iva_descrizione/iva_aliquota; natura_id/esigibilita/split_payment sempre NULL per gli ordini). Lettura pura dalla vista derivata vendite.vw_ordini_riepilogo_iva_dettaglio: l'IVA è calcolata per gruppo aliquota (ROUND(SUM(imponibile_riga)), poi imposta sul gruppo — regola DPR 633/72 art. 21 + DM 24/12/93, identica ai preventivi); nessun calcolo Python. La vista riflette le righe attive correnti e i totali di testata (*_tot) sono mantenuti coerenti dal trigger fn_ricalcola_totali_ordine. Ordinamento iva_aliquota NULLS LAST, iva_id NULLS LAST. Scope/visibilità via security_invoker=on + RLS su vendite.ordini (ordine fuori perimetro → lista vuota). Usato dal pannello "Riepilogo IVA" del drawer e dal context builder PDF.

Indirizzi documento GET/POST /<id>/indirizzi/ + DELETE /<id>/indirizzi/<iid>/¶

BB condiviso sui 5 domini vendite (ambito ORDINI: CON, FATT; editabile solo DRAFT): contratto completo in api_indirizzi_documento.md.

Update testata PATCH /api/v1/vendite/ordini/<id>/¶

Solo in DRAFT. request.data (non handle_post_json, api.md). Campi aggiornabili: utility_id, valuta_id, modalita_pagamento_id, termine_pagamento_id, fatturazione_trigger, agente_soggetto_ruolo_id, data, meta.

Cliente immutabile post-creazione (2026-06-04): billing_account_id non è aggiornabile (a differenza del create, dove deriva soggetto_ruolo_id). vendite.ordini denormalizza soggetto_ruolo_id (NOT NULL) accanto a billing_account_id. Un PATCH che cambia billing_account_id è rifiutato con E_ORD_CLIENTE_IMMUTABILE; lo stesso BA reinviato invariato è tollerato (il form FE lo può rimandare). Regola «cambiare cliente = nuovo ordine».

Difesa DB autoritativa atterrata (DB-ORD-LOCK, 2026-06-04): billing_account_id e soggetto_ruolo_id sono immutabili su UPDATE via lock-columns data-driven (registro dbops.automation_lock_columns, non trigger a mano), che solleva lo stesso codice E_ORD_CLIENTE_IMMUTABILE (estratto da _db_errors su UPDATE diretta che bypassa il service). Conseguenza correlata: trgfn_ordini_normalize ora ri-eredita fatturazione_trigger dal BA solo su INSERT (il ramo UPDATE era diventato logica morta). Override straordinario: SET LOCAL zeroerp.allow_lock_columns_override = 'on'. Brief: db-brief-ordini-lock-cliente.md (docs/it/dev/work-done/db-brief-ordini-lock-cliente.md).

Delete DELETE /api/v1/vendite/ordini/<id>/¶

Hard-delete della sola bozza orfana (supporto al pattern "abbandono bozza": il create auto-salva una BOZZA per abilitare le righe; se l'operatore esce senza inserirne, la bozza vuota va rimossa). Guard (allineato a elimina_preventivo, niente hard-delete di dati reali): stato DRAFT e zero righe. Un ordine con righe non si cancella, si annulla (cambia-stato → ANNULLATO): E_ORD_STATO_TRANSIZIONE con messaggio dedicato. Le righe/componenti della bozza vuota hanno ON DELETE CASCADE; il trigger DB blocca se collegato a DDT.

Emetti POST /api/v1/vendite/ordini/<id>/emetti/ (multipart)¶

Flusso target della famiglia vendite (§6 brief-ordini-stampa.md (docs/it/dev/work-done/brief-ordini-stampa.md)): emissione = conferma documentale. Clone di ApiPreventivoEmetti/ApiOffertaEmetti. Orchestra in una transazione atomica (savepoint annidato):

  1. ordini_service.conferma(id) — transizione DRAFT → CONFERMATO (riusa il punto di dominio esistente, che governa anche il push a commessa: la logica di stato non è duplicata né spostata);
  2. DocumentGenerationService.genera_documento(...) sullo stato CONFERMATO (lo snapshot del context riflette il nuovo stato);
  3. allegati multipart opzionali (allegati).

Se la generazione fallisce, il rollback dell'atomic annulla la conferma → lo stato resta DRAFT, niente record documentale orfano (come preventivi/offerte). Body multipart: template_documento_id, tipo_documento_output_id, allegati (tutti opzionali). Risposta: { "ordine": <esito conferma>, "documento": <documento generato> }. Prerequisito: template ORDINE_VENDITA con versione PUBBLICATA (vedi Documenti).

Conferma POST /api/v1/vendite/ordini/<id>/conferma/¶

DRAFT -> CONFERMATO. Endpoint di sola transizione: il flusso utente passa da /emetti/ (conferma + documento), mentre /conferma/ resta come API di servizio (riusata internamente da emetti). La transizione e la precondizione "≥1 riga" sono validate dal trigger guard DB trgfn_ordini_guard_transizione (E_ORDINE_CONFERMA_SENZA_RIGHE); il service mantiene anche il guard applicativo E_ORD_NESSUNA_RIGA (defense-in-depth + messaggio). Le altre transizioni manuali (es. annulla) passano da cambia-stato.

Percorso pratica — auto-completamento step CONFERMA_ORDINE (9013, bivio rev.3): se l'ordine è COLLEGATO a una pratica, la conferma completa anche lo step CONFERMA_ORDINE con esito POSITIVO, nella stessa transazione (atomico: conferma + completamento). Sblocca INVIO_COMMESSA (prereq POSITIVO). Riusa l'azione standalone (la pratica orchestra, non decide al posto dell'operatore); delega al BB motore pratiche_service.completa_step_pratica, idempotente (no-op se lo step è già terminale o l'ordine non nasce da una pratica). L'user del JWT è propagato per l'audit del completamento.

Cambia stato POST /api/v1/vendite/ordini/<id>/cambia-stato/¶

Transizione di stato generica data-driven (es. annulla DRAFT→ANNULLATO). Body: stato_codice (= target_state dell'azione da available_actions). L'ammissibilità della transizione è validata dal trigger guard DB trgfn_ordini_guard_transizione (matrice config.transizioni_stati_ordini): transizione non ammessa → E_ORDINE_TRANSIZIONE_NON_AMMESSA. La conferma (DRAFT→CONFERMATO) ha l'endpoint dedicato /conferma/ per le sue precondizioni.

Push singolo a commessa POST /api/v1/vendite/ordini/<id>/push/¶

Push del singolo ordine CONFERMATO via fn_list_ordini_da_pushare(…, p_ordine_id) + orchestratore (pr_run_commesse_push_one, sorgente ORDINE_VENDITA) → attivita_fatturabili. Guard: stato CONFERMATO + righe eleggibili.

Ponte emittibilità (2026-06-10): a push COMPLETATO, nella stessa transazione, ogni commessa toccata viene resa emittibile — attività BOZZA → APPROVATA (fn_approva_commessa_attivita) + testata → PRONTA_FATTURAZIONE (fn_cambia_stato_commessa, skip idempotente se già pronta da una sorgente precedente). Regola di modello: il documento pushato è già autorizzato (ordine CONFERMATO), quindi il push è esso stesso l'autorizzazione delle attività generate. Il ponte vive in pr_run_commesse_push_one e vale per ogni percorso (preventivi standalone, ordini, handler pratica; il batch pr_run_commesse_push lo applica best-effort per commessa con errori in emittibilita_errors).

Percorso pratica — auto-completamento step INVIO_COMMESSA (9014, bivio rev.3): a push COMPLETATO, se l'ordine è COLLEGATO a una pratica, si completa anche lo step INVIO_COMMESSA con esito POSITIVO. È lo step terminale del ramo merce: completandolo (nessun altro flusso aperto, obbligatori fatti) la pratica si auto-chiude (chiusura data-driven del motore). Stesso BB pratiche_service.completa_step_pratica (idempotente, no-op fuori-pratica); gated su push COMPLETATO (PARZIALE/ERRORE non completano lo step). user JWT propagato.

Semantica transazionale (fix analisi-fix-transazioni #4, 2026-07-08): push + transizione CONFERMATO→EVASO + chiusura step INVIO_COMMESSA avvengono in un unico transaction.atomic(). Un fallimento della chiusura-step pratica rolla l'intero push (commesse + ponte emittibilità): la pratica non resta mai non-riconciliata con commesse committate (prima la chiusura-step era una scrittura separata post-push). Il push è idempotente/ri-eseguibile → retry sicuro. La sola transizione EVASO resta best-effort su un savepoint dedicato (fallimento loggato, non rollbacka push+step).

La response espone commesse_ids (commesse toccate dal push), oltre a stato/push_log_id/handlers/righe_pushable/fatturazione_trigger.

Righe¶

Metodo / Path Scopo
GET /<id>/righe/ Lista righe attive (decodifiche articolo/uom/iva + importo_riga + is_composito_caso_a)
POST /<id>/righe/ Aggiunge una riga (solo DRAFT). riga_nr autoassegnato. Pricing auto-fill via PricingService se prezzo assente e articolo non composito; per articolo composito init componenti BoM con override prezzi opzionali (componenti_overrides, vedi sotto)
PATCH /<id>/righe/<riga_id>/ Aggiorna riga (solo DRAFT). request.data
DELETE /<id>/righe/<riga_id>/ Hard-delete riga (solo DRAFT)

Payload riga (create): articolo_id (obbligatorio), descrizione, quantita, qta_operativa, uom_operativa_id, factor_to_base, prezzo_unitario, sconto_percentuale, iva_id, meta. La doppia quantità operativa/base segue il pattern standard (input con priorità all'operativa; quantita base derivata dal trigger trgfn_qta_from_operativa). I totali testata sono ricalcolati da trigger DB.

Componenti BoM (CASO A)¶

Metodo / Path Scopo
POST /<id>/righe/preview-componenti/ Preview read-only dei componenti BoM (pre-save). Payload: articolo_id, uom_operativa_id, quantita
GET /<id>/righe/<riga_id>/componenti/ Lista componenti persistiti (?solo_attivi=true)
PATCH /<id>/righe/<riga_id>/componenti/<componente_id>/ Aggiorna componente (solo DRAFT): prezzo_unitario, attivo, esposto_in_fattura, meta
DELETE /<id>/righe/<riga_id>/componenti/<componente_id>/ Soft-delete componente (attivo=FALSE, solo DRAFT)

Override prezzi componente pre-save (CREATE riga composita, simmetria preventivi/contratti): il POST /<id>/righe/ accetta componenti_overrides (mappa {componente_id: prezzo}) dal dialog FE. È normalizzato (normalize_componenti_overrides) e passato a fn_ordine_riga_componenti_init; i componenti senza override ricadono sul pricing risolto. L'override manuale richiede il permesso prezzo_override_manuale (gate L1 validate_componenti_overrides_authorization → E_PRICING_OVERRIDE_NON_AUTORIZZATO se assente). La fn DB rifiuta override prezzo 0 su componente obbligatorio (E_PARAMETRO_INVALIDO). In assenza di componenti_overrides l'init usa i prezzi del resolver (comportamento storico).

Note GET/POST /<id>/note/ + GET/PATCH/DELETE /<id>/note/<note_id>/¶

Note partizionate (vendite.note_ordini, target_tipo='ORDINE') via building block PartitionedNoteRepository + make_note_views. Contratto identico agli altri cinque domini (testata + riga via target_riga_id): payload, filtri, Idempotency-Key, codici errore e permessi stanno in api_note_documento.

Documenti / Stampa …/<id>/documenti/…¶

Stampa conferma d'ordine via motore documenti (sorgente ORDINE_VENDITA, quarto dominio dopo preventivo/offerta/contratto). Flusso allineato alla famiglia (§6 brief-ordini-stampa.md (docs/it/dev/work-done/brief-ordini-stampa.md)): in DRAFT solo anteprima on-demand; la generazione documentale avviene nel passaggio DRAFT → CONFERMATO via POST /<id>/emetti/ (vedi sopra). Gli endpoint sotto coprono ristampa e gestione documentale post-bozza.

Metodo / Path Scopo
POST /<id>/emetti/ Emissione: conferma + genera PDF + allegati, atomica (vedi sezione Emetti)
POST /<id>/documenti/genera/ Genera e persiste un PDF (documenti_generati + evento GENERATO). Body opzionale: template_documento_id, tipo_documento_output_id
POST /<id>/documenti/anteprima/ Anteprima PDF temporanea (no persist, no evento). Risposta binaria application/pdf inline
GET /<id>/documenti/ Lista paginata documenti generati per l'ordine (scope emittente, page/page_size)
GET /<id>/documenti/<documento_id>/file/ Download PDF principale + evento SCARICATO
GET/POST /<id>/documenti/<documento_id>/allegati/ Lista file (principale + allegati) / append allegati (multipart)
GET /<id>/documenti/<documento_id>/file/<file_id>/ Download di uno specifico file (principale o allegato) + evento SCARICATO

Risoluzione: _CODICE_SORGENTE_ORDINE = "ORDINE_VENDITA" → resolve_contesto_documentale risolve sorgente_tipo_id; il context è prodotto da OrdineDocumentContextBuilder (CODE='ORDINE_VENDITA'). Orchestrazione, scope e render restano in DocumentGenerationService (invariato). Permessi: area vendite (lettura) — la generazione è riproduzione PDF di un dato già visibile, non modifica dell'ordine. Prerequisito: template ORDINE_VENDITA con versione PUBBLICATA (creazione manuale, vedi documenti-e-stampe.md): senza, genera/anteprima falliscono con E_DOCUMENTI_*.

Output¶

Envelope standard success_response ({"data": …, "meta": {request_id}}). Liste: paginated_envelope (count, page, page_size, total_pages, results).

Regole¶

  • Modifiche (testata/righe/componenti) ammesse solo in DRAFT (E_ORD_STATO_TRANSIZIONE).
  • Pricing sempre via PricingService.resolve_prezzo (BB condiviso, mai query dirette su listini). Il gate prezzi L2/L3 stile contratti non è applicato: scelta ratificata (analisi §8.bis) — pricing stile preventivo (resolve + prezzo dal caller).
  • Cliente immutabile in update: billing_account_id fuori dalla whitelist PATCH; cambio rifiutato con E_ORD_CLIENTE_IMMUTABILE (guard BE + lock-columns DB autoritativo, vedi Update testata).
  • Scope emittente: la vista è security_invoker=on (RLS attiva sulla tabella base); il filtro applicativo fn_get_emittenti_scope_pk_ids si somma (defense-in-depth). Un detail fuori scope torna 404.
  • Numero: generato dal trigger all'INSERT (mai NULL), immutabile dopo.

Lineage / genealogia (brief-be-fe-lineage, 2026-07-15)¶

  • Colonne lineage in lista (Fase B): la lista espone anche fase (proiezione normalizzata dallo stato), pratica_id/pratica_numero/ n_pratiche (pratica collegata), frontiera_tipo_id + frontiera_tipo_codice_interno e frontiera_natura_doc_codice_interno (dalla vista, non piu' decodificati dal repository: changeSet 20260829-01/02 — ⛔ il nome e' cambiato, e con lui la sorgente), frontiera_codice/frontiera_stato_codice_interno/frontiera_fase, n_discendenti_attivi, is_transitato — dalla vista canonica estesa (LEFT JOIN vendite.vw_documento_lineage). Colonne configurabili pratica/fase/transito visibili di default (seed preset). order_by accetta anche pratica_numero e fase (la frontiera NON e' ordinabile).
  • Passaggi GET /api/v1/vendite/ordini/<id>/passaggi/ — genealogia del documento: pratica + frontiera + catena transiti in entrambe le direzioni. Contratto completo nel manuale del BB condiviso: api_lineage_passaggi.md.

Codici errore¶

Codice HTTP Quando
E_ORD_NOT_FOUND 404 ordine/riga/componente inesistente o fuori scope
E_ORD_VALIDAZIONE 400 payload non valido (cliente mancante, campi vuoti, billing_account_id non numerico, ecc.)
E_ORD_CLIENTE_IMMUTABILE 400 tentativo di cambiare billing_account_id/soggetto_ruolo_id in update (guard BE + lock-columns DB)
E_ORD_STATO_TRANSIZIONE 409 operazione non ammessa nello stato (modifica fuori DRAFT; delete bozza con righe → annullare)
E_ORD_NESSUNA_RIGA 409 conferma/push senza righe eleggibili (guard applicativo conferma())
E_ORD_OFFERTA_GIA_CONVERTITA 409 conversione offerta→ordine già avvenuta (univocità 1:1): guard BE fail-fast + rete UNIQUE parziale uq_ordini_v_documento_origine_offerta (via map_integrity_error)
E_ORDINE_TRANSIZIONE_NON_AMMESSA varia trigger guard: transizione di stato non presente/attiva in config.transizioni_stati_ordini (es. cambia-stato verso uno stato non ammesso)
E_ORDINE_CONFERMA_SENZA_RIGHE varia trigger guard: DRAFT→CONFERMATO senza righe (precondizione DB, gemella di E_ORD_NESSUNA_RIGA)
E_VENDITE_DUPLICATO / E_VENDITE_FK 409 / 400 violazione UNIQUE/FK (via map_integrity_error)
E_ORDINE_* varia altri codici sollevati dai trigger DB (estratti via regex)
E_UI_EXPORT_FORMAT_INVALID / E_UI_EXPORT_LIMIT_EXCEEDED 400 / 422 export
E_DOCUMENTI_NOT_FOUND / E_DOCUMENTI_VALIDATION / E_DOCUMENTI_RENDER_FAILED 404 / 400 / 422 stampa: ordine o template/versione non risolti, input invalido, render fallito

Tutti registrati in error_policies.py (gli E_VENDITE_* e gli E_UI_* preesistono; gli E_ORD_* aggiunti con questo scheletro).
