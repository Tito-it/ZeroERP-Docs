API Contratti vendite.contratti¶

Scopo¶

CRUD operativo dei contratti commerciali cliente-listino, con sub-entita' righe (vendite.contratti_righe) e utility 1:1 (vendite.contratti_utilities). E' il ponte tra il cliente (BA) e il listino di riferimento.

Modello unificato (refactor 2026-05-15)¶

Le vecchie modalita' A/B/C sono state rimosse come scelta utente. Il contratto ha ora una forma derivata dai campi di testata:

Forma derivata listino_id Eccezioni in contratti_righe
con_listino NOT NULL Opzionali. Tipi: OVERRIDE (prezzo personalizzato), ESCLUSIONE (articolo non disponibile), AGGIUNTA (articolo fuori-listino)
senza_listino NULL Tutte AGGIUNTA con prezzo_unitario NOT NULL (sostituisce ex-modalita' C "interamente negoziato")

In forma "con_listino" la variazione globale (tipo_variazione_globale + valore_variazione_globale) e' un campo opzionale che si applica alle righe non-eccezione lette dal listino. Il vecchio vincolo "A/B/C" e' droppato: qualunque combinazione di listino + variazione + eccezioni e' ammessa.

Snapshot versione listino all'attivazione¶

Il contratto referenzia listino_id + nuovo campo listino_versione_id. In DRAFT la versione e' NULL (il contratto segue la versione corrente del listino). All'attivazione, il trigger trgfn_contratti_freeze_listino_versione fissa la versione corrente: da quel momento la versione e' immutabile (Profilo A), e cambi del listino non si propagano al contratto. Le eccezioni sono blindate in ogni fase.

Riferimento: refactor-contratti-modalita.md (docs/it/dev/work-done/refactor-contratti-modalita) §3-bis-A/A-schema.

Contesto¶

  • Il numero contratto e' generato via script.fn_generate_codice('contratto') (prefix CNT, len 7, config in config.sistema_codici) dentro la funzione madre vendite.fn_create_contratto (fix analisi-fix-transazioni #2, 2026-07-08 — prima lato service, prima dell'INSERT). NON e' accettato in payload (lock via trigger trgfn_lock_columns('numero', 'CODICE_NON_MODIFICABILE')).
  • Lo stato iniziale di ogni contratto e' DRAFT (risolto dentro la fn madre da config.stati_doc_contratti.codice_interno).
  • Atomicità creazione (#2): generazione numero + INSERT testata + INSERT utility 1:1 opzionale avvengono in un'unica SELECT vendite.fn_create_contratto(...), atomica per costruzione: o tutto o rollback (contatore numero incluso). Prima erano generate_numero() + 2 INSERT separati in autocommit → un fallimento dell'INSERT utility lasciava un contratto orfano. NB: il numero viene da una sequence e un rollback lascia comunque un gap di numerazione (innocuo, gia' cosi' in precedenza).
  • Le coerenze cross-table (tipo/classe utenza per ambito utility, no-overlap, coerenza tipo_eccezione/prezzo) sono enforced dai trigger DB e dal temporal UNIQUE PG18:
  • trgfn_contratti_freeze_listino_versione_upd — fissa listino_versione_id al passaggio DRAFT→ATTIVO
  • trgfn_contratti_lock_post_attivazione_upd — testata immutabile (listino, versione, variazione globale) dopo l'attivazione
  • trgfn_contratti_righe_lock_post_attivazione_* — eccezioni immutabili dopo l'attivazione del contratto padre
  • trgfn_contratti_righe_guard_aggiunta_fuori_listino — blocca AGGIUNTA su articolo gia' presente nel listino
  • trgfn_contratti_utilities_guard_tipo_classe
  • CHECK chk_contrighe_prezzo_per_tipo_eccezione — ESCLUSIONE ↔ prezzo NULL
  • EXCLUDE gist parziale ex_contratti_no_overlap su (billing_account_id WITH =, istanza_utility_id WITH =, utility_id WITH =, ambito WITH =, validita WITH &&) WHERE (partecipa_overlap_snapshot) (migration 20260521-03; predicato DRAFT-escluso da 20260602-17..22). I contratti DRAFT e quelli abortiti non partecipano al vincolo: l'esclusivita' scatta solo all'attivazione (vedi nota DRAFT-scope sotto). Governato dal framework dbops.automazione_overlap (re-apply notturno).
  • Il service ContrattiService traduce gli errori P0001 dei trigger nei codici applicativi documentati piu' sotto.

Lista contratti GET /api/v1/vendite/contratti/¶

DEF-8 (2026-06-02): la lista legge dalla vista vendite.vw_contratti_lista (lista configurabile vendite.contratti, ritiro dinamico colonne lato FE). I campi display usano i nomi canonici della vista — cliente = ragione_sociale_completa, id. fiscale = id_fiscale_univoco_cf_piva (niente alias ba_*); stato = stato_descrizione (display) + stato_codice (codice mutabile, display) + stato_codice_interno (codice immutabile, per la logica — es. confronti DRAFT/ATTIVO/CESSATO; vedi linee-guida-sql.md §6c). Il dettaglio (GET .../<id>/) conserva invece i nomi storici (ba_ragione_sociale, id_fiscale): è una fonte diversa (JOIN su tabelle base, non la vista).

Parametro Tipo Descrizione

billing_account_id int Filtro cliente
stato_doc_contratto_id int Filtro stato (FK config.stati_doc_contratti)
utility_id int Filtro utility
ambito string COMMODITY o COMMERCIO
listino_id int Filtro listino di pricing (debug forma con_listino vs senza_listino)
data_da ISO date Filtro periodo validità (overlap valido_dal/valido_al). Default: 1 gennaio anno-1 (regola standard liste con date)
data_a ISO date Filtro periodo validità
scadenza_mese string YYYY-MM: contratti con valido_al (ultimo giorno di validità) nel mese indicato
limit int Default 25, max 200
offset int Default 0
order_by string numero data valido_dal valido_al ba_codice ragione_sociale_completa id_fiscale_univoco_cf_piva utility_codice ambito listino_codice stato_descrizione stato_codice categoria_cliente_snapshot_codice data_insert data_update
order_dir string asc (default) o desc

Scope emittente applicato a livello DB (RLS security_invoker sulla vista) + filtro applicativo fn_get_emittenti_scope_pk_ids (defense-in-depth).

Export lista GET /api/v1/vendite/contratti/export/¶

Genera un file CSV o Excel con i contratti filtrati (stessi parametri della lista). Renderer generico DEF-1 (ListaExportService); le colonne sono coerenti con la DataTable a video (config runtime: preferenza + preset + permessi — colonne nascoste escluse, ordine utente rispettato).

Parametro Tipo Descrizione
formato string csv (default) o xlsx. NB: parametro formato (italiano), NON format (magic param DRF)
search, billing_account_id, stato_doc_contratto_id, utility_id, ambito, listino_id, data_da, data_a, scadenza_mese, order_by, order_dir — stessi della lista
  • Hard cap 10.000 righe: oltre → 422 E_UI_EXPORT_LIMIT_EXCEEDED.
  • formato non valido → 400 E_UI_EXPORT_FORMAT_INVALID.
  • Risposta binaria: Content-Disposition: attachment; filename="contratti.csv|xlsx"; i filtri attivi sono inclusi come metadato nel file.
  • Coda condivisa: apps.ui.api.export_helpers.{parse_export_format,build_export_response} (building block DEF-1, gemello clienti/soggetti/fornitori).

Note (refactor 2026-05-15):

  • valuta_id opzionale (2026-05-29). Snapshot fissato al CREATE, immutabile in PATCH (non in _UPDATE_KEYS_TESTATA). Se omesso, il trigger DB _a*_set_valuta_default_ins lo risolve via vendite.fn_get_valuta_id (catena BA → emittente → gestore). Il FE può pre-popolare via GET /api/v1/vendite/contratti/form-defaults/?billing_account_id=....
  • numero e stato_doc_contratto_id NON vanno mai inviati in payload (rifiutati con E_VENDITE_VALIDATION).
  • utility (sub-payload opzionale): se presente, crea la riga utility 1:1 nello stesso round-trip. istanza_utility_id e utility_id sono derivati dalla testata, NON dal sub-payload.
  • Niente piu' "modalita": listino_id e variazione globale sono campi opzionali liberi. Forma "senza_listino" → omettere listino_id; la variazione e' comunque ammessa (anche se il suo effetto sara' visibile solo se aggiungerai eccezioni AGGIUNTA con prezzo > 0).
  • Coppia variazione coerente: tipo_variazione_globale e valore_variazione_globale devono essere entrambi NULL o entrambi NOT NULL. Pre-validation in _validate_variazione_globale_coppia_coerente → E_VENDITE_VALIDATION ("tipo e valore devono essere entrambi presenti o entrambi NULL").

Detail GET /api/v1/vendite/contratti/<id>/¶

Output: testata + utility + righe[] + capabilities spalmate top-level (Fase 1.B2 refactor frontend vendite, da script.fn_available_actions_contratto):

Campo Tipo Significato
available_actions[] array Azioni cambio stato disponibili. L'azione cessa e' arricchita runtime con requires_date=true, default_date=today, min_date=valido_dal
can_change_state bool true se almeno un'azione manuale disponibile
can_edit_testata bool true in DRAFT (full whitelist) e in ATTIVO (solo valido_al+meta); false in CESSATO
can_edit_righe bool true solo in DRAFT
non_editable_fields[] string[] Whitelist BE coerente con _CONTRATTO_PATCH_ALLOWED_BY_STATE. In ATTIVO include tutto eccetto valido_al+meta; in CESSATO include tutto

Il frontend (ContrattoDrawer.vue) usa default_date/min_date dell'azione cessa per pre-popolare il dialog di cessazione: niente new Date() cablato.

Update testata PATCH /api/v1/vendite/contratti/<id>/¶

Solo campi mutabili: ambito, valido_dal, valido_al, parent_contratto_id, data, listino_id, tipo_variazione_globale, valore_variazione_globale, categoria_cliente_id_snapshot, meta. Identificativi (numero, BA, istanza, utility, stato) sono immutabili. categoria_cliente_id_snapshot e' modificabile solo in stato DRAFT; in altri stati il service lo rifiuta con E_VENDITE_VALIDATION.

Post-attivazione (refactor 2026-05-15 §3-bis-A): listino_id, listino_versione_id, tipo_variazione_globale, valore_variazione_globale diventano immutabili (Profilo A). Tentativo di modifica → 409 con E_CONTRATTO_CAMPI_BLOCCATI_POST_ATTIVAZIONE. Per cambi sostanziali serve un nuovo contratto.

Blocco rimozione listino con eccezioni (refactor §3-bis-F): se il PATCH porta listino_id da NOT NULL a NULL e ci sono OVERRIDE/ESCLUSIONE attive, il service ritorna 422 con E_CONTRATTO_LISTINO_RIMOZIONE_CON_ECCEZIONI. AGGIUNTA non blocca (resta valida anche senza listino). L'operatore deve rimuovere/sostituire prima le eccezioni.

Gate L2 sulla variazione globale (refactor §3-bis-E): se il PATCH tocca valore_variazione_globale con tipo_variazione_globale = PERCENTUALE, si applica il gate L2 (cascata user → categoria_cliente → group → emittente). Sconto/maggiorazione oltre soglia → 403 retryable con E_PRICING_SCONTO_ECCESSIVO/E_PRICING_MAGGIORAZIONE_ECCESSIVA. VALORE_FISSO skip (non e' percentuale, gate non applicabile). Superuser bypass.

Cambio stato POST /api/v1/vendite/contratti/<id>/cambia-stato/¶

{"codice_interno": "SOSPESO"}

Stati ammessi via questo endpoint: SOSPESO, CESSATO, ANNULLATO e ritorni → DRAFT ammessi dal modello. ATTIVO non è ammesso da questo endpoint (refactor 2026-05-28): il service fail-fast con E_VENDITE_VALIDATION (400) e indirizza all'endpoint dedicato POST /<id>/emetti/ (sezione seguente). Motivo: l'attivazione deve orchestrare atomicamente cambio stato + generazione documento + allegati per garantire l'invariante "stato ATTIVO ⇒ esiste un documento PDF persistito".

Le altre transizioni (DRAFT → SOSPESO, ATTIVO → SOSPESO, SOSPESO → ATTIVO, ecc.) restano gestite da questo endpoint. La transizione * → ATTIVO dovrà comunque passare per /emetti/ (anche da SOSPESO, per coerenza con l'invariante documentale).

Attivazione DRAFT→ATTIVO POST /api/v1/vendite/contratti/<id>/emetti/¶

Nuovo endpoint multipart 2026-05-28. Mirror del flusso offerta/preventivo (ApiOffertaEmetti / ApiPreventivoEmetti). Sostituisce la transizione DRAFT→ATTIVO precedentemente esposta via /cambia-stato/.

  • Metodo: POST
  • Content-Type: multipart/form-data
  • Parser: MultiPartParser, FormParser
  • Auth: JWT, area_funzionale = "vendite". Nessun post_permission specifico (allineato al cambio stato contratti — l'autorizzazione è a livello area, non azione di processo dedicata)
  • Body multipart:
  • template_documento_id (int, opzionale)
  • tipo_documento_output_id (int, opzionale)
  • allegati (file ripetuto, opzionale) — file secondari da persistere assieme al PDF principale del contratto
  • Output 200:
{
  "data": {
    "contratto": { "...": "testata aggiornata dopo cambio stato" },
    "documento": {
      "documento_generato_id": 42,
      "uid": "...",
      "progressivo_sorgente": 1,
      "nome_file": "CONTRATTO_CNT0000001_v1.pdf",
      "size_bytes": 34567,
      "allegati_count": 1
    }
  },
  "meta": { "request_id": "..." }
}
  • Semantica transazionale: la view apre transaction.atomic() che racchiude (in ordine): ContrattiService().emetti(contratto_id) (cambio stato DRAFT→ATTIVO + freeze listino_versione_id via trigger trgfn_contratti_freeze_listino_versione) → _resolve_contesto_contratto → DocumentGenerationService.genera_documento(allegati=...). Se il render fallisce o un allegato viola MIME/size, l'atomic esterno rollbacka tutto → il contratto resta DRAFT, nessun record orfano. Invariante di dominio: stato='ATTIVO' ⇒ esiste almeno un record documenti_generati con sorgente_tipo=CONTRATTO, sorgente_id=contratto.id.
  • Regole pre-attivazione (validate dal trigger DB):
  • Listino operativo (ATTIVA/CHIUSA) valido alla data del contratto (versioni BOZZA ignorate)
  • Forma "senza_listino" → almeno una riga AGGIUNTA con prezzo valorizzato, altrimenti E_CONTRATTO_NEGOZIATO_PURO_SENZA_RIGHE (422)
  • Template documento applicabile (PUBBLICATA valido alla data)
  • Errori:
  • E_VENDITE_NOT_FOUND (404) — contratto inesistente
  • E_VENDITE_VALIDATION (400) — contratto non in DRAFT
  • E_CONTRATTO_NEGOZIATO_PURO_SENZA_RIGHE (422) — forma senza_listino senza righe valorizzate
  • E_DOCUMENTI_VALIDATION (400/422) — emittente non risolto / sorgente CONTRATTO non attiva / template assente / MIME/size allegato non ammesso
  • E_DOCUMENTI_NOT_FOUND (404)

Righe POST /api/v1/vendite/contratti/<id>/righe/¶

Refactor 2026-05-15: le righe sono eccezioni tipizzate del listino. Il campo tipo_eccezione e' obbligatorio in CREATE e immutabile in UPDATE (per cambiare tipo serve DELETE + INSERT).

{
  "articolo_id": "00000000-0000-0000-0000-000000000001",
  "tipo_eccezione": "OVERRIDE",
  "tipo_erogazione": "CANONE",
  "fonte_quantita_attesa": "FISSA",
  "prezzo_unitario": "25.50",
  "qta_operativa": "1",
  "uom_operativa_id": 5,
  "ordine": 10
}

Tipi ammessi (allineati col CHECK DB chk_contrighe_prezzo_per_tipo_eccezione):

tipo_eccezione Significato prezzo_unitario
OVERRIDE Prezzo personalizzato per un articolo presente nel listino NOT NULL
ESCLUSIONE L'articolo del listino non e' disponibile per il cliente NULL
AGGIUNTA Articolo fuori-listino, aggiunto al contratto NOT NULL

Vincoli:

  • AGGIUNTA su articolo presente nel listino: bloccata dal trigger trgfn_contratti_righe_guard_aggiunta_fuori_listino → E_CONTRATTO_AGGIUNTA_GIA_IN_LISTINO (422). L'operatore avrebbe dovuto usare OVERRIDE.
  • Coerenza prezzo/tipo: ESCLUSIONE con prezzo NOT NULL o OVERRIDE/AGGIUNTA con prezzo NULL → E_VENDITE_VALIDATION (pre-DB) o CHECK violation (DB).
  • Unicita' eccezione: max 1 eccezione OVERRIDE/ESCLUSIONE per coppia (contratto_id, articolo_id). Stessa univocita' per AGGIUNTA.
  • Post-attivazione: tutte le eccezioni sono immutabili (INSERT/UPDATE/DELETE bloccati dal trigger trgfn_contratti_righe_lock_post_attivazione*) → E_CONTRATTO_CAMPI_BLOCCATI_POST_ATTIVAZIONE (409).

PATCH /api/v1/vendite/contratti/<id>/righe/<riga_id>/ aggiorna i campi mutabili; articolo_id e tipo_eccezione immutabili. Cambio di prezzo_unitario validato in coerenza col tipo_eccezione esistente (pre-DB con messaggio parlante).

DELETE /api/v1/vendite/contratti/<id>/righe/<riga_id>/ hard-delete (bloccato dal trigger se note collegate o contratto ATTIVO).

Campo fonte_quantita_attesa (refactor 2026-05-19)¶

Workflow autorizzazioni prezzo L1+L2+L3 (refactor 2026-05-19)¶

CREATE e UPDATE riga sono cablati al BB orchestratore _pricing_gate_helpers.resolve_or_check_override_prezzo. Matrice gate per tipo_eccezione (decisione Alternativa B 2026-05-18):

tipo_eccezione L1 permesso prezzo_override_manuale L2 soglia % L3 richiesta_approvazione
OVERRIDE sempre sempre (vs prezzo resolver) opt-in via payload
AGGIUNTA sempre condizionale: solo se resolver trova base (stadio 3 categoria_cliente o stadio 0 promo) condizionale, simmetrico a L2
ESCLUSIONE skip (prezzo NULL, niente gate) skip skip

L1 — permesso override. Senza azione di processo prezzo_override_manuale sull'utente, il prezzo non puo' essere salvato manualmente. Codice errore: E_PRICING_OVERRIDE_NON_AUTORIZZATO (403, retryable=false: senza permesso non c'e' nulla da ritentare).

L2 — soglia variazione %. Il prezzo manuale viene confrontato con il prezzo del resolver (contratti_suggerisci_prezzo_riga). Il delta % deve restare entro la soglia configurata via parameter VENDITE_MAX_SCONTO_PCT / VENDITE_MAX_MAGGIORAZIONE_PCT con cascata estesa user → categoria_cliente → group → emittente → default (refactor 2026-05-15 cascata BA-aware). Se viola: E_PRICING_SCONTO_ECCESSIVO o E_PRICING_MAGGIORAZIONE_ECCESSIVA (403, retryable=true: il FE puo' offrire la CTA "Richiedi approvazione"). Codici stabili per distinguere direzione downstream (dashboard / log / pratiche); user_message generico "Variazione prezzo oltre il limite consentito per il tuo ruolo" (refactor 2026-05-20) — il detail riporta direzione esplicita "in diminuzione" / "in aumento" + percentuale + limite.

Fast path resolver per contratti (refactor 2026-05-20). Il pricing gate L2 invoca fn_resolve_prezzo_listino_v2 passando come 9° argomento il listino_versione_id del contratto (snapshot se ATTIVO, lookup dinamico ATTIVA/CHIUSA @ valido_dal con BOZZA esclusa per DRAFT, replicato via ContrattiRepository.get_listino_versione_attiva_alla_data). Questo attiva lo stadio CONTRATTO_LISTINO del resolver e impedisce il drift verso lo stadio CATEGORIA (che pesca da categorie_clienti_listini un listino diverso da quello del contratto). Senza fast path il check L2 confronterebbe il prezzo OVERRIDE con un prezzo categoria semanticamente non pertinente. Quando il fast path attivo trova il prezzo, l'output del resolver ha contratto_id / tipo_eccezione = NULL e tipo_variazione_applicata = 'NESSUNA' (nessun lookup contratto).

L3 — workflow approvazione. Quando il payload include richiesta_approvazione=true, una violazione L2 non solleva ma apre una pratica APPROVAZIONE_PREZZO e salva la riga con stato_approvazione_prezzo='PENDING' + pratica_approvazione_prezzo_id valorizzato. Il trigger DB trg_contratti_righe_a10_guard_pending_upd blocca modifiche struttura sulla riga finche' l'admin non chiude la pratica via POST /api/v1/vendite/righe-contratto/<riga_id>/approva-prezzo/ o POST /api/v1/vendite/righe-contratto/<riga_id>/rifiuta-prezzo/ (simmetrici agli endpoint preventivi /righe/<id>/...).

Il meta della pratica include sorgente='contratto' + riga_contratto_id per routing FE corretto degli endpoint approva/rifiuta. La coda GET /api/v1/vendite/approvazioni-prezzo/ espone item da entrambe le sorgenti (preventivi + contratti); ogni item include sorgente per permettere alla UI ApprovazioniPrezzoListView di dispatchare al path corretto.

Integrazione FE (ContrattoRigheDrawer.vue, simmetrico a PreventiviRigaForm.vue):

  • Il save normale (onSave) intercetta specificamente i codici E_PRICING_SCONTO_ECCESSIVO / E_PRICING_MAGGIORAZIONE_ECCESSIVA e mostra un banner inline (no toast) con la CTA "Richiedi approvazione".
  • Il click sulla CTA invoca onRichiediApprovazione che ri-tenta il save aggiungendo richiesta_approvazione: true al payload. In caso di riuscita la riga e' salvata in PENDING e l'operatore riceve un toast esplicito. Eventuali errori del retry tornano sul toast standard.
  • Per le righe gia' in PENDING il trigger DB _a10_guard_pending_upd blocca ogni modifica struttura: la UI mostra la pratica nella coda approvazioni dell'admin (vedi sopra) — l'operatore deve attendere l'esito o chiedere all'approver di rifiutare per riprovare.

Per i 3 tipi tipo_eccezione:

  • OVERRIDE su articolo del listino → workflow completo (L1+L2+L3)
  • AGGIUNTA fuori-listino → workflow attivo solo se il resolver trova comunque una base prezzo (matrice categoria_cliente_listino o promo). Senza base, il prezzo manuale e' accettato sotto L1 senza confronto.
  • ESCLUSIONE → workflow non applicabile (prezzo NULL per design).

Documenti contratto¶

Endpoint del motore documentale parametrico per la sorgente CONTRATTO. Risolvono il contesto comune (contratto + emittente fiscale + sorgente attiva) via helper condiviso apps.documenti.api.contesto_helpers.resolve_contesto_documentale (vedi api_documenti_helpers).

Metodo Path Effetto
GET /api/v1/vendite/contratti/<id>/documenti/ Lista documenti generati dal contratto (paginata, scope emittente)
POST /api/v1/vendite/contratti/<id>/documenti/anteprima/ Render PDF temporaneo, non persistito
POST /api/v1/vendite/contratti/<id>/documenti/genera/ Persiste PDF + record DB + evento GENERATO (per contratti già ATTIVI: ristampe successive all'attivazione)
GET /api/v1/vendite/contratti/<id>/documenti/<documento_id>/file/ Download PDF principale + evento SCARICATO
GET /api/v1/vendite/contratti/<id>/documenti/<documento_id>/allegati/ Lista files del documento (principale + allegati)
POST /api/v1/vendite/contratti/<id>/documenti/<documento_id>/allegati/ Append allegati multipart su documento esistente

L'attivazione iniziale (DRAFT→ATTIVO con generazione del documento originale) passa per il nuovo endpoint /emetti/ multipart (vedi sezione "Attivazione DRAFT→ATTIVO" sopra), non per documenti/genera/. Questo endpoint genera/ resta per ristampe/varianti successive su contratti già ATTIVI.

Payload opzionale per anteprima/ e genera/:

{
  "template_documento_id": 123,
  "tipo_documento_output_id": 2
}

Se template_documento_id non e' indicato, il service usa il template is_default=true per (sorgente=CONTRATTO, emittente_fiscale_id, tipo_documento_output_id). Il context builder backend e' CONTRATTO; il template iniziale e' documentato in template_contratto_iniziale.

Endpoint allegati/ (nuovi 2026-05-28):

  • GET: ritorna {"data": {"principale": {...}, "allegati": [{...}, {...}]}}. Consumato dal row-expand di DocumentiGeneratiSorgenteList per popolare filesPerDoc
  • POST: multipart con campo ripetuto allegati. Modalità append post-attivazione. Non rigenera il PDF principale, aggiunge solo file secondari al documento esistente. MIME/size validati dal service

Regole stampa contratto¶

  • In stato DRAFT, il frontend usa anteprima/: il PDF viene renderizzato ma non viene persistito in documenti.documenti_generati.
  • La transizione DRAFT → ATTIVO passa ora per l'endpoint dedicato POST /<id>/emetti/ (multipart), che in transaction.atomic() cambia stato (con freeze listino_versione_id via trigger) e persiste il PDF contrattuale + allegati come documenti_generati con sorgente=CONTRATTO. Invariante: stato=ATTIVO ⇒ almeno un record documentale generato.
  • Dopo l'attivazione, ristampe/download usano il documento salvato; non viene rigenerato il layout storico. Nuove versioni esplicite si ottengono via POST documenti/genera/.
  • Allegati post-attivazione: append via POST documenti/<doc_id>/allegati/. Non rigenera il principale.
  • La lista GET /documenti/ espone i documenti gia' generati per il contratto, ed e' la fonte usata dal drawer e dalla tabella ricerca per le ristampe.
  • La generazione richiede un emittente_fiscale_id sul contratto e almeno una versione PUBBLICATA attiva del template applicabile alla data corrente.

Regole¶

  1. Numero contratto generato dal service (mai in payload).
  2. Stato iniziale DRAFT; transizioni via endpoint dedicato. La transizione DRAFT -> ATTIVO genera e salva il documento contratto + fissa listino_versione_id alla versione corrente del listino.
  3. Identificativi (BA, istanza, utility) immutabili in update — per cambiarli si crea un nuovo contratto.
  4. Forma "senza_listino" valida a livello DB solo se esistono righe AGGIUNTA con prezzo_unitario valorizzato. Il guard di attivazione solleva E_CONTRATTO_NEGOZIATO_PURO_SENZA_RIGHE (422). Sostituisce i vecchi guard di "modalita' C" rimossi col refactor 2026-05-15.
  5. Profilo A — congelamento post-attivazione: dopo DRAFT → ATTIVO, tutti i campi pricing della testata (listino_id, listino_versione_id, tipo_variazione_globale, valore_variazione_globale) sono immutabili, cosi' come le eccezioni in contratti_righe. Tentativi di modifica sollevano E_CONTRATTO_CAMPI_BLOCCATI_POST_ATTIVAZIONE (409). Per modifiche sostanziali serve un nuovo contratto.
  6. Coerenza coppia variazione globale: tipo_variazione_globale e valore_variazione_globale entrambi NULL o entrambi NOT NULL (pre-validation _validate_variazione_globale_coppia_coerente).
  7. Coerenza prezzo/tipo_eccezione: ESCLUSIONE ↔ prezzo NULL, OVERRIDE/AGGIUNTA ↔ prezzo NOT NULL. Validato in service (pre-DB con messaggio parlante) e in DB (chk_contrighe_prezzo_per_tipo_eccezione).
  8. Tipo/classe utenza obbligatori per utility con dimensione (es. GAS, EE), vietati per utility commercio (Base). Coerenza classi_utenze.tipo_utenza_id = contratti_utilities.tipo_utenza_id imposta dal trigger DB.
  9. EXCLUDE no-overlap: un solo contratto attivo per (BA, istanza_utility, utility, ambito) su validita' sovrapposta. DRAFT-scope (2026-06-02): i contratti in DRAFT sono esclusi dal vincolo (colonna generata partecipa_overlap_snapshot = NOT abortito AND NOT draft). Conseguenze: due bozze sovrapposte sono ammesse, e una bozza puo' sovrapporsi a un contratto attivo (preparazione della successione); il blocco scatta solo all'attivazione (POST .../emetti/). All'emissione il service esegue un pre-check proattivo (fn_contratto_sovrapposto) che, se trova un incumbent attivo sovrapposto, solleva E_VENDITE_CONTRATTO_OVERLAP con un messaggio che nomina il contratto in conflitto (es. "il contratto CNT0000027 e' gia' attivo..."), prima che l'EXCLUDE sollevi l'errore generico.
  10. categoria_cliente_id_snapshot e' congelato alla creazione del contratto (dal trigger DB, che lo popola dal BA). Rappresenta la categoria commerciale del cliente al momento della stipula. Non e' modificabile in update. In risposta vengono esposti anche categoria_cliente_snapshot_codice e categoria_cliente_snapshot_descrizione (JOIN display).

Dipendenze DB¶

Tabelle: vendite.contratti, vendite.contratti_righe, vendite.contratti_utilities, vendite.contratti_righe_componenti (modello unificato BoM 2026-05-13, simmetrico a preventivi_righe_componenti).

Funzioni:

  • script.fn_generate_codice('contratto') — numero contratto (prefix CNT).
  • vendite.fn_contratto_riga_componenti_init(riga_id, emittente_sr_id, data_riferimento, componenti_overrides::jsonb) -> integer — auto-init componenti BoM idempotente. Default attivo=TRUE per tutti i componenti (BoM contratto immutabile, decisione 2026-05-13).
  • vendite.fn_contratto_riga_componenti_preview(articolo_id, uom_id, quantita_padre, data_riferimento, ba_id, utility_id, emittente_sr_id, classe_utenza_id) -> SETOF record — read-only STABLE, ritorna 14 colonne (vedi contratti_repository.preview_componenti_riga).
  • vendite.fn_resolve_prezzo_listino_v2(..., p_articolo_padre_contesto) — resolver bundle-aware usato dalla preview (vedi api_pricing.md).

Trigger autoritativi: come da tabella codici errore. Inoltre su contratti_righe_componenti:

  • trg_contratti_righe_propaga_qta_componenti — ricalcolo quantita componente al cambio quantita riga padre.
  • trgfn_contratti_righe_componenti_guard_pending — immutabilita' componenti quando stato_approvazione_prezzo = PENDING (L3 approvazioni prezzo).

Stati gestiti via config.stati_doc_contratti (DRAFT/ATTIVO/SOSPESO/CESSATO). Cessazione manuale solo con valido_al >= CURRENT_DATE; il job pgAgent fn_apply_chiusura_scadenze chiude i contratti scaduti via GUC app.cessazione_automatica='true'.
