OfferteService (Django)¶

Scopo¶

Facade applicativa CRUD per vendite.offerte_commerciali + eccezioni (mirror di contratti_righe) + utility 1:1 (estensione contratti_utilities), con gestione della state machine di processo (BOZZA / EMESSA / ACCETTATA / RIFIUTATA / ANNULLATA / SUPERATA) e propagazione fedele dei codici errore E_OFFERTA_* sollevati dai trigger DB.

Contesto¶

L'offerta commerciale e' lo specchio strutturale del contratto: stessa forma di testata (mono-utility, listino + versione, variazione globale), stesso enum tipo_eccezione, stessa cardinalita' utility (1:1). La fedelta' garantisce che il push offerta -> contratto in DRAFT sia copia 1:1 senza conversioni (step 8 brief DB, non ancora cablato).

La logica di business autoritativa vive in DB:

  • State machine: trigger trgfn_offerte_commerciali_guard_transizione verifica le transizioni contro config.stati_doc_offerte_transizioni e valorizza i timestamp di transizione + motivazione_rifiuto.
  • 5 CHECK eccezioni: replicati con nomi chk_offerte_eccezioni_*, identici alla logica contratti_righe.
  • UNIQUE: codice offerta, uid, utility 1:1 per offerta, eccezione unica per (offerta, articolo, tipo).

Il service e' sottile: applica solo pre-condizioni applicative (stato corrente, payload non vuoto, motivazione obbligatoria su transizioni negative) e traduce gli errori DB in ServiceError con codice originale.

Perimetro D6 (rev. 2026-05-25 PM) — completo¶

Tutti i metodi cablati. Step DB 1-9 atterrati:

  • step 1-4 + addendum (commit 2026-05-24): testata, eccezioni, utility 1:1, state machine, motivazione_rifiuto
  • step 5-7 (commit 2026-05-25 AM): codice automatico OFC-* via trigger, crea_revisione, list_revisioni
  • step 8-9 (commit 2026-05-25 PM): push_a_contratto + suite pgTAP completa lato DB

Il dominio offerta commerciale lato BE e' funzionalmente completo: restano solo cantieri FE (drawer, dialog, lista) e l'eventuale cablaggio del building block note partizionate sul nuovo target OFFERTA.

Input¶

Lookup e dettaglio¶

  • list_offerte(*, search, billing_account_id, stato_codice_interno, utility_id, listino_id, validita_dal_min, validita_dal_max, limit, offset, order_by, order_dir) -> (list\[OffertaRow\], int)
  • search opzionale; vuoto/whitespace-only -> nessun filtro; non vuoto -> min 3 char
  • order_by whitelist: vedi _ORDER_BY_OFFERTE
  • get_offerta(offerta_id) -> OffertaRow — arricchito con eccezioni[], utility (1:1, None se non ancora creato) e capability blob (available_actions[], can_edit_*, can_push_contratto*, non_editable_fields[], stato_codice) mergeato da repo.get_available_actions (wrapper su script.fn_available_actions_offerta, D7 2026-05-26). Il FE consuma il blob con useEntityCapabilities + mapAvailableActionsToDrawerActions, eliminando ogni state-machine hardcoded lato client.

Mutazione testata¶

  • crea_offerta(payload) -> OffertaRow — payload richiede emittente_fiscale_id, billing_account_id, istanza_utility_id, utility_id, listino_id, validita_dal. Il codice non va nel payload (rifiutato come unknown_key): lo genera il trigger DB trgfn_offerte_commerciali_gen_codice (BEFORE INSERT). Stato iniziale BOZZA risolto via repo.get_stato_id_by_codice(StatoOfferta.BOZZA). Sub-oggetto opzionale utility (D7, 2026-05-26): se valorizzato, _add_utility_inline esegue create_utility nella stessa transaction.atomic() della testata, ereditando istanza_utility_id/utility_id dalla testata se non specificati nel sub-payload. Niente piu' rischio di "offerta orfana di utility" del flusso a 2 round-trip.
  • aggiorna_offerta(offerta_id, payload) -> OffertaRow — solo in BOZZA. Sub-oggetto opzionale utility (D7, simmetria col create): _upsert_utility_inline distingue create vs update via repo.get_utility(offerta_id). Ramo update: filtra il payload sulla whitelist _UPDATE_KEYS_UTILITY (immutabili istanza_utility_id/utility_id). Ramo create: stesso _add_utility_inline di sopra. Payload {} rifiutato; payload con SOLO utility (zero campi testata) ammesso ed esegue solo l'upsert utility.
  • elimina_offerta(offerta_id) -> None — solo in BOZZA. Pulizia tecnica; l'annullamento di processo passa da annulla.

Transizioni di stato¶

  • emetti(offerta_id) -> OffertaRow — BOZZA -> EMESSA
  • registra_accettazione(offerta_id) -> OffertaRow — EMESSA -> ACCETTATA
  • registra_rifiuto(offerta_id, *, motivazione) -> OffertaRow — EMESSA -> RIFIUTATA + motivazione obbligatoria
  • registra_esito(offerta_id, *, esito, motivazione=None) -> OffertaRow — routing unificato per la view: esito IN ('ACCETTATA', 'RIFIUTATA') delega al metodo specifico
  • annulla(offerta_id, *, motivazione) -> OffertaRow — BOZZA -> ANNULLATA + motivazione obbligatoria

Push a contratto (step 8, 2026-05-25 PM)¶

  • push_a_contratto(offerta_id, *, pratica_id=None) -> OffertaPushResult — invoca vendite.fn_push_offerta_a_contratto(p_offerta_id, p_pratica_id). Guard applicativo ACCETTATA (defense-in-depth, il DB e' guard finale con E_OFFERTA_PUSH_STATO_NON_AMMESSO). Pattern A idempotenza: doppia chiamata su stessa offerta → E_OFFERTA_CONTRATTO_GIA_GENERATO propagato come code originale. Ritorna {contratto_id, contratto_codice, sorgente_uid} letto via repo.get_contratto_minimal (no coupling cross-service).

Revisioni (step 6-7, 2026-05-25)¶

  • crea_revisione(offerta_id, *, user=None) -> OffertaRow — invoca vendite.fn_crea_revisione_offerta(p_offerta_id, p_user). Guard applicativo EMESSA; il DB rifiuta con E_OFFERTA_REVISIONE_STATO_NON_AMMESSO propagato come code originale. Ritorna la nuova rev.N+1 (dettaglio completo via get_offerta).
  • list_revisioni(offerta_id) -> list[OffertaRow] — catena di revisioni che condividono il root con l'offerta passata. CTE ricorsiva ancestors → root → descendants. Lettura libera in ogni stato.

Mutazione sub-resource¶

  • Eccezioni: list_eccezioni (libera), crea_eccezione / aggiorna_eccezione / elimina_eccezione (solo BOZZA + ownership URL)
  • Utility 1:1: get_utility (libera), crea_utility / aggiorna_utility (solo BOZZA + UNIQUE su offerta_id)

Output¶

Tutti i metodi di mutazione restituiscono la versione aggiornata della testata via get_offerta(offerta_id) (read-after-write). I metodi sub-resource restituiscono il record creato/aggiornato (con display fields da JOIN backend).

Errori sono ServiceError con code semantico:

  • E_VENDITE_VALIDATION — struttura payload, payload vuoto, esito non valido, motivazione mancante, search < 3 char, order_by fuori whitelist
  • E_VENDITE_NOT_FOUND — offerta/eccezione/utility non trovata; mismatch ownership URL
  • E_VENDITE_DUPLICATO — UNIQUE violations
  • E_VENDITE_FK — FK violations
  • E_OFFERTA_* — codici sollevati dai trigger DB, propagati come code originale via regex _DB_ERROR_CODE_RE sul MESSAGE del trigger

Regole¶

  1. Stato BOZZA = unico stato editabile per testata, eccezioni, utility. Defense-in-depth applicativa via _assert_stato_corrente(expected=_STATI_EDITABILI); il trigger DB e' guard finale.
  2. Annullamento solo da BOZZA, rifiuto solo da EMESSA. State machine asimmetrica: niente BOZZA -> RIFIUTATA (non esiste un "no del cliente" prima dell'emissione) ne' EMESSA -> ANNULLATA (correzioni post-emissione passano da revisione che genera SUPERATA, step 7 DB).
  3. Motivazione obbligatoria per registra_rifiuto e annulla: stringa non vuota post-strip; whitespace-only rifiutato.
  4. Payload {} rifiutato in tutti i PATCH/UPDATE (_guard_payload_non_vuoto): niente no-op silenziosi.
  5. Anti-tampering URL su sub-resource: il service verifica eccezione.offerta_id == offerta_id (e analogo per utility) prima di mutare. Mismatch -> 404 esplicito.
  6. Codici errore DB propagati come code originale (fix critico rev. 2026-05-25 analisi codice): senza propagazione il FE non puo' discriminare per codice (es. mostrare dialog "versione listino non ATTIVA" diverso da "transizione non ammessa"). Estrazione via regex \b(E_[A-Z][A-Z0-9_]+)\b sul MESSAGE del trigger.
  7. Codice offerta dal payload finche' step 5 DB non chiude. Dopo diventera' generato e immutabile (lock_columns).
  8. Costanti di stato in StatoOfferta (BOZZA/EMESSA/ACCETTATA/ RIFIUTATA/ANNULLATA/SUPERATA); niente stringhe magiche sparse.

Dipendenze DB¶

Tabelle:

  • vendite.offerte_commerciali
  • vendite.offerte_commerciali_eccezioni
  • vendite.offerte_commerciali_utilities
  • config.stati_doc_offerte (lookup id stato per codice_interno)
  • config.stati_doc_offerte_transizioni (autoritativa per state machine)

Trigger autoritativi:

  • trgfn_offerte_commerciali_guard_transizione — state machine + guard versione listino + valorizzazione data_* di transizione

Funzioni:

  • script.fn_generate_codice('offerta_commerciale') — step 5 DB (invocata dal trigger BEFORE INSERT, non chiamata direttamente dal service)
  • vendite.fn_crea_revisione_offerta(p_offerta_id, p_user) — step 7 DB, invocata da repo.crea_revisione
  • vendite.fn_push_offerta_a_contratto(p_offerta_id, p_pratica_id) — step 8 DB, invocata da repo.push_a_contratto

Helper applicativi (apps.core):

  • apps.core.services.payload_helpers.PayloadValidator — guard payload
  • apps.core.services.payload_helpers.map_integrity_error — UNIQUE/FK mapping
  • apps.core.services.error_manager.ErrorManager — raise/require coerente
