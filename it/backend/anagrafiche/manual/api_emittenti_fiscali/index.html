API Emittenti Fiscali (Anagrafiche)¶

Scopo¶

Endpoint REST per la gestione degli emittenti fiscali. L'emittente fiscale e' un ruolo specializzato del soggetto base (pattern soggetti -> soggetti_ruoli -> emittenti_fiscali, relazione 1:1 via soggetto_ruolo_id, codice ruolo EF).

Rappresenta l'identita' fiscale che compare nei documenti emessi dal sistema e consente la gestione multi-emittente (piu' soggetti emittenti nella stessa istanza).

Contesto¶

Tutti gli endpoint risiedono sotto /api/v1/anagrafiche/emittenti-fiscali/.

L'autenticazione avviene tramite token JWT (Authorization: Bearer <token>). Le risposte seguono l'envelope standard {"data": ...} per il successo e {"error": {"code": "...", "message": "..."}} per gli errori.

Accesso riservato agli amministratori: tutte le view ereditano da AdminAPIView (apps.core.api.base_views), che applica IsAdminZeroERP (controllo diretto su ruolo_sistema = "ADMIN" con bypass del resolver aree). Un utente non admin riceve 403 Forbidden.

Base URL¶

/api/v1/anagrafiche/emittenti-fiscali/

Headers comuni¶

Header Valore Note
Authorization Bearer <jwt> Token di accesso valido (utente con ruolo_sistema = ADMIN)
Content-Type application/json Richiesto per POST/PATCH
Accept application/json Opzionale, default JSON

Sommario endpoint¶

1 GET /emittenti-fiscali/ Lista paginata + filtro attivo
2 GET /emittenti-fiscali/<id>/ Dettaglio emittente

4 PATCH /emittenti-fiscali/<id>/ Aggiorna emittente
5.1 GET /emittenti-fiscali/<id>/billing-account/ Lista mapping BA
5.2 POST /emittenti-fiscali/<id>/billing-account/ Crea mapping BA o default globale
5.3 DELETE /emittenti-fiscali/<id>/billing-account/<mapping_id>/ Elimina mapping BA
5.4 GET /emittenti-fiscali/<id>/billing-account/summary/ Summary mapping (has_default + count_specifici)
6.1 GET /emittenti-fiscali/<id>/utilities/ Lista record utility per emittente
6.2 POST /emittenti-fiscali/<id>/utilities/ Crea record utility
6.3 PATCH /emittenti-fiscali/<id>/utilities/<record_id>/ Aggiorna record utility
6.4 DELETE /emittenti-fiscali/<id>/utilities/<record_id>/ Elimina record utility

Codici errore (envelope {"error": {"code", "message"}})¶

Codice HTTP Descrizione
E_AUTH_REQUIRED 401 Token JWT mancante o non valido
E_FORBIDDEN_ROLE 403 Utente autenticato ma non admin
E_ANAG_VALIDAZIONE 400 Campi obbligatori mancanti o non validi
E_ANAG_NOT_FOUND 404 Risorsa non trovata o non appartenente al padre
E_ANAG_DUPLICATO 409 Vincolo univocita' violato (codice, soggetto, default)
E_BA_EMITTENTE_CON_STORIA 409 Sub-resource 5: si sta spostando un billing account che ha gia' fatture o commesse. Nasce nel database (20260826-49) e arriva al client senza codice Python: la classe CONFLITTO_STATO a catalogo lo mappa a 409 dalla catena centralizzata. ⚠️ Non c'e' la chiave campo nel contesto — su un conflitto di stato non esiste un input da accendere
E_EMITTENTE_DEFAULT_SINGLETON 409 Sub-resource 5: si sta cancellando il gestore globale, che deve sempre esistere e non e' mai rimovibile

Eccezioni inattese vengono normalizzate dal middleware error-handling-api in envelope {"error": {"code": "E_INTERNAL", ...}} con HTTP 500.

1. Lista emittenti fiscali¶

Restituisce l'elenco paginato degli emittenti fiscali con ricerca full-text e filtro opzionale per stato attivo.
Metodo GET
URL /api/v1/anagrafiche/emittenti-fiscali/
Throttling is_search_endpoint = True (DRF rate limit per ricerca)

1.1 Parametri query¶

Parametro Tipo Obbligatorio Default Descrizione
search string No — Ricerca ILIKE su codice, descrizione, ragione_sociale_completa, P.IVA, CF
attivo bool No — Filtra per flag attivo (true/false). Se omesso: nessun filtro
limit int No 25 Risultati per pagina (max: 200)
offset int No 0 Offset per paginazione
order_by string No descrizione Campo di ordinamento (vedi sotto)
order_dir string No asc Direzione: asc / desc

Colonne ordinabili: codice, descrizione, ragione_sociale_completa, attivo, data_insert.

3. Crea emittente fiscale¶
Metodo POST
URL /api/v1/anagrafiche/emittenti-fiscali/

3.1 Body richiesta¶

Campo Tipo Obbligatorio Note
soggetto_id uuid Si UUID di un anagrafiche.soggetti esistente con P.IVA valorizzata
codice string Si Univoco; immutabile dopo la creazione (lock_columns trigger)
descrizione string Si Etichetta visibile
attivo bool No Default DB true
regime_fiscale_rf string No Codice regime fiscale RF del tracciato FE/SdI (es. RF01)
bollo_auto bool No Calcolo bollo automatico
bollo_soglia numeric No Soglia per applicare il bollo
rounding_policy enum No Uno tra: UP, DOWN, HALF_UP, HALF_DOWN (allineato alla matrice utility)
valuta_id int No FK config.valute

3.2 Comportamento¶

  1. Validazione campi obbligatori (soggetto_id, codice, descrizione).
  2. Validazione P.IVA del soggetto: query su anagrafiche.soggetti.partita_iva; se NULL/empty -> E_ANAG_VALIDAZIONE 400. Requisito legale per emissione fattura SDI.
  3. Apertura transazione atomica.
  4. Se il soggetto non ha ancora un ruolo EF, viene creato tramite script.fn_get_or_create_soggetto_ruolo.
  5. Insert nella tabella anagrafiche.emittenti_fiscali. I trigger DB gestiscono audit, tx_id, normalize, storicizzazione.
  6. Alla creazione del primo emittente, il trigger default_bootstrap inserisce automaticamente il record di default in emittenti_fiscali_billing_account con billing_account_id = NULL e is_default = true.

3.3 Esempio cURL¶

curl -X POST "https://api.example.com/api/v1/anagrafiche/emittenti-fiscali/" \
     -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{
       "soggetto_id": "019bac81-3f96-7ce8-a086-7e0bd0a2fec0",
       "codice": "EF-001",
       "descrizione": "Sede principale",
       "regime_fiscale_rf": "RF01",
       "bollo_auto": true,
       "bollo_soglia": 77.47
     }'

3.4 Risposta (200)¶

{
  "data": {
    "id": 1,
    "soggetto_ruolo_id": 50
  }
}

3.5 Errori specifici¶

Codice HTTP Descrizione
E_ANAG_VALIDAZIONE 400 soggetto_id, codice o descrizione mancanti, oppure soggetto senza P.IVA
E_ANAG_DUPLICATO 409 Esiste gia' un emittente per questo soggetto o codice

4. Aggiorna emittente fiscale¶
Metodo PATCH
URL /api/v1/anagrafiche/emittenti-fiscali/<emittente_id>/

4.1 Campi editabili¶

descrizione, attivo, regime_fiscale_rf, bollo_auto, bollo_soglia, rounding_policy, valuta_id.

Nota: il campo codice e' bloccato dal trigger DB lock_columns (errore CODICE_NON_MODIFICABILE). Il backend lo ignora se incluso nel payload tramite whitelist _UPDATE_ALLOWED.

4.2 Regole¶

  • I campi nullable (es. regime_fiscale_rf, bollo_soglia) accettano stringhe vuote che vengono normalizzate a NULL.
  • rounding_policy accetta solo i valori enum UP, DOWN, HALF_UP, HALF_DOWN (allineato ai metodi della matrice utility).
  • Disattivazione (attivo = false): rifiutata dal trigger DB se l'emittente ha record collegati in emittenti_fiscali_billing_account, emittenti_fiscali_utilities, parameter_overrides o user_emittenti_fiscali.

4.3 Esempio cURL¶

curl -X PATCH "https://api.example.com/api/v1/anagrafiche/emittenti-fiscali/1/" \
     -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{ "descrizione": "Sede principale 2026", "split_payment_default": true }'

4.4 Risposta (200)¶

{ "data": { "updated": true } }

4.5 Errori specifici¶

Codice HTTP Descrizione
E_ANAG_NOT_FOUND 404 Emittente non trovato o nessun campo modificato

5. Sub-resource: mapping Billing Account → Emittente¶

Gestione del mapping emittenti_fiscali_billing_account per associare uno o piu' billing account a un emittente fiscale, oppure definire il default globale (record con billing_account_id IS NULL e is_default = true).

5.0 Regole DB¶

  • CHECK constraint chk_emittenti_fiscali_ba_default: (is_default = true AND billing_account_id IS NULL) OR (is_default = false AND billing_account_id IS NOT NULL)
  • UNIQUE su billing_account_id: un BA puo' essere mappato a un solo emittente.
  • UNIQUE WHERE is_default = true: un solo default globale in tutto il sistema.
  • Trigger default_guard su INSERT/UPDATE/DELETE per rispetto invarianti.
  • ⭐ Trigger trg_emittenti_fiscali_ba_a10_guard_storia_emittente_ins_upd_dlt (dal 20260826-49): un billing account che ha gia' fatture o commesse non cambia piu' emittente. ⛔ E il movimento da presidiare non e' solo l'INSERT: il backend non espone nessun UPDATE sul mapping, quindi «spostare un cliente da un emittente all'altro» si fa con DELETE + INSERT — ed e' la cancellazione a fare il danno.
  • Tutte le richieste sono validate dal service tramite _resolve_soggetto_ruolo_id (l'emittente padre deve esistere) e, su DELETE, da belongs_to_emittente (il mapping deve appartenere all'emittente atteso, fail safe).

Il backend non espone is_default come campo modificabile: viene derivato automaticamente da billing_account_id (NULL → default globale, valorizzato → mapping specifico).

Capability di riga — can_remove e il motivo del blocco¶

Ogni riga porta tre campi che riguardano la sola azione «rimuovi»:

Campo Tipo Significato
can_remove bool false quando la riga non si puo' togliere
rimozione_blocco_reason string | null codice macchina del primo motivo. null = ammesso
rimozione_blocco_reason_key string | null chiave i18n del tooltip. Il testo non viaggia mai nel payload

⚠️ can_remove NON e' piu' true per costruzione, ed e' il cambiamento del 2026-08-27: prima era scritto a mano nel service, e da quando un billing account con storia non cambia piu' emittente era diventato una promessa falsa — l'operatore scopriva il divieto premendo, dopo aver confermato un dialog. Chi consuma questa lista non deve piu' presumerlo.

⭐ I tre campi vengono dalla stessa funzione che il database usa per rifiutare — script.fn_check_ba_cambio_emittente, chiamata in LATERAL sulla riga e chiamata dalla madre fn_guard_ba_cambio_emittente per sollevare l'errore. ⇒ Tooltip e rifiuto non «coincidono oggi»: non possono divergere, perche' la regola sta scritta in un posto solo (linee-guida-sql §12.5.2).

I due motivi oggi a contratto — l'elenco lo decide il database, non questa pagina, e puo' crescere senza che il backend cambi:

reason codice sollevato Quando
BA_CON_STORIA E_BA_EMITTENTE_CON_STORIA il cliente ha fatture o commesse e l'emittente cambierebbe davvero
DEFAULT_SINGLETON E_EMITTENTE_DEFAULT_SINGLETON riga del gestore globale: deve sempre esistercene una, quindi non si toglie mai

⛔ Il predicato di un mapping specifico e' una COPPIA, e la meta' che si dimentica e' la prima: togliere l'aggancio fa ricadere il billing account sul gestore globale, quindi il cambio di emittente esiste solo se l'emittente della riga e' diverso da quello del default. Se coincidono non si sposta nessun documento e la rimozione resta ammessa — e' manutenzione ordinaria. ⚠️ Su un'installazione con un solo emittente questo e' il caso normale: chi consumasse un can_remove derivato dalla sola presenza di storia spegnerebbe il gesto su quasi tutte le righe, tutte a torto.

⛔ Il client non ricalcola il motivo e non compone il testo: rende reason_key (con ripiego su reason se la chiave manca) e disabilita l'azione. Il BA mapping non ha PATCH, quindi can_update/can_configure non sono applicabili.

6. Sub-resource: utilities per emittente fiscale¶

Gestione della matrice emittenti_fiscali_utilities (parametri di fatturazione per ogni coppia emittente x utility: soglie minime, decimali e metodo di arrotondamento).

6.0 Regole DB¶

  • UNIQUE (emittente_soggetto_ruolo_id, utility_id): una sola riga per coppia.
  • Trigger child_requires_active_parent: l'emittente padre deve essere attivo.
  • Trigger guard_utility_tipo_ruolo: la utility deve essere ammessa per il ruolo EF (matrice config.utilities_tipi_ruolo, fail-open se la utility non ha alcuna configurazione di matrice).
  • Validazione di proprieta' (record figlio appartiene all'emittente padre) applicata su PATCH e DELETE tramite _verify_record_ownership.

Nota lookup utility (UI): la combo di scelta utility nel frontend usa il componente core riusabile UtilityPerRuoloSelect, che chiama l'endpoint GET /api/v1/core/lookup/tipi-ruolo/EF/utilities/. L'endpoint applica filtro strict sulla matrice config.utilities_tipi_ruolo: ritorna solo utility con riga ATTIVA per il tipo_ruolo_codice indicato e nel periodo di validita' corrente. Coerente con il trigger DB script.fn_guard_utility_tipo_ruolo, evitando errori E_UTILITY_RUOLO_NON_AMMESSO lato UI.

6.1 Lista matrice utility per emittente¶
Metodo GET
URL /api/v1/anagrafiche/emittenti-fiscali/<emittente_id>/utilities/

Pattern slot/override: ritorna SEMPRE tutte le utility ammesse per il ruolo EF (da config.utilities_tipi_ruolo), con sovrapposti i parametri specifici dell'emittente (da anagrafiche.emittenti_fiscali_utilities) solo dove esistono. Fase 4 — capability di riga data-driven:

Campo Tipo Quando true
can_configure bool Slot vuoto (record_id == null) + emittente.attivo == true + utility_attiva == true. L'admin puo' creare la configurazione
can_update bool Record configurato (record_id != null). L'admin puo' modificare i parametri
can_remove bool Record configurato (record_id != null). L'admin puo' rimuovere

Il FE consuma le capability per gating UI (mostra/nasconde "Configura"/"Modifica"/"Rimuovi" nel RowActionsMenu) invece di derivare da record_id. L'autorita' resta il trigger DB (child_requires_active_parent, guard_utility_tipo_ruolo): le capability sono preview UX, non garanzia (race tra sessioni).

Il campo utility_attiva: bool proietta config.utilities.attivo (fonte primaria del flag globale di disattivazione utility).

Note di migrazione¶

  • Le rotte sono registrate in apps/anagrafiche/api/urls.py.
  • Le view ereditano da AdminAPIView: skip_area_check = True, nessun area_funzionale necessario; il check di autorizzazione si limita a IsAdminZeroERP (ruolo sistema ADMIN o superuser Django).
  • Il sub-resource utilities/lookup/ deve restare registrato prima delle rotte <int:emittente_id>/utilities/ in urls.py, altrimenti Django risolverebbe lookup come emittente_id letterale.
  • Helper di service _verify_record_ownership (modulo emittenti_fiscali_service) e' condiviso da EmittentiFiscaliBillingAccountService e EmittentiFiscaliUtilitiesService per evitare duplicazione del pattern "resolve padre + verifica appartenenza".
  • I test mockano IsAdminZeroERP.has_permission per bypassare il check ADMIN in CI; sono presenti test 403 specifici sia per l'endpoint principale che per i sub-resource BA e Utilities.
