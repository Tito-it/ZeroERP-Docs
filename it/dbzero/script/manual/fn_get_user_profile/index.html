Fn get user profile

Documentazione Concettuale -- Funzione script.fn_get_user_profile¶

Vedi anche

Funzione base:

script.fn_get_soggetto_dati_by_ruolo

Approfondimento tabelle:

anagrafiche.risorse_umane_auth_user anagrafiche.risorse_umane anagrafiche.soggetti anagrafiche.emittenti_fiscali config.user_emittenti_fiscali config.qualifiche config.unita_organizzative

Approfondimento viste modello:

anagrafiche.vw_risorse_umane_dettaglio

La funzione script.fn_get_user_profile(p_auth_user_id INTEGER) restituisce un JSONB con il profilo completo dell'utente loggato: dati auth_user, ruolo sistema, risorse umane (con qualifica e unita' organizzativa risolte), soggetto anagrafico (con dati societari se presenti), e emittente fiscale associato.

E' progettata come unico punto di accesso per l'endpoint GET /api/v1/core/me/ del frontend, aggregando in una singola chiamata DB tutti i dati necessari per il profilo utente.

🎯 Scopo Principale¶

  • Profilo utente completo in una chiamata: evita al backend di orchestrare query multiple per comporre il profilo.

  • 6 blocchi JSONB strutturati:

  • utente — dati da auth_user
  • ruolo_sistema — enum dalla tabella ponte
  • risorse_umane — dettaglio risorsa umana con qualifica e UO risolti
  • soggetto — dati anagrafici completi (delegati a fn_get_soggetto_dati_by_ruolo)
  • emittente — dati emittente fiscale + soggetto della ditta (null se non associato)

  • permessi_area — mappa {schema_db: livello_accesso} per tutte le aree attive (delegata a fn_get_user_permissions_map)

  • Riuso di fn_get_soggetto_dati_by_ruolo: i blocchi soggetto e emittente sono generati dalla stessa funzione, garantendo output uniforme con tutti gli ID e le descrizioni risolte.

  • Risoluzione emittente intelligente: prima cerca nella whitelist user_emittenti_fiscali (primo attivo), poi fallback sul gestore globale definito in emittenti_fiscali_billing_account (riga con billing_account_id IS NULL e is_default = true).

Parametri di Input¶

Nome Tipo Obbligatorio Descrizione
p_auth_user_id INTEGER Si ID dell'utente Django (auth_user.id). Deve essere > 0.

Guard di validazione:

Condizione Codice errore Messaggio
p_auth_user_id NULL o <= 0 E_ADMIN_VALIDAZIONE p_auth_user_id obbligatorio e > 0
auth_user non trovato E_ADMIN_VALIDAZIONE auth_user con id=X non trovato
Nessun record risorse_umane_auth_user E_ADMIN_VALIDAZIONE Nessun record risorse_umane_auth_user
ruolo_sistema = DISABILITATO E_UTENTE_DISABILITATO Utente disabilitato: ruolo_sistema=DISABILITATO
Nessun record risorse_umane E_ADMIN_VALIDAZIONE Nessun record risorse_umane
risorse_umane.attivo = false E_UTENTE_DISABILITATO Utente disabilitato: risorsa umana non attiva
CURRENT_DATE < valido_dal E_UTENTE_NON_ATTIVO Utente non ancora attivo
CURRENT_DATE > valido_al E_UTENTE_SCADUTO Utente scaduto

Tutti i guard usano script.fn_log_and_raise_error (errori loggati in dbops.error_log).

Dettaglio blocco soggetto¶

Output completo di fn_get_soggetto_dati_by_ruolo(risorse_umane.soggetto_ruolo_id), convertito in JSONB tramite row_to_json. Vedi documentazione della funzione base per l'elenco completo delle 42 colonne.

Dettaglio blocco emittente¶

Se un emittente fiscale e' associato all'utente, il blocco contiene:

Campi specifici emittente:

Chiave Tipo Fonte
emittente_fiscale_id BIGINT emittenti_fiscali.id
emittente_fiscale_uid UUID emittenti_fiscali.uid
emittente_codice VARCHAR emittenti_fiscali.codice
emittente_descrizione VARCHAR emittenti_fiscali.descrizione
user_emittente_fiscale_id BIGINT user_emittenti_fiscali.id (null se fallback)
regime_fiscale_rf VARCHAR emittenti_fiscali.regime_fiscale_rf (codice RF del tracciato FE/SdI)
valuta_id INTEGER emittenti_fiscali.valuta_id

Campi soggetto emittente: tutti i campi di fn_get_soggetto_dati_by_ruolo(emittenti_fiscali.soggetto_ruolo_id), mergiati nello stesso oggetto JSON.

Se nessun emittente e' associato, emittente e' null.

Dettaglio blocco permessi_area¶

Mappa JSONB con una chiave per ogni area funzionale attiva (config.aree_funzionali.schema_db). Generata da fn_get_user_permissions_map(p_auth_user_id).

Chiave Tipo Descrizione
<schema_db> TEXT Livello accesso: TUTTO, SCRITTURA, LETTURA, BLOCCATO

Catena di risoluzione per area (delegata a fn_resolve_livello_area):

  1. ruolo_sistema → ADMIN = TUTTO, DISABILITATO = BLOCCATO
  2. Override utente area (config.user_override_aree) se presente e valido
  3. Profilo reparto (config.profili_reparto_aree) ereditato dalla UO
  4. Default → BLOCCATO

Flusso Logico Interno¶

  1. Validazione parametro: guard su NULL e <= 0.

  2. Blocco utente: lettura da auth_user (id, username, first_name, last_name, email). Se utente non esiste → no_data_found.

  3. Risorse umane: risoluzione catena risorse_umane_auth_user → risorse_umane con LEFT JOIN su qualifiche e unita_organizzative. Se nessun record ponte → no_data_found.

  4. Blocco soggetto: chiamata a fn_get_soggetto_dati_by_ruolo(soggetto_ruolo_id) e conversione in JSONB.

  5. Risoluzione emittente (revisione 07-04-2026):

  6. 4a. Whitelist: cerca il primo user_emittenti_fiscali attivo per l'utente (ordine id), con JOIN su emittenti_fiscali attivo. Imposta sia v_ef_id che v_uef_id.
  7. 4b. Fallback gestore globale: se whitelist vuota, cerca la riga in anagrafiche.emittenti_fiscali_billing_account con billing_account_id IS NULL AND is_default = true, joinando su emittenti_fiscali per ottenere la PK reale (ef.id) filtrando per attivo = true. v_uef_id resta NULL (il blocco non riflette un'associazione personale).
  8. Se trovato: lettura campi emittente + fn_get_soggetto_dati_by_ruolo(ef.soggetto_ruolo_id), merge in unico oggetto JSONB.
  9. Se non trovato: emittente = null.

Cambiamento rispetto alla versione precedente: il vecchio fallback usava "emittente unico attivo" (SELECT COUNT(*) WHERE attivo = true = 1), che era ambiguo per installazioni multi-tenant con N>1 emittenti e richiedeva un full scan. Il nuovo fallback usa la convenzione del gestore globale (BA NULL + is_default=true), coerente con anagrafiche.fn_get_emittente_fiscale_pk.

  1. Mappa permessi area: chiamata a fn_get_user_permissions_map(p_auth_user_id) che risolve il livello per ogni area funzionale attiva.

  2. Composizione finale: jsonb_build_object con le 6 chiavi.

Esempi di Utilizzo¶

-- 1) Profilo completo dell'utente con id=1
SELECT script.fn_get_user_profile(1);

-- 2) Estrarre solo il blocco soggetto
SELECT script.fn_get_user_profile(1) -> 'soggetto';

-- 3) Username e ragione sociale emittente
SELECT
    script.fn_get_user_profile(1) -> 'utente' ->> 'username' AS username,
    script.fn_get_user_profile(1) -> 'emittente' ->> 'ragione_sociale_completa' AS ditta;

-- 4) Uso dal backend Django (endpoint /api/v1/core/me/)

Caratteristiche Tecniche¶

  • Volatilita': STABLE — non modifica dati.
  • Linguaggio: PL/pgSQL
  • Output: JSONB (flessibile, estendibile senza modifiche alla signature).
  • Dipendenze: script.fn_get_soggetto_dati_by_ruolo, script.fn_get_user_permissions_map (devono esistere).
  • Errori: invalid_parameter_value per input invalido, no_data_found per utente/risorsa umana inesistente.
