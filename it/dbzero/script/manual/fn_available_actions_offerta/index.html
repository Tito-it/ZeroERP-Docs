fn_available_actions_offerta¶

Scopo¶

Restituisce in un unico JSONB tutte le capability dell'offerta commerciale necessarie al detail endpoint BE. Permette ai drawer Vue di eliminare qualsiasi ricalcolo di stato/transizioni lato client.

Pattern data-driven capability layer: specchio strutturale di fn_available_actions_preventivo, adattato al dominio offerte commerciali.

Differenze rispetto al preventivo:

  • Le transizioni manuali vengono lette da config.stati_doc_offerte_transizioni (stesso schema di config.transizioni_stati_preventivi).
  • I check can_push_contratto e can_genera_ordine sono cross-dominio (EXISTS su vendite.contratti.offerta_id e su vendite.ordini.documento_origine_*), a differenza di can_push_commessa del preventivo che usa solo lo stato e rinvia il check cross-dominio a Fase 3.
  • Le azioni speciali hardcoded sono crea_revisione (EMESSA), push_contratto e genera_ordine (entrambe ACCETTATA). Tutte hanno target_state: null e appaiono in available_actions (non solo come flag).
  • Mutua esclusività contratto/ordine (rev 2026-06-08): push_contratto e genera_ordine hanno la stessa condizione di abilitazione (ACCETTATA + nessun contratto + nessun ordine generati dall'offerta) e sono quindi mutuamente esclusive — un'offerta ne genera al massimo una: la prima generazione disabilita anche l'altra. Vedi brief-db-univocita-offerta-ordine §10 (docs/it/dev/work-done/brief-db-univocita-offerta-ordine).

Vedi anche

  • trgfn_offerte_commerciali_guard_transizione — guard transizioni (regola reale)
  • stati_doc_offerte_transizioni — matrice transizioni + meta UI
  • fn_push_offerta_a_contratto — esegue il push (guard idempotenza reale)
  • fn_crea_revisione_offerta — esegue la revisione

Schema¶

script (cross-dominio: legge vendite.*, config.*).

Firma¶

script.fn_available_actions_offerta(
    p_offerta_id vendite.offerte_commerciali.id%TYPE  -- bigint
) RETURNS jsonb

Parametri¶

Parametro Tipo Obbligatorio Descrizione
p_offerta_id bigint Sì ID dell'offerta. Ritorna NULL se non esiste (gestito dal BE come 404).

Output¶

jsonb con le seguenti chiavi (contratto API stabile):

{
    // Lista azioni manuali + speciali disponibili dallo stato corrente.
    // Vuota (\[\]) per stati terminali (ACCETTATA con contratto O ordine, RIFIUTATA, ANNULLATA, SUPERATA).
    // Costruita da config.stati_doc_offerte_transizioni.meta + azioni hardcoded.
    "available_actions": [
        {
            "key": "emetti",
            "target_state": "EMESSA",          // null per azioni speciali (crea_revisione, push_contratto, genera_ordine)
            "label_key": "offerte.azione_emetti",
            "severity": "success",
            "icon": "pi pi-send",
            "requires_confirm": true,
            "requires_motivazione": false       // true per annulla e rifiuta
        }
        // ...
    ],
    "can_change_state":             true,    // true se esiste almeno un'azione
    "can_edit_testata":             true,    // true solo in BOZZA
    "can_edit_eccezioni":           true,    // true solo in BOZZA
    "can_edit_utility":             true,    // true solo in BOZZA (utility 1:1 inline)
    "can_create_revisione":         false,   // true solo in EMESSA
    // push_contratto e genera_ordine: MUTUAMENTE ESCLUSIVE — stessa abilitazione
    // (ACCETTATA + nessun contratto + nessun ordine). can_push == can_genera sempre.
    "can_push_contratto":           false,   // true solo in ACCETTATA senza contratto NE ordine
    "can_push_contratto_reason":    "OFFERTA_NON_ACCETTATA",  // null se can_push=true
    "can_push_contratto_reason_key": "offerte.push_reason.non_accettata", // null se can_push=true
    "can_genera_ordine":            false,   // true solo in ACCETTATA senza ordine NE contratto
    "can_genera_ordine_reason":     "OFFERTA_NON_ACCETTATA",  // null se can_genera=true
    "can_genera_ordine_reason_key": "offerte.push_reason.non_accettata", // null se can_genera=true
    "non_editable_fields":          \[...\],   // vedi dettaglio sotto
    "stato_codice":                 "BOZZA"

Dettaglio available_actions per stato¶

stato_codice Azioni in available_actions Note
BOZZA emetti, annulla Da matrice transizioni
EMESSA accetta, rifiuta, crea_revisione crea_revisione hardcoded
ACCETTATA (né contratto né ordine) push_contratto, genera_ordine Hardcoded, mutuamente esclusive: entrambe esposte finché l'offerta è «vergine»
ACCETTATA (con contratto o ordine) [] Generata una delle due, entrambe spariscono (mutua esclusività)
RIFIUTATA [] Terminale
ANNULLATA [] Terminale
SUPERATA [] Terminale tecnico (sostituita da revisione successiva)

Reason di can_push_contratto / can_genera_ordine¶

Le due capability condividono l'abilitazione (ACCETTATA + nessun contratto + nessun ordine), quindi can_push_contratto == can_genera_ordine sempre. Quando bloccate, il reason segue una priorità own-doc first (la propria sorgente prima dell'altra, poi lo stato). I reason_key i18n sono riusati.

Caso can_* can_push_contratto_reason can_genera_ordine_reason
ACCETTATA, né contratto né ordine true null null
ACCETTATA, contratto già generato false OFFERTA_CONTRATTO_GIA_GENERATO OFFERTA_CONTRATTO_GIA_GENERATO
ACCETTATA, ordine già generato false OFFERTA_ORDINE_GIA_GENERATO OFFERTA_ORDINE_GIA_GENERATO
Qualsiasi altro stato false OFFERTA_NON_ACCETTATA OFFERTA_NON_ACCETTATA

reason_key: offerte.push_reason.gia_generato (contratto), offerte.push_reason.ordine_gia_generato (ordine), offerte.push_reason.non_accettata (stato).

Dettaglio non_editable_fields¶

Due famiglie di immutabilità:

Famiglia Campi
Sempre immutabili (gestiti da trigger transizione stato) codice, uid, revisione_numero, revisione_padre_id, stato_doc_offerta_id, data_emissione, data_accettazione, data_rifiuto, data_annullamento, motivazione_rifiuto
Bloccati fuori BOZZA emittente_fiscale_id, billing_account_id, istanza_utility_id, utility_id, listino_id, listino_versione_id, valore_variazione_globale, tipo_variazione_globale, validita_dal, validita_al, meta

Risultato per stato:

Stato non_editable_fields
BOZZA Solo famiglia "sempre immutabili" (10 campi)
Tutti gli altri Unione delle due famiglie (21 campi)

Algoritmo¶

  1. Lookup offerta — JOIN vendite.offerte_commerciali × config.stati_doc_offerte per ottenere stato_id e codice_interno. NOT FOUND → RETURN NULL.
  2. Transizioni manuali — jsonb_agg su config.stati_doc_offerte_transizioni filtrata per stato_da_id = v_stato_id AND attivo IS TRUE AND manuale IS NOT FALSE. I metadati UI (label_key, severity, icon, requires_confirm, requires_motivazione) vengono letti da t.meta. Ordine: sa.ordine. Filtro defense-in-depth: AND t.meta ?? 'action_key' AND t.meta ?? 'label_key'.
  3. Presenza documenti — due EXISTS calcolati una volta:
  4. v_has_contratto = EXISTS contratto con offerta_id = p_offerta_id.
  5. v_has_ordine = EXISTS ordine con documento_origine_tipo = 'OFFERTA' AND documento_origine_id = p_offerta_id. «Esiste» = in qualsiasi stato (esclusività permanente).
  6. Abilitazione condivisa — v_enabled = (stato = 'ACCETTATA' AND NOT v_has_contratto AND NOT v_has_ordine).
  7. Azioni speciali — aggiunte hardcoded in coda a v_actions:
  8. crea_revisione se v_stato_cod = 'EMESSA'.
  9. push_contratto e genera_ordine se v_enabled (entrambe o nessuna).
  10. Capability derivate:
  11. can_edit_* = (stato = 'BOZZA').
  12. can_create_revisione = (stato = 'EMESSA').
  13. can_push_contratto = can_genera_ordine = v_enabled. Reason con priorità own-doc first quando bloccate (contratto>ordine per push; ordine>contratto per genera; poi OFFERTA_NON_ACCETTATA).
  14. Build JSONB — jsonb_build_object con tutte le chiavi.

Oggetto Tipo Ruolo

Note operative¶

  • STABLE: solo lettura; il pianificatore può riusare il risultato nella stessa transazione.
  • Fallback NULL: il BE interpreta NULL come offerta non trovata e risponde 404 prima di serializzare il payload.
  • Meta mancante: se una transizione non ha manuale in meta, viene trattata come manuale (COALESCE(..., true)). Se non ha requires_confirm o requires_motivazione, il valore default è false.
  • Guard meta keys: il WHERE esclude transizioni manuali senza action_key o label_key (defense-in-depth equivalente a ck_transizioni_stati_prev_meta_ui dei preventivi).
  • Idempotenza/esclusività reali a write-path: questa funzione calcola solo l'abilitabilità UI. Le guard reali risiedono nelle funzioni di scrittura:
  • lato contratto, vendite.fn_push_offerta_a_contratto fallisce sia se esiste già un contratto (E_OFFERTA_CONTRATTO_GIA_GENERATO + UNIQUE uq_contratti_offerta_id) sia se esiste già un ordine (E_OFFERTA_ORDINE_GIA_GENERATO, guard mutua esclusività rev6);
  • lato ordine, il guard speculare (impedire l'ordine se esiste un contratto) vive nel BE crea_ordine_da_offerta (fuori scope DB). L'indice uq_ordini_v_documento_origine_offerta impedisce ordini duplicati dalla stessa offerta.
  • La race cross-tab (push + genera_ordine simultanei) non è coperta da alcun vincolo strutturale: scelta esplicita (back-office mono-utente).
  • Azioni speciali target_state: null: il FE distingue queste azioni dal key (crea_revisione, push_contratto e genera_ordine usano routing speciale nel drawer; le transizioni standard usano l'endpoint generico cambio-stato).
